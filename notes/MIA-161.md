## Реализация

### `frontend/components/landing-v2/landing-v2-banner.vue` — карусель

- `slides` (строка 129) = `[promoSlide, ...STATIC_SLIDES]`, если `promoSlide` не `null`, иначе только два статичных слайда (`board`, `time`). `promoSlide` (52-82) строится из `findMonthlyPromoOffer(sorted.value)` — если оффера с активной промо-скидкой нет или `discountPercent` не считается, слайд не рендерится вовсе (комментарий в коде: «слайд весь про скидку, вариант "то же самое, но без цены" рекламирует несуществующее предложение»). Это и есть механика «выключили акцию → первый слайд пропал» из комментария разработчика.
- Цены баннера берутся из того же `offerPrices()`/`discountPercent()` (`frontend/utils/offer-pricing.ts`), что и карточка месяца в `landing-v2-pricing.vue` и, по показаниям Андрея, `/select-tariff?plan=month_std` — общий источник, число не хардкожено.
- Автопрокрутка вынесена в композабл `use-banner-carousel.ts` (`useBannerCarousel`, `BANNER_SLIDE_MS = 7000`). `sync()` (61-68) запускает таймер только при `visible && autoplay && !held && total()>1` — четыре независимых переключателя видимости/паузы/ховера/reduced-motion объединены в одно условие, поэтому проверять их можно по отдельности.
- Пауза на hover: `onPointerHold` (banner.vue:178-181) вызывает `carousel.setHeld()` только для `pointerType==='mouse'` — на тач-устройствах `pointerenter` без последующего `pointerleave` не должен вешать автоход намертво (это и есть причина, по которой Андрей не смог автоматизировать hover-паузу браузерным драйвером — поведение специально завязано на реальный mouse pointer).
- Ручная пауза — отдельный тумблер `paused`/`togglePause()` (145-148), не завязанный на hover; она же учитывается в `carousel.setAutoplay(!paused && !reducedMotion)`.
- `prefers-reduced-motion`: `motionQuery`/`syncMotion` (155-162) выключает автоход через `setAutoplay(false)`. В `<style>` (936-947) `@media (prefers-reduced-motion: reduce)` дополнительно снимает `transition`/`animation` у `.banner__track`, `.banner__progress-fill`, `.banner__cta`, `.banner__dot`, `.banner__kicker-dot` — то есть и автоход, и CSS-анимации выключаются одновременно, а не только JS-таймер.
- Вне вьюпорта: `IntersectionObserver` с `rootMargin: '120px 0px'` (164-168) зовёт `carousel.setVisible()` — отсюда наблюдение Андрея «за 14,5 с вне вьюпорта слайд не менялся».
- Аналитика клика по CTA слайда — `onCta()` (183-186), см. «Аналитика/API».

### `frontend/composables/use-banner-carousel.ts`

- `total()` читает `unref(count)` при каждом обращении, а не один раз при инициализации (комментарий: «число слайдов приходит ссылкой: промо-баннер появляется вместе с офферами, и карусель, посчитавшая слайды один раз на старте, до него не доезжает») — покрыто юнит-тестом `starts autoplaying once a second slide shows up` (`frontend/tests/use-banner-carousel.test.ts:105-118`).

- Юнит-тесты также покрывают: cycle prev/next через границы (`wraps around…`, `wraps prev…`), остановку таймера при `scope.stop()` (`drops the timer when the scope is disposed`), полное игнорирование автохода при `setAutoplay(false)` с сохранением ручного `next()` (`never autoplays when motion is turned down`) — то есть reduced-motion и «пауза» проверены на уровне композабла отдельно от компонента.

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Happy path карусели — автопрокрутка, точки, стрелки

1. Открыть лендинг, первый экран — тёмная карусель (`.banner`), НЕ старый hero с заголовком и сеткой 2×2.
2. С активной акцией — 3 слайда (промо первым), без активной акции у оффера месяца — 2 слайда (`board`, `time`) и первый слайд не промо.
3. Не трогая карусель, засечь ~7 секунд — слайд должен смениться автоматически (`BANNER_SLIDE_MS=7000`), полоса прогресса (`.banner__progress-fill`) идёт слева направо и обнуляется при смене слайда.
4. Точки (`.banner__dot`) — клик на любую переkey слайд мгновенно и без «доезда» предыдущего (значение `elapsed` сбрасывается в 0, `use-banner-carousel.ts:70-76`) — новый слайд должен получить полные ~7 секунд до следующего автопереключения.
5. Стрелки «вперёд»/«назад» — переключают по кругу (с последнего на первый и наоборот).
6. Кнопка паузы (`data-testid="banner-pause"`, aria-pressed) останавливает автоход; повторный клик возобновляет его — по коду это независимый флаг `paused`, не связанный с hover.
7. Фокус клавиатурой внутри баннера (Tab до кнопки/точки) — `@focusin="carousel.setHeld(true)"` на `<section>` — автоход должен встать, пока фокус внутри.

### 2. Пауза на hover (частично не покрыта автотестами по словам QA)

1. Навести курсор мыши на область баннера (`.banner__stage`) и не убирать 10+ секунд — слайд не должен смениться (`onPointerHold` реагирует только на `pointerType==='mouse'`, `landing-v2-banner.vue:178-181`).
2. Убрать курсор — автоход должен возобновиться со следующего тика.
3. Отдельно проверить touch/тач-устройство (или эмуляцию `pointerType: 'touch'` в DevTools) — прикосновение к баннеру НЕ должно навсегда останавливать автоход (в коде тач специально исключён из `setHeld`, иначе `pointerleave` за тач-`pointerenter` не приходит и карусель замирает — прямая цитата из комментария в коде).

### 3. Пауза вне вьюпорта

1. Прокрутить страницу так, чтобы баннер полностью ушёл из зоны видимости (с учётом `rootMargin: '120px 0px'` — то есть на 120px за реальной границей вьюпорта карусель ещё может считаться видимой).
2. Подождать 10+ секунд, вернуться к баннеру — активный слайд не должен был измениться за время отсутствия в кадре.
3. Остаться на странице и подождать один интервал (~7 с) — автоход должен возобновиться.

### 4. prefers-reduced-motion

1. Включить `prefers-reduced-motion: reduce` в ОС/DevTools, открыть лендинг.
2. Подождать 10-15 секунд без действий — слайд карусели не должен смениться автоматически.
3. Ручное переключение (стрелки/точки) должно продолжать работать.
4. Через DevTools убедиться, что `.banner__track`/`.banner__progress-fill`/`.banner__cta`/`.banner__dot` имеют `transition: none`, а `.banner__kicker-dot` — `animation-name: none` (`landing-v2-banner.vue:936-947`).

### 10. [ИЗВЕСТНЫЙ ДЕФЕКТ, НЕ ПОФИКШЕН] Горизонтальная прокрутка на 320px

Подтверждено чтением кода.

1. Открыть лендинг в viewport 320px по ширине, довести демо-доску (`id="demo-board"`) до состояния «выбор класса» (экран с вопросом «В каком ты классе?», `board.state.value === 'asking-grade'`).
2. Проверить `document.documentElement.scrollWidth` — по отчёту Андрея фактическое значение 371 > 320.

Причина по коду, `frontend/components/landing/landing-demo-board.vue`:
- `.demo-board__gate-card` (строка 640-652) имеет фиксированный `max-width: 380px` без единого адаптивного переопределения под `bp.phone`/`bp.tablet` (в файле такие блоки есть — строки 832-868 — но `.demo-board__gate-card`/`.demo-board__gate-row`/`.demo-board__grade` в них не упомянуты ни разу).
- Внутри — `.demo-board__gate-row` (677-681, `display: flex; gap: 8px`, без `flex-wrap`) с пятью кнопками `.demo-board__grade` (683-686: `flex: 1; width: 52px; height: 52px`, `GRADES = [5,6,7,8,9]`, строка 11) — фиксированная ширина кнопок в сумме с паддингом карточки (`clamp(20px, 2.4vw, 28px)` с каждой стороны) удерживает контентную ширину карточки около верхней границы `max-width: 380px` независимо от viewport — это и даёт зафиксированные Андреем ~371px на экране 320px.
- Важно: сам блок `.demo-board__gate-card` этим MR не менялся (в диффе MR по `landing-demo-board.vue` — только переименование двух цветовых литералов в токен `$landing-sand-border`, строки 357-364 файла; сам `gate-card`/`gate-row`/`grade` идентичен коду до MIA-161) — то есть это, вероятно, не регрессия конкретно этого MR, а ранее существовавший дефект адаптива демо-доски, который стал видимым/блокирующим именно сейчас, потому что acceptance MIA-161 прямо требует «мобильная и планшетная раскладки без горизонтального скролла» для всей страницы целиком, а демо-доска — одна из секций на этой странице.

Второй виновник по отчёту Андрея — `.wb-toolbar__group` (до 380px). Компонент найден: `frontend/components/whiteboard/toolbar.vue` (класс `.wb-toolbar__group`, строки 199-326 в шаблоне, стили 439-443: `display: flex; align-items: center; gap: 6px` — фиксированной ширины на самом `__group` нет). Этот файл **не входит в список изменённых файлов MR !390** (проверено по `git diff` между родителями merge-коммита `60c8f960` — правки в `landing-demo-board.vue` этим MR не затрагивают тулбар вовсе) — `WhiteboardToolbar` используется на демо-доске как готовый, ранее существовавший компонент доски/тренажёра. Внутренний `.wb-toolbar__scroll` специально сделан с `flex-wrap: wrap` и комментарием в коде о том, что перенос строк — осознанное решение против переполнения на любой ширине; тем не менее Андрей зафиксировал фактическое переполнение до 380px на 320px viewport. Это похоже на смежный/общий баг компонента доски, не специфичный для MIA-161 напрямую, но он всё равно блокирует acceptance-пункт задачи «мобильная и планшетная раскладки без горизонтального скролла» и достаточно повода, чтобы завести отдельный тикет и синхронизировать его с этим (либо чинить оба вместе в рамках MIA-161, по решению автора/тимлида).

Ожидаемый результат обоих пунктов: `scrollWidth <= innerWidth` на 320px. Фактически — не так, дефект открыт на момент заметки.

### 11. [ИЗВЕСТНЫЙ ДЕФЕКТ, НЕ ПОФИКШЕН] Срок акции на лендинге не совпадает с реальным `offer.promo.endsAt`

Подтверждено чтением кода.

1. Получить актуальный `promo.endsAt` месячного оффера через `/api/offers` (или админку).
2. Сравнить с текстом на лендинге: плашка над баннером («Скидка на первый платёж — …»), плашка «Действует …» рядом с заголовком блока тарифов, и текст под каждой карточкой тарифа с промо (`promoBadge`).
3. Ожидалось: дата матчится с `offer.promo.endsAt`. Фактически (по отчёту Андрея, тест-1): каталог отдаёт `promo.endsAt = 2026-10-04T21:00:00.000Z`, а лендинг везде показывает «до 20 сентября».

Причина по коду — константа `PROMO_ENDS`:
- Объявлена в `frontend/constants/promo.ts:6`: `export const PROMO_ENDS = 'до 20 сентября';`. Комментарий в файле (строки 1-5) прямо признаёт риск: «Значение должно совпадать с valid_until промо в админке — иначе страница обещает больше, чем даёт оффер» — то есть синхронизация ручная, и это осознанный компромисс автора MR, а не оплошность.
- Используется как хардкод в трёх местах на странице:
  - `frontend/components/landing-v2/landing-v2-banner.vue:6,68` — `extra: \`Скидка на первый платёж — ${PROMO_ENDS}\`` (текст под ценой на промо-слайде баннера).
  - `frontend/components/landing-v2/landing-v2-pricing.vue:6,105` — `Действует {{ PROMO_ENDS }}` (плашка со сроком акции рядом с заголовком блока тарифов).
  - `frontend/components/landing-v2/landing-v2-pricing.vue:77` — `promoNote: promoBadge(offer, PROMO_ENDS)` — `PROMO_ENDS` передаётся как `endsOverride` в `promoBadge()`.
- При этом в `frontend/utils/offer-pricing.ts` уже есть готовая функция `promoEndsLabel(offer)` (строки 117-124), которая как раз читает `offer.promo.endsAt` из каталога и форматирует «до N месяца» — но эта функция для лендинговых плашек нигде не вызывается без `endsOverride`; `promoBadge(offer, endsOverride?)` (126-137) специально принимает необязательный override именно для этого случая («датавыровнял пока живёт в UI», комментарий строк 129-131), и лендинг всегда передаёт override.
- Риск (прямо назван в известных ограничениях комментария 1 автора): если срок акции продлят только в админке (обновят `valid_until`/`promo.endsAt` у оффера), не поправив константу `PROMO_ENDS`, лендинг продолжит показывать старую дату (в примере — «до 20 сентября» при живом каталожном сроке до 4 октября) — страница будет либо преждевременно пугать читателя близким дедлайном, либо (в обратном случае) обещать скидку дольше, чем она реально действует.

Рекомендация для тикета фикса (не для этой заметки, но стоит указать разработчику): либо убрать `endsOverride` и звать `promoBadge(offer)`/`promoEndsLabel(offer)` без него на всех трёх местах, либо доказательно объяснить, почему хардкод должен остаться (например, если промо в каталоге размечено на несколько дней позже реальной маркетинговой границы акции).

## Аналитика/API

- Новое событие фичи — ровно одно: `LANDING_BANNER_CTA_CLICK` (`landing_banner_cta_click`), заведено синхронно в `frontend/constants/analytics-events.ts:18` и `api/src/constants/analytics-events.ts:18` (по `git diff` между родителями merge-коммита — по 2 добавленные строки в каждом файле, комментарий-label «[Лендинг/Баннер] Клик по кнопке слайда»). Шлётся из `onCta()` (`landing-v2-banner.vue:183-186`) с параметром `{ placement: slide.key }` (`'promo' | 'board' | 'time'`) при клике на CTA-кнопку любого слайда.
- Других новых событий карусели фича не заводит: нет отдельных событий на клик по точке, по стрелке, на паузу/возобновление или на автопереключение слайда — в коде компонента (`carousel.go`, `carousel.next/prev`, `togglePause`) вызовов `track()`/`landingAnalytics.track()` нет нигде, кроме `onCta`. Если продукту нужна воронка по вовлечённости в карусель саму по себе (а не только по клику CTA), это отдельный скоуп, не покрытый MIA-161.
- Известное ограничение из комментария разработчика (не дефект тестирования, инфраструктурный блокер): цель `landing_banner_cta_click` не заведена в Яндекс.Метрике — оба счётчика (тест и прод) упёрлись в лимит целей (207/208), API отдаёт `limit_exceeded`. Событие фактически отправляется на фронте/бэке (что и подтвердил Андрей — «подтверждалось UI-действие CTA, но не появление события в воронках»), но в отчётах Метрики не появится, пока лимит не расчистят. Вместе с этим событием там же в очереди ждут своих целей ещё 11 событий из прошлых задач — то есть проблема шире одного MIA-161.
- API-проверки, актуальные для фичи: `GET /api/offers` — источник цен/скидок для баннера и карточек тарифов (проверено Андреем: доступен ученику и анонимно 200-кой в части полей, `admin/offers` требует прав, 401 без них); поле `promo.endsAt` в ответе — источник правды для тест-кейса №11 выше.

## Открытые вопросы

- **Лимит целей Яндекс.Метрики (207/208) не позволяет завести `landing_banner_cta_click`.** Инфраструктурный блокер, не баг MIA-161 — событие в коде отправляется корректно, но не может быть проверено end-to-end через воронки Метрики, пока цели не расчищены. Нужен отдельный тикет на ревизию неиспользуемых целей (в очереди уже минимум 12 событий, включая это).
- **Круглый штамп скидки скрывается на 620px, а не на «своём» брейкпоинте вёрстки.** `landing-v2-banner.vue:369,667-669` использует локальную константу `$banner-stamp-min: 620px`, никак не связанную с общими миксинами проекта `bp.phone` (≤768px) / `bp.tablet` (≤1024px) / `bp.tablet-portrait` (769-960px) из `frontend/assets/scss/_breakpoints.scss`. Сам файл `_breakpoints.scss` явно задуман как общий источник правды («Pull in per file with `@use '~/assets/scss/breakpoints' as bp;`»), и `landing-v2-banner.vue` этот `@use` подключает (строка 362) и использует `bp.tablet`/`bp.phone` в части правил — но для порогов, специфичных для макета баннера (860/1100/940/620), заводит свои пиксельные константы прямо в файле, не через общие миксины. Это не обязательно баг (значения продиктованы конкретным макетом карусели, а не общей сеткой сайта), но стоит уточнить у дизайна/автора, должен ли порог штампа (620px) совпадать с каким-то другим уже названным брейкпоинтом макета — сейчас он не совпадает ни с одним из четырёх других локальных порогов того же файла.
- **То же самое верно для `landing-v2-about.vue` (пороги 1024px и 700px через прямой `@media`) и `landing-v2-pricing.vue`/`landing-v2-banner.vue` (используют `bp.tablet`/`bp.phone` из общих миксинов там, где пороги совпадают с общими 1024/768).** То есть в рамках одного MR соседствуют оба подхода — где макет совпадает с общими breakpoint-миксинами, используются `bp.*`; где нет — заводятся точечные `@media (max-width: …)`. С точки зрения `docs/code-style.md` прямого запрета на это нет (гайд не описывает соглашения по SCSS-брейкпоинтам отдельно), но неоднородность стоит иметь в виду, если у команды есть негласное правило «все брейкпоинты только через bp.*» — тогда 700/860/940/1100/620 стоит вынести в именованные миксины по аналогии с `bp.phone`/`bp.tablet`.
- **Два непочиненных дефекта из QA-отчёта Андрея подтверждены чтением кода** (полные детали — тест-кейсы №10 и №11 выше): горизонтальная прокрутка на 320px из-за `.demo-board__gate-card { max-width: 380px }` + пять кнопок `.demo-board__grade { width: 52px }` без адаптивных переопределений (плюс отдельный, вероятно смежный/не-MIA-161 источник — `.wb-toolbar__group` в `frontend/components/whiteboard/toolbar.vue`, файл не в дифе этого MR); и хардкод `PROMO_ENDS = 'до 20 сентября'` (`frontend/constants/promo.ts:6`), используемый вместо `promoEndsLabel(offer)`/`offer.promo.endsAt` в трёх местах лендинга (`landing-v2-banner.vue:68`, `landing-v2-pricing.vue:77,105`) — при продлении акции в одной только админке текст на лендинге разъедется с реальным сроком, если не поправить константу вручную.
- **`.demo-board__gate-card` не менялся этим MR** (диф `landing-demo-board.vue` — только переименование двух цветовых литералов в SCSS-токен). Похоже, что переполнение на 320px существовало и до MIA-161, но раньше не было явным acceptance-требованием «без горизонтального скролла на всей странице» — стоит уточнить у автора/тимлида, чинить ли это в рамках текущего MR или заводить отдельный тикет на демо-доску (с быстрой синхронизацией статусов между двумя задачами, чтобы дефект не потерялся).
