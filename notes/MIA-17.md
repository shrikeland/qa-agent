## Контекст

Задача пришла из Jira (LL-1728, только как поисковый ключ - Jira не читаем) с формулировкой «подключить Sentry». **По факту команда развернула не Sentry SaaS/self-hosted, а self-hosted GlitchTip** (протокол совместим со Sentry SDK) - Sentry SaaS не подошёл по трансграничной передаче данных (юридическое ограничение РФ), Sentry self-hosted не подошёл по железу (просит 16 GB RAM, на хосте мониторинга доступно 3.9 GB). GlitchTip развёрнут на хосте `mon` рядом с Grafana/Loki, отдельный vhost `errors.mia360.ru`. Slack-алерты из исходного скоупа задачи заменены на Telegram (тот же relay, что используется для остальных алертов) - Slack API недоступен из РФ. Детали решения - `docs/superpowers/specs/2026-09-15-error-tracking-glitchtip-design.md`.

Это преимущественно инфраструктурная/бэкенд задача, почти без пользовательского UI - основная QA-работа здесь не «пройти экран», а подтвердить сквозную доставку ошибки от каждого из 4 сервисов до трекера с корректным скрабом ПДн.

**Уже прошёл один раунд QA (15.09) с FAIL по ключевому пункту** - не удалось подтвердить приём событий в GlitchTip: доступа к самой панели GlitchTip не было (переданный URL вёл в админку продукта, не в GlitchTip), а переиспользовать Basic Auth от другой панели без явного подтверждения QA не стал - технически верное решение, не занижать критичность. Остальное прошло: health/авторизация, WS-цепочка тренажёра без утечки полей, изоляция сессий, DSN присутствует в паблик-конфиге и клиентском бандле. Отдельно найдено (не блокер): `GET /_nuxt/*.js.map` отвечает `500` вместо ожидаемого ответа для отсутствующего ресурса.

**После этого раунда есть ещё один коммит по теме** - `2eeba8fe fix(sentry): маскировать аргументы консоли и все форматы телефона` - это ответ на находки ревью/тестирования, отдельная зона регресса, см. ниже.

## Реализация

Ключевые файлы (идентичны по паттерну на api/socket-gateway/ai-proxy, отдельно frontend): `<service>/src/sentry-boot.ts`, `<service>/src/helpers/sentry.helper.ts`, `<service>/src/helpers/sentry-scrub.ts`, `frontend/plugins/sentry.client.ts`, `frontend/utils/sentry-scrub.ts`, `api/scripts/sentry-smoke.ts`, `monitoring/alert-telegram-relay/relay.py`.

### Скраб ПДн - четыре реализации побайтово идентичны, и это гарантировано CI

`api/src/helpers/sentry-scrub.ts`, `socket-gateway/.../sentry-scrub.ts`, `ai-proxy/.../sentry-scrub.ts`, `frontend/utils/sentry-scrub.ts` - все четыре файла идентичны. Это не совпадение: job `sentry_scrub_mirror_check` (`gitlab/pipeline-prepare-test.yml`, правила в `gitlab/templates.yml`) гоняет `diff` между всеми копиями в CI и **падает пайплайн**, если хоть одна копия разошлась - регрессия «поправили скраб в одном сервисе, забыли в другом» физически не проедет.

Маски:
- email: `[email]`.
- телефон (**после фикса `2eeba8fe`**): расширенное окно `{9,18}` цифр/разделителей с границами по не-словесным символам → `[phone]` - раньше формат `8 (999) 123-45-67` не матчился вовсе, а `+7 (999) 123 45 67` маскировался только частично (хвост номера утекал в событие).
- Bearer-токены → `Bearer [token]`; секреты по префиксу (`glpat-`, `sk-`, `lin_api_`, `PMAK-`) → `[token]`.
- `user` схлопывается до `{id}` или `{}` (email/имя не попадают вообще).
- Из `request` вырезаются `data`, `cookies`, `query_string`, `env`, заголовки `authorization/cookie/set-cookie/x-api-key/user-agent/referer`; URL обрезается до пути без query.
- `extra` - allow-list конкретных ключей (`kind`, `reqId`, `method`, `routeUrl`, `statusCode`, `code`, `socketId`, `streamId`, `model`, длины полей, `durationMs`, `attempt`), значения дополнительно маскируются тем же `maskText` (это тоже часть фикса `2eeba8fe` - раньше `extra` только фильтровался по списку ключей, но не чистился внутри).
- **Важно для теста**: маски ловят email/телефон/токены по форме данных, а не по семантике «это данные ребёнка» - произвольный текст с ФИО ученика в тексте исключения НЕ маскируется, если в нём нет email/телефона/токена. Стоит явно проверить сообщение с ФИО.

### Фикс `2eeba8fe` - три изменения, все три - зона обязательного регресс-теста

1. `maskText` стала рекурсивной по массивам/объектам - раньше `breadcrumb.data.arguments` (сырые аргументы `console.*`) оставались нетронутыми рядом с уже замаскированным `message`.
2. Телефонный паттерн `{9,13}` → `{9,18}` - см. выше, раньше часть форматов не ловилась или ловилась наполовину.
3. `extra` теперь дополнительно прогоняется через `maskText`, а не только фильтруется по allow-list ключей.

### `api/scripts/sentry-smoke.ts` - способ обойти проблему доступа из прошлого раунда

Скрипт падает с ошибкой, если `SENTRY_DSN` пуст; иначе инициализирует Sentry для `api`, шлёт `Sentry.captureException(new Error('sentry smoke test'))`, флашит (5с) и печатает `eventId`. Запуск: `SENTRY_DSN=<dsn> bun run api/scripts/sentry-smoke.ts`. Успех - печать `eventId <hex>` без ошибок в консоли. **Это и есть обходной путь для незакрытого пункта прошлого раунда**: не нужен доступ к самой панели GlitchTip, чтобы подтвердить факт отправки - достаточно получить `eventId` и попросить того, у кого есть доступ к GlitchTip, найти issue "sentry smoke test" по этому id/времени создания.

### Пустой DSN отключает отправку - на всех четырёх поверхностях

Backend (все три сервиса): `if (!dsn) return;` до `Sentry.init` в `sentry.helper.ts`. Frontend: тот же паттерн в `sentry.client.ts`. Стенды без переменных окружения продолжают работать как раньше, ошибка отправки не блокирует работу сервиса ни при каком значении DSN.

### Sourcemaps и гипотеза по `500` вместо `404`

`frontend/Dockerfile`: при наличии `SENTRY_AUTH_TOKEN`+`SENTRY_RELEASE` - `sentry-cli sourcemaps inject/upload`, затем безусловное удаление всех `*.map` из собранного образа. Гипотеза по находке прошлого раунда (500 вместо 404 на отсутствующей карте): скрипт синхронизации манифеста ассетов Nitro (`frontend/scripts/sync-nitro-asset-manifest.mjs`) запускается ПОСЛЕ удаления `.map`-файлов и пропускает патч записи, если не смог прочитать файл - то есть запись в манифесте для уже удалённого `.map` остаётся «как будто файл есть», и Nitro на рантайме пытается отдать несуществующий файл и падает на `ENOENT` вместо обычного fallback на 404. Это гипотеза по коду, не подтверждена логами - стоит явно проверить на реальном контейнере, если будет время, но это не блокер приёмки (карта не отдаёт содержимое ни в 500, ни в 404 сценарии).

### Telegram-алерты - условия срабатывания

Design-doc подтверждает переход Slack → Telegram из-за недоступности `api.telegram.org`... то есть наоборот, `api.slack.com` недоступен из РФ, Telegram выбран как реально работающий канал. Правила в GlitchTip (только прод-проект, тестовый молчит): новая ошибка - `quantity=1/timespan=1мин`, всплеск - `quantity=25/timespan=10мин`. **Правила "регрессия" как отдельного типа алерта нет** - модель GlitchTip его не поддерживает (одно из отличий от полноценного Sentry, стоит иметь в виду при сверке с исходным скоупом задачи, где регрессия была отдельным пунктом). `relay.py` различает формат GlitchTip/Grafana по форме payload; автотестами (`test_relay.py`) покрыты: детект формата, форматирование сообщения, экранирование HTML в заголовке, обрезка не-`http(s)` ссылок.

### Конфигурация

`.env.example`: единые `SENTRY_DSN` (бэкенд) и `NUXT_PUBLIC_SENTRY_DSN` (паблик, фронт), а не по сервису (`SENTRY_DSN_FRONTEND` и т.п. из исходного скоупа задачи не прижились - реализовано проще, один DSN на окружение). `SENTRY_ENVIRONMENT`, `SENTRY_RELEASE`, `SENTRY_URL`/`SENTRY_ORG`/`SENTRY_AUTH_TOKEN` (только для CI-аплоада sourcemaps). Инфраструктура GlitchTip - `GLITCHTIP_HOST` (по умолчанию `errors.mia360.ru`), `GLITCHTIP_DB_PASSWORD`, `GLITCHTIP_SECRET_KEY`, `ALERT_HOOK_PATH`.

## Тест-кейсы / чек-лист

Acceptance у задачи не оформлен явным списком - список ниже собран из целей/скоупа тикета и того, что реально реализовано.

### 1. [ПРИОРИТЕТ, незакрыто с прошлого раунда] Подтверждение сквозной доставки

Нужен либо безопасно выданный доступ к самой панели GlitchTip (URL + отдельные credentials/токен), либо прогон `sentry-smoke.ts` с последующей просьбой к тому, у кого есть доступ, найти событие по `eventId`.

1. Запустить `SENTRY_DSN=<dsn с тест-окружения> bun run api/scripts/sentry-smoke.ts` - получить `eventId`.
2. Повторить аналогичный smoke для socket-gateway и ai-proxy, если для них есть свой скрипт (проверить наличие - в изменённых файлах MR явного smoke-скрипта для этих двух сервисов не было, только для api; для них можно спровоцировать реальную ошибку через штатный сценарий, например оборванное WS-соединение).
3. В браузере на тестовом стенде намеренно вызвать клиентскую JS-ошибку (например, через консоль) - проверить, что она долетает и что стек читаем (не minified-мусор) благодаря загруженным sourcemaps.
4. Получить подтверждение (от админа GlitchTip) по каждому из 4 событий: тег `service`, привязка к релизу (git SHA/тег), в теле события нет текста ученика/email/телефона/IP.

### 2. [ПРИОРИТЕТ] Скраб ПДн - регресс после фикса `2eeba8fe`

1. Спровоцировать ошибку, где в сообщении/аргументах есть email - убедиться, что в событии он заменён на `[email]`.
2. То же с телефоном в формате `8 (999) 123-45-67` (раньше не матчился) и `+7 999 123 45 67` (раньше матчился частично) - оба должны стать `[phone]` целиком, без утечки хвоста номера.
3. Спровоцировать `console.log(email, phone)` (не просто `throw` с текстом, а именно консольные аргументы, попадающие в breadcrumbs) - убедиться, что аргументы тоже замаскированы, не только основной `message` (это и был баг, который чинил `2eeba8fe`).
4. Проверить `extra.routeUrl` с query-параметрами (например `?token=...`) - хвост после `?` должен быть обрезан, значение не должно долететь целиком.
5. Спровоцировать ошибку с ФИО ученика в тексте (без email/телефона рядом) - **ожидаемо ФИО НЕ будет замаскировано** (маски ловят только формы данных) - это не баг, а особенность реализации; если для продукта это неприемлемо (152-ФЗ, дети) - поднять вопрос отдельно, не как баг этого MR.

### 3. Пустой DSN не ломает сервис

На стенде/локально с `SENTRY_DSN`/`NUXT_PUBLIC_SENTRY_DSN` не заданными - все 4 сервиса поднимаются и работают штатно, ошибки в консоли/логах об инициализации Sentry быть не должно.

### 4. Sourcemaps

1. Проверить, что в собранном образе фронтенда `.map`-файлов нет физически (`find .output/public -name '*.map'` в контейнере - пусто).
2. Проверить `GET /_nuxt/<любой>.js.map` на стенде - зафиксировать текущий код ответа (известно: `500`, ожидалось `404`) - не блокер, но стоит подтвердить, что поведение не ухудшилось и не начало отдавать реальное содержимое карты.

### 5. Telegram-алерты (инфраструктурная часть, не блокирует основной acceptance)

1. Спровоцировать всплеск ошибок на прод-подобном окружении (если тестовый проект в GlitchTip алерты не шлёт - по дизайну, не баг) - убедиться, что сообщение приходит в Telegram-канал в разумное время.
2. Если специально проверять невозможно (нет доступа к прод-алертам) - отметить как «не покрыто», не как FAIL - `test_relay.py` уже покрывает форматирование и парсинг на уровне юнит-тестов.

## Аналитика/API

Это не пользовательская фича - отдельных бизнес-аналитических событий не добавляет. Ключевой «API для удобства тестирования» - `api/scripts/sentry-smoke.ts` (см. тест-кейс 1) - им стоит пользоваться вместо попыток достучаться до UI GlitchTip напрямую, если доступ не выдан.

## Не покрыто (перенесено из прошлого раунда + новое)

- Визуальная проверка панели GlitchTip (создание/приём событий по всем 4 поверхностям, PII-скраббер на принятых событиях, релиз и символизация фронтенд-стека) - не выполнена без доступа к самому трекеру, см. тест-кейс 1.
- Причина `500` вместо `404` на отсутствующей `.js.map` - гипотеза в разделе «Реализация» не подтверждена логами прод-контейнера.
- Реальное срабатывание Telegram-алертов по порогам (новая ошибка, всплеск) на проде - не гонялось.

## Открытые вопросы

- **Нужен безопасный способ выдать доступ к GlitchTip для QA** (отдельные credentials/токен, не переиспользование чужой Basic Auth) - без этого каждый раунд будет упираться в один и тот же незакрытый пункт. Это главный блокер приёмки, а не код.
- Алерт-правило «регрессия» из исходного скоупа задачи не реализовано - модель GlitchTip его не поддерживает; стоит явно закрыть вопрос с постановщиком, устраивает ли это как финальное решение или нужен обходной путь (например, отдельное правило по повторному появлению issue после resolve, если GlitchTip это умеет).
- Маскировка ФИО в тексте ошибки не реализована (маски по форме данных, не по семантике) - см. тест-кейс 2.5, решить, требуется ли это для соответствия 152-ФЗ.
