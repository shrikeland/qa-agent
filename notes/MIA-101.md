# MIA-101: тайминги AI-запросов — длительность, исход и алерт на таймауты

## Контекст

До фичи длительность и исход AI-запроса были видны только частями: у проверки решения с доски — в базе, у чата — в метриках без привязки к ученику, у вызовов из api (приветствие, память Мии, отчёт родителю) — вообще никак. Неудачные вызовы (таймаут/ошибка) не попадали в учёт совсем, поэтому нельзя было увидеть, что медиана генерации приветствия (2.9 с) стоит на грани лимита в 3 с и каждый четвёртый вызов срывается в шаблон.

Это уже третий раунд: первый MR (!306, `feat/MIA-101-ai-request-timings`, коммит `88f76dff`) завёл тайминги/исход в общем учёте и на дашборде `/admin/ai-cost`. QA-прогон 31.07 нашёл три расхождения (см. историю тикета) — все три закрыты коммитами `d33f70fb` и `f5bde952` (смёржены в master, `master@2793ba2f` на момент «готово»).

## Реализация

**Расхождение 1 — неудачные вызовы попадают в учёт.**
- Чат и проверка решения (`socket-gateway`) уже писали исход при первом раунде: `socket-gateway/src/helpers/ai-usage.helper.ts` → `recordStreamAiUsage`/`recordFailedCall`; `conversation.stream.ts` и `recognition.stream.ts` зовут `finish(undefined, 'timeout')` на авто-аборте (120 с) и `finish(undefined, 'error')` на ошибке прокси.
- Отчёт родителю (`api/src/services/parent-report-ai.service.ts` + `parent-report.service.ts`) — новый общий хелпер `recordParentReportUsage`: пишет `status = outcome.ok ? 'ok' : outcome.status` (`'timeout' | 'error'`) для диагностического, недельного и месячного отчёта. Единственный случай без записи — `status === 'skipped'` (не задан ключ провайдера, запрос вообще никуда не уходил).

**Расхождение 2 — тайминги видны по конкретному ученику.**
- `api/src/admin/ai-cost.service.ts`, метод `breakdownForParent`: добавлен отдельный SQL-запрос с `p50Ms`/`p95Ms`/`timeouts`/`errors` в разрезе `surface`/`kind` — раньше карточка ученика отдавала только `usd`/`calls`. Перцентили считаются отдельным запросом, а не расширением прежнего (нельзя сложить после группировки по моделям).
- `frontend/components/admin/admin-user-ai-cost.vue` — колонка «Медиана / 95%» в таблице «По фичам», рядом бейджи `N таймаут.` / `N ошиб.`; тултип на времени — полная расшифровка (медиана/p95/таймауты/ошибки).

**Расхождение 3 — исход `error` виден в UI.**
- И на карточке ученика (`admin-user-ai-cost.vue`), и на общем дашборде (`frontend/pages/admin/ai-cost/index.vue`) добавлен счётчик `errors` рядом с уже существующим `timeouts` — `v-if="k.errors"` / `v-if="r.errors"`.

**Общее поведение (не менялось в этом раунде, проверить как регресс):**
- `p50Ms`/`p95Ms` = 0 (или отсутствие данных) рендерится как `-`, а не `0.0 с` — важно для старых записей до миграции (`duration_ms = NULL`).
- Доля таймаутов считается одним SQL-запросом (`COUNT(*) FILTER (WHERE status = 'timeout')`), без похода в логи.
- Алерт на рост доли таймаутов — **вне поставки этого тикета**, настраивается отдельно на monitoring-хосте после того, как метрика доедет до прода.

## Тест-кейсы

### Админка: дашборд `/admin/ai-cost`

1. **Тайминги и исход у всех типов вызовов.** Под свежим учеником пройти: `greeting` (вход в тему), `chat` (пара сообщений Мии), `recognition` (отправка решения текстом/фото), `memory_extraction` (пара сессий с чатом — извлечение памяти фоновое), `parent_report` (сформировать/дождаться отчёт родителю, если возможно на стенде — иначе см. «Не покрыто» ниже).
   Ожидание: в таблице «по фиче/типу» у каждой строки — медиана и 95-й процентиль (`X.X с / Y.Y с`), не прочерк.
2. **Таймаут отображается.** Поймать/сымитировать таймаут одного из вызовов (например у `greeting`, лимит 3 с — можно поймать на живом трафике, см. историю прогона 31.07).
   Ожидание: у строки красным `N таймаут.`, число вызовов и стоимость учитывают этот вызов (стоимость — без токенов, `usd` не растёт от неудачного вызова).
3. **Ошибка отображается.** Спровоцировать `status='error'` (недоступный провайдер/сетевая ошибка — если недостижимо на стенде вручную, проверить по коду и юнит-тестам `ai-cost.service.test.ts`).
   Ожидание: рядом с таймаутами — красным `N ошиб.`, по тултипу видно раздельно «таймаутов N, ошибок M».
4. **Отчёт родителю: неуспех тоже пишется.** Спровоцировать сбой генерации сводки отчёта (если возможно — например истекший таймаут на стенде) и проверить, что строка `parent_report` получает `status='timeout'`/`'error'`, а не пропадает из учёта.
5. **Пустые/старые данные не ломают вид.** На периоде, где есть только старые записи (до миграции, `duration_ms=NULL`) — колонка времени показывает `-`, не `NaN` и не `0.0 с`; на смешанном периоде (старые + новые) — перцентиль считается по новым, старые не искажают картину.
6. **Единый счётчик таймаутов через SQL.** Не критично проверять напрямую (внутренняя деталь), но косвенно: цифра в UI должна совпадать с количеством фактических срывов лимита за период — свериться на небольшой контролируемой выборке.

### Админка: карточка ученика `/admin/users/:parentId`

7. **Тайминги и исход видны по конкретному ученику.** Открыть карточку ученика с историей вызовов (в т.ч. с пойманным таймаутом/ошибкой) → в блоке «AI-расходы по этому пользователю» у каждой фичи — медиана/95% и, если есть, `N таймаут.`/`N ошиб.` — так же, как на общем дашборде, а не только `$` и «вызовы».
8. **Пустое состояние.** Ученик без единого вызова AI → блок показывает «Вызовов AI ещё не было», без пустой таблицы и без ошибок в консоли.
9. **Ссылка на общий дашборд.** Клик по «В AI-расходах» из карточки ученика ведёт на `/admin/ai-cost` (общий, не отфильтрованный по ученику, если фильтрация по пользователю не входит в скоуп этой фичи — свериться).
10. **Расхождение с дашбордом отсутствует.** Для одного и того же вызова тайминг/исход в карточке ученика и в общем дашборде за тот же период совпадают (перцентили считаются раздельными запросами — риск разъехаться, если один из двух запросов не обновили синхронно).

### Регресс / общее

11. **Грейдинг и функциональность не задеты.** Тренажёр и диагностика продолжают штатно проверять решения (правильный/неправильный ответ) — фича только добавляет учёт, не меняет бизнес-логику вызовов.
12. **Деплой без простоя.** Не тест-кейс для ручной проверки на стенде, но стоит свериться с DBA/автором, что миграция была `expand-only` (добавление nullable-колонок) — так заявлено в acceptance.
13. **`/api/metrics` (Prometheus).** Гистограмма `ai_request_duration_seconds` с лейблами `kind`/`model`/`status` — второй независимый канал, свериться, что для пойманного в п.2–4 случая метка `status` совпадает с записью в БД (не блокер, но полезная сверка при регрессе).

## Аналитика/API

- Фича не добавляет пользовательских аналитических событий (`analytics-events.ts`) — это внутренняя админ-метрика, событий в `frontend/constants/analytics-events.ts` / `api/src/constants/analytics-events.ts` проверять не нужно.
- Для удобства тестирования полезны: `GET /api/admin/ai-cost` (общий дашборд, JSON) и `GET /api/admin/users/:parentId` → поле `aiUsage.bySurfaceKind` (карточка ученика) — оба под basic-auth админки.

## Открытые вопросы

- Алерт на рост доли таймаутов — отдельный шаг вне этого тикета (настраивается на monitoring-хосте вручную), тестировать в рамках MIA-101 не нужно.
- `kind='ocr'` (Mathpix) исторически не проверялся в рамках тикета — если время позволяет, стоит один раз свериться, что и у него тайминги/исход учитываются по общей схеме.
- Из наблюдений прошлых прогонов (не блокеры, но стоит держать в уме): склонение «N таймаут.» не учитывает число (при 5 будет «5 таймаут.»); `/api/metrics` отдаётся без авторизации; `/api/internal/ai-usage` без HMAC отвечает 400 с текстом ошибки схемы раньше проверки авторизации. Эти пункты не входят в скоуп MIA-101 и чинить/проверять их здесь не требуется — упомянуты только для контекста, если попадутся на глаза при прогоне.
