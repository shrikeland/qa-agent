# MIA-101: Тайминги AI-запросов — длительность, исход, алерт на таймауты

## Контекст

Цель — видеть длительность и исход (успех/таймаут/ошибка) каждого запроса к AI, включая неудачные, без грепа логов контейнера. Повод: генерация приветствия у лимита в 3с, каждый четвёртый вызов не укладывается — а таймауты были не видны нигде, кроме ротируемых логов.

MR !306 (`feat/MIA-101-ai-request-timings` → master). Алерт на рост доли таймаутов вынесен отдельным шагом на monitoring-хост — не в этом MR, out of scope здесь намеренно.

**Важно:** задача уже прогонялась QA на test-1 (комментарий от 31.07) и там же найдены конкретные незакрытые дефекты — они подтверждены и этим прогоном по коду (см. «Открытые вопросы»). Статус в Linear остаётся `Testing`, фикс ещё не пришёл.

## Реализация (код, ветка MR !306)

**Схема:** `ai_usage` получила `duration_ms` (nullable) и `status` (`ok` / `timeout` / `error`, дефолт `ok`) — миграция чисто аддитивная (`ADD COLUMN`), простоя не требует, старые строки остаются валидными с `duration_ms = NULL`.

**Кто пишет тайминги:**
- `api/src/services/memory/greeting-ai.service.ts` — таймаут по `TIMEOUT_MS = 3_000`, пишет `status: outcome.status` (`ok`/`timeout`) и длительность даже на неуспехе. Это единственный канал, где явно проверен живой таймаут.
- `api/src/services/memory/memory-extraction.service.ts` — аналогично, неуспех тоже попадает в учёт.
- `api/src/admin/ai-cost.service.ts` (`dashboard()`) — один `$queryRaw` считает `timeouts` (`COUNT(*) FILTER (WHERE status = 'timeout')`) и `p50Ms`/`p95Ms` (`percentile_cont` по `duration_ms`) в разрезе `surface`/`kind`, за период. `p50Ms`/`p95Ms` сворачивают `NULL` в `0` (комментарий в коде: «Null until rows written before durations existed age out of the window») — в UI ноль неотличим от «нет данных», спасает только `v-if`.
- `socket-gateway/src/helpers/ai-usage.helper.ts` (`recordStreamAiUsage`, обслуживает `chat` и `recognition`) — **статус захардкожен `'ok'`**, а функция выходит по раннему `return` при `!endPayload` (строка 17) или при `!usage || !model` (строка 22). И таймаут по `AiStreamAutoAbortTimeout`, и обрыв соединения провайдером идут через эти ранние выходы — то есть неудачные вызовы `chat`/`recognition` в базу вообще не попадают.
- `api/src/services/parent-report-ai.service.ts` / `parent-report.service.ts` — при `!outcome.ok` `requestSummary` отдаёт `null`, а запись в `ai_usage` происходит только внутри `if (summaryResult)` — ветки на неуспех нет вовсе.

**UI** (`frontend/pages/admin/ai-cost/index.vue`): в блоке «По фичам продукта» у каждого `kind` — время (`p50 / p95` в секундах через `secs()`) и, если `timeouts > 0`, красный бейдж `{{ k.timeouts }} таймаут.` (без склонения — при 5 будет «5 таймаут.»). Тултип на этой колонке — «Медиана … мс, 95-й процентиль … мс, таймаутов …». `status: 'error'` **нигде отдельно не отображается** — такой вызов попадёт в `calls` и в перцентили неотличимо от успешного.

**Карточка ученика** (`aiCostService.breakdownForParent`, используется в `/admin/users/:parentId`) отдаёт только `{ model, surface, kind, usd, calls }` — полей `duration`/`status`/`timeouts` там нет вообще. Разрез «по ученику + время + исход» существует только для общего дашборда за период, не для конкретного ученика.

**Prometheus:** `ai_request_duration_seconds` в `api/src/metrics.ts`, с лейблами `kind`/`model`/`status` — независимый от БД канал, полезен как перекрёстная проверка.

## Тест-кейсы / чек-лист

### Дашборд `/admin/ai-cost` — happy path
1. Свежий ученик → тренажёр: 1 приветствие, диалог в чате (2+ сообщений), отправка решения текстом → в разрезе «По фичам продукта» у `trainer/greeting` и `trainer/chat` появляются время (не прочерк) и `0 таймаутов` вместо пустоты.
2. Переключение периода (7 дней / 30 дней / этот месяц) — числа пересчитываются, `p50`/`p95` за более длинный период учитывают только строки с `duration_ms IS NOT NULL` (не искажаются старыми NULL-строками).
3. Смешанный период (захватывает дни до раскатки миграции) — старые строки не ломают ни один блок дашборда, у них в колонке времени прочерк «-», не `NaN`/`0.0 с`.

### Неудачные попытки — по каналам (ядро скоупа)
4. **Приветствие.** Смоделировать превышение `TIMEOUT_MS=3000` (несколько параллельных регистраций в момент нагрузки, либо дождаться медианы вблизи лимита) → в БД появляется строка `status='timeout'`, `duration_ms≈3000`, без `usage`/стоимости; ученик получает шаблонное приветствие, не персональное; на дашборде счётчик таймаутов у `trainer/greeting` вырос на 1.
5. **Память (`memory_extraction`)** — то же самое ожидание: неуспех должен создавать запись `status≠'ok'`.
6. **Чат/распознавание тренажёра (`socket-gateway`).** ЗАВЕДОМО НЕ РАБОТАЕТ по коду — см. «Открытые вопросы» п.1. Проверить всё равно стоит при каждом ретесте: оборвать соединение с ai-proxy или дождаться зависшего ответа во время чата → ожидание «появляется запись с status=timeout/error» не выполняется, запись не появляется вовсе (ни успешной, ни неуспешной), либо появляется как `ok`.
7. **Отчёт родителю (`parent_report`).** Форсировать сбой генерации отчёта → ожидание «попадает в учёт с фактом и временем, без стоимости» не выполняется — записи не будет вовсе (see «Открытые вопросы» п.1).

### Видимость по ученику (acceptance «по любому ученику и типу запроса видно время и исход»)
8. Открыть карточку конкретного ученика в админке (`/admin/users/:parentId`) → в блоке AI-расходов этого ученика проверить, есть ли время/исход у вызовов. Ожидаемо (по коду) — только `usd`/`calls`, без времени и исхода: пункт acceptance не выполняется, см. «Открытые вопросы» п.2.

### Исход `error`
9. Смоделировать ошибку провайдера (не таймаут, а явный error-ответ) там, где статус пишется (`greeting`/`memory_extraction`) → в БД `status='error'`. В UI этот вызов ничем не выделен (нет отдельного счётчика/бейджа для `error`, только для `timeout`) — сверить визуально, что вызов просто «теряется» среди обычных.

### Не должно сломаться (регресс)
10. Полный цикл ученика (диагностика + тренажёр + чат) после раскатки миграции — сабмишены, скоринг, чат работают как раньше; ни один существующий экран (карточка ученика, дашборд AI-расходов, `/api/metrics`) не отдаёт 500.
11. Период целиком на старых (до миграции) данных — запрос дашборда не падает, суммы/`calls` совпадают с тем, что было до раскатки.
12. `/api/admin/ai-cost` доступен только с basic-auth (401 без него/с чужой сессией); `/api/internal/ai-usage` без HMAC — не проходит.

### Склонение и мелкий UI (не блокер, но стоит проверить глазами)
13. У `k.timeouts` при значениях 1/2/5 текст не склоняется («5 таймаут.») — стоит показать дизайнеру/фронту, не блокирует приёмку функционала.

## Аналитика / API

Отдельного клиентского аналитического события в этой задаче нет — это внутренняя admin-метрика. Точка для регресса: `/api/metrics` (Prometheus) отдаётся наружу без авторизации — если алерт на таймауты будет строиться на этих данных (следующий шаг, monitoring-хост), стоит заранее решить вопрос доступа.

## Открытые вопросы

Взято из прогона QA на test-1 (комментарий Andrei Chepurchenko, 31.07) и подтверждено чтением кода ветки MR !306 в этом прогоне — актуально на сегодня, фикса в Linear пока нет:

1. **«Неудачные попытки тоже попадают в учёт» реализовано только для `greeting` и `memory_extraction`.** Для `chat`/`recognition` (весь трафик тренажёра и диагностики через socket-gateway) и для `parent_report` неуспешный вызов не создаёт записи вовсе. Причина в коде: `recordStreamAiUsage` (`socket-gateway/src/helpers/ai-usage.helper.ts:17,22`) делает ранний `return` при отсутствии `endPayload` или `usage`/`model` — то есть ровно в момент abort/error/timeout; `status: 'ok'` захардкожен для оставшейся ветки. `parent-report.service.ts` пишет `ai_usage` только внутри `if (summaryResult)`.
2. **«По любому ученику и типу запроса видно время и исход» не выполняется для карточки ученика.** `breakdownForParent` (`api/src/admin/ai-cost.service.ts`) отдаёт только `usd`/`calls`; время и исход видны только на общем дашборде за период, агрегированно по всем ученикам. Нужно продуктовое решение: тянуть ли `durationMs`/`status` в карточку ученика, или считать общий дашборд с фильтром по периоду достаточным.
3. **Исход `error` нигде не отображается в UI** — виден только счётчик таймаутов; вызов со `status='error'` неотличим от успешного в интерфейсе, хотя в базе записан верно.
4. Наблюдения не блокеры (не проверять специально, но иметь в виду при ретесте): перцентили считаются по всем строкам периода включая таймауты (`duration_ms≈3001`) — искажает p95; `p50Ms`/`p95Ms = 0` неотличимо от «нет данных» на уровне API; успешный ответ без блока `usage` в `greeting-ai.service.ts` не пишется в учёт вообще (молча теряется); `CREATE INDEX` в миграции без `CONCURRENTLY` (не проблема на текущем объёме).
