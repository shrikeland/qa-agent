# MIA-101: Тайминги AI-запросов — длительность, исход, алерт на таймауты

## Контекст

Цель — видеть длительность и исход (успех/таймаут/ошибка) каждого запроса к AI, включая неудачные, без грепа логов контейнера, и по любому ученику и типу вызова. Повод: генерация приветствия — медиана 2,9с при лимите 3с, каждый четвёртый вызов не укладывается, а таймауты нигде не были видны, кроме ротируемых логов.

Алерт на рост доли таймаутов вынесен отдельным шагом на monitoring-хост — намеренно не в поставке этого MR (см. «Открытые вопросы»).

**Хронология:** основной функционал пришёл MR!306 (`feat/MIA-101-ai-request-timings` → master, коммит `88f76dff`). Первый прогон QA нашёл 3 расхождения (неудачные попытки не учитывались для chat/recognition/parent_report; по ученику не было видно время/исход; исход `error` нигде не отображался). Все три закрыты веткой `fix/MIA-101-call-outcome`, слитой в master коммитом `c02dccfc` (два коммита внутри: `d33f70fb` — отчёт родителю, `f5bde952` — разрез по ученику и `error` в UI). Формального MR в GitLab для этой ветки не нашлось — фикс подтверждён только git-историей master. Текущий HEAD `/tmp/repo` (`7accf5a8`) содержит всё перечисленное.

## Реализация

### Схема данных

`ai_usage` (`api/prisma/schema.prisma`, миграция `api/prisma/migrations/20260730060000_ai_usage_duration_status/migration.sql`):
- `duration_ms INTEGER` — nullable, без дефолта;
- `status TEXT NOT NULL DEFAULT 'ok'`;
- `CREATE INDEX ai_usage_status_created_at_idx ON ai_usage(status, created_at)` — **без `CONCURRENTLY`** (см. «Открытые вопросы»).

Миграция expand-only (`ADD COLUMN` + дефолт) — соответствует правилу blue-green из `docs/code-style.md` («Миграции БД — только backward-compatible»); старый код пишет в старую схему без изменений, простоя не требует.

### Кто и как пишет тайминги/исход

- **`api/src/services/openai/openai-responses.client.ts`** — единая точка выхода в провайдера. `call()` теперь возвращает `ResponsesOutcome` (`{ ok: true, durationMs, ...ResponsesResult }` или `{ ok: false, status: 'timeout'|'error'|'skipped', durationMs }`). `status='skipped'` — не задан `OPENAI_API_KEY`, запрос вообще не уходил (не логируется в `ai_usage`). `TimeoutError`/`AbortError` от `AbortSignal.timeout` → `'timeout'`, всё остальное (не-2xx, сетевая ошибка) → `'error'`.
- **`api/src/services/memory/greeting-ai.service.ts`** (`TIMEOUT_MS = 3_000`, `kind: 'greeting'`, `surface: 'trainer'`) — на неуспехе (кроме `skipped`) пишет `status`/`durationMs` без `usage`. Edge-кейс: если `outcome.ok` true, но `result.usage` пуст (успешный ответ без блока usage) — запись **не создаётся вовсе**, молча (наблюдение из финального комментария, не блокер).
- **`api/src/services/memory/memory-extraction.service.ts`** (`TIMEOUT_MS = 30_000`, `kind: 'memory_extraction'`, `surface: 'memory'`) — тот же паттерн через `outcome.ok`.
- **`socket-gateway/src/helpers/ai-usage.helper.ts`** (`recordStreamAiUsage`, обслуживает `chat`/`recognition` — весь трафик тренажёра/диагностики/домашнего чата/`home`). Начиная с этого прогона фикс подтверждён: есть `recordFailedCall()`, который пишет `status: 'error'|'timeout'` с `durationMs`, но без `usage`, когда стрим завершился без `endPayload` и передан `failure`. **Важная деталь для контекста ретеста:** сама инфраструктура `recordFailedCall`/параметр `failure` у `recordStreamAiUsage` физически попала в код не из веток MIA-101, а из более раннего и формально не связанного коммита `23c51799` («MIA-106: защита контекста AI-чата», 04.08, до финальных фиксов MIA-101 от 18.08) — там же `conversation.stream.ts`/`recognition.stream.ts` стали передавать `'timeout'` при auto-abort (`AiStreamAutoAbortTimeout`) и `'error'` при ошибке потока/прокси. Функционально расхождение 1 по chat/recognition оказалось закрыто к моменту финального фикса, хотя финальный комментарий разработчика явно перечисляет только починку отчёта родителю — стоит перепроверить это в проде отдельно, т.к. никакой тест-кейс на chat/recognition explicit не зафиксирован в истории MIA-101.
- **`api/src/services/parent-report-ai.service.ts`** — `requestSummary()` возвращает `AiSummaryOutcome` (`AiSummaryResult { ok: true, ... }` | `AiSummaryFailure { ok: false, status: 'timeout'|'error'|'skipped', model, durationMs }`), а не `null` как раньше.
- **`api/src/services/parent-report.service.ts`** — общий хелпер `recordParentReportUsage()` пишет `ai_usage` для всех трёх видов отчёта (диагностический/недельный/месячный, `kind: 'parent_report'`) на любом исходе кроме `skipped`.
- **`api/src/routes/internal.routes.ts`** (`aiUsageBodySchema`, POST `/internal/ai-usage`) — `usage` теперь `type: ['object', 'null']`, добавлены `status: enum['ok','timeout','error']` и `durationMs: ['integer','null']`.
- **`api/src/services/ai-usage/ai-usage.service.ts`** (`AiUsageService.record`) — при `usage === null` цена не считается (`costUsdMicros = null`) и алерт «нет цены» не срабатывает; `aiRequestDuration` (Prometheus-гистограмма) пишется всегда, когда есть `durationMs`, независимо от исхода.
- **`api/src/metrics.ts`** — `ai_request_duration_seconds` (Histogram, лейблы `kind`/`model`/`status`, бакеты 0.5–60с) — независимый от БД канал.

### Админка — общий дашборд (`/admin/ai-cost`)

`api/src/admin/ai-cost.service.ts` → `AiCostService.dashboard()`: один `$queryRaw` на `surface`/`kind` считает `calls`, `timeouts` (`COUNT(*) FILTER (WHERE status='timeout')`), **`errors`** (аналогично `status='error'`, добавлено в `f5bde952`), `p50Ms`/`p95Ms` (`percentile_cont(0.5|0.95) WITHIN GROUP (ORDER BY duration_ms)`). `NULL` из `percentile_cont` (нет ни одной строки с `duration_ms`) сворачивается в `Math.round(r.p50_ms ?? 0)` = `0`.

Фронт `frontend/pages/admin/ai-cost/index.vue`, блок «По фичам продукта»: у каждого `kind` колонка `secs(p50Ms) / secs(p95Ms)`, при `p50Ms` falsy (0) — прочерк `-` (`v-if="k.p50Ms"`); если `timeouts>0` — красный (`--c-pulse`) бейдж `«N таймаут.»`; если `errors>0` — отдельный красный бейдж `«N ошиб.»`. Оба склонения фиксированные, не меняются по числу.

### Админка — карточка ученика (`GET /admin/users/:id`)

`AiCostService.breakdownForParent(parentId)` — переписан на два отдельных запроса (`f5bde952`): один по моделям (`usd`/`calls`), второй по `surface`/`kind` с той же схемой полей, что и в дашборде (`timeouts`, `errors`, `p50Ms`, `p95Ms`) — посчитан отдельно, потому что перцентили нельзя агрегировать после группировки по моделям.

Отдаётся в `adminService.getUserDetail()` (`api/src/admin/admin.service.ts`, поле `aiUsage`) и рисуется в `frontend/components/admin/admin-user-ai-cost.vue`: колонка «Медиана / 95%» с тем же прочерком при отсутствии данных и теми же бейджами таймаутов/ошибок, что и на общем дашборде. При `totalCalls === 0` — блок «Вызовов AI ещё не было» вместо таблицы.

### Эндпоинты и авторизация (фактическая, из кода, а не из описания задачи)

- `GET /admin/ai-cost` — общий дашборд, `?from&to` (по умолчанию последние 30 дней).
- `GET /admin/users/:id` — карточка пользователя, поле `data.aiUsage`.
- Обе смонтированы под `fastify.register(adminRoutes, { prefix: '/admin' })`, hook `onRequest: requireAdmin` (`api/src/middleware/require-admin.ts`) — проверяет заголовок `x-forwarded-user` (непустая строка), без него → **403 Forbidden** (не 401 и не basic-auth challenge на уровне самого API — заголовок явно рассчитан на то, что basic-auth обслуживает upstream-прокси/nginx перед сервисом; в тестовом окружении саму basic-auth форму нужно проверять на уровне того прокси, а API — по факту заголовка).
- `POST /internal/ai-usage` — hook `requireInternalKey` (`api/src/middleware/require-internal-key.ts`): не HMAC-подпись, а `Authorization: Bearer <JWT>`, подписанный общим секретом `API_KEY` (тот же секрет, что верифицирует запрос); без заголовка/с невалидным токеном → **401 Unauthorized**.
- `GET /metrics` — регистрируется в `api/src/index.ts` до `adminRoutes`/`internalRoutes`, никакого auth-хука нет, отдаёт Prometheus-текст всем.

(Внешний префикс `/api/...`, упомянутый в описании задачи, добавляется на уровне reverse-proxy/gateway — в самом `api`-сервисе роуты смонтированы без него; проверить оба варианта пути на стенде.)

**TC-10. Записи до миграции не ломают дашборд и показывают прочерк вместо 0.0с**
Приоритет: High.

Шаги:

   Ожидаемо: `p50Ms`/`p95Ms` = 0 из-за `NULL` → `percentile_cont` → `Math.round(... ?? 0)`; в UI это должно отрисоваться как прочерк `-`, а не «0.0 с» и не `NaN` (проверить `v-if="k.p50Ms"` действительно перехватывает `0`).
2. То же для карточки конкретного ученика со старыми записями.

**TC-11. Смешанный период (старые + новые записи)**
Приоритет: Medium.
Шаги:
1. Выбрать период, где для одного `kind` есть и записи без `duration_ms` (старые), и с `duration_ms` (новые).

### Edge-кейсы из наблюдений разработчика

**TC-12. Успешный ответ greeting без блока usage — молча не учитывается**
Приоритет: Low (задокументированный, маловероятный кейс, не блокер).
Шаги:
1. Если удастся спровоцировать ответ от `gpt-5-mini` на приветствие без `usage` в payload (маловероятно у штатного провайдера, но стоит попробовать через мок/staging-прокси).
   Ожидаемо: `greeting-ai.service.ts` не вызывает `aiUsageService.record` вовсе (нет ни строки в БД, ни инкремента гистограммы) — это ожидаемое (задокументированное) поведение, а не баг; тест-кейс — зафиксировать, что это действительно так, и что при этом сама генерация приветствия для пользователя не ломается.

**TC-13. Перцентиль прижимается к лимиту при росте доли таймаутов**
Приоритет: Low, наблюдательный.
Шаги:
1. Насытить период вызовами `greeting`, где заметная доля (>5%) — таймауты на 3000мс.
   Ожидаемо: `p95Ms` у `trainer/greeting` близок к 3000 (таймауты считаются в перцентиле наравне с успешными, `duration_ms` таймаута — это фактическое время до обрыва, не искусственный выброс) — задокументированное поведение, не дефект.

**TC-14. Склонение «N таймаут.» не меняется по числам**
Приоритет: Low, UI-полировка.
Шаги:
1. Добиться `timeouts=1` и `timeouts=5` (или больше) у одной и той же фичи в разные периоды.
   Ожидаемо (текущее поведение, не баг для этого MR): в обоих случаях текст «1 таймаут.» / «5 таймаут.» — грамматически некорректно для 5, но осознанно вне скоупа полировки. Задокументировать как известное ограничение, не заводить как блокер.

### Периметр / авторизация

**TC-15. `/admin/ai-cost` без `x-forwarded-user` → 403**
Приоритет: High, Security.
Шаги:
1. Запросить `GET /admin/ai-cost` напрямую к api-сервису без заголовка `x-forwarded-user` (в обход прокси, если это возможно на тестовом стенде) или с пустым значением заголовка.
   Ожидаемо: `403 Forbidden`, `{ message: 'Forbidden' }`.
2. Через обычный браузер без прохождения basic-auth на уровне reverse-proxy (если он настроен на стенде) — отдельно проверить, что сам прокси не пускает дальше без валидных basic-auth кредов (это уровень инфраструктуры, не кода api, но стоит проверить end-to-end).
3. С cookie/сессией обычного ученика (не админа) — убедиться, что она не подставляет `x-forwarded-user` и тоже даёт 403.

**TC-16. `/admin/users/:id` — тот же периметр**
Приоритет: High, Security.
Шаги:
1. Аналогично TC-15, но для карточки пользователя.
   Ожидаемо: 403 без валидного `x-forwarded-user`.

**TC-17. `/internal/ai-usage` без валидного Bearer JWT → 401**
Приоритет: High, Security.
Шаги:
1. `POST /internal/ai-usage` без заголовка `Authorization`.
   Ожидаемо: `401 Unauthorized` (`ERRORS.unauthorizedAccess`), лог `internal 401: missing or non-Bearer Authorization`.
2. С `Authorization: Bearer <мусор>` / просроченным/подписанным другим секретом токеном.
   Ожидаемо: `401 Unauthorized`, лог `internal 401: JWT verify failed`.
3. С валидным токеном (тем же, что использует `socket-gateway`), но телом, не проходящим `aiUsageBodySchema` (например, без обязательных полей `studentId`/`surface`/`kind`/`model`/`usage`) — отдельно проверить, что схема действительно требует `usage` присутствовать в теле (может быть `null`, но ключ обязателен), а `kind` ограничен `enum: ['chat', 'recognition']` именно для этого роута (greeting/memory_extraction/parent_report сюда не ходят — они пишут в БД напрямую из api-процесса).

**TC-18. `/metrics` — публичный доступ, ожидаемо**
Приоритет: Medium, регресс-подтверждение (это by-design, не баг).
Шаги:
1. `GET /metrics` без какой-либо авторизации.
   Ожидаемо: `200`, тело в формате Prometheus text exposition, содержит `ai_request_duration_seconds` с лейблами `kind`, `model`, `status` (как минимум после хотя бы одного вызова с `durationMs`, заданным в проверяемом окружении).
   Примечание: подтвердить с продуктом/безопасностью, что публичность `/metrics` — осознанное решение (обычно закрывается на уровне сетевого периметра/прокси, а не в самом коде).

## Аналитика/API

- `GET /admin/ai-cost?from&to` — общий дашборд, ответ `{ data: AiCostDashboard }`, поле `bySurfaceKind[]` содержит `{ surface, kind, usd, calls, timeouts, errors, p50Ms, p95Ms }`.
- `GET /admin/users/:id` — карточка пользователя, ответ `{ data: { ..., aiUsage: AiCostBreakdown } }`, `aiUsage.bySurfaceKind[]` — та же форма записи, что и в дашборде.
- `POST /internal/ai-usage` — служебный роут для `socket-gateway` (JWT `Bearer`, секрет `API_KEY`), тело по `aiUsageBodySchema`; `kind` там ограничен `'chat'|'recognition'` (остальные kind'ы — `greeting`/`memory_extraction`/`parent_report` — пишутся напрямую вызовом `aiUsageService.record()` внутри процесса api, минуя HTTP).
- `GET /metrics` — Prometheus, без авторизации, гистограмма `ai_request_duration_seconds{kind,model,status}` плюс счётчик `ai_usage_missing_price_total{model}` (не по теме тикета, но виден рядом).
- Внешний путь с префиксом `/api/...` из описания задачи — на уровне самого `api`-сервиса не встречается (роуты смонтированы как `/admin/...`, `/internal/...`, `/metrics`); проверить фактический внешний путь на тестовом стенде отдельно, префикс добавляется прокси/gateway перед сервисом.

## Открытые вопросы

1. **Алерт на рост доли таймаутов** — сознательно вне скоупа этого MR, выносится отдельным шагом на monitoring-хост. В этой поставке проверяется только то, что данные для будущего алерта корректно копятся (`status`, `duration_ms`, счётчики `timeouts`/`errors` в дашборде, Prometheus-гистограмма) — самого алерта нет и тестировать его здесь не нужно.
2. **Склонение «N таймаут.»/«N ошиб.»** не меняется по числительным (грамматически некорректно при N≠1, но и при N=1 «1 таймаут.» с точкой выглядит как сокращение, а не число+слово) — известное ограничение UI, обсудить с фронтом/дизайном, не блокер приёмки.
3. **`CREATE INDEX` без `CONCURRENTLY`** в миграции `20260730060000_ai_usage_duration_status` — на текущем объёме `ai_usage`, видимо, не проблема, но при выкатке на прод с уже большой таблицей стоит замерить время выполнения индекса (блокирующая операция) и при необходимости попросить накатить его отдельным ручным шагом с `CONCURRENTLY` перед основным деплоем.
4. **Фикс chat/recognition (расхождение 1 в части socket-gateway) физически пришёл не из веток MIA-101**, а был побочным следствием более раннего и тематически не связанного коммита `23c51799` (MIA-106, 04.08). Финальный комментарий разработчика по MIA-101 явно упоминает только починку отчёта родителю для расхождения 1 — при ретесте стоит явно перепроверить сценарий таймаута/ошибки в чате и распознавании (TC-05), а не полагаться на то, что фраза «все три расхождения закрыты» это покрывает по умолчанию.
5. Успешный ответ `greeting` без блока `usage` в ответе провайдера по-прежнему **молча** не создаёт запись в `ai_usage` (ни `ok`, ни что-либо ещё) — задокументированный, маловероятный кейс, не блокер, но стоит иметь в виду при разборе расхождений между Prometheus-гистограммой (`aiRequestDuration.observe()` пишется всегда при наличии `durationMs`, независимо от `usage`) и таблицей `ai_usage` (строка пишется только при выполнении `if (result.usage)`).
