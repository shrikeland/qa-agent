## Контекст

Фича (лейблов нет): раньше длительность и исход AI-вызова было видно только частями - у проверки решения с доски длительность писалась в базу, у чата - в Prometheus-метрики без привязки к ученику, а вызовы из api (приветствие, память Мии, отчёт родителю) вообще не измерялись. Неудачные вызовы (таймауты, ошибки провайдера) не попадали в учёт совсем - поводом стала генерация приветствия ученику: медиана 2,9 с при лимите 3 с, каждый четвёртый вызов не укладывается, и таймауты были видны только через грep логов контейнера (которые ротируются).

MR !306 добавляет `durationMs`/`status` (`ok` | `timeout` | `error`) в модель учёта `ai_usage`, инструментирует вызовы к AI-провайдеру длительностью и исходом, и показывает медиану/95-й процентиль/число таймаутов в админке "AI-расходы".

## Реализация

**Схема и миграция** - `api/prisma/schema.prisma` + `api/prisma/migrations/20260730060000_ai_usage_duration_status/migration.sql`:
```sql
ALTER TABLE "ai_usage" ADD COLUMN "duration_ms" INTEGER;
ALTER TABLE "ai_usage" ADD COLUMN "status" TEXT NOT NULL DEFAULT 'ok';
CREATE INDEX "ai_usage_status_created_at_idx" ON "ai_usage"("status", "created_at");
```
`duration_ms` nullable, `status` со значением по умолчанию `'ok'` - существующие строки получают его автоматически, без бэкфилла. Само добавление колонки с константным DEFAULT в Postgres - metadata-only (без переписывания таблицы). Единственная оговорка: `CREATE INDEX` без `CONCURRENTLY` в теории держит блокировку на запись на время построения индекса - на маленькой/средней таблице это доли секунды, но если `ai_usage` уже большая, стоит уточнить у автора, замерялось ли время индексации на проде-по-размеру (в описании ticket "деплой не требует простоя" заявлен как acceptance, а не просто пожелание).

**Клиент LLM** - `api/src/services/openai/openai-responses.client.ts`. Раньше `call()` возвращал `ResponsesResult | null`, теперь - discriminated union `ResponsesOutcome`: `{ ok: true, durationMs, ...result }` либо `{ ok: false, status: 'timeout' | 'error' | 'skipped', durationMs }`. `'skipped'` - когда `OPENAI_API_KEY` не задан (запроса не было вовсе). Таймаут отличается от прочей ошибки по `err.name === 'TimeoutError' | 'AbortError'` (из `AbortSignal.timeout`).

**Запись в БД** - `api/src/services/ai-usage/ai-usage.service.ts` (`AiUsageService.record`): при `input.usage == null` (неуспех) `costUsdMicros` пишется `null` без похода за прайсингом (иначе таймаут ложно триггерил бы алерт "нет цены для модели" - `aiUsageMissingPriceTotal`). Одновременно с записью в БД идёт `aiRequestDuration.labels(kind, model, status).observe(...)` - Prometheus-гистограмма `ai_request_duration_seconds` (`api/src/metrics.ts`).

**Кто теперь пишет `durationMs`/`status`:**
- `api/src/services/memory/greeting-ai.service.ts` (kind `greeting`, timeout 3000 мс - совпадает с "лимитом 3" из тикета) - пишет запись и на успех, и на `timeout`/`error` (не на `skipped`).
- `api/src/services/memory/memory-extraction.service.ts` (kind `memory_extraction`) - аналогично, пишет и неуспех.
- `socket-gateway/src/helpers/ai-usage.helper.ts` (`recordStreamAiUsage`, kind `chat`/`recognition` - трафик тренажёра и диагностики через socket-gateway) - **пишет только успех**, см. "Открытые вопросы".
- `api/src/services/parent-report-ai.service.ts` + `parent-report.service.ts` (kind `parent_report`) - **пишет только успех**, см. "Открытые вопросы".

**Админка** - `api/src/admin/ai-cost.service.ts` (`AiCostService.dashboard`) и `frontend/pages/admin/ai-cost/index.vue`. В SQL-агрегате по `surface`+`kind` добавлены:
```sql
COUNT(*) FILTER (WHERE status = 'timeout')::bigint AS timeouts,
percentile_cont(0.5) WITHIN GROUP (ORDER BY duration_ms)::float8 AS p50_ms,
percentile_cont(0.95) WITHIN GROUP (ORDER BY duration_ms)::float8 AS p95_ms
```
`percentile_cont` игнорирует NULL в упорядочиваемом наборе - строки без `duration_ms` (старые, до миграции) просто не участвуют в перцентиле и не ломают запрос. В UI (`admin-cost/index.vue`, блок "По фичам продукта", строка `k` на уровне `surface`+`kind`): если `k.p50Ms` truthy - показывается `"{p50} / {p95}"` в секундах (`secs()`: `(ms/1000).toFixed(1) + " с"`), иначе - `"-"` (прочерк). Число таймаутов, если `k.timeouts > 0`, выводится отдельным спаном `color: var(--c-pulse)` (акцентный/красный тон темы) с текстом `"{n} таймаут."`; на строке есть `title`-тултип с полной расшифровкой ("Медиана N мс, 95-й процентиль N мс, таймаутов N"). Это единственное место в проверяемом UI, где значения времени/таймаутов видны.

## Тест-кейсы / чек-лист

### 1. Основной сценарий (по тексту комментария разработчика)
1. Зайти в тренажёр под учеником, отправить решение с доски (recognition) и пару сообщений в чат (chat).
2. Дождаться, чтобы также сработала генерация приветствия (`greeting`, если ученик попадает в когорту `memory`) в рамках сессии - см. `context.cohort !== 'memory'` в `greeting-ai.service.ts`, без этой когорты вызова просто не будет.
3. Открыть Админка → AI-расходы за период "Этот месяц" или "30 дней" (сегодняшний день должен попасть в диапазон).
4. Ожидается: у строк «Приветствие», «Чат», «Распознавание» в блоке "По фичам продукта" вместо прочерка показывается пара значений медиана/p95 в секундах (не прочерк `-`).
5. Навести курсор на значение времени - тултип должен показывать точные мс медианы/p95 и число таймаутов текстом.

### 2. Медиана приветствия около лимита (ключевой инсайт тикета)
- У «Приветствие» медиана времени должна быть в районе ~2-3 с (лимит по коду `TIMEOUT_MS = 3_000` в `greeting-ai.service.ts`). Если по факту вызовов приветствия было мало за период - значения могут быть нерепрезентативны, стоит смотреть за более длинный период (30 дней/месяц).

### 3. Регресс: старые записи не ломают отображение (acceptance "прежние записи учёта остаются валидными")
- Найти период, где заведомо есть старые вызовы (до вливания миграции - `duration_ms` = NULL, `status` = `'ok'` по дефолту). Ожидается: страница AI-расходов открывается без ошибок, для тех типов вызова, где все записи периода старые (без `duration_ms`), в колонке времени - прочерк `-`, а не `NaN`/`0.0 с`/сломанная вёрстка. Это обеспечено тем, что UI проверяет `k.p50Ms` truthy, а `percentile_cont` в SQL просто игнорирует NULL.
- Если в одном и том же периоде есть смесь старых (без duration) и новых (с duration) записей одного kind - агрегат должен посчитать перцентиль только по новым, без падения запроса.

### 4. Доля таймаутов по приветствию считается запросом к базе (acceptance)
- Агрегирующий SQL - в `api/src/admin/ai-cost.service.ts`, метод `dashboard()`, подзапрос `bySurfaceKind` (см. код выше, `COUNT(*) FILTER (WHERE status = 'timeout')`). Это один `$queryRaw`-запрос на весь период и на все surface/kind сразу, без похода в приложение/логи - соответствует acceptance буквально.
- Проверить на живых данных: спровоцировать пару таймаутов приветствия (например, временно уменьшить лимит легко не получится без деплоя - но можно проверить косвенно: если за сегодня уже были таймауты у приветствия по естественным причинам возле лимита 2.9-3с, красное число должно появиться у "Приветствие").

### 5. Три исхода на живом стенде - success / provider unavailable / provider hangs to timeout
- Разработчик заявляет, что все три исхода проверены (для потока приветствия, судя по коду и юнит-тестам - `greeting-ai.service.test.ts`, `openai-responses.client.test.ts`). Стоит целенаправленно повторить это визуально в админке для **разных kind**, а не только для приветствия - см. открытый вопрос №1 ниже, там есть основания полагать, что для чата/распознавания/отчёта родителю таймаут в БД вообще не попадёт.

## Открытые вопросы / находки по коду

1. **Неуспешные вызовы `chat` и `recognition` (трафик тренажёра/диагностики через socket-gateway) в учёт НЕ попадают, несмотря на acceptance "неудачные попытки тоже попадают в учёт".** В `socket-gateway/src/helpers/ai-usage.helper.ts`, функция `recordStreamAiUsage`:
   ```ts
   if (!endPayload) { return; }
   ...
   if (!usage || !model) { logger.warn(...); return; }
   ```
   `finish()` в `conversation.stream.ts`/`recognition.stream.ts` вызывается **без** `endPayload` и на таймауте (`abort()` → `this.finish()`), и на ошибке прокси (`boundErrorHandler` → `this.finish()`), и `status: 'ok'` в `recordStreamAiUsage` жёстко захардкожен - записи для этих путей просто не создаётся вовсе (ни `ok`, ни `timeout`, ни `error`). Это прямо подтверждено собственным юнит-тестом MR: `socket-gateway/src/helpers/__tests__/ai-usage.helper.test.ts`, тест `'does nothing when usage is missing'` - ожидает `expect(spy).not.toHaveBeenCalled()` именно в сценарии без usage (== таймаут/ошибка). Т.е. для «Чат» и «Распознавание» в админке таймауты/ошибки заведомо не будут учтены и не будут видны - только успешные вызовы. На практике стоит: (а) уронить/подвесить прокси в тестовом стенде и отправить сообщение в чат тренажёра или решение на распознавание, (б) проверить в БД / в админке, что для этого вызова НЕ появилась строка со `status='timeout'/'error'` - если строки нет вовсе, это подтверждает разрыв в скоупе, который стоит обсудить с автором (возможно, осознанное решение оставить на потом, а не баг, но описание тикета явно требует иное).

2. **Неуспешные вызовы `parent_report` тоже не попадают в учёт.** В `api/src/services/parent-report-ai.service.ts`, `requestSummary`:
   ```ts
   if (!outcome.ok || !outcome.text) return null;
   ```
   При `!outcome.ok` (таймаут/ошибка) метод просто возвращает `null` без вызова `aiUsageService.record`; в `parent-report.service.ts` `ai_usage.record` вызывается только внутри `if (summaryResult) { ... status: 'ok' ... }` - веток на `summaryResult === null` c записью неуспеха нет вообще. Итог: для «Отчёт родителю» в БД появляются только успешные вызовы, таймауты/ошибки логически не будут видны рядом со стоимостью - тот же пробел, что и в п.1, но для другого surface.
   Вывод: из четырёх типов вызова, перечисленных в описании тикета (приветствие, память Мии, отчёт родителю, плюс уже существовавшие чат/распознавание), acceptance "неудачные попытки тоже попадают в учёт" по факту реализован только для **приветствия** (`greeting`) и **извлечения памяти** (`memory_extraction`) - именно тех двух, что вызывают `openAiResponsesClient` напрямую из api и явно ветвятся по `outcome.ok`. Стоит уточнить у автора, это осознанно оставлено на следующий шаг, или недосмотр при реализации.

3. **Учёт по ученику - только через общий SQL-агрегат по всем ученикам сразу, а не "по любому ученику" отдельно.** Acceptance гласит: "по любому ученику и типу запроса видно время и исход, без чтения логов". Единственное место, где реально показаны время/исход (`p50Ms`/`p95Ms`/`timeouts`) - это `aiCostService.dashboard()` и страница `/admin/ai-cost` - агрегат **по всем ученикам за период**, точки входа "по конкретному ученику" там нет. Отдельный виджет для одного ученика - `admin-user-ai-cost.vue` (использует `aiCostService.breakdownForParent`, тип `AiCostBreakdown`) - в этом MR **не тронут**: у него по-прежнему только `usd`/`calls` в разрезе surface/kind, без `durationMs`/`status`/`p50`/`p95`/`timeouts` (проверено по диффу `api/src/admin/ai-cost.service.ts` - изменения только в интерфейсе/запросе `AiCostDashboard`/`dashboard()`, метод `breakdownForParent` и тип `AiCostBreakdown` не менялись). Формально буквальный acceptance "по любому ученику" не выполнен - только "по всем ученикам сразу за период". Инструкция автора по проверке ("зайти в тренажёр под учеником... затем открыть админку за сегодня") на практике проверяет именно общий агрегат за сегодня, а не персональную страницу ученика - с этим стоит определиться, ожидание продукта было "открыть карточку конкретного ученика и увидеть его тайминги" или "открыть общий дашборд за узкий период (сегодня), где по факту виден в основном этот ученик".

4. **Алерт на рост доли таймаутов - вне скоупа этого MR.** Прямая цитата из комментария автора: "Осталось отдельным шагом: алерт «доля таймаутов выросла» - он настраивается на monitoring-хосте руками и только после того, как метрика доедет до прода." Соответствующий пункт скоупа/acceptance тикета ("алерт, когда доля таймаутов вырастает") в этой поставке не реализован и не тестируется - его нельзя закрыть проверкой этого MR. Отдельно стоит отметить: технически метрика для будущего алерта, скорее всего, будет строиться на Prometheus-гистограмме `ai_request_duration_seconds` (labels `kind`, `model`, `status`) из `api/src/metrics.ts`, а не на SQL-агрегате из БД (агрегат из БД используется только в самой админке) - стоит уточнить у автора при настройке алерта, откуда именно он будет читать долю таймаутов, чтобы не разошлись два независимых источника чисел (метрика vs БД) при разном поведении на неуспешных `chat`/`recognition`/`parent_report` (см. п.1-2 - в БД эти неуспехи не попадут, а в Prometheus-гистограмму `aiRequestDuration` - попадут, т.к. она пишется в `aiUsageService.record()` независимо от того, есть ли `usage`, при условии что `record()` вообще был вызван; но раз `record()` для chat/recognition/parent_report неуспехов не вызывается вовсе - см. п.1-2 - то и в гистограмму эти случаи тоже не попадут. Единственный путь, где таймаут дойдёт и до БД, и до метрики - `greeting`/`memory_extraction`).

5. **Мелкая деталь, не блокер:** в `greeting-ai.service.ts` при `outcome.ok === true`, но `result.usage == null` (ok-ответ без объекта `usage` от провайдера) запись в `ai_usage` не создаётся вовсе - ни как успех, ни как что-либо ещё (условие `if (result.usage) { ...record... }`). Маловероятный, но теоретически возможный кейс (провайдер вернул 2xx без usage-блока) выпадает из учёта молча.
