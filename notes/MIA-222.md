## Контекст

Баг-репорт по продовому инциденту: ученик, открывший ссылку доступа (`/ref/<token>`) на новом устройстве, в первые секунды после входа видел тост «Сессия прервана», и связь с Мией поднималась только после ручной перезагрузки страницы. На проде это воспроизводилось на КАЖДОМ заходе по ссылке — 16 из 16 за 3 дня (по описанию задачи).

Причина по формулировке автора: страница ссылки активировала её 2-3 раза подряд, а каждая активация выпускает новую сессию устройства и гасит предыдущую. Сокет, успевший подключиться под уже погашенной (первой) сессией, гейтвей отбивает.

Фикс сделан и смержен в master: MR !525 `fix(frontend): ссылка доступа активируется один раз` (source branch `fix/ref-double-activate`, 3 изменённых файла).

## Что было сломано

- По ссылке `/ref/<token>` уходило 2-3 запроса `POST /auth/activate` вместо одного.
- Каждая повторная активация в `authService`/`session` создаёт новую сессию устройства и инвалидирует предыдущую. Сокет успевал подключиться к сессии №1, но пока фронт ещё донабирал повторные активации, сессия №1 гасилась — сокет-гейтвей не находил сессию по её id и обрывал соединение (`socket-gateway/src/handlers/connection.handler.ts`: `'SGW client connection rejected: user session not found'` → `socket.emit('error', { message: 'connection rejected due session not found' })` → `socket.disconnect(true)`).
- На фронте это проявлялось как тост-баннер «Сессия прервана» (`frontend/components/cabinet/shell/shell-connection-toast.vue`, текст: заголовок «Сессия прервана», подсказка «Сессия истекла — обнови страницу, и занятие продолжится с того же места.», кнопка «Обновить»). Кнопка баннера для этого состояния не переподключает сокет, а делает `window.location.reload()` — отсюда наблюдение «связь поднималась только после перезагрузки».
- Корневая причина именно повторной активации — в `frontend/middleware/auth.global.ts`: проверка «пользователь уже вошёл» (`if (userStore.user) {...}`) была вложена ВНУТРЬ общего `try`-блока, уже ПОСЛЕ вызова `setLoading(true)`. То есть даже для уже аутентифицированного пользователя (а сразу после `activate()` на странице `/ref/[token].vue` пользователь именно такой — `userStore.setSessionId` + `userStore.loadMe()` уже отработали) middleware всё равно поднимало флаг загрузки на каждый переход. Это заставляло layout дашборда размонтировать/перемонтировать страницу посреди навигации — соответственно `onMounted` страницы `/ref/[token].vue` с вызовом `api.activate(token, visitorId)` срабатывал повторно.
- Отдельно: сокет-плагин (`frontend/plugins/socket.ts`) слушал только `userStore.sessionId`, а не факт авторизации в целом — если `isAuthorized()` в момент срабатывания watcher'а ещё не был true (пользователь из `/me` ещё не подтянулся), первая попытка подключения сокета молча ничего не делала и не переигрывалась, из-за чего связь с Мией не поднималась сама и требовала перезагрузки страницы.

## Что изменено

MR !525 трогает 3 файла:

1. **`frontend/middleware/auth.global.ts`** — блок `if (userStore.user) {...}` (стрип `?login=open`, редирект родителя не по «разрешённому» пути на `/`, редирект ученика без профиля на `ROUTES.hello`) вынесен из глубины `try` наружу, СРАЗУ после вычисления `publicPath`, ещё до `setLoading(true)`. Для уже вошедшего пользователя middleware теперь сразу делает `setLoading(false)` + `setNetworkError(false)` и возвращается, не поднимая флаг загрузки вообще — страница больше не перемонтируется на переходе, и `/ref/[token].vue` не вызывает `activate()` второй раз после того, как пользователь уже аутентифицирован первым успешным вызовом.
2. **`frontend/plugins/socket.ts`** — watcher подключения сокета следит теперь не только за `userStore.sessionId`, но и за `isAuthorized()` (`watch(() => [userStore.sessionId, isAuthorized()], ...)`). По комментарию в коде: активация записывает сессию в стор раньше, чем `/me` заполняет пользователя, поэтому раньше строка могла остаться неподнятой, если первая попытка совпадала с моментом, когда авторизации ещё не было. Теперь смена любого из двух значений триггерит `connectSocket(socket)` — сокет подключается сразу после активации, без перезагрузки страницы.
3. **`e2e/specs/product/access-link-activation.spec.ts`** (новый файл) — e2e-тест: регистрирует родителя, берёт ссылку доступа из модалки успеха, открывает её в отдельном браузерном контексте (со своим fingerprint), считает число запросов `POST .../api/auth/activate` и ждёт фрейм `session:joined` по сокету. Ассерты: `activations === 1` и что среди websocket-фреймов нет `session not found`. Тест намеренно НЕ использует общий хелпер `loginAsStudent` (он делает `reload()`, который замаскировал бы баг — после перезагрузки сокет подключается и в старом коде).

## Как перепроверить

1. Зарегистрировать родителя и получить ссылку доступа ученика (как в обычном онбординге).
2. Открыть эту ссылку на новом устройстве / в приватном окне / в новом браузерном профиле (важно — «чистый» fingerprint, без уже активного устройства).
3. **Ожидается:** ученика сразу переносит на карту знаний (`ROUTES.dashboard`) или на greeting (`ROUTES.hello`, если у ребёнка ещё не выбран класс) без промежуточных экранов ошибки.
4. В первые 10-15 секунд после входа тоста «Сессия прервана» / «Нет связи с Мией» быть не должно. Открыть чат с Миёй и убедиться, что он отвечает сразу, без перезагрузки страницы.
5. Через DevTools (Network) проверить, что на переход по ссылке ушёл РОВНО ОДИН запрос `POST /api/auth/activate` (не 2-3).
6. Через DevTools (Network → WS) проверить, что сокет-соединение не разрывается сразу после установления и что нет ответа с `session not found`.
7. Пройтись по кабинету (переход между разделами) — полоса загрузки/спиннер не должны мигать/дёргаться на обычных переходах авторизованного пользователя (регресс на правку в `auth.global.ts`, затрагивающую вообще все переходы залогиненных, не только `/ref`).
8. Дополнительно проверить старый (уже известный, ожидаемый) сценарий — повторный переход по УЖЕ использованной ссылке на том же устройстве, где сессия жива: должен сработать silent-редирект без экрана 410 (см. ветку `code === 'revoked' || code === 'expired'` при `userStore.isLoggedIn` в `frontend/pages/ref/[token].vue`), а не показывать «Ссылка уже использована».
9. Быстрый двойной/тройной переход по одной и той же ссылке (например, повторный клик/двойной тап до полной загрузки) — тоже не должен приводить к повторной активации и обрыву сокета.

## Что посмотреть рядом (регресс)

- **Общее поведение `auth.global.ts` для ВСЕХ залогиненных пользователей**, а не только для только что активировавшихся по ссылке — правка меняет порядок проверок на каждом переходе. Отдельно проверить: обычный логин по паролю/через модалку, вход родителя (редирект с непустого пути на `/`, кроме исключений — `/admin`, `/ref/`, `/parent...`, `/report`, `/blog`, `/invite/`, UZ-роуты, legal-роуты), сброс параметра `?login=open` в URL для уже вошедшего пользователя.
- **Просмотр кабинета ребёнка родителем через `?preview=...`** — путь исключён из принудительного редиректа родителя (`isParentExemptPath`), убедиться, что он не задет правкой порядка проверок.
- **Ученик без класса (`studentNeedsProfile`)** — редирект на `ROUTES.hello` при заходе по ссылке (или иным путём) должен по-прежнему срабатывать, теперь эта проверка выполняется раньше (до `setLoading(true)`).
- **Другие состояния страницы `/ref/[token].vue`**: `not_found`, `revoked`, `expired`, `error` — фикс не трогал эту логику напрямую, но раз символ обхода включает саму механику монтирования страницы, стоит один раз перепроверить, что эти экраны по-прежнему показываются корректно (истёкшая/отозванная/несуществующая ссылка), включая кнопку «Запросить новую ссылку».
- **Сокет на обычном логине (не по ссылке)** — раз watcher в `socket.ts` теперь реагирует на пару `[sessionId, isAuthorized()]`, стоит удостовериться, что обычный логин (пароль, магическая ссылка и т.п.) по-прежнему поднимает сокет с первой попытки и не дублирует подключение (`isDemoSocket`/сброс auth для demo-чата рядом в том же файле — тоже кандидат на попутную проверку).
- **Мультивход**: если у одного ребёнка несколько устройств, активация новой ссылки на одном из них по продуктовой логике всё ещё должна гасить сессию на предыдущем устройстве (это ожидаемое поведение, не баг) — проверить, что уже активное устройство корректно получает тот самый тост «Сессия прервана» с предложением обновить страницу, а НЕ то устройство, которое только что зашло по новой ссылке.

## Аналитика/API

- Активация по ссылке шлёт клиентское событие `AUTH_DEVICE_ACTIVATED` (`auth_device_activated`, `frontend/constants/analytics-events.ts`) — вызывается в `frontend/pages/ref/[token].vue` сразу после успешного `api.activate(...)`, до фикса могло уходить 2-3 раза за один заход по ссылке. После фикса ожидается ровно одно срабатывание на одну активацию ссылки — стоит сверить по аналитике (например, в вебвизор/трекере события) на тестовом прогоне, что число событий `auth_device_activated` для одного захода по ссылке равно числу заходов, а не превышает его.
- В `api/src/constants/analytics-events.ts` отдельного зеркального server-side события именно для активации по ссылке доступа не найдено (есть `INVITE_ACTIVATED`, `SESSION_START/END`, `BIND_NO_SESSION_SHOWN` — они про другие сценарии, не про `/ref/<token>`), так что server-side дублирования события для сверки нет — контроль только по клиентскому событию и по логам `POST /auth/activate`.

## Открытые вопросы

- Обсуждений/ревью-комментариев в MR !525 нет (только системная запись о мерже) — не с кем свериться по нюансам реализации, кроме текста самого MR и комментария автора в Linear.
- В комментарии автора к задаче фигурируют другие цифры прогонов («до фикса 6 из 6, после — 8 из 8 чистые» на тестовом стенде), чем в описании issue («16 из 16 за 3 дня» — про прод) — это разные выборки (прод vs тестовый стенд), но при финальной проверке стоит явно зафиксировать собственное число чистых прогонов подряд (комментарий автора предлагает шаги 1-4, см. текст комментария).
