## Контекст

Новая задача, заведена и сразу переведена в Ready for Test в один день (23.09) самим разработчиком (Kirill Verzhitskii), он же автор MR. Сценарий: ребёнок регистрируется сам (на платформе одна форма регистрации, она родительская), доходит до конца второго ML-блока первой темы — и вместо фримиум-пейволла (который ребёнку показывать бессмысленно, платить ему нечем) видит модалку с просьбой позвать родителя по короткой суточной ссылке. Родитель по ссылке видит персональный рассказ про ребёнка, регистрируется или входит в существующий кабинет, забирает ребёнка к себе, проходит короткий онбординг кабинета и упирается в обычный пейволл. Ученику начисляется +50 баллов рейтинга, тренажёр открывается.

Рядом с MR лежат спек и план (`docs/superpowers/specs/2026-09-23-student-to-parent-cj-design.md`, `docs/superpowers/plans/2026-09-23-student-to-parent-cj.md`) — оба на 100+/2000+ строк, спек прочитан целиком, план — частично (архитектурная часть и таблица файлов). В конце спека отдельным коммитом (`a8d8bc7a`, «docs: расхождения реализации со спеком CJ») сам разработчик задокументировал 5 мест, где реализация разошлась с первоначальным дизайном — это самая полезная часть спека для QA, приведена в «Реализации» ниже.

Задача помечена как «вторая версия истории родитель-ученик» — в коде уже есть родительский кабинет, семейные слоты, страница `/parent`, `parent-sidebar.vue` и т.д. (следы более ранней работы над кабинетом родителя — судя по репозиторию, ветка `feat/MIA-96-family-slots`). MIA-208 не переписывает эти вещи, а достраивает поверх них: новую сущность `parent_invite`, новый уровень доступа `parent_pending`, страницу приглашения, онбординг и режим просмотра «глазами ребёнка». Подробнее пересечения — в «Открытые вопросы».

## Реализация

Код прочитан целиком на HEAD ветки `feat/MIA-208-student-to-parent-cj` (коммит `0e56296a`, вершина 21 коммита — 17 `feat`, один `docs`, три `fix` по итогам собственного ревью, один `test(e2e)`, один `chore`). ### Распознавание «это ребёнок завёл аккаунт сам» — два сигнала, не один

Форма регистрации осталась одна (по ТЗ: «отдельного лендинга и формы для детей нет»), но у STUDENT-записи появились два поля: `selfSignupPendingAt` и `selfSignupConfirmedAt`.

1. **Сигнал 1 — тот же fingerprint, что при регистрации, в пределах получаса.** `api/src/services/self-signup.service.ts`, `markPendingIfSameDevice`: при активации ученической ссылки (`/ref/<token>`, тот же механизм, что раньше) проверяется, есть ли на **этом же устройстве** (по fingerprint) живая сессия родителя этого же ребёнка, выпущенная не больше `STUDENT_SELF_SIGNUP_WINDOW_MIN` (по умолчанию 30) минут назад. Если да — ставится `selfSignupPendingAt`.
2. **Сигнал 2 — отправленное решение в этой же сессии.** `confirmOnSubmission` — вызывается из `api/src/controllers/trainer.controller.ts:363` (при сабмишене тренажёра) и `api/src/controllers/diagnostic.controller.ts:358` (при сабмишене диагностики). Переводит `pending → confirmed`, только если `pending` уже стоит и `confirmed` ещё нет.

Разделение на два сигнала обязательно: один совпавший fingerprint бывает и у настоящего родителя, который открыл ссылку ребёнка на своём телефоне просто посмотреть — решать задачи он там не станет, поэтому `confirmed` не выставится, и гейт (ниже) не сработает.

### Гейт тренажёра — `parent_pending`, отдельно от пейволла

`api/src/services/access.service.ts:44` — `AccessLevel = 'full' | 'freemium' | 'parent_pending'`. Условие (`needsParentConfirmation`, строки 56-74):
```ts
if (user.selfSignupConfirmedAt === null) return false;
if (user.parentConfirmedAt !== null) return false;
if (user.freeTopicId === null) return false;
const closedMl2 = await prisma.topicMlProgress.findFirst({
  where: { userId: user.id, topicId: user.freeTopicId, mlLevel: 2, status: { in: CLOSED_ML_STATUSES } },
  select: { id: true },
});
return closedMl2 !== null;
```
`CLOSED_ML_STATUSES` — не только `passed`, но и `credited` (значок силы), иначе сильный ученик, которому блок зачли, а не решили пошагово, прошёл бы мимо гейта. `canAccessTrainer` проверяет `parent_pending` первым, раньше обычной проверки подписки (`access.service.ts:125-127`).

`api/src/middleware/require-topic-access.ts:44-57` — на уровне мидлвары `parent_pending` отдаёт **403 с кодом `PARENT_CONSENT_REQUIRED`** (`helpers/errors.helper.ts`), не `PAYWALL`. Диагностика, кабинет ученика, рейтинг и чат Мии при этом продолжают работать — закрыт только тренажёр, ровно как в ТЗ.

Фронтенд ловит именно этот код в едином перехватчике `frontend/composables/use-api.ts:26-37`:
```ts
if (response?.status === 403 && response._data?.code === 'PARENT_CONSENT_REQUIRED') {
  const { useParentInviteStore } = await import('~/stores/parent-invite');
  await useParentInviteStore().open();
  return;
}
```
— проверяется **раньше** обработки кода `PAYWALL` в том же перехватчике, комментарий в коде прямо это объясняет: «ребёнку, которого ждёт подтверждение родителя, показывать цену незачем».

### Ссылка приглашения — суточная, переиспользуемая, одноразовая

Новая таблица `parent_invite` (`token`, `studentId`, `createdAt`, `expiresAt`, `usedAt`, `usedByUserId`). `api/src/services/parent-invite.service.ts`:
- `issueFor(studentId)` — переиспользует уже живую (не использованную и не истёкшую) ссылку вместо того чтобы плодить новую при каждом открытии модалки; выдаётся только если `selfSignupConfirmedAt !== null && parentConfirmedAt === null` (иначе ученик с уже подтверждённым родителем мог бы выпустить рабочую ссылку на живой аккаунт — отдельная проверка `ParentInviteError('not_a_placeholder')`).
- TTL — переменная окружения `PARENT_INVITE_TTL_HOURS`, по умолчанию 24 (соответствует ТЗ «сутки»).
- `markUsed` — CAS-погашение (`updateMany({ where: { token, usedAt: null }, ... })`), возвращает `false` при проигранной гонке — то есть при одновременном открытии одной ссылки на двух устройствах второй запрос не пройдёт молча.

### Два разных исхода для взрослого — занять заглушку или забрать ребёнка

Это ключевое архитектурное решение спека — родительская запись ребёнка (STUDENT + PARENT-заглушка, заведённая при обычной регистрации) **не удаляется и не переносится**, а либо перезаписывается, либо гасится:

- **`takeoverPlaceholder`** (у взрослого ещё нет аккаунта) — перезаписывает email/телефон/имя той же PARENT-записи (подписка, слоты, отчёты, `acquisition_source` остаются на месте), email ребёнка при этом переезжает на STUDENT-запись. Проверка email родителя ≠ email ребёнка (код `email_is_child_email`) и email родителя ещё не занят другим аккаунтом (код `email_registered`, добавлен по итогам ревью, см. ниже) — обе проверки **до** погашения ссылки, чтобы неудачная попытка не сжигала токен.
- **`attachToExistingParent`** (у взрослого уже есть свой кабинет) — ребёнок переезжает (`parentId` меняется), старая PARENT-заглушка гасится (`deletedAt`), её подписка помечается `CANCELLED`, а место в подписке заглушки явно освобождается (`subscriptionSlot.releasedAt`) — иначе, как отмечено в комментарии кода, фримиум-слот заглушки (с `expiresAt` в 2099 году) пережил бы гашение и продолжал бы выигрывать у настоящей подписки родителя при выборе активной подписки для ребёнка (сортировка по `expiresAt desc`).

Оба пути начисляют +50 баллов (`ratingAwardService.awardParentConfirmed`, причина `parent_confirmed`, `EFFORT_POINTS.parentConfirmed = 50`, идемпотентно — уникальность по `reason + user_id`, как у `first_login`).

### Расхождения с исходным спеком (задокументированы автором, коммит `a8d8bc7a`)

1. **Регистрация родителя — отдельная ручка**, не переиспользование `POST /auth/register`: обычная схема регистрации требует `student.grade`, а взрослому, пришедшему по ссылке, заводить ребёнка не нужно — он уже есть. Реализовано как `POST /parent-invite/:token/register` со своим телом.
2. **«Войти» — не мгновенный вход.** У родителя ещё нет пароля, вход всегда идёт письмом со ссылкой; `loginRequest` теперь принимает `parentInviteToken` и дописывает `&invite=<token>` в ссылку письма, а страница `/parent/enter` после успешного входа сама вызывает `attach`.
3. **Новый код ошибки `email_registered`** — раньше конфликт email упал бы на constraint 500; теперь проверяется явно до погашения ссылки, а фронт уводит на `/parent/enter?invite=<token>` (форму входа с сохранённым приглашением).
4. **Кнопка «Родитель подтвердил» в модалке гейта** — подтверждение приходит на другом устройстве, вкладка ученика сама об этом не узнаёт; без ручной кнопки ученик сидел бы перед модалкой до перезагрузки страницы. `parent-invite-gate-modal.vue` вызывает `store.recheck()` → `userStore.loadMe()` → сверяет `access.level !== 'parent_pending'`.
5. **Срабатывание самого гейта не покрыто e2e** — довести ML2 кликами (десятки задач) сочли слишком долгим для прогона; правило гейта закрыто юнит-тестами (`access.parent-pending.test.ts`), а e2e-сценарий (`e2e/specs/product/student-to-parent-cj.spec.ts`) начинается сразу с выдачи ссылки. Автор отдельно предупредил в комментарии Linear, что весь e2e-сценарий **написан, но не прогнан локально** (не было свободной памяти под второй стек) — стоит внимательно прогнать этот файл вручную или через CI при перепроверке, а не полагаться на «раз написан — значит зелёный».

### Онбординг и просмотр «глазами ребёнка»

- `frontend/components/parent/parent-onboarding.vue` — три слайда поверх кабинета при первом входе, состояние — `user.onboarding.parentCabinetDoneAt` (JSON-колонка, общая с разметкой ученика, ключи не пересекаются), пропускается одной кнопкой, второй раз не показывается. **Существующие родители не видят экран** — это обеспечено отдельной миграцией-бэкафиллом (`20260923140000_parent_cabinet_onboarding_backfill`), которая молча проставляет `parentCabinetDoneAt` всем, у кого роль `PARENT` и это поле ещё не заполнено, на момент выката.
- **Просмотр глазами ребёнка** — `frontend/components/parent/parent-sidebar.vue:151-154`, ссылка `?preview=<childId>` на `/app/dash`; на бэке `api/src/middleware/allow-parent-preview.ts` пускает родителя в **GET**-ручки ребёнка, только если `childId` действительно его ребёнок, любой не-`GET`-запрос с `preview` — сразу 403 `PREVIEW_READ_ONLY`. `parent-preview-bar.vue` — полоса сверху «Вы смотрите глазами {имя} — решать и писать Мии отсюда нельзя» со ссылкой «Выйти из просмотра». Полноценной имперсонации (входа под сессией ребёнка) сознательно нет — она сломала бы device-привязку ученика.
- **Персонализация страницы родителя без обращений к модели** (осознанный отказ в Out of scope) — `parentInviteService.publicView`: имя и число решённых задач берутся из `topicMlProgress`, «сильная сторона» — последняя активная запись `student_memory` с `kind='pedagogy', valence='strength'`. Если такой записи нет — абзац про сильную сторону просто выпадает, ничего не выдумывается.

## Тест-кейсы

1. **[Happy path, приоритет] Полный цикл на двух устройствах.** Устройство А: зарегистрироваться на `/register`, тут же на этом же устройстве открыть ученическую ссылку из модалки (в пределах получаса). Решать в тренажёре до закрытия второго ML-блока первой темы → вместо пейволла должна подняться модалка Мии со ссылкой для родителя и текстом про +50 баллов. Устройство Б: открыть ссылку → видно имя ребёнка, тему, число решённых задач (и, если есть, строку про сильную сторону) → зарегистрироваться своим email (не тем, что у ребёнка) → должен открыться кабинет родителя, три экрана онбординга, затем экран оплаты (`/select-tariff`). Вернуться на устройство А, нажать «Родитель подтвердил» → тренажёр открыт, в рейтинге +50 баллов.
2. **Родитель, у которого уже есть аккаунт.** Открыть ссылку → «У меня уже есть аккаунт» → письмо со ссылкой входа → войти → ребёнок должен появиться в существующем кабинете этого родителя (без создания нового), онбординг у уже существующего родителя **не** показывается.
3. **Повторное открытие уже использованной ссылки.** Открыть ту же ссылку вторым браузером/устройством после того, как она уже была использована → «Ребёнок уже привязан» + кнопка входа, никакой повторной привязки/перезаписи не происходит.
4. **Истёкшая ссылка.** Ссылка старше суток → «Ссылка устарела, попросите новую у ребёнка», форма регистрации не показывается.
5. **Мусорный/несуществующий токен.** Прямой заход на `/invite/<случайная строка>` → публичная ручка отвечает 404, страница не должна показывать форму или данные ребёнка.
6. **Email родителя совпадает с email ребёнка.** При регистрации по ссылке ввести тот же email, что уже числится за ребёнком (детский email на заглушке) → понятная ошибка формы, без 500 и без порчи данных.
7. **Email родителя уже зарегистрирован, но пользователь пытается «Создать кабинет».** Ввести email существующего аккаунта в форму регистрации (не через «У меня уже есть аккаунт») → должен прийти код `email_registered`, фронт должен сам увести на `/parent/enter?invite=<token>`, а не показать техническую ошибку/500.
8. **«Я родитель» в модалке гейта (ложное срабатывание распознавания).** Взрослый регистрируется и сам же по ошибке открывает ученическую ссылку на своём устройстве, попадает в гейт — нажать «Я родитель» в модалке → отметки распознавания снимаются, тренажёр открывается без прохождения цепочки приглашения.
9. **Просмотр «глазами ребёнка» — только чтение.** В кабинете родителя нажать «Посмотреть, как выглядит Мия глазами ребёнка» → открывается ученический кабинет с полосой сверху; попытка отправить решение или написать в чат должна быть заблокирована (UI и/или 403 `PREVIEW_READ_ONLY` при прямом POST/PUT/DELETE с `?preview=`). Кнопка «Выйти из просмотра» возвращает в обычный кабинет родителя.
10. **Гейт не трогает другие поверхности.** Пока ученик в состоянии `parent_pending` — диагностика, кабинет ученика, рейтинг и чат с Мией (не тренажёр) должны оставаться доступны как обычно; закрыт **только** тренажёр.
11. **Регресс: обычная (не self-signup) регистрация.** Родитель, регистрирующийся штатно на `/register` для собственного ребёнка (без ученической активности с того же устройства до этого) — не должен попадать ни в `parent_pending`, ни видеть какие-либо элементы CJ «от ученика к родителю».
12. **Регресс: пейволл для обычного фримиум-ученика (не self-signup).** Убедиться, что появление уровня `parent_pending` не изменило поведение для «обычного» фримиум-ученика без активированных `selfSignup*`-полей — тот по-прежнему должен видеть обычный пейволл, а не модалку про родителя.
13. **Адаптив / мобильный.** Страница `/invite/<token>` и модалка гейта — на мобильной ширине форма и текст не должны обрезаться (обе страницы — самостоятельные лендинги без основного макета кабинета, `definePageMeta({ layout: false })`/`layout: 'parent'`).
14. **E2E-сценарий из репозитория.** `e2e/specs/product/student-to-parent-cj.spec.ts` — по признанию автора **не был прогнан локально**; при перепроверке стоит явно запустить его (в CI или на стенде с доступным вторым стеком) и не полагаться на то, что раз он написан — значит проходит.

## Аналитика/API

- Новых целей Метрики или новых событий аналитики задача не добавляет (по плану — «только новые параметры к существующим»); отдельно проверять появление новых аналитических событий не требуется.
- `POST /student/parent-invite` — выдать/переиспользовать ссылку (только для роли STUDENT); `POST /student/parent-invite/dismiss` — «я родитель», снимает отметки распознавания.
- `GET /parent-invite/:token` — публичная, без авторизации, отдаёт `{status, studentName, grade, topicTitle, solvedCount, strength}` (для `used`/`expired` — все поля `null`, только статус, чтобы не палить данные о ребёнке по протухшей/использованной ссылке).
- `POST /parent-invite/:token/register` — занять заглушку (тело: email, phone?, name?, consents, fingerprint?).
- `POST /parent-invite/:token/attach` — привязать к уже вошедшему родителю (требует роль PARENT).
- 403 `PARENT_CONSENT_REQUIRED` — единственный новый код ошибки на уровне гейта тренажёра, обрабатывается глобальным перехватчиком `use-api.ts`, не полагается на отдельную проверку в каждом месте, где вызывается тренажёр.

## Открытые вопросы

- **Пересечение с более ранней архитектурой родитель-ученик-класс.** В коде уже есть `parent-sidebar.vue`, страница `/parent`, семейные слоты (`subscriptionSlotRepository`, `familyService`) — судя по репозиторию, результат отдельной более ранней работы (ветка вида `feat/MIA-96-family-slots`). MIA-208 добавляет в существующий `parent-sidebar.vue` только одну ссылку («Посмотреть глазами ребёнка») и подключает `parent-onboarding.vue`/`parent-preview-bar.vue` как новые независимые компоненты поверх существующего кабинета — построчно не проверялось, не задевает ли это какие-то другие сценарии того же кабинета (например, переключение между несколькими детьми в `parent-sidebar.vue`, если у родителя их несколько и один из них — self-signup, а другой обычный). Стоит явно прогнать сценарий с двумя детьми одного родителя, один из которых пришёл через self-signup-приглашение, а другой — заведён обычным способом.

Стоит целенаправленно прогнать сценарий «у родителя подписка на 1 ребёнка, он уже занят, приходит второй по self-signup-ссылке».
