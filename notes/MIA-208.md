## Контекст

CJ «от ученика к родителю»: ребёнок регистрируется сам (без взрослого), доходит в тренажёре до конца ML2 первой темы — и вместо пейволла с ценой видит модалку со ссылкой для родителя. Цели тикета (`## Цели`/`## Скоуп` в тикете): распознать самостоятельную регистрацию по устройству и факту решения, закрыть тренажёр отдельным гейтом `parent_pending` (не фримиум-пейволл — ребёнку цену не показываем), выдать суточную одноразовую ссылку, довести родителя до кабинета и экрана оплаты, начислить ребёнку +50 баллов за подтверждение, показать новому родителю короткий онбординг и дать посмотреть кабинет «глазами ребёнка». Вне скоупа — отдельный лендинг/форма для детской регистрации и новые обращения к модели ради текста на странице родителя.

MR !481 — единственный и финальный, крупная фича (~45 изменённых файлов и 2 новых миграции). Проверка в этой заметке сделана по коду в `/tmp/wt-MIA-208`, detached HEAD на `0e56296a` — это верхний коммит смёрженной ветки, включающий не только фичевые коммиты, но и `fix: дефекты CJ от ученика к родителю по итогам ревью` (правки после собственного код-ревью автора, ещё до QA).

Хронология: 2026-09-23 Kirill Verzhitskii отметил MR смёрженным, дал инструкцию по ручной проверке (два устройства, e2e написан, но не прогнан локально). 2026-09-24 QA Andrei Chepurchenko прогнал фичу на `master` (commit `5020cfec`, то есть MIA-208 уже вместе с MIA-212 «мягкие просьбы», смёрженным поверх) и нашёл **три блокирующих, ещё не исправленных бага** — из-за них тикет и вернули в `Testing`. Большая часть остального поведения (распознавание, гейт, суточность и одноразовость ссылки, страница родителя, начисление +50, регресс фримиума) подтверждена и не вызывает вопросов — см. полный текст отчёта QA как источник для happy-path кейсов ниже. В этом коде (`0e56296a`) MIA-212 не смёржен, но базовая инфраструктура гейта (`parent_pending`, поля `selfSignup*`) уже заложена — с ней и работаем; тексты «мягких просьб» (`soft_ml1`/`soft_ml2`) относятся к параллельному тикету и здесь не разбираются.

## Реализация

### Распознавание ученической регистрации — `api/src/services/self-signup.service.ts`

Два сигнала, оба нужны:
1. **`markPendingIfSameDevice`** — ссылку ребёнка на `/register` открыли с того же устройства (по fingerprint), с которого только что была активная родительская сессия, и в окне `STUDENT_SELF_SIGNUP_WINDOW_MIN` (по умолчанию 30 минут, `windowMs()`). Ставит `selfSignupPendingAt`.
2. **`confirmOnSubmission`** — на любой отправке решения, если `selfSignupPendingAt` уже стоит, а `selfSignupConfirmedAt` ещё нет, проставляет `selfSignupConfirmedAt` (однократно, `updateMany` с условием в `where`).

`dismiss(studentId)` (вызывается кнопкой «Я родитель») снимает **оба** поля — `selfSignupPendingAt: null, selfSignupConfirmedAt: null`. Это важно для одного из наблюдений ниже: сама выданная ссылка (запись в `parent_invite`) при этом не гасится.

### Гейт `parent_pending` — `api/src/services/access.service.ts`, `api/src/middleware/require-topic-access.ts`

`needsParentConfirmation(user)` — `true`, когда `selfSignupConfirmedAt !== null`, `parentConfirmedAt === null`, есть `freeTopicId`, и по нему закрыт (в статусах `CLOSED_ML_STATUSES`, не только `passed` — засчитывается и `credited`, чтобы сильный ученик не проходил гейт мимо) второй ML-блок:

```ts
export const needsParentConfirmation = async (user) => {
  if (user.selfSignupConfirmedAt === null) return false;
  if (user.parentConfirmedAt !== null) return false;
  if (user.freeTopicId === null) return false;
  const closedMl2 = await prisma.topicMlProgress.findFirst({
    where: { userId: user.id, topicId: user.freeTopicId, mlLevel: 2, status: { in: CLOSED_ML_STATUSES } },
    select: { id: true },
  });
  return closedMl2 !== null;
};
```

`canAccessTrainer` проверяет это **раньше** подписки и возвращает `level: 'parent_pending'` без данных о цене. `requireTopicAccess` (преHandler на всех тренажёрных роутах — `/trainers/:id`, отправка решения, сессии, `/trainer/topics/:topicId/rating` и т.д.) на `level === 'parent_pending'` сразу отвечает `403 PARENT_CONSENT_REQUIRED`, до проверки конкретной темы:

```ts
const access = await accessService.canAccessTrainer(request.currentUser);
if (access.level === 'full') return;
if (access.level === 'parent_pending') {
  sendAndStop(reply, 403, PARENT_CONSENT_RESPONSE); // { code: 'PARENT_CONSENT_REQUIRED', message: '...' }
  return;
}
```
Диагностика (`diagnostic.controller.ts`) этот преHandler не использует вовсе — гейт закрывает только тренажёрные роуты, что соответствует спеке («тренажёр закрыт, кабинет/чат/рейтинг/диагностика — нет»).

**Гейт по HTTP полный, по сокету — нет.** `accessService.canAccessTopic` (её вызывает `topicAllowed`) не смотрит на `level === 'parent_pending'` вообще:
```ts
const topicAllowed = (access: AccessInfo, topicId: string): boolean =>
  access.level === 'full' || access.freeTopicId === null || access.freeTopicId === topicId;
```
Для бесплатной темы это `true` при любом уровне, кроме `full`, — сокет пускает `join`/`next-assignment`. Спасает то, что отдельная проверка `ensureFreemiumSubmissionAllowed` **явно** отбивает `parent_pending` на отправке решения:
```ts
if (access.level === 'full') return true;
if (access.level === 'parent_pending') return false; // ждём взрослого — решать нельзя даже в бесплатной теме
```
То есть данные не текут, но сам факт входа в канал бесплатной темы во время гейта (наблюдение QA: `freemium:paywall_trigger` уходит через шлюз) в коде подтверждается — `canAccessTopic`/`topicAllowed` о `parent_pending` не знает.

### Модалка гейта и её Pinia-стор — БАГ 1 (см. «Известные баги»)

Разобран ниже вместе с репродукцией, здесь только механика: `frontend/composables/use-api.ts`, перехватчик `onResponseError` глобального `$fetch`-инстанса, реагирует на `403 PARENT_CONSENT_REQUIRED` и **открывает** модалку из любого места приложения:
```ts
if (import.meta.client && response?.status === 403 &&
    (response._data as { code?: string } | undefined)?.code === 'PARENT_CONSENT_REQUIRED') {
  const { useParentInviteStore } = await import('~/stores/parent-invite');
  await useParentInviteStore().open();
  return;
}
```
`open()` (`frontend/stores/parent-invite.ts`) один раз запрашивает `POST /student/parent-invite` и выставляет `visible = true`; повторные вызовы (та же вкладка снова упёрлась в гейт) переиспользуют уже полученную ссылку. Закрывает модалку **только** `recheck()` (если подтверждение реально пришло) или `iAmParent()` — оба явно ставят `visible = false`. Метод `close()` в сторе есть, но его никто не вызывает.

### Ссылка приглашения — `api/src/services/parent-invite.service.ts`

`issueFor(studentId)` — сначала проверяет, что за учеником всё ещё стоит заглушка (`selfSignupConfirmedAt !== null && parentConfirmedAt === null`), иначе `not_a_placeholder`; переиспользует активную ссылку (`findActiveByStudent`), если она уже есть, иначе создаёт новую с TTL `PARENT_INVITE_TTL_HOURS` (по умолчанию 24 часа). `publicView(token)` не палит факты о погашенной/просроченной ссылке — просто возвращает `blank('used')`/`blank('expired')` без имени и темы. Текст, который видит родитель, собирается на фронте в `frontend/utils/parent-invite-copy.ts` из полей ответа и **не** обращается к модели повторно (соответствует Out of scope). Заметный момент: текст всегда мужского рода —
```ts
sentences[0] += ` и уже решил ${tasks} по теме «${view.topicTitle}», он большой молодец!`;
...
sentences.push(`Я заметила, что у него ${view.strength}.`);
```
— поле пола ребёнка в `ParentInviteView` не приходит и не учитывается, форма фиксированная («начал», «решил», «него», «ему»).

### Регистрация родителя по ссылке и email-проверка — БАГ 2 (см. «Известные баги»)

Две ветки в `parent-invite.service.ts`: `takeoverPlaceholder` (новый email → родитель занимает заглушку) и `attachToExistingParent` (родитель уже вошёл в свой кабинет → ребёнок переезжает к нему, заглушка гасится вместе со своей пустой подпиской). Механика бага — ниже, в «Известных багах», разобрана построчно.

Регистрация родителя по ссылке — **отдельная ручка** `POST /parent-invite/:token/register`, а не `POST /auth/register`: так задокументировано в `docs/superpowers/specs/2026-09-23-student-to-parent-cj-design.md` («Что разошлось с дизайном при реализации») — обычная схема регистрации требует `student.grade`, а ребёнок уже есть, заводить его заново не нужно. Там же зафиксировано осознанное решение сделать «Войти» не мгновенным входом, а письмом со ссылкой: `loginRequest` принимает `parentInviteToken` и дописывает `&invite=<token>` в письмо, а `frontend/pages/parent/enter.vue` после успешного входа по этой ссылке сам вызывает `attachInvitedChild()` (`POST /parent-invite/:token/attach`).

### Подтверждение → тренажёр и +50

`ratingAwardService.awardParentConfirmed(studentId)` начисляет `EFFORT_POINTS.parentConfirmed` — в `api/src/services/rating-rules.ts` это `parentConfirmed: 50`; вызывается из обеих веток (`takeoverPlaceholder` и `attachToExistingParent`), ключуется на `userId` ученика, так что повторный родитель (второй заход) не оплатит очки дважды. На стороне ребёнка кнопка «Родитель подтвердил» (`store.recheck()`) перезапрашивает `/me` и закрывает модалку, если `access.level` уже не `parent_pending` — без этого, как явно написано в комментарии кода и в спек-доке, вкладка ученика о подтверждении с другого устройства не узнала бы вовсе.

### «Посмотреть, как выглядит Мия глазами ребёнка» — БАГ 3 (см. «Известные баги»)

Сервер: `api/src/middleware/allow-parent-preview.ts` — под родительской сессией и параметром `?preview=<childId>` подменяет `request.currentUser` на ребёнка **только для GET** и только если `child.parentId === user.id`, иначе `403 PREVIEW_READ_ONLY`:
```ts
if (request.method !== 'GET') { sendAndStop(reply, 403, PREVIEW_FORBIDDEN); return; }
const child = await prisma.user.findUnique({ where: { id: childId } });
if (!child || child.role !== Role.STUDENT || child.parentId !== user.id) {
  sendAndStop(reply, 403, PREVIEW_FORBIDDEN); return;
}
request.currentUser = buildCurrentUser(child, user.sessionId);
```
Это чисто серверная подмена по запросу; за перенос параметра в адрес и обновление интерфейса отвечает фронт — там и лежит баг. Разбор — в «Известных багах».

### Онбординг кабинета родителя

`frontend/components/parent/parent-onboarding.vue` — 3 слайда, полноэкранный оверлей (`position: fixed; inset: 0; z-index: 40`), кнопки «Дальше»/«Понятно»/«Пропустить» (обе финальные ведут в `finish()`). Показывается, если `state === 'ready'` и `!onboardingDone` (`frontend/pages/parent/index.vue`), где `onboardingDone` читается из `user.onboarding?.parentCabinetDoneAt`. Миграция `20260923140000_parent_cabinet_onboarding_backfill` проставляет эту метку **всем существующим на момент релиза** родителям (`WHERE role = 'PARENT' AND onboarding->>'parentCabinetDoneAt' IS NULL`), поэтому «нынешние» (проверено в первом прогоне) экрана не видят. Но это флаг не специфичный для CJ — он показывается **любому** новому родителю, зарегистрировавшемуся после релиза, независимо от пути (обычная регистрация, take­over по ссылке ребёнка, attach к существующему аккаунту) — так и задумано по споку («иначе платящего родителя онбординг сносил бы на пейволл» — про обратный случай), но стоит подтвердить у продукта, что это осознанно шире CJ. Также имя ребёнка на первом слайде берётся не из только что привязанного/зарегистрированного ребёнка, а из первого в списке:
```ts
<ParentOnboarding v-if="showOnboarding" :student-name="children[0]?.name ?? null" @finished="onOnboardingFinished" />
```
— для CJ, где ребёнок обычно единственный, разницы не видно, но у attach-родителя с несколькими детьми слайд назовёт не того, кого только что привязали.

## Известные, ещё не исправленные баги

Три блокера из отчёта QA (2026-09-24, стенд `master@5020cfec` = MIA-208 + MIA-212). Ниже — точная механика по коду в `0e56296a` и шаги для быстрой проверки на ретесте.

### Баг 1. Модалка гейта — софтлок, из неё нельзя выйти без «лжи» или перезагрузки

**Где:** `frontend/components/parent-invite-gate-modal.vue`, `frontend/stores/parent-invite.ts`.

**Механика:** `store.visible` — состояние Pinia, живёт до явного `false`. В разметке модалки (`v-if="store.visible"`) нет ни крестика закрытия, ни обработчика `Escape`, ни клика по фону — единственные два способа снять `visible`: `store.recheck()` (кнопка «Родитель подтвердил», не помогает, если подтверждения ещё нет) и `store.iAmParent()` (кнопка «Я родитель» — по сути ложь системе). Модалка триггерится глобальным перехватчиком `onResponseError` в `use-api.ts` на **любой** запрос, вернувший `403 PARENT_CONSENT_REQUIRED` — то есть она не привязана к странице тренажёра и переживает переход на `/app/map`, `/app/diagnostic`, чат, `/app/dash` (сам API по этим разделам по-прежнему отвечает `200` — сервер не софтлокает, софтлок чисто в сторе).

**Как проверить:** довести ученика-заглушку до гейта (см. кейс 1 ниже) → модалка открылась → перейти в кабинете на карту тем/диагностику/чат Мии/дашборд, не нажимая ни одну из двух кнопок в модалке → **ожидается по спеке**, что модалка не должна перекрывать эти разделы либо в ней должна быть кнопка «Вернуться в кабинет»; **баг**, если модалка остаётся поверх экрана и единственный выход — `F5` или «Я родитель».

**Куда смотреть при фиксе:** `store.close()` уже существует, но ничего его не вызывает — либо звать его при уходе с тренажёра/смене роута, либо добавить в саму модалку явную кнопку закрытия, которая не эмулирует «Я родитель».

### Баг 2. Email при регистрации родителя по ссылке сравнивается с учётом регистра — дубли аккаунтов

**Где:** `api/src/services/parent-invite.service.ts` (`takeoverPlaceholder`), `api/src/services/auth.service.ts` (обычная регистрация), `api/src/repositories/user.repository.ts` (`findByEmail`/`findParentByEmail`).

**Механика:** обычная регистрация (`auth.service.ts:85,108`) сохраняет email **как введён**, без нормализации регистра: `userRepository.findByEmail(input.parent.email)` на проверке дублей и `email: input.parent.email` на записи. `findByEmail`/`findParentByEmail` (`user.repository.ts:23-33`) — простое `prisma.user.findFirst({ where: { email } })`, сравнение регистрозависимое (PostgreSQL `text` по умолчанию). А вот `takeoverPlaceholder` нормализует **только входной** email к нижнему регистру перед проверкой занятости:
```ts
const email = input.email.trim().toLowerCase();
...
const taken = await prisma.user.findFirst({ where: { email }, select: { id: true } });
if (taken) throw new ParentInviteError('email_registered');
```
Если существующий родитель зарегистрирован с email, где есть заглавные буквы (обычная регистрация их сохраняет как есть), то `taken`-проверка сравнивает **лowercase-версию** ввода со **строкой из БД в исходном регистре** — совпадение не находится, даже если по чужой ссылке ввести email символ-в-символ так же, как он хранится (с теми же заглавными буквами). Итог — второй, дублирующий аккаунт родителя с email, отличающимся только регистром, вместо ожидаемого `409 email_registered`. Если у существующего родителя email хранится целиком в нижнем регистре (типичный случай при аккуратном вводе с клавиатуры на телефоне) — проверка срабатывает, баг именно в сочетании «email с заглавными буквами у существующего родителя» + «повторная регистрация по чужой ссылке».

**Как проверить:** зарегистрировать родителя обычным путём (`/register`) с email, содержащим заглавную букву не в начале (например, `parent-Test-1@example.com`); получить чужую (любую активную) ссылку `/invite/<token>`; ввести на форме **тот же** email (тем же регистром) → ожидается `409 email_registered` и переход на `/parent/enter?invite=...` с формой запроса письма для входа; баг — если приходит `200 { nextStep: 'onboarding' }` и создаётся второй аккаунт.

**Куда смотреть при фиксе:** нормализовать email при сохранении в `auth.service.ts` (регистрация, `input.parent.email`) и сравнивать без учёта регистра в `findByEmail`/`findParentByEmail`, либо приводить обе стороны сравнения к одному регистру непосредственно в `takeoverPlaceholder`.

### Баг 3. Кнопка «глазами ребёнка» в сайдбаре без перезагрузки показывает данные родителя, а не ребёнка

**Где:** `frontend/components/parent/parent-sidebar.vue` (кнопка), `frontend/middleware/auth.global.ts`, `frontend/composables/use-parent-preview.ts`, `frontend/components/parent/parent-preview-bar.vue`, `frontend/layouts/cabinet.vue`.

**Механика:** ссылка в сайдбаре — обычный `NuxtLink`, клиентская SPA-навигация:
```ts
const previewHref = computed(() => (props.childId ? `${ROUTES.dashboard}?preview=${props.childId}` : null));
```
```html
<NuxtLink v-if="previewHref" :to="previewHref">Посмотреть, как выглядит Мия глазами ребёнка</NuxtLink>
```
При клиентской навигации `auth.global.ts` срабатывает, но выходит рано:
```ts
if (userStore.user) {
  if (to.query.login === 'open') { ... }
  if (userStore.user.role === 'PARENT') {
    const isExempt = isParentExemptPath(path, to.query); // true из-за query.preview
    if (!isExempt) { ... }
  }
  ...
  return; // <-- userStore.loadMe() здесь не вызывается
}
```
Раз `userStore.user` уже заполнен (родитель залогинен), middleware только проверяет, что путь «исключён» (что верно — `isParentExemptPath` возвращает `true` при наличии `query.preview`), и возвращается — **`userStore.loadMe()` с новым `?preview=` не перезапрашивается**. `ParentPreviewBar` в `cabinet.vue` берёт имя из того же стора: `:student-name="userStore.getUser?.name ?? null"` — а там всё ещё имя родителя. При этом `use-api.ts` подставляет `?preview=` во **все** остальные API-запросы (читает его напрямую из `window.location.search`, не из стора), так что часть данных (например, курс/тема) может частично соответствовать ребёнку, а часть UI (полоса «Вы смотрите глазами …», данные `/me`) — ещё нет, из-за чего экран показывает несогласованную, «родительскую» картину (у QA — «Курс ещё не открыт»). После **перезагрузки** того же адреса `auth.global.ts` идёт по ветке `userStore.loadMe()` (`userStore.user` в свежем сторе пуст), `/me` уходит уже с `?preview=`, и всё показывается верно.

**Как проверить:** зайти в кабинет родителя с открытым курсом у ребёнка → в сайдбаре нажать «Посмотреть, как выглядит Мия глазами ребёнка», **не перезагружая страницу** → ожидается сразу полоса «Вы смотрите глазами <имя ребёнка>» и открытая тема ребёнка; баг — если видно родительские данные/«Курс ещё не открыт». Затем вручную перезагрузить тот же URL → должно стать корректно (это уже работает и является подсказкой, что дело именно в отсутствии `loadMe()` на клиентской навигации, а не в сервере).

**Куда смотреть при фиксе:** вызывать `userStore.loadMe()` явно при входе в `?preview=` (например, watcher на `route.query.preview` в `cabinet.vue`/`use-parent-preview.ts`), либо сделать переход из сайдбара жёсткой навигацией (`<a href>`/`window.location.assign`) вместо `NuxtLink`.

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Happy path: ребёнок сам регистрируется → гейт после ML2 → приглашение → подтверждение родителя

Нужны два устройства/окна (второе — приватное окно браузера или другой браузер, чтобы не делить cookies).

1. На первом устройстве открыть `/register`, зарегистрироваться как ученик, сразу открыть ученическую ссылку из модалки регистрации (это и есть «ребёнок завёл аккаунт сам» — совпадение fingerprint + окно `STUDENT_SELF_SIGNUP_WINDOW_MIN`, по умолчанию 30 минут).
2. Решать в тренажёре, пока не закроется второй ML-блок (ML2) первой (бесплатной) темы.
3. Ожидается: вместо экрана оплаты — модалка «…дальше тебя ждут задания поинтереснее…» со ссылкой, текстом «Ссылка действует сутки», блоком «+50 баллов», кнопками «Родитель подтвердил» и «Я родитель». Цены/тарифа в модалке нет.
4. Скопировать ссылку (кнопка «Скопировать» на форме, либо взять из поля), открыть её на втором устройстве.
5. Ожидается страница `/invite/<token>`: имя ребёнка, класс, тема, число решённых задач в связном тексте от лица Мии; если у ребёнка есть отмеченная сильная сторона (`studentMemory`, `kind: pedagogy`, `valence: strength`) — отдельное предложение про неё; если нет — абзаца нет (не выдумывается).
6. Заполнить форму своим email (не тем, что у ребёнка) и телефоном (необязательно), отметить оба чекбокса согласий, «Создать кабинет».
7. Ожидается: переход в `/parent`, 3 слайда знакомства с кабинетом («Мия уже занимается с …», «Отчёты приходят на почту», «Можно посмотреть глазами ребёнка»), после «Понятно»/«Пропустить» — `/select-tariff?from=register`.
8. Вернуться на первое устройство (в кабинете ученика модалка гейта должна всё ещё быть открыта — либо перейти в тренажёр заново, если ушли из него, с поправкой на баг 1), нажать «Родитель подтвердил».
9. Ожидается: модалка закрывается без перезагрузки, тренажёр открыт (обычные запросы тренажёра больше не отдают `403 PARENT_CONSENT_REQUIRED`), в рейтинге ученика +50 баллов.
10. Повторно зайти в кабинет родителя (без перезагрузки страницы после первого входа) — экран знакомства второй раз не показывается.

### 2. Известные баги — быстрая проверка на ретесте (см. «Известные, ещё не исправленные баги» выше за подробной механикой)

11. **Баг 1 (софтлок модалки).** Дойти до модалки гейта (шаги 1-3 кейса 1). Не нажимая кнопки модалки, перейти в кабинете на карту тем (`/app/map`), в диагностику (`/app/diagnostic`), в чат Мии, на дашборд (`/app/dash`). Ожидается способ вернуться в кабинет из самой модалки без `F5` и без «Я родитель» — если такого способа по-прежнему нет и модалка перекрывает эти разделы, баг не исправлен.
12. **Баг 2 (email без учёта регистра).** Зарегистрировать родителя обычным путём с email вида `parent-Test-N@example.com` (заглавная буква не в начале). Получить любую чужую активную ссылку `/invite/<token>` (можно — другого тестового ребёнка), ввести на форме тот же email тем же регистром. Ожидается `409 email_registered` → переход на `/parent/enter` с формой запроса письма для входа; баг — если форма отправляется успешно (`200`, переход в `/parent`) и создаётся второй аккаунт с почти тем же email.
13. **Баг 3 (глазами ребёнка без перезагрузки).** В кабинете родителя (с уже открытым курсом у ребёнка) нажать в сайдбаре «Посмотреть, как выглядит Мия глазами ребёнка», не перезагружая страницу. Ожидается сразу полоса «Вы смотрите глазами <имя>» и данные ребёнка; баг — если видно данные/состояние родителя (например, «Курс ещё не открыт») до ручной перезагрузки того же адреса.

### 3. Родитель с уже существующим аккаунтом — «У меня уже есть аккаунт»

14. Открыть `/invite/<token>` от имени родителя, у которого уже есть кабинет (другой ребёнок или ранее зарегистрированный аккаунт). Нажать «У меня уже есть аккаунт» (без попытки регистрации).
15. Ожидается переход на `/parent/enter?invite=<token>` с текстом «Введите email вашего кабинета — пришлём ссылку для входа, и ребёнок появится в нём», отправка формы → «Если такой email зарегистрирован — мы отправили на него ссылку для входа… проверьте почту».
16. Перейти по ссылке из письма → `parentLogin` открывает сессию, `attachInvitedChild()` вызывает `POST /parent-invite/:token/attach`, кабинет открывается на `/parent` (с учётом `?child=` из письма, если было). Ребёнок появляется в списке детей этого родителя, старая заглушка (её `parentId`) получает `deletedAt`, её пустая подписка переводится в `CANCELLED`, а место — освобождается (`subscriptionSlot.releasedAt`). Рейтинг ребёнка +50.
17. Негативы: `POST /parent-invite/:token/attach` без авторизации → `401`; от ученика (роль `STUDENT`) → `403`.

### 4. Ветка «занять заглушку своим email» — негативы

18. Email ребёнка (в любом регистре) в форме `/invite/<token>` → `email_is_child_email`, текст «Укажите свой email — этот уже принадлежит ребёнку».
19. Не отмечена оферта/согласие на ПДн → `400` (форма не даёт отправить — кнопка недоступна без обеих галочек, `isFormValid`).
20. Успешная регистрация новым email → `nextStep: 'onboarding'`, сессия открыта cookie, переход `/parent`.

### 5. Одноразовость и срок жизни ссылки

21. Повторно открыть уже использованную (после кейса 1 или 3) ссылку `/invite/<token>` → `GET /parent-invite/:token` отдаёт `{ status: 'used' }`, страница показывает «Ребёнок уже привязан» и кнопку «Войти» (без имени/темы/прогресса — эти поля обнулены на сервере для погашенной ссылки).
22. Повторная попытка `register`/`attach` по тому же токену → `409 invite_used`.
23. Ссылка старше суток (`expiresAt` в прошлом) → `GET` отдаёт `{ status: 'expired' }`, страница — «Ссылка устарела», «Она действует сутки. Попросите ребёнка прислать новую» (данных ребёнка тоже не отдаётся). *Не покрыто QA в прошлом прогоне — нужна ручная правка `expires_at` в БД или ожидание суток; стоит явно проверить в этом прогоне.*
24. Мусорный/несуществующий токен → `404` на `GET /parent-invite/:token`, страница инвайта кидает `createError({ statusCode: 404, fatal: true })`.

### 6. «Я родитель» — ложное срабатывание распознавания

25. В модалке гейта нажать «Я родитель» → `POST /student/parent-invite/dismiss` снимает `selfSignupPendingAt`/`selfSignupConfirmedAt`, модалка закрывается, тренажёр открыт без подтверждения взрослого и без +50 (ожидаемо — это же не признание себя ребёнком).
26. Дойти до гейта снова (например, закрыть ML2 другой темы, если это возможно, либо повторно инициировать сценарий на новом аккаунте) → новая попытка получить ссылку (`POST /student/parent-invite`) должна дать `409` (по коду `issueFor` — `selfSignupConfirmedAt === null` после `dismiss`, значит `not_a_placeholder`), если признаки ученической регистрации не появились заново.
27. **Отдельно проверить (наблюдение QA, не блокер):** ссылка, выданная **до** нажатия «Я родитель», остаётся физически рабочей (запись `parent_invite` не гасится в `dismiss`) — открыть её на втором устройстве, она всё ещё показывает имя/успехи ребёнка; попытка зарегистрироваться по ней → `409 not_a_placeholder`, но на UI (`invite/[token].vue`, ветка `else`) для этого кода нет отдельной обработки — падает в общий `catch`, текст «Не получилось. Попробуйте ещё раз» без объяснения причины. Для взрослого, дошедшего до этой точки, это тупик — стоит завести как отдельный (не блокирующий) баг, если ещё не заведён.

### 7. Регресс обычного фримиума и гейта до решения

28. Обычная (не self-signup) регистрация — на другом устройстве/без совпадения fingerprint. Попытка открыть чужую (не бесплатную) тему до и после решения задач → `403 PAYWALL`, не `PARENT_CONSENT_REQUIRED` — гейт не должен путаться с обычным пейволлом.
29. Тот же аккаунт с признаками self-signup, но **до** первого отправленного решения (`selfSignupConfirmedAt` ещё `null`): `POST /student/parent-invite` → `409 not_a_placeholder` (ссылку рано выдавать — второй сигнал ещё не пришёл).

### 8. Прочие разделы кабинета во время гейта (серверная часть, без учёта бага 1)

30. Пока стоит `parent_pending`, напрямую (без модалки, отдельными запросами/через другую вкладку) проверить: `GET /me`, `GET /rating/dashboard`, `GET /diagnostic/:id`, `GET /me/memory`, `GET /homework/open`, `GET /challenge/today`, `GET /topic/:id` — все должны отдавать `200`; `GET /trainers/:id` и `GET /trainer/topics/:id/rating` — `403 PARENT_CONSENT_REQUIRED`. Диагностика по сокету должна открываться и работать.
31. По сокету бесплатной темы: `join`/`next-assignment` во время `parent_pending` проходят (это не баг форм ULI — гейт на HTTP полный, но стоит зафиксировать поведение отдельно, раз оно расходится с «сокет ничего не знает о parent_pending»), а вот отправка решения — отбивается (`freemium:paywall_trigger`/PAYWALL через шлюз). Проверить, что в UI это не протекает (по отчёту QA — не протекало, модалка гейта уже закрывает экран раньше).

### 9. Адаптив страницы родителя

32. `/invite/<token>` на ширине 390px — без горизонтальной прокрутки, форма и текст читаемы.

## Аналитика/API

- **Выделенных analytics-событий на саму воронку CJ не заведено** (проверено по `frontend/constants/analytics-events.ts` — совпадений по `PARENT_INVITE`/`SELF_SIGNUP` нет; в коде инвайт-модалки, страницы `/invite/[token]`, стора `parent-invite.ts`, `self-signup.service.ts`, `parent-invite.controller.ts` вызовов `analytics.track`/`trackServerEvent` нет). Единственное исключение — ветка «У меня уже есть аккаунт»: там переиспользованы существующие `PARENT_CABINET_LOGIN_REQUEST_SUBMIT` (`{ result: 'success'|'fail', reason? }`) и `PARENT_CABINET_LOGIN_LINK_FAIL` из `parent/enter.vue`, которые были заведены не под этот тикет. Стоит уточнить у продукта/аналитиков, ожидались ли отдельные метки на «ссылка выдана / открыта / гейт показан / родитель зарегистрировался / подтвердил» — с целями тикета («довести родителя до кабинета и экрана оплаты») без них сложно посчитать конверсию воронки.
- Основные эндпоинты и коды:
  - `POST /student/parent-invite` → `200 { url, expiresAt }` / `409 { code: 'not_a_placeholder' }`.
  - `POST /student/parent-invite/dismiss` → `200 { ok: true }`.
  - `GET /parent-invite/:token` → `200 ParentInviteView` (`status: 'pending'|'used'|'expired'`, `studentName`, `grade`, `topicTitle`, `solvedCount`, `strength`) / `404 { code: 'not_found' }`.
  - `POST /parent-invite/:token/register` → `200 { nextStep: 'onboarding', sessionId? }` / `409 { code }` где `code` ∈ `invite_not_found | invite_used | invite_expired | email_is_child_email | email_registered | not_a_placeholder`.
  - `POST /parent-invite/:token/attach` (только авторизованный `PARENT`) → `200 { studentId }` / `401` без сессии / `403` не-родителю / `409 { code }` (та же линейка кодов).
  - Гейт: `403 { code: 'PARENT_CONSENT_REQUIRED', message: 'Parent confirmation required' }` — отдельный код от `403 { code: 'PAYWALL' }`, специально разведены (`errors.helper.ts`), чтобы фронт не путал гейт и обычный пейволл.
  - Preview: `403 { code: 'PREVIEW_READ_ONLY' }` на неразрешённый метод/чужого ребёнка.
- Начисление рейтинга: `rating-rules.ts` → `parentConfirmed: 50`; `ratingAwardRepository.award({ kind: 'effort', reason: 'parent_confirmed', sourceId: studentId })` — `sourceId` = id ученика, так что повторное подтверждение (второй родитель, повторный вызов) не задвоит очки.
- Переменные окружения (`.env.example`): `PARENT_INVITE_TTL_HOURS` (по умолчанию 24 — TTL ссылки) и `STUDENT_SELF_SIGNUP_WINDOW_MIN` (по умолчанию 30 — окно совпадения fingerprint для первого сигнала self-signup). Полезно для теста кейса «просроченная ссылка» — можно временно уменьшить TTL на тестовом стенде вместо правки БД.

## Открытые вопросы

- **Три блокирующих бага (софтлок модалки, регистрозависимый email, «глазами ребёнка» без перезагрузки)** — см. «Известные, ещё не исправленные баги». Именно они вернули тикет в `Testing`; на момент этой заметки фиксов под них в коде нет. Приоритет ретеста — кейс 2 (пункты 11-13) выше.
- **Аналитика воронки не заведена вовсе** (см. «Аналитика/API») — при целях тикета «довести родителя до кабинета и экрана оплаты» отсутствие событий на промежуточных шагах (ссылка выдана/открыта/родитель зарегистрировался) не даст посчитать, где родители отваливаются. Стоит уточнить у автора/продукта, ожидалась ли эта аналитика в скоупе MIA-208 или заведена отдельным тикетом.
- **Стор `parent-invite.ts` знает о собственном методе `close()`, но он мёртвый код** — потенциально самый дешёвый первый шаг к фиксу бага 1, если решение будет «звать close() при уходе с тренажёра», а не «добавить кнопку в модалку».
- **Гендерно нейтральный текст на странице родителя не поддержан** (`parent-invite-copy.ts`, всегда «он»/«ему»/«начал»/«решил») — не в acceptance тикета буквально, но если у продукта есть ожидание про девочек-учениц, стоит завести отдельным пунктом.
- **Стейл-ссылка после «Я родитель» ведёт в тупик без объяснения** (кейс 6, п. 27) — `not_a_placeholder` на форме регистрации родителя не имеет отдельного текста, падает в общий catch. Не блокер, но полезно зафиксировать как отдельную находку, если ещё не заведена.
- **Онбординг кабинета показывается всем новым родителям, а не только CJ-веткам** (backfill покрывает только тех, кто существовал до релиза) — по споку это осознанное решение («иначе платящего родителя онбординг сносил бы на пейволл» — про обратный случай непокрытия), но стоит явно свериться с продуктом, что это ожидаемо и для обычной регистрации/attach, а не только для take­over по детской ссылке; также имя на первом слайде — `children[0]`, а не только что привязанный ребёнок (см. «Реализация» → «Онбординг кабинета родителя»).
- **E2E `e2e/specs/product/student-to-parent-cj.spec.ts` не прогонялся на актуальном стенде «из коробки»** — по отчёту QA падал из-за устаревших фикстур (форма `/register` требует поле «Телефон родителя», которое `fillRegisterForm` не заполняет; тур доски `board-coach` перекрывает кнопку отправки). После этих двух правок в локальной копии QA — зелёный (13с). Это инфраструктурная проблема теста, а не фичи, но стоит поправить сами фикстуры в репозитории, иначе CI не будет ловить регрессии по этому сценарию до следующего ручного прогона.
- **Не покрыто QA в прошлом прогоне** (стоит явно закрыть в этом): протухшая ссылка (>24ч — см. кейс 5, п. 23; можно ускорить через `PARENT_INVITE_TTL_HOURS` на тестовом стенде), окно распознавания 30 минут (закрыто юнит-тестом, е2е/ручной проверки нет), attach к родителю с полностью занятыми местами семейной подписки (за рамками acceptance тикета, но может быть интересно как крайний случай).
