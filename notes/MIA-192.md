## Контекст

Задача сформулирована как «алерты из Sentry в отдельный чат Telegram», но в проекте Sentry SaaS не используется вовсе — это подтверждено и кодом, и `CLAUDE.md` (раздел «Трекинг ошибок - GlitchTip, свой, в РФ-контуре»): вместо него давно поднят self-hosted GlitchTip (`errors.mia360.ru`), сознательно, чтобы не гонять персональные данные несовершеннолетних (`user.id`, IP) за границу через Sentry SaaS. Формулировка задачи, судя по всему, унаследована от привычного названия класса инструментов («шлём в Sentry» = «шлём в трекер ошибок»); реализация во всех трёх MR прямо и последовательно называет GlitchTip, никакого параллельного Sentry-контура в коде нет.

До этой задачи ошибки GlitchTip и инфраструктурные алерты Grafana шли в один общий Telegram-чат через один и тот же relay (`monitoring/alert-telegram-relay/relay.py`), который изначально был написан только под формат Grafana-вебхука. Скоуп задачи выполнен тремя последовательными MR одного автора (Kirill Verzhitskii) в течение одного дня (23.09.2026):

- **!487** `feat(monitoring): свой чат под ошибки GlitchTip + починка вебхука алертов` — основная реализация: разделение чатов + попутный фикс сломанной с 20.09 доставки.
- **!488** `fix(ci): monitoring-setup пишет в .env токен и чаты Telegram` — CI-джоб перестаёт терять секреты при каждом прогоне.
- **!489** `docs: разбор алертов GlitchTip` — раннер, задокументировавший три найденные грабли в `CLAUDE.md`.

По дороге к основному скоупу нашлись и попутно почищены три реальные поломки продакшена (см. «Реализация» и отчёт разработчика в Linear-комментарии от 23.09.2026 07:10):
1. Алерты вообще не приходили с 20.09.2026 (nginx кешировал старый docker-адрес relay).
2. Джоб `monitoring-setup` ронял relay при каждом прогоне (`.env` затирался целиком, секретные токен/чаты хранились только руками на сервере).
3. У проекта `mia360-test` не было ни одного правила алертов вообще.

## Реализация

Код прочитан целиком на HEAD master (коммит `45e14901`, объединяет все три MR — они последовательные потомки друг друга).

### Разделение чатов на уровне relay

`monitoring/alert-telegram-relay/relay.py`:
```python
BOT_TOKEN = os.environ["TELEGRAM_BOT_TOKEN"]
CHAT_ID = os.environ["TELEGRAM_ALERT_CHAT_ID"]
# Свой чат под ошибки приложения. Не задан - всё идёт в общий, как было.
GLITCHTIP_CHAT_ID = os.environ.get("TELEGRAM_GLITCHTIP_CHAT_ID") or CHAT_ID
...
def is_glitchtip(payload) -> bool:
    """GlitchTip posts a Slack-shaped body; Grafana always carries "alerts"."""
    return isinstance(payload, dict) and "attachments" in payload and "alerts" not in payload

def chat_for(from_glitchtip: bool) -> str:
    return GLITCHTIP_CHAT_ID if from_glitchtip else CHAT_ID
```
Различение форматов чисто структурное (GlitchTip шлёт Slack-совместимый payload с `attachments`, Grafana — всегда `alerts`), без явного заголовка/типа. Если `TELEGRAM_GLITCHTIP_CHAT_ID` не задан — поведение полностью прежнее (всё в один чат), это явный откат по умолчанию.

Формат GlitchTip-сообщения (`format_glitchtip`) собирает: заголовок пачки (`payload.text`, вида «GlitchTip Alert (N issues)» — это и есть единственный носитель счётчика повторов/масштаба пачки, отдельного числа повторов на issue нет), эмодзи-жук + ссылку на issue (title/title_link), culprit (`attachment.text`), и строку `Project: … · Environment: … · Release: …` собранную из `attachment.fields` (`GLITCHTIP_FIELDS = ("Project", "Environment", "Release")` — фиксированный порядок, т.к. в payload поля идут в порядке найденных тегов issue). Есть защита от XSS/небезопасных ссылок: `safe_url()` пропускает только `http(s)://`-ссылки (тест `test_ignores_javascript_links`), и HTML экранируется (`html.escape`).

Реальные проектные окружения различимы полем `Project` (`mia360-prod` vs `mia360-test`) — это прямое покрытие acceptance-критерия «тестовый и продовый проекты различимы в сообщении».

### Три попутные починки

1. **502 из-за кеша DNS в nginx** (`monitoring/nginx/nginx.conf.template`, location `/__ALERT_HOOK_PATH__/`): раньше имя контейнера-relay резолвилось при загрузке конфига и кешировалось навсегда — пересозданный контейнер получал новый docker-адрес, nginx продолжал стучаться в старый. Комментарий в файле прямо документирует инцидент: «That is how GlitchTip alerts sat on 502 from 20.09.2026 without anyone noticing». Фикс:
   ```nginx
   location /__ALERT_HOOK_PATH__/ {
       resolver 127.0.0.11 valid=10s ipv6=off;
       set $alert_relay alert-telegram-relay;
       proxy_pass http://$alert_relay:9099/;
       ...
   }
   ```
   Резолв на каждый запрос вместо резолва один раз при старте.

2. **`monitoring-setup` (`gitlab/monitoring-setup.yml`) теперь пишет секреты из CI-переменных, а не полагается на ручную правку `.env` на сервере**: джоб полностью перезаписывает серверный `.env` при каждом прогоне (`scp monitoring.env ${TARGET_HOST}:~/ai-math/.env`), поэтому любое значение, оставленное руками, терялось при следующем деплое. Прекчек до выката:
   ```bash
   for v in TELEGRAM_BOT_TOKEN TELEGRAM_ALERT_CHAT_ID; do eval "val=\$$v"; if [ -z "$val" ]; then echo "$v is empty" >&2; exit 1; fi; done
   ```
   `TELEGRAM_GLITCHTIP_CHAT_ID` и `PROXY_KEY` тоже пишутся из CI-переменных, но без прекчека на пустоту (обоснованно — пустой `GLITCHTIP_CHAT_ID` это штатный fallback на общий чат).

3. **Правило алертов для `mia360-test`** — заведено в БД GlitchTip («Новая ошибка (тест)»: 1 событие / 1 минута, как на проде). Это состояние GlitchTip, не файл в гите — подтвердить можно только через UI/API GlitchTip, кодом не проверяется.

### docker-compose / переменные окружения

`docker-compose.monitoring.yml`, сервис `alert-telegram-relay`:
```yaml
environment:
  TELEGRAM_API_BASES: "http://${PROXY_1_HOST}:8080/tg,http://${PROXY_2_HOST}:8080/tg"
  TELEGRAM_GLITCHTIP_CHAT_ID: "${TELEGRAM_GLITCHTIP_CHAT_ID:-}"
```

### Тесты

`monitoring/alert-telegram-relay/test_relay.py` — 9 тестов: детекция GlitchTip vs Grafana payload по структуре, форматирование сообщения (заголовок, ссылка, culprit), защита от `javascript:`-ссылок, экранирование HTML в заголовке, наличие Project/Environment/Release в сообщении, поведение без полей, и два теста именно на разделение чатов (`test_glitchtip_goes_to_its_own_chat`, `test_falls_back_to_the_shared_chat`). Юнит-тесты покрывают только форматирование/маршрутизацию Python-скрипта — они не гоняются против реального GlitchTip/Telegram, поэтому сквозная доставка проверяется исключительно вручную (см. ниже).

## Тест-кейсы

Это по большей части инфраструктурная задача без пользовательского UI — тестировать нужно сквозняком через реальный webhook/Telegram, а не через код.

1. **[P0] Новая ошибка на проде уходит в свой чат.** Вызвать/дождаться реальной новой ошибки в `mia360-prod` (или переотправить существующее уведомление, способ описан в `CLAUDE.md` — see «Открытые вопросы» про доступ) → сообщение должно прийти в чат «Mia 360 Errors», не в «Mia 360 Tech». Проверить поля: заголовок ошибки кликабельной ссылкой на issue, под ним culprit, следующей строкой — `Project: mia360-prod`, `Environment: …`, `Release: …`.
2. **[P0] Тест и прод различимы.** То же самое для `mia360-test` (или искусственный POST на вебхук с телом `mia360-test`) → в сообщении `Project: mia360-test`, чат тот же («Mia 360 Errors») — разделение по чатам идёт только «ошибка vs алерт», не «прод vs тест».
3. **Алерты Grafana остаются в старом чате.** Инфраструктурный алерт (например, дождаться срабатывания `binding-failure-ratio` из MIA-191, если доступен на стенде) должен по-прежнему прийти в «Mia 360 Tech», не в «Mia 360 Errors».
4. **Не спамить: агрегация повторов.** Несколько событий одной issue за короткое время должны схлопнуться в одно сообщение с заголовком вида «GlitchTip Alert (N issues)», не породить N отдельных сообщений.
5. **Регресс вебхука (это и был основной прод-баг).** POST на `https://mon.mia360.ru/$ALERT_HOOK_PATH/` должен возвращать `200`, а не `502` — особенно сразу после пересоздания контейнера `alert-telegram-relay` (например, после ручного `docker compose restart alert-telegram-relay` или после повторного прогона `monitoring-setup`, который меняет docker-адрес relay). Признак регресса из `CLAUDE.md`: `connect() failed (111: Connection refused)` в логе `monitoring-nginx`.
6. **Регресс `monitoring-setup`.** Повторный ручной прогон джоба не должен приводить к падению relay с `KeyError: TELEGRAM_BOT_TOKEN` — после прогона `GET /health` на relay (или сам факт живой доставки следующего события) подтверждает, что секреты записались.
7. **Fallback без своего чата.** Если `TELEGRAM_GLITCHTIP_CHAT_ID` не задан (гипотетически, для регрессии) — ошибки GlitchTip должны идти в тот же общий чат, что и раньше, без ошибок relay.
8. **Безопасность ссылок/контента.** Issue с вредоносным заголовком/ссылкой (`javascript:...`, HTML-теги в заголовке) не должны попасть в Telegram как есть — только текст, ссылка экранирована/отфильтрована. Специально организовать такой кейс на реальном стенде вряд ли возможно/нужно — покрыто юнит-тестами, но стоит держать в уме при разборе первой же странной ошибки.

## Аналитика/API

Отдельной аналитики или публичного API эта задача не добавляет — только внутренний docker-network вебхук GlitchTip → relay → Telegram Bot API. Наблюдаемость самой доставки: строка `relayed N glitchtip issue(s)` в логе контейнера `alert-telegram-relay` — это единственный способ подтвердить, что вебхук дошёл и сообщение отправлено (ручной POST в relay проверяет по признанию автора «лишь половину цепочки»).

## Открытые вопросы

- **Доступ к панели GlitchTip (`errors.mia360.ru`) для QA.** Предыдущий раунд по related-тикету MIA-17 (см. дневной индекс 2026-09-18) отмечал, что end-to-end тестирование доставки ошибок было заблокировано отсутствием безопасного доступа к панели — тот же вопрос актуален и здесь: чтобы проверить пункты 1-2 вживую, нужен либо доступ к GlitchTip UI (создать тестовую ошибку/переотправить существующее уведомление), либо доверенно попросить разработчика инициировать её и подтвердить по скриншоту переписки в Telegram.
- **Правило алертов для `mia360-test`** («Новая ошибка (тест)», 1 событие/1 минута) — это состояние базы GlitchTip, не код; текущим прочтением репозитория подтвердить нельзя, полагаться приходится на слова автора в Linear-комментарии.
- **Разделение чатов различает только «ошибка приложения vs инфраструктурный алерт», не «прод vs тест».** Formально это соответствует Acceptance («тестовый и продовый проекты различимы в сообщении» — через поле `Project`, не через отдельный чат) — но стоит явно подтвердить с автором/PM, что это осознанное прочтение AC, а не недосмотр: два проекта используют один Telegram-чат «Mia 360 Errors» и различаются только текстом сообщения.
- Юнит-тесты relay покрывают только форматирование и маршрутизацию по чату, не реальную доставку в Telegram/от GlitchTip — это ожидаемо (внешние сервисы), но означает, что весь P0 раздел тест-кейсов выполним только вручную на стенде с доступом к чатам/панели.
