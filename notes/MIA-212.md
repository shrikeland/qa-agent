## Контекст

Базовая инфраструктура «ребёнок зовёт родителя» — из MIA-208: ребёнок может зарегистрироваться сам (без взрослого), получает `selfSignupConfirmedAt`, и как только он закрывает ML2 бесплатной темы, а родитель так и не подтвердился (`parentConfirmedAt === null`), тренажёр блокируется модалкой `parent-invite-gate-modal.vue` с единственной ссылкой `/invite/:token` — по ней взрослый либо заводит новый родительский кабинет («takeover» заглушки), либо, если у него уже есть аккаунт, привязывает ребёнка к существующему. Вся эта база (`access.service.ts`, `parent-invite.service.ts`, страница `/invite/[token]`, модалка) уже была в `master` до MIA-212 и в MR !505 не переписывалась заново — только донастраивалась.

MIA-212 — правки по ревью CJ поверх неё, четыре независимых пункта:
1. Гейт из двух мягких предупреждений («скоро понадобится подтверждение») без блокировки и одного жёсткого (как раньше) вместо одного мгновенного жёсткого.
2. Кнопка «Я родитель» (обходной путь, гасящий признак самостоятельной регистрации) скрыта для тех, кто на лендинге сам назвался учеником.
3. На странице приглашения — логотип «Мия 360» сверху со ссылкой на сайт.
4. Если email, который вводит родитель на странице приглашения, уже занят существующим родительским кабинетом — сразу шлётся письмо со ссылкой входа, без редиректа на отдельный экран повторного ввода email.

MR !505 (`feat/MIA-212-parent-invite-soft-asks`, Kirill Verzhitskii) состоит из трёх коммитов, все уже в `master`:
- `a0d00b10` — основная реализация (три состояния гейта, скрытие «Я родитель», логотип, прямая отправка ссылки входа).
- `dab2c54e` — самостоятельная правка внутри того же MR: открытие мягкого окна перенесено в `onMounted` (чтобы не разъезжалось с SSR-разметкой) и добавлена ветка `isRegistered === false` на странице приглашения (email из формы принадлежит не родителю, а, например, ребёнку — письма нет).
- `27f3c90e` — вторая самостоятельная правка: мягкая просьба теперь ждёт закрытия обзорного тура кабинета (`dashboardTourDoneAt`).

## Реализация

### Бэкенд: три степени просьбы вместо булева гейта — `api/src/services/access.service.ts`

Было: `needsParentConfirmation()` возвращала `boolean` по одному `findFirst` на статус ML2. Стало: `parentAskFor()` возвращает `'soft_ml1' | 'soft_ml2' | 'hard' | null`, читает оба блока темы одним `findMany` (`where: { userId, topicId: freeTopicId, mlLevel: { in: [1, 2] } }`, поля `mlLevel/status/completionSolved`) и решает по приоритету:

```ts
const SOFT_ML2_SOLVED = 5;
const closed = (level) => blocks.some(b => b.mlLevel === level && CLOSED_ML_STATUSES.includes(b.status));
const ml2 = blocks.find(b => b.mlLevel === 2);
if (closed(2)) return 'hard';
if (ml2 && ml2.completionSolved >= SOFT_ML2_SOLVED) return 'soft_ml2';
if (closed(1)) return 'soft_ml1';
return null;
```

Ранние отсечки не изменились: `null`, если `selfSignupConfirmedAt === null` (не самостоятельная регистрация), `parentConfirmedAt !== null` (родитель уже подтверждён) или `freeTopicId === null`. `CLOSED_ML_STATUSES` (`topic-ml-progress.service.ts`) включает `passed`, `credited`, `credited_exhausted` — значок силы, закрывающий блок без обычного прохождения, учитывается так же, как и раньше.

Важно: **только `'hard'` продолжает реально блокировать доступ.** `canAccessTrainer()`:
```ts
const parentAsk = await parentAskFor(user);
if (parentAsk === 'hard') {
  return { allowed: false, level: 'parent_pending', subscription: null, freeTopicId, parentAsk };
}
```
При `'soft_ml1'`/`'soft_ml2'` выполнение идёт дальше как обычно (freemium/full), но `parentAsk` всё равно кладётся в `AccessInfo` — фронт использует это поле, чтобы решить, показывать ли мягкое окно, отдельно от вопроса «пускать в тренажёр».

`AccessInfo.parentAsk` — новое поле (`api/src/services/access.service.ts`, зеркалом `frontend/types/index.ts: ParentAsk = 'soft_ml1' | 'soft_ml2' | 'hard'`), приходит клиенту в `/me` (и это же поле участвует в `/trainer/...` и `require-topic-access` — но там смотрят только `level`, не `parentAsk`).

### Жёсткий гейт запускается независимо от мягких — `frontend/composables/use-api.ts` (не менялся в этом MR)

Жёсткая блокировка по-прежнему не завязана на `parentAsk`/стор: любой API-запрос, получивший `403 { code: 'PARENT_CONSENT_REQUIRED' }` (это бросает `require-topic-access` middleware при `access.level === 'parent_pending'`, т.е. `parentAsk === 'hard'`), перехватывается глобально в `onResponseError` и вызывает `useParentInviteStore().open()` **без** `{ soft: true }` — окно без «Продолжить занятия» и без возможности закрыть иначе как через «Родитель подтвердил»/«Я родитель». Это тот самый «как раньше» третий пункт скоупа, и код этой ветки в MR !505 не тронут.

### Мягкие просьбы: `frontend/stores/parent-invite.ts`

Новое состояние `soft: boolean` и `softSeen: ParentAsk | null`, плюс `localStorage`-ключ на пользователя: `mia:parent-soft-ask:${userId}`, хранит **одну** последнюю показанную стадию (`'soft_ml1'` или `'soft_ml2'`) простой строкой, не массивом.

```ts
async askSoftly(userId: string, ask: ParentAsk | null | undefined) {
  if (!ask || !SOFT_ASKS.includes(ask) || this.visible) return;
  const seen = [this.softSeen, readSeen(userId)].map(s => (s ? SOFT_ASKS.indexOf(s) : -1));
  if (Math.max(...seen) >= SOFT_ASKS.indexOf(ask)) return;
  this.softSeen = ask;
  writeSeen(userId, ask);
  await this.open({ soft: true });
}
```
`SOFT_ASKS = ['soft_ml1', 'soft_ml2']` — сравнение по индексу означает: если уже был показан (в сторе этой вкладки или в `localStorage`) `soft_ml2`, `soft_ml1` больше не покажется, даже если запрошен явно (естественный порядок и так не даёт этого сценария — ML2 не открыть, не закрыв ML1). `'hard'` в `SOFT_ASKS` не входит — `askSoftly('hard', …)` всегда no-op, жёсткий гейт эта функция не открывает и не закрывает. Если `this.visible === true` (любое окно уже открыто — хоть мягкое, хоть жёсткое), новый вызов `askSoftly` молча выходит — мягкое окно не может перекрыть уже открытое жёсткое или другое мягкое.

`open({ soft })` — общий метод и для мягкого, и для жёсткого пути, ставит `this.soft` и один раз запрашивает ссылку `POST /student/parent-invite` (переиспользуется, если уже загружена — `if (this.link !== null || this.loading) return`).

`recheck()` (кнопка «Родитель подтвердил») перечитывает `/me` и закрывает окно, если `!access.parentAsk` (раньше проверялось `access.level === 'parent_pending'` — теперь так же корректно закроет и мягкое окно, если вдруг к моменту клика родитель уже подтвердился).

### Когда именно срабатывает мягкая просьба — `frontend/components/parent-invite-gate-modal.vue`

```ts
const canClaimParent = getStoredAudience() !== 'student';

onMounted(() => {
  watch(
    () => [userStore.user?.id, userStore.user?.access?.parentAsk, userStore.user?.onboarding?.dashboardTourDoneAt] as const,
    ([userId, ask, tourDoneAt]) => {
      if (userId && tourDoneAt) void store.askSoftly(userId, ask);
    },
    { immediate: true },
  );
});
```
- `onMounted` — самостоятельная правка в коммите `dab2c54e`: открытие окна во время гидрации расходилось бы с серверной разметкой (SSR не мог знать про клиентский `localStorage`).
- Третье условие, `tourDoneAt` — правка `27f3c90e`: пока обзорный тур кабинета не завершён (`user.onboarding.dashboardTourDoneAt` не проставлен), `askSoftly` вообще не вызывается — при любом `parentAsk` мягкое окно ждёт. Тур (`frontend/cabinet/shell/use-cabinet.ts`, `useCabinetTour`) идёт только для роли `STUDENT` и только пока `!onboarding.dashboardTourDoneAt`; **оба** исхода — «Дальше» до конца и «Пропустить» — ведут в один `onFinish`, который безусловно вызывает `userStore.markOnboarding('dashboardTourDoneAt')` (локально проставляется оптимистично, до ответа `PATCH /me/onboarding`).
- Обновление `access.parentAsk` в сторе пользователя без перезагрузки страницы приходит через WebSocket: `frontend/plugins/socket/handlers/trainer-handlers.ts` вызывает `useUserStore().loadMe()` после каждого зачтённого ответа (`payload.submission.status !== 'review-error'`) — именно так закрытие последней задачи ML1/ML2 обновляет `parentAsk`, и вотчер модалки реагирует сразу же, без ручного рефреша.
- **Жёсткий гейт (`'hard'`) этой проверки на тур не проходит** — он приходит не через `askSoftly`, а через перехват 403 в `use-api.ts` (см. выше), который вообще не смотрит на `dashboardTourDoneAt`. См. «Открытые вопросы».
- `canClaimParent` — вычисляется один раз при монтировании из куки `mia_audience` (`getStoredAudience()`, `frontend/composables/use-landing-audience.ts`) — это отдельная, более ранняя фича (оверлей «Я родитель / Я ученик» на лендинге, `docs/landing-audience-gate.md`, компонент `frontend/components/landing-audience/landing-audience-gate.vue`), которую MIA-212 не трогает, а только читает её результат. Кука `mia_audience` живёт 180 дней, ставится один раз при первом ответе на оверлей (пути `/`, `/blog`, `/blog/*`, не кабинет). `canClaimParent = false`, если сохранённое значение — `'student'`; для `'parent'` и для отсутствующей куки (например, прямой заход на `/register`, старый визит до фичи) кнопка остаётся.

### Три состояния модалки в разметке (`parent-invite-gate-modal.vue`)

- `store.soft === true`: текст «Скоро, чтобы продолжить, мне понадобится подтверждение твоих родителей. Попроси их заранее — это займёт минуту.» + кнопка `.parent-gate__later` «Продолжить занятия» (`@click="store.close()"` — просто закрывает окно, никакого запроса на сервер, состояние `parentAsk` не меняется).
- `store.soft === false` (жёсткий): прежний текст «Но для того, чтобы продолжить, мне нужно подтверждение твоих родителей.», кнопки «Продолжить занятия» нет вовсе (не задизейблена — отсутствует в DOM, `v-if="store.soft"`).
- Кнопка «Я родитель» — теперь `v-if="canClaimParent"` (была безусловной), в обоих режимах (мягком и жёстком) видна одинаково, если условие не сработало.
- Ссылка на тренажёр («Готовлю ссылку…» / поле + «Копировать») и блок «Родитель подтвердил» — общие для мягкого и жёсткого состояний, логика не менялась.

### Что делает «Я родитель» (`iAmParent()`, не менялось в этом MR, но важно для понимания скоупа скрытия)

`POST /student/parent-invite/dismiss` → `selfSignupService.dismiss(studentId)` → `UPDATE user SET selfSignupPendingAt = NULL, selfSignupConfirmedAt = NULL`. Поскольку `parentAskFor()` в самом начале выходит с `null`, если `selfSignupConfirmedAt === null`, клик по «Я родитель» полностью снимает признак «этот аккаунт завёл сам ребёнок» — весь гейт (и мягкий, и жёсткий) для этого пользователя перестаёт срабатывать вообще, не только на одну сессию. Отсюда и смысл правки: показывать эту кнопку тому, кто на первом экране честно назвался учеником, — значит дать ему официальную лазейку из объявленного признания «я ребёнок» в «я родитель, всё в порядке».

### Логотип на странице приглашения (`frontend/pages/invite/[token].vue`)

```html
<a :href="ROUTES.home" class="invite__brand" target="_blank" rel="noopener" aria-label="Мия360">
  <Mia360Logo variant="wordmark" />

```
Рендерится вне `<template v-if="status === …">` — то есть виден на **всех** состояниях страницы (форма email, «Ребёнок уже привязан», «Ссылка устарела», «Проверьте почту»). `ROUTES.home = '/'`, `target="_blank" rel="noopener"` — открывает лендинг в новой вкладке, страница приглашения не теряется. Вариант логотипа `wordmark` (без слогана, обычный `Mia360Logo` компонент, не новый — переиспользован существующий `frontend/components/mia360-logo.vue`), высота 31px, класс `.invite__brand { display: inline-flex; margin-bottom: 24px; }`.

### Email, который уже есть в базе — прямая отправка письма (`frontend/pages/invite/[token].vue`)

Раньше `code === 'email_registered'` от `POST /parent-invite/:token/register` вёл на `router.push('${ROUTES.parentEnter}?invite=…')` — отдельный экран `/parent/enter`, где нужно было **второй раз** ввести тот же email. Теперь:
```ts
const sendLoginLink = async () => {
  const { isRegistered } = await authApi.loginRequest(email.value.trim(), token.value);
  if (!isRegistered) { emailError.value = 'Этот email уже занят. Укажите другой'; return; }
  status.value = 'link_sent';
};
```
- `/parent-invite/:token/register` (`registerByParentInviteHandler` → `parentInviteService.takeoverPlaceholder`) отдаёт `email_registered`, если **любой** пользователь (`prisma.user.findFirst({ where: { email } })`, без фильтра по роли) уже занял этот email — не обязательно родитель.
- `sendLoginLink()` использует уже существующий (не новый в этом MR) эндпоинт `POST /auth/login-request` (`loginRequestHandler` → `authService.loginRequest`), который ищет **именно родителя** (`userRepository.findParentByEmail`). Если email принадлежит не родителю (например, тому же ребёнку или другому ученику) — `isRegistered: false`, письма нет, фронт показывает «Этот email уже занят. Укажите другой» (эта ветка — `isRegistered === false` — добавлена отдельным коммитом `dab2c54e`, то есть найдена и закрыта в ходе того же MR, а не является скоупом изначального описания).
- Если email действительно принадлежит родителю — сервис шлёт письмо с двумя ссылками сразу: ссылкой входа для ученика (`/ref/:token`) и ссылкой входа для родителя `/parent/enter?token=…&invite=<исходный token приглашения>` (`signParentLoginToken` + проброс `parentInviteToken`). Экран переключается на `status.value = 'link_sent'` → заголовок «Проверьте почту» + «Кабинет с адресом {{ email }} уже есть. Мы отправили на него ссылку для входа...».
- `/auth/login-request` имеет фиксированный тайминг-пол 800мс (защита от угадывания email по времени ответа) и **rate-limit 5 запросов/час** на ключ `ip:email` (`api/src/routes/auth.routes.ts`) — общий для всех вызовов этого эндпоинта, не только со страницы приглашения.
- На самой странице `/invite/[token]` нет отдельной кнопки «отправить письмо ещё раз» — переотправка возможна только повторным сабмитом всей формы (email + оба чекбокса) с тем же email; с экрана «Проверьте почту» вернуться к форме без перезагрузки страницы нельзя (см. «Открытые вопросы»).
- **Переход по ссылке из письма**: `frontend/pages/parent/enter.vue` (не менялся в этом MR, читает `route.query.invite`) — после успешного `parentLogin()` вызывает `attachInvitedChild()` → `POST /parent-invite/:token/attach` → `parentInviteService.attachToExistingParent()`: ребёнка переносит на `parentId` существующего родителя, гасит старую (`selfSignupConfirmedAt`) родительскую запись-заглушку (`deletedAt`), переносит подписочные слоты и `awardParentConfirmed`. Если родитель уже был залогинен в этом браузере на момент открытия ссылки — `attachInvitedChild()` всё равно вызывается (в `catch` у `parentLogin`, при `role === 'PARENT'`), т.е. привязка отрабатывает и без повторного логина.

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Полный happy path: ML1 → soft, ML2×5 → soft, ML2 закрыт → hard

1. С лендинга (`/`) выбрать «Я ученик» на оверлее, зарегистрироваться самостоятельно (без родителя), открыть ссылку ученика на этом же устройстве/браузере.
2. Пройти обзорный тур кабинета до конца («Дальше» на всех шагах) **или** нажать «Пропустить» — важно проверить оба варианта отдельно (см. кейс 6), в этом кейсе — любой из них, тур должен быть закрыт.
3. Решить задачи бесплатной темы до закрытия ML1 (все задачи блока получают статус `passed`/`credited`).
4. Ожидается: сразу после зачтения последней задачи ML1 (без ручного обновления страницы — событие приходит по сокету) появляется окно «...дальше тебя ждут задания поинтереснее...» с текстом «Скоро, чтобы продолжить, мне понадобится подтверждение твоих родителей. Попроси их заранее — это займёт минуту.», кнопками «Продолжить занятия» и «Я родитель» (последняя — если не выбирался «Я ученик» на лендинге, см. кейс 4), ссылка на кабинет родителя уже подгружена или показывает «Готовлю ссылку…».
5. Нажать «Продолжить занятия» — окно закрывается, доступ к тренажёру не блокируется, задачи ML2 решаются свободно.
6. Перезагрузить страницу — окно не появляется повторно (флаг в `localStorage`, ключ `mia:parent-soft-ask:<userId>`).
7. Решить 5 задач ML2 (`completionSolved === 5` по блоку ML2, статус блока при этом ещё не `passed`/`credited`) — окно появляется снова, тот же текст и кнопки. Проверить: если 5-я задача решена без перезагрузки (в той же сессии), реакция мгновенная.
8. Нажать «Продолжить занятия» — закрывается, перезагрузка страницы — не возвращается.
9. Закрыть ML2 полностью (последняя задача блока получает `passed`/`credited`) — на этот раз при следующем обращении к тренажёру (открытии любой закрытой темы/задачи) появляется окно **без** «Продолжить занятия»: только ссылка/«Копировать», «Родитель подтвердил» и «Я родитель». Закрыть Escape/кликом по фону — окно **не закрывает себя** (нет обработчика на фон/`Escape`, у окна вообще нет крестика — не проверять его отдельно, в разметке нет).
10. Прямой запрос к API тренажёра (любая попытка открыть задачу) в этот момент должен возвращать `403 { code: 'PARENT_CONSENT_REQUIRED' }`.

### 2. Одна мягкая просьба на стадию, порядок не откатывается

11. Дойти до showcase soft_ml2 (кейс 1, шаг 7), закрыть его через «Продолжить занятия».
12. Обновить страницу несколько раз, порешать что-то ещё в ML2 (но не закрывая блок) — soft_ml1 повторно **не** должен появиться (индекс `soft_ml2` в `localStorage` перекрывает более раннюю стадию).
13. Открыть тот же аккаунт в другом браузере/приватном окне того же устройства (другой `localStorage`) — soft_ml1 должен показаться заново при выполнении условий (нюанс из комментария разработчика: «на другом устройстве просьба может показаться ещё раз» — ожидаемое поведение, не баг).

### 3. Обзорный тур блокирует мягкую просьбу (ключевая правка `27f3c90e`)

14. Новый самостоятельно зарегистрированный ученик, тур кабинета ещё не пройден (`dashboardTourDoneAt` не проставлен). Технически довести аккаунт до состояния «ML1 закрыт» (например, через диагностику/бэкдор, если тур обычно не даёт добраться до задач раньше своего завершения) — окно мягкой просьбы **не должно** появляться, пока тур виден на экране.
15. Нажать «Пропустить» на туре — сразу после этого (без дополнительных действий) окно мягкой просьбы должно появиться, если условие по ML уже выполнено.
16. Пройти тур до конца («Дальше» на всех шагах, финальный экран) — аналогично, окно должно появиться сразу по завершении, если условие выполнено к этому моменту.
17. Проверить обратный порядок: тур ещё не показан (например, первый вход, `topics` ещё не загрузились) — мягкая просьба должна ждать, а не появиться поверх/до тура.

### 4. Жёсткий гейт не проверяет тур — потенциальная нестыковка (см. «Открытые вопросы»)

18. Попытаться воспроизвести ситуацию, где ML2 уже закрыт, а тур кабинета ещё не пройден (например, у аккаунта, где прогресс есть, а `dashboardTourDoneAt` почему-то не проставлен — миграция/ручная правка данных, либо тур был прерван программно). Любой запрос к тренажёру в этом состоянии — должен ли жёсткий гейт появиться поверх недопройденного тура? Ожидание по коду: да, появится, независимо от тура (в отличие от мягких просьб). Зафиксировать фактическое поведение и решить с командой, ожидаемо ли это.

### 5. Кнопка «Я родитель» скрыта для тех, кто выбрал «Я ученик»

19. С лендинга явно выбрать «Я ученик» в оверлее аудитории → зарегистрироваться → дойти до любого из трёх окон (soft_ml1/soft_ml2/hard) — кнопки «Я родитель» не должно быть в DOM ни в одном из трёх состояний.
20. С лендинга выбрать «Я родитель» (или зайти напрямую на `/register` без прохождения оверлея — кука `mia_audience` не выставлена) → тем не менее пройти по флоу самостоятельной регистрации ученика (если это в принципе достижимо на выбранной ветке) → кнопка «Я родитель» должна присутствовать во всех трёх окнах.
21. Проверить, что кука `mia_audience` не сбрасывается по ходу флоу (истекает через 180 дней) — повторный визит с тем же браузером после выбора «Я ученик» сохраняет скрытие кнопки.
22. Клик по «Я родитель» (когда видна) — окно закрывается, `POST /student/parent-invite/dismiss` уходит; после этого клика **все три** типа просьбы (soft/hard) должны перестать появляться для этого аккаунта вообще (не только на эту сессию) — признак самостоятельной регистрации снят на сервере. Проверить отдельным заходом/перезагрузкой.

### 6. Логотип на странице приглашения

23. Открыть `/invite/:token` на всех четырёх состояниях (форма — обычный `pending`, `used` — «Ребёнок уже привязан», `expired` — «Ссылка устарела», `link_sent` — «Проверьте почту», см. кейс 7) — логотип «Мия360» должен быть виден вверху карточки во всех случаях.
24. Клик по логотипу — открывается `/` (лендинг) в **новой вкладке**, исходная страница приглашения не закрывается и не теряет введённые данные (email/чекбоксы).
25. Проверить на мобильной ширине — логотип не съезжает, не обрезается, отступ до заголовка сохраняется.

### 7. [ПРИОРИТЕТ] Email существующего родителя — прямая ссылка на почту, без второго экрана

26. Скопировать ссылку из окна мягкой/жёсткой просьбы (пункт «Перешли эту ссылку одному из родителей...»), открыть в другом браузере (или режиме инкогнито — новый визит без сессии).
27. На форме ввести email существующего родительского кабинета (другой семьи, с активной регистрацией), поставить оба чекбокса согласий, отправить.
28. Ожидается: **без перехода на отдельную страницу/URL** экран переключается на «Проверьте почту» с текстом «Кабинет с адресом {{ email }} уже есть. Мы отправили на него ссылку для входа — откройте её, и ребёнок появится в вашем кабинете.» (email в тексте — тот, что ввели, с `.trim()`).
29. Открыть письмо (реальная отправка или лог/мок почтового сервиса на тесте) — в нём должна быть ссылка `/parent/enter?token=...&invite=<token приглашения>`.
30. Перейти по ссылке из письма — родитель логинится в свой кабинет, и ребёнок с исходного приглашения должен появиться в списке детей этого родителя (проверить также, что старая заглушка/несуществующий второй родительский аккаунт для этого ребёнка не остаётся видимой — `attachToExistingParent` помечает её `deletedAt`).
31. Повторить сценарий, когда родитель уже залогинен в этом браузере на момент перехода по ссылке (например, открыл письмо в той же вкладке, где уже работает в своём кабинете) — привязка должна пройти и без повторного логина (ветка `catch` в `parent/enter.vue`, `role === 'PARENT'`).

### 8. Email занят, но не родителем — новая ветка `isRegistered === false`

32. На форме приглашения ввести email, который принадлежит **ребёнку** (самому себе или другому ученику), а не родительскому кабинету.
33. Ожидается: `POST /parent-invite/:token/register` вернёт `email_registered` → фронт вызовет `sendLoginLink()` → `POST /auth/login-request` вернёт `isRegistered: false` (т.к. `findParentByEmail` не найдёт родителя с таким email) → форма остаётся на месте, показывается ошибка «Этот email уже занят. Укажите другой» (не «Проверьте почту», письмо не уходит).
34. Отдельно свериться со старой веткой `email_is_child_email` — если введён email именно того ребёнка, который стоит за **этим конкретным** приглашением (`childEmail === email`, из `takeoverPlaceholder`), текст ошибки другой: «Укажите свой email — этот уже принадлежит ребёнку». Не перепутать эти два похожих, но разных сообщения при багрепорте.

### 9. Rate limit и сетевые ошибки на отправке письма

35. Отправить форму с одним и тем же email существующего родителя 6 раз подряд (пересылка формы возможна только полным ресабмитом — на экране `link_sent` формы уже нет, см. «Открытые вопросы»; для теста — держать email родителя, а раз за разом менять телефон/чекбоксы обратно, либо тестировать через прямой вызов `/auth/login-request`, если инструмент доступен QA) — 6-й запрос должен вернуть `429`, фронт должен показать «Слишком много запросов подряд. Подождите немного и попробуйте ещё раз».
36. Смоделировать сетевую ошибку на `/auth/login-request` (не 429) — должно показаться «Не получилось отправить письмо. Попробуйте ещё раз», форма/экран остаются на исходном состоянии (не переключаются на «Проверьте почту»).
37. Проверить, что `used`/`expired` статусы приглашения по-прежнему корректно отображаются (эта логика не менялась, но регрессия возможна из-за перестановки `<template>`-веток при добавлении `link_sent`): открыть уже использованное приглашение → «Ребёнок уже привязан» + «Войти»; открыть просроченное (>24ч) → «Ссылка устарела».

### 10. Регрессия старого пути «У меня уже есть аккаунт»

38. На форме приглашения (ещё не отправляя её) нажать «У меня уже есть аккаунт» внизу — должен вести на `/parent/enter?invite=<token>`, отдельно от нового прямого сценария кейса 7. Этот путь не менялся MIA-212, но раз рядом появился альтернативный (автоматический) — стоит перепроверить, что оба не конфликтуют, если пользователь сначала пришёл через «У меня уже есть аккаунт», а потом всё равно ввёл email в форму (маловероятно, но проверить, что состояние `status` не путается между ними).

### 11. Состояния и адаптив

39. `loading`/`sending` состояния: во время отправки формы регистрации кнопка «Создать кабинет» задизейблена (`:disabled="submitting"`), повторный клик не шлёт дублирующий запрос.
40. Ошибка сети на самой отправке формы (`onSubmit`, не `sendLoginLink`) — «Не получилось. Попробуйте ещё раз», форма остаётся.
41. Пустое состояние для мягкого/жёсткого окна до получения ссылки — «Готовлю ссылку…» вместо поля со ссылкой, кнопка «Копировать» не показывается, пока ссылки нет.
42. Мобильная ширина: карточка `.parent-gate__card` (`max-width: 460px; width: calc(100% - 32px)`) и `.invite__card` — обе должны корректно сжиматься, кнопки не наезжать друг на друга (`.parent-gate__later`/`.parent-gate__recheck` идут по 100% ширины друг под другом).
43. Десктоп — стандартная раскладка карточек по центру экрана, без специфичных для этой фичи проблем ширины.

## Аналитика/API

- Новых аналитических событий под три состояния гейта (открытие мягкой/жёсткой просьбы, клик «Продолжить занятия», клик «Я родитель» именно в этом гейте) в MR **не добавлено** — ни во `frontend/constants/analytics-events.ts`, ни в `api/src/constants/analytics-events.ts` нет `PARENT_GATE_*`/`PARENT_ASK_*`. Событий про сам факт показа soft_ml1/soft_ml2/hard или про закрытие мягкого окна нет — если аналитике нужна воронка по этим трём точкам (а тикет явно вводит две новые точки, которых не было), это стоит уточнить у автора/продукта отдельно от QA (см. «Открытые вопросы»).
- `PARENT_CABINET_LOGIN_REQUEST_SUBMIT = 'parent_cabinet_login_request_submit'` (`:386`, не новое, из более ранней фичи `/parent/enter`) — трекается с `{ result: 'success' | 'fail', reason?: 'rate_limit' | 'error' }`, но **только** на странице `/parent/enter.vue`; вызов `sendLoginLink()` со страницы `/invite/[token].vue` этот (или любой другой) ивент не шлёт вовсе — стоит сверить с аналитиками, ожидается ли трекинг отправки письма с этой новой точки входа.
- `LANDING_AUDIENCE_PARENT_CLICK` / `SIGNUP_PARENT_AUDIENCE_SUCCESS` (`:36`, `:38`) — относятся к оверлею «Я родитель/Я ученик» на лендинге (более ранняя фича), не к кнопке «Я родитель» внутри гейта — не путать при проверке аналитики.
- API-контракты:
  - `POST /student/parent-invite` — без изменений, `{ url, expiresAt }`.
  - `POST /student/parent-invite/dismiss` — без изменений, `{ ok: true }`.
  - `GET /parent-invite/:token` — без изменений, `{ status: 'pending'|'used'|'expired', studentName, grade, topicTitle, solvedCount, strength }`.
  - `POST /parent-invite/:token/register` — без изменений в теле/кодах ошибок (`409 { code }`, коды: `not_a_placeholder`, `invite_used`, `invite_expired`, `email_is_child_email`, `email_registered`); используется фронтом иначе (ветка `email_registered` теперь не редиректит).
  - `POST /parent-invite/:token/attach` — без изменений, `{ studentId }`, требует роли `PARENT`.
  - `POST /auth/login-request` — без изменений в контракте (`{ isRegistered: boolean }`, rate-limit 5/час по `ip:email`), **новый вызывающий** — страница приглашения передаёт `parentInviteToken`, из-за чего письмо у уже существующего родителя содержит ссылку с `&invite=...`, чего раньше с этой точки входа не происходило.
  - `/me` — новое поле в ответе: `access.parentAsk: 'soft_ml1' | 'soft_ml2' | 'hard' | null`.

## Открытые вопросы

- **Жёсткий гейт не ждёт обзорный тур.** Мягкие просьбы явно ждут `dashboardTourDoneAt` (правка `27f3c90e`), а перехват `403 PARENT_CONSENT_REQUIRED` в `frontend/composables/use-api.ts` (запускающий жёсткое окно) — нет, он ни разу не проверяет состояние тура. Если технически возможна ситуация «ML2 закрыт, а тур ещё не пройден» (маловероятно при обычном порядке действий, но не невозможно — например, если тур прерван программной ошибкой или пропущен нестандартным способом), жёсткое окно перекроет недопройденный тур, а мягкие — нет. Это несогласованность, которую стоит показать разработчику: осознанная (тур не должен мешать блокировке, раз уж дошло до неё) или недосмотр.
- **Нет аналитических событий на сами точки показа/закрытия гейта** (см. «Аналитика/API») — ни на открытие soft_ml1/soft_ml2/hard, ни на клик «Продолжить занятия», ни (в новом месте) на успешную отправку письма со страницы приглашения. Стоит уточнить у продукта/аналитиков, нужны ли они для этой доработки, прежде чем считать пункт закрытым.
- **Нет пути «назад» с экрана «Проверьте почту».** После `sendLoginLink()` форма email пропадает из разметки (`v-else` ветка), вернуться к вводу другого email можно только перезагрузкой всей страницы (что заново дёргает `GET /parent-invite/:token` — если ссылка ещё жива, форма снова появится, но введённые ранее данные потеряются). Если родитель ошибся email на этом шаге — придётся перезагружать страницу; не блокер, но стоит подтвердить с продуктом, ожидаемо ли это, и если нет — завести отдельный тикет.
- **`localStorage`, а не сервер, помнит показанные мягкие просьбы** — прямо признано в комментарии разработчика («на другом устройстве просьба может показаться ещё раз»). Это осознанное решение не тест-блокер, но стоит явно принять как ожидаемое поведение при тестировании на нескольких устройствах/браузерах одного аккаунта, а не заводить как баг.
- Первый экран «Я родитель / Я ученик» — не часть этого MR (более ранняя фича с курьёзным техническим отличием: ответ хранится в куке `mia_audience`, а не в сторе/localStorage, и оверлей живёт на лендинге, а не в кабинете) — MIA-212 только читает результат (`getStoredAudience()`) для решения о кнопке «Я родитель» внутри гейта. Если оверлей на лендинге в принципе не был показан (прямой заход на `/register`, реферальная ссылка без прохождения `/`), `canClaimParent` останется `true` по умолчанию — уточнить у QA/продукта, ожидаемо ли показывать «Я родитель» в таком случае (по коду — да, ожидаемо, раз это не однозначно «ученик»).
