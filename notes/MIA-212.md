## Реализация

MR 505 (`feat/MIA-212-parent-invite-soft-asks` → `master`, merged), файлы:

- `api/src/services/access.service.ts` + `api/src/services/__tests__/access.parent-pending.test.ts`
- `frontend/stores/parent-invite.ts` + `frontend/tests/parent-invite-store.spec.ts`
- `frontend/components/parent-invite-gate-modal.vue`
- `frontend/pages/invite/[token].vue`
- `frontend/types/index.ts`

**Бэкенд (`api/src/services/access.service.ts`)**

`needsParentConfirmation(): boolean` заменён на `parentAskFor(): Promise<ParentAsk | null>`, `ParentAsk = 'soft_ml1' | 'soft_ml2' | 'hard'`. Логика (`SOFT_ML2_SOLVED = 5`):

```
if (parent уже подтвердил / нет самостоятельной регистрации / нет свободной темы) → null
блоки ML1/ML2 темы читаются одним findMany (было findFirst только по ML2)
closed(2) (passed/credited/credited_exhausted)            → 'hard'
ML2 существует и completionSolved >= 5                     → 'soft_ml2'
closed(1)                                                   → 'soft_ml1'
иначе                                                        → null
```
`canAccessTrainer()` возвращает `parentAsk` в `AccessInfo` всегда (а не только когда блокирует); `'hard'` по-прежнему единственное значение, которое ставит `level: 'parent_pending'` и режет `allowed: false` — жёсткая блокировка через `/me` → `access.level` не поменялась.

**Фронт, стор (`frontend/stores/parent-invite.ts`)**

Новое состояние `soft: boolean`, `softSeen: ParentAsk | null`. Новый экшен `askSoftly(userId, ask)`:
- игнорирует `ask` не из `SOFT_ASKS = ['soft_ml1', 'soft_ml2']` (то есть `'hard'` и `null` не открывают мягкое окно) и если модалка уже открыта;
- сравнивает индекс `ask` в `SOFT_ASKS` с максимумом из in-memory `softSeen` и `localStorage['mia:parent-soft-ask:<userId>']` — просьба показывается только если её индекс строго больше уже показанной (soft_ml1 → soft_ml2 однонаправленно, повтор одной и той же не откроется);
- пишет отметку в `localStorage` **до** открытия окна, ключ per-`userId`, **без TTL и без sync между вкладками/устройствами** — разработчик прямо предупреждает: на другом браузере/устройстве та же просьба покажется снова.

Хард-гейт (`level: 'parent_pending'`, 403 `PARENT_CONSENT_REQUIRED`) по-прежнему открывается глобальным перехватчиком в `frontend/composables/use-api.ts` (`onResponseError` → `useParentInviteStore().open()`, `soft` не передаётся → `false`) — этот путь MR не менял, это база для регрессионной проверки.

**Модалка (`frontend/components/parent-invite-gate-modal.vue`)**

- `canClaimParent = getStoredAudience() !== 'student'` — читает cookie лендинга (`use-landing-audience`), кнопка «Я родитель» скрыта только если на первом экране лендинга выбрано «Я ученик» (сохранённая аудитория ≠ `'student'`, включая `null`/родителя — кнопка остаётся).
- `onMounted` → `watch` по `[user.id, user.access.parentAsk, user.onboarding.dashboardTourDoneAt]`, `immediate: true`, вызывает `askSoftly` только когда `tourDoneAt` уже проставлен (обзорный тур кабинета ждёт своей очереди, мягкая просьба не перебивает его).
- В шаблоне: `store.soft` переключает текст («Скоро… Попроси заранее» vs «Но для того, чтобы продолжить…») и показывает кнопку «Продолжить занятия» (`store.close()`, чисто клиентское скрытие, без запроса на сервер). Кнопка «Я родитель» условна по `canClaimParent`, при жёсткой блокировке её нет, если аудитория `'student'`.
- Важно: скрытие кнопки «Я родитель» — только вёрстка (cookie на клиенте); сам эндпоинт `/student/parent-invite/dismiss` не проверяет источник аудитории — см. открытые вопросы.

**Страница приглашения (`frontend/pages/invite/[token].vue`)**

- Логотип добавлен как `<a href="ROUTES.home" target="_blank" rel="noopener"><Mia360Logo variant="wordmark"/></a>` над карточкой, виден на всех статусах (`pending`/`used`/`expired`/новый `link_sent`).
- Новый статус `link_sent`: при коде ошибки `email_registered` от `/parent-invite/:token/register` фронт теперь не редиректит на `/parent/enter`, а дергает `useAuthApi().loginRequest(email, token)` (`POST /auth/login-request`, rate-limit 5/час на связку `ip:email`, всегда фиксированная задержка ~800мс, чтобы не палить наличие email) и показывает «Проверьте почту» с текстом, содержащим введённый email.
  - `isRegistered: false` (адрес не принадлежит ни одному родителю) → `emailError = 'Этот email уже занят. Укажите другой'` (защитный кейс, не должен встречаться в норме, т.к. `email_registered` от `register`-ручки уже означает, что email — родительский).
  - `429` → `'Слишком много запросов подряд...'`; прочие ошибки → `'Не получилось отправить письмо...'`.
- `email_is_child_email` (email принадлежит ребёнку, не родителю) обрабатывается отдельно, копирайтом `'Укажите свой email — этот уже принадлежит ребёнку'` — эта ветка MR не трогал, но она соседствует с новым кодом и легко ломается регрессией.
- `invite_used` / `invite_expired` не изменились.

**SCSS/токены**: правки используют существующие переменные (`$color-vast`, `$color-bg-page`, `$font-body`, `$font-heading`), новых токенов не заводили — `docs/code-style.md` (раздел SCSS) соблюдён, `$color-trainer-*` в этом MR не участвуют.

## Тест-кейсы

### TC-1. Кнопка «Я родитель» скрыта для «Я ученик»

**Приоритет:** High · **Тип:** Functional/UI

**Прекондиции:** очищены cookies (`LANDING_AUDIENCE_COOKIE`) и localStorage; переход на лендинг.

1. На лендинге выбрать «Я ученик» → зарегистрироваться → дойти до состояния, когда открыта модалка приглашения родителя (мягкая или жёсткая — см. TC-2/TC-3/TC-4).
   **Ожидаемо:** кнопка «Я родитель» в модалке отсутствует в DOM (не просто visually hidden).
2. Обновить страницу (F5) с той же учёткой.
   **Ожидаемо:** кнопка по-прежнему отсутствует (аудитория хранится в cookie, переживает reload).
3. Открыть DevTools → Application → Cookies, убедиться что `LANDING_AUDIENCE_COOKIE = student` (или аналогичное значение).

**Проверка сохранения опции для родителя:**
4. Очистить cookies/localStorage, на лендинге выбрать «Я родитель» (или не отвечать на вопрос лендинга вовсе — например, зайти по прямой ссылке в обход лендинга), зарегистрироваться как ученик тем же способом, дойти до модалки.
   **Ожидаемо:** кнопка «Я родитель» присутствует и кликабельна; клик вызывает `POST /student/parent-invite/dismiss` и закрывает модалку.

### TC-2. Мягкая просьба после закрытия ML1 (без блокировки)

**Приоритет:** High · **Тип:** Functional

**Прекондиции:** новый ученик с самостоятельной регистрацией (`selfSignupConfirmedAt` проставлен), бесплатная тема закреплена (`freeTopicId`), пройден обзорный тур кабинета (`onboarding.dashboardTourDoneAt` не пусто) — иначе модалка не покажется, даже если ML1 закрыт.

1. Решать задачи бесплатной темы до закрытия ML1 (`passed`/`credited`/`credited_exhausted`).
   **Ожидаемо:** сразу после закрытия блока показывается окно «Дальше тебя ждут задания поинтереснее…» с текстом «Скоро, чтобы продолжить, мне понадобится подтверждение твоих родителей...».
2. Убедиться, что тренажёр НЕ заблокирован: под модалкой/после её закрытия можно продолжать отправлять решения.
   **Ожидаемо:** есть кнопка «Продолжить занятия», задачи в теме доступны и до, и после закрытия окна.
3. Нажать «Продолжить занятия».
   **Ожидаемо:** окно закрывается (клиентски, без сетевого запроса), занятия продолжаются без ограничений.
4. Перезагрузить страницу / зайти в кабинет заново на том же устройстве/браузере (задача ML1 всё ещё «soft_ml1», ML2 не пройдено 5 задач).
   **Ожидаемо:** окно НЕ появляется повторно (флаг в localStorage `mia:parent-soft-ask:<userId>` = `soft_ml1`).
5. Проверить кнопку «Родитель подтвердил» / «Я родитель» отсутствуют лишние блокирующие элементы — форма ссылки-приглашения генерируется (`POST /student/parent-invite`), ссылку можно скопировать.

**Граничный случай — тур кабинета не пройден:**
6. Смоделировать состояние, когда ML1 уже закрыт, но `dashboardTourDoneAt` ещё не проставлен (например, новый браузерный профиль без прохождения тура).
   **Ожидаемо:** мягкая просьба не показывается, пока тур не закрыт; сразу после закрытия тура — появляется.

### TC-3. Мягкая просьба после 5 решённых задач ML2 (без блокировки)

**Приоритет:** High · **Тип:** Functional

**Прекондиции:** ML1 уже закрыт и мягкая просьба `soft_ml1` уже показана/закрыта (как в TC-2).

1. Решить 5 задач ML2 (`completionSolved >= 5`), ML2 при этом ещё не закрыт целиком.
   **Ожидаемо:** сразу после 5-й решённой задачи показывается второе мягкое окно (тот же текст/поведение, что в TC-2).
2. Убедиться, что кнопка «Продолжить занятия» есть, тренажёр не блокирован, задачи ML2 продолжают выдаваться.
3. Нажать «Продолжить занятия», перезагрузить страницу.
   **Ожидаемо:** окно не появляется повторно (localStorage теперь хранит `soft_ml2`).
4. Проверка однонаправленности: искусственно откатить прогресс/повторно открыть кабинет так, чтобы сервер снова вернул `soft_ml1` (например, другой ученик/сброс окружения) при уже сохранённом `soft_ml2` в localStorage.
   **Ожидаемо (по коду `askSoftly`):** повторный `soft_ml1` не откроет модалку, т.к. его индекс меньше уже показанного `soft_ml2` — стоит держать в уме при подготовке тестовых данных, чтобы не принять это за баг.

### TC-4. Жёсткая блокировка после ML2 (регресс — «как было»)

**Приоритет:** Critical · **Тип:** Regression

**Прекондиции:** обе мягкие просьбы уже показаны (или не важно — `hard` не входит в `SOFT_ASKS` и не зависит от истории мягких показов).

1. Закрыть ML2 полностью (`passed`, либо `credited`/`credited_exhausted` через значок силы).
   **Ожидаемо:** при следующем запросе к API, задевающем гейт (`ensureFreemiumSubmissionAllowed`/любой запрос, вернувший 403 `PARENT_CONSENT_REQUIRED`), модалка открывается автоматически с текстом «Но для того, чтобы продолжить, мне нужно подтверждение твоих родителей» (не мягкий вариант).
2. Убедиться, что кнопки «Продолжить занятия» НЕТ — окно нельзя закрыть без действия.
   **Ожидаемо:** попытка отправить решение задачи в этой же/другой бесплатной теме отклоняется (403), модалка переоткрывается при следующем запросе.
3. Проверить кнопку «Родитель подтвердил» — до подтверждения родителем показывает «Подтверждения пока не вижу — попробуй ещё раз через минуту», доступ не открывается.
4. Пройти полный сценарий: скопировать ссылку → открыть в родительском окружении → зарегистрировать/привязать родителя (см. TC-6/сквозной сценарий) → нажать «Родитель подтвердил» на ученическом устройстве.
   **Ожидаемо:** доступ открывается (`access.level` уходит от `parent_pending`), модалка закрывается, +50 баллов рейтинга начислено ученику.
5. Убедиться, что если аудитория лендинга = «Я ученик» — кнопки «Я родитель» здесь тоже нет (см. TC-1, применимо и к жёсткому окну).

### TC-5. Страница приглашения родителя — логотип и ссылка на сайт

**Приоритет:** Medium · **Тип:** UI

1. Открыть `/invite/<валидный_token>` (статус `pending`).
   **Ожидаемо:** над карточкой отображается логотип «Мия360» (вариант `wordmark`, без слогана).
2. Кликнуть по логотипу.
   **Ожидаемо:** открывается `ROUTES.home` (`/`) в новой вкладке (`target="_blank" rel="noopener"`), текущая вкладка с формой приглашения не теряется.
3. Проверить, что логотип виден на ВСЕХ статусах страницы: `pending` (форма), `used` (уже привязан), `expired` (устарела), `link_sent` (после мгновенной отправки письма) — логотип рендерится вне `<template v-if=status>` веток.
4. Мобильная ширина (375px, 390px, 428px) и десктоп (1280px+): логотип не обрезается, не наезжает на текст, отступ снизу выдержан (`margin-bottom: 24px`).
5. Проверить `aria-label="Мия360"` на ссылке доступен для скринридера (базовая проверка a11y).

### TC-6. Email родителя уже зарегистрирован — мгновенная ссылка входа

**Приоритет:** Critical · **Тип:** Functional

**Прекондиции:** есть активный родительский аккаунт с email `parent@example.com`; есть валидный `invite token` для другого/нового ученика.

1. Открыть `/invite/<token>`, ввести `parent@example.com` в поле email, поставить оба чекбокса согласий, нажать «Создать кабинет».
   **Ожидаемо:** без промежуточного экрана «У меня уже есть аккаунт» и без запроса email повторно — сразу подставляется статус «Проверьте почту»: заголовок «Проверьте почту», текст с указанием введённого email (`Кабинет с адресом parent@example.com уже есть...`).
2. Проверить письмо на `parent@example.com`.
   **Ожидаемо:** пришло письмо со ссылкой вида `.../parent/enter?token=...&invite=<encoded token>`.
3. Перейти по ссылке из письма.
   **Ожидаемо:** родитель авторизован, ребёнок (по инвайту) появляется в его кабинете (список детей).
4. Повторить шаг 1 больше 5 раз за час с одним и тем же email/IP.
   **Ожидаемо:** после 5-го запроса — `429`, на странице текст «Слишком много запросов подряд. Подождите немного и попробуйте ещё раз» (rate limit `POST /auth/login-request`: 5/час на ключ `ip:email`).
5. Негативный кейс — email принадлежит ребёнку (использован при регистрации ученика), не родителю: ввести такой email в форму приглашения.
   **Ожидаемо:** ошибка `'Укажите свой email — этот уже принадлежит ребёнку'` (код `email_is_child_email`), письмо не отправляется, статус страницы не меняется.
6. Обновить страницу на статусе `link_sent` (F5).
   **Ожидаемо:** т.к. состояние `link_sent` не персистится на сервере (`view.value?.status` из `/parent-invite/:token` вернёт исходный `pending`), после reload форма снова показывается с пустым email — уточнить у разработчика/дизайна, ожидаемо ли это (см. «Открытые вопросы»).

### Состояния форм — сквозная проверка (для TC-5/TC-6 и модалок TC-2–TC-4)

| Состояние | Где проверять | Ожидаемо |
| --- | --- | --- |
| Пусто | Форма `/invite/:token` до ввода | кнопка «Создать кабинет» не блокирует клик, но при клике без данных — `submitAttempted=true`, текст «Заполните email и поставьте обе галочки» |
| Загрузка | Клик «Создать кабинет» / «Родитель подтвердил» / открытие модалки (`store.loading`) | кнопка задизейблена, текст меняется на «Проверяю…» (recheck) либо «Готовлю ссылку…» (пока `store.link === null`) |
| Ошибка | Невалидный/просроченный токен, 429, серверная ошибка | человекочитаемое сообщение, форма не ломается, повторный сабмит возможен |
| Успех | Регистрация нового родителя / `link_sent` / «Родитель подтвердил» → доступ открыт | редирект на `ROUTES.parent`, либо статус меняется, либо модалка закрывается |
| Адаптив | 360–428px (мобильный), 1280px+ (десктоп) | карточка `max-width: 460–560px` центрируется, не обрезается, кнопки на всю ширину на мобильном |

## Аналитика/API

- Новых записей в `frontend/constants/analytics-events.ts` и `api/src/constants/analytics-events.ts` этот MR не добавляет (сверено — событий вида `parent_gate_shown`/`soft_ask_*`/`invite_gate_*` нет ни на фронте, ни на бэке). Показ мягких/жёсткой модалки, клик «Продолжить занятия», клик «Я родитель», отправка письма при уже занятом email — **никак не размечены аналитикой**. Указано это и в исходном плане реализации CJ (`docs/superpowers/plans/2026-09-23-student-to-parent-cj.md`): «новых событий аналитики нет, только новые параметры к существующим» — похоже, осознанное решение, но стоит подтвердить с продактом, раз это конверсионная воронка.
- Затронутые эндпоинты:
  - `POST /student/parent-invite` — выдача/переиспользование ссылки приглашения (auth required, STUDENT).
  - `POST /student/parent-invite/dismiss` — «Я родитель» (auth required, STUDENT); клиентская видимость кнопки не проверяется на сервере — эндпоинт отвечает одинаково независимо от того, какая аудитория выбрана на лендинге.
  - `GET /parent-invite/:token` — публичный просмотр приглашения, rate limit 60/час.
  - `POST /parent-invite/:token/register` — регистрация родителя по инвайту, rate limit 20/час; коды ошибок `email_registered`, `email_is_child_email`, `invite_used`, `invite_expired`.
  - `POST /auth/login-request` — новый путь для email_registered на странице инвайта, rate limit 5/час на `ip:email`, фиксированная задержка ~800мс на обеих ветках (registered/unknown) — специально против тайминг-атак на существование email, это НЕ баг производительности.
  - `GET /me` — поле `access.parentAsk: 'soft_ml1' | 'soft_ml2' | 'hard' | null` теперь приходит всегда (раньше поля не было вовсе).

## Открытые вопросы

1. **Мультиустройство/мультибраузер:** отметка «просьба уже показана» лежит в `localStorage` по `userId`, без синхронизации между устройствами/браузерами. Разработчик явно предупредил, что на другом устройстве мягкая просьба может показаться повторно. Это ожидаемое поведение по комментарию к MR — не заводить баг, но стоит явно проговорить это в тест-ране, чтобы не задвоить баг-репорты.
2. **Отсутствие аналитики** по показам мягких/жёсткой модалки и по кнопке «Я родитель» — стоит уточнить у продакта/аналитика, нужно ли добавлять события в это же окно тестирования или отдельным тикетом.
3. **Скрытие «Я родитель» — только на клиенте:** аудитория лендинга (`getStoredAudience()`) читается из cookie в браузере; сам `/student/parent-invite/dismiss` не валидирует, что вызывающий действительно не выбирал «Я ученик». Если это осознанно (кнопка — это UX-подсказка, а не access control), пометить как «by design», иначе — завести баг безопасности/логики отдельно.
4. **Состояние `link_sent` не персистится:** после F5 на странице «Проверьте почту» форма откатывается к исходному состоянию `pending` (т.к. статус хранится только в реактивном `ref`, а не в ответе `/parent-invite/:token`). Нужно решить с разработчиком/дизайном, баг это или ожидаемое поведение (письмо уже отправлено, повторный reload не критичен, но UX может смутить пользователя, подумавшего, что письмо не ушло).
5. **Визуальное соответствие Figma** логотипа и мягких/жёсткой модалок не проверялось (ссылка на дизайн в тикете отсутствует) — при наличии Figma-ссылки стоит добавить отдельную сверку пикселей (шрифты, отступы, `$color-vast`/`$color-bg-page`).
6. Тест-план полагается на возможность руками спровоцировать `completionSolved`/статусы ML-блоков через тестовое окружение/сид-данные — нужно уточнить у QA-инфраструктуры, есть ли готовый способ быстро довести ученика до нужного состояния (иначе решение 5+ реальных задач ML2 в раннере вручную будет медленным).
