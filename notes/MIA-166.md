## Обновление (17.09)

Статус в Linear сменился на Testing, задача не редактировалась (`title`/`description`/атач не менялись), но появился новый QA-комментарий (15.09, 18:58) - **FAIL по регрессии закрытого доступа**: при GET `/api/homework` с фремиум-cookie ожидался `403`, фактически `200 []`; плитка «Решить домашку» открыта без замка; прямой `/app/homework` рендерится вместо редиректа на пейволл.

**Чтение кода на актуальном HEAD (master) показывает: это не регрессия в коде MIA-166, а более новый отдельный коммит.** `HOMEWORK_ON_FREEMIUM` на текущем master - **`true`** в обеих копиях (`api/src/constants/homework-access.ts`, `frontend/constants/homework-access.ts`), а не `false`, как было на момент прошлой заметки и как написано в комментарии разработчика к MIA-166 («тумблер стоит в false»). Константу перевёл в `true` коммит `6d85a998` («feat(homework): домашка открыта на бесплатном доступе», 14.09 16:35, автор Kirill Verzhitskiy) - **он не упоминает MIA-166 и не является частью MR !397**, это отдельное, более позднее решение продукта. Тем же коммитом бесплатная карточка тарифов (`frontend/components/landing-v2/landing-v2-pricing.vue`) пополнила список включённого пунктом «Разбор домашки» - подтверждает, что открытие домашки на фремиуме сейчас осознанное продуктовое решение, а не утечка тестового тумблера.

**Практический вывод для ретеста:** то, что увидел QA 15.09 (домашка открыта на фремиуме), - это текущее ожидаемое поведение кода, а не FAIL этой задачи. Логика самого MIA-166 (`canAccessHomework`, `homeworkOpen`) не менялась и работает корректно **для значения `true`** - см. тест-кейсы раздела 2 ниже, они теперь описывают то, что должно наблюдаться на стенде по умолчанию. Раздел 1 (поведение при `false`) с этого момента проверяем только через намеренный локальный откат константы - на общем стенде `false` больше не воспроизвести.

Ни `title`, ни `description`, ни `gitBranchName` тикета не менялись - Linear-текст задачи по-прежнему описывает флаг с дефолтом `false`, хотя код продвинулся дальше её исходного скоупа. Стоит уточнить у разработчика/постановщика, относится ли включение флага к MIA-166 или к отдельной задаче (в Linear её не нашли).

## Контекст

Тумблер в коде (не в админке, не env-переменная - осознанно, см. «Out of scope» задачи) для проверки гипотезы: открыть разбор домашки фремиум-ученикам без подписки, не выкатывая платёжную логику. MR !397 (`feat/MIA-166-homework-freemium-flag`) смержен в master с дефолтом `HOMEWORK_ON_FREEMIUM=false`, деплой прошёл автоматически через master-пайплайн. **На текущем HEAD константа - `true`** (см. «Обновление» выше) - более поздний, отдельный от MIA-166 коммит `6d85a998` (14.09) включил её. Фича сейчас физически включена на любом стенде, разворачивающем актуальный master.

## Реализация

Код прочитан целиком на текущем HEAD (`master`, включает `a4836871` MR !397 и последующий `6d85a998`).

### Тумблер - две синхронные копии константы

- `api/src/constants/homework-access.ts` и `frontend/constants/homework-access.ts` - в обоих на актуальном HEAD `export const HOMEWORK_ON_FREEMIUM = true` (изначально MR !397 заводил её как `false`, значение переключил последующий коммит `6d85a998`, см. «Обновление»). Комментарий в обоих файлах прямо предупреждает: «копия во фронте/на бэке - менять обе». Общего модуля между api и frontend в проекте нет, рассинхрон возможен только вручную при правке.

### Бэкенд - гейт домашки вынесен из контроллера в `accessService.canAccessHomework`

`api/src/services/access.service.ts`:
```ts
async canAccessHomework(user): Promise<boolean> {
  const access = await this.canAccessTrainer(user);
  if (access.allowed) return true;                 // оплаченный доступ - всегда пускает
  if (!HOMEWORK_ON_FREEMIUM) return false;          // тумблер выключен - как раньше
  const status = access.subscription?.status ?? null;
  return status === null || status === SUBSCRIPTION_STATUS.FREEMIUM;  // пускает только "чистый" фремиум
}
```
Ключевая логика: `canAccessTrainer.allowed === false` смешивает в одном флаге два разных состояния - ученика, который **никогда не платил** (`status === null` или `FREEMIUM`), и ученика, у которого доступ **прервался** (`EXPIRED`, `CANCELLED` без активного окна, `PENDING_BINDING`, `BINDING_FAILED`, `TRIAL_CHARGE_FAILED`, `AWAITING_PAYMENT`, неудачный `CHARGING`). Тумблер открывает **только первую категорию** - прерванный доступ остаётся запертым при любом значении флага. Это прямо соответствует Out of scope задачи («Expired и binding_failed остаются за пейволлом»).

`api/src/controllers/homework.controller.ts` - `denyUnpaid()` и список открытых домашек теперь вызывают `canAccessHomework()` вместо прежнего прямого `canAccessTrainer().allowed` - гейт применяется на каждом роуте домашки (не только на странице), включая `listOpenHomeworkHandler` (при отказе - пустой список, не ошибка).

### Фронтенд - `homeworkOpen(mode)` и точки использования

`frontend/cabinet/shared/access.ts`:
```ts
export function homeworkOpen(mode: AccessMode): boolean {
  if (mode === 'paid') return true;
  return mode === 'freemium' && HOMEWORK_ON_FREEMIUM;
}
```
`AccessMode` - `'paid' | 'freemium' | 'expired'` (см. `toAccessMode()` тут же: `expired` - это именно прерванный доступ, отдельно от `freemium` = никогда не терявший).

Две точки использования:
1. **Плитка «Решить домашку»** (`frontend/cabinet/shared/next-step.ts`, `homeworkTile()` в `frontend/cabinet/shell/nav-vals.ts`): при `expired` - плитка заблокирована (замок), подпись «на паузе до оплаты», клик → `onPaywall('expired')`. При `free && !homeworkOpen(access)` - тоже заблокирована, подпись «доступна с подпиской», клик → `onPaywall('homework')`. Иначе - открытая плитка «Решить домашку» / «Сфотографируй задание — разберём вместе», ведёт на `ROUTES.homework`.
2. **Страница домашки** (`frontend/pages/app/homework/[[id]].vue`): `watchEffect` при `!homeworkOpen(toAccessMode(user.access))` редиректит на `${ROUTES.appChat}?paywall=homework` (раньше редирект был при `mode !== 'paid'`, то есть чисто по факту оплаты).

Пейволл-модалка (`frontend/cabinet/overlay/paywall.ts`) для `reason === 'homework'` уже существовала (заголовок «Разбор домашки — в подписке», текст «Сфотографировать домашку и разобрать её с Мией можно с подпиской. Тренироваться по бесплатной теме можно и дальше.») - этим MR не менялась, но именно её должен увидеть фремиум-ученик при клике на закрытую плитку/прямом заходе на страницу домашки.

## Тест-кейсы

### 1. [ПРИОРИТЕТ, актуально на текущем HEAD] Поведение при включённом тумблере (`HOMEWORK_ON_FREEMIUM=true` на обеих копиях - текущее состояние master)

Это и есть то, что сейчас должно наблюдаться на любом стенде с актуальным master (см. «Обновление»). QA-комментарий 15.09 зафиксировал часть этого поведения как FAIL, ожидая ещё старый `false` - по факту это не баг, а несовпадение ожиданий с уже переключённой константой.

1. Зайти фремиум-учеником (никогда не платил) в кабинет. Плитка «Решить домашку» должна быть **открыта** (без замка), подпись «Сфотографируй задание — разберём вместе», ведёт на `/app/homework`.
2. Страница `/app/homework` открывается без редиректа в пейволл, задания решаются без ограничений.
3. `GET` списка открытых домашек от лица фремиум-ученика → `200` со списком его домашек (не 403), пустой массив `[]`, если домашек ещё не было - это тоже ожидаемо, не баг.
4. Оплативший ученик (`access.allowed === true`) - плитка домашки открыта, страница открывается без редиректа, как и раньше (флаг на эту категорию не влияет).
5. Ученик с прерванным доступом (`expired`) - **по-прежнему заперт** даже при `true`: замок, подпись «на паузе до оплаты», клик → `onPaywall('expired')`, не `'homework'`. Это ключевая проверка, что тумблер не открывает лишнего - `canAccessHomework`/`homeworkOpen` для `expired` не зависят от значения флага вообще.
6. Юнит-тесты на оба значения флага есть в диффе MR !397 (`api/src/services/__tests__/access.service.test.ts`, `frontend/tests/cabinet-access.test.ts`) - при живом прогоне достаточно свериться с их сценариями.

### 2. Регрессия при выключенном тумблере (`HOMEWORK_ON_FREEMIUM=false` - воспроизводимо только через намеренный локальный откат константы, на общем стенде с master уже не наблюдается)

1. Зайти фремиум-учеником (никогда не платил, доступ `freemium`) в кабинет. Плитка «Решить домашку» должна быть заблокирована (иконка замка), подпись - «доступна с подпиской».
2. Кликнуть по заблокированной плитке → должна открыться пейволл-модалка «Разбор домашки — в подписке» (`onPaywall('homework')`), а не переход на страницу домашки.
3. Прямым переходом по URL открыть `/app/homework` (или `/app/homework/<id>` с любым id) под тем же фремиум-учеником → должен произойти редирект на `/app/chat?paywall=homework`, страница домашки не должна отрендериться даже на мгновение.
4. `GET` списка открытых домашек от лица этого ученика (через сетевую панель браузера или напрямую) → пустой список `[]`, без ошибки.
5. Любой POST/GET на роуты домашки (`api/src/routes/homework...`, если есть прямой доступ к API) от фремиум-ученика → `403` с телом `{ message: 'Разбор домашки открывается с подпиской', reason: 'homework' }`.
6. Оплативший ученик (`access.allowed === true`) - плитка домашки открыта, страница домашки открывается без редиректа, как и до этой задачи (флаг на эту категорию не влияет вообще).
7. Ученик с прерванным доступом (например, `EXPIRED` - смоделировать через тестовый аккаунт с истёкшей подпиской, если такой есть на стенде) - плитка заблокирована с подписью **«на паузе до оплаты»** (не «доступна с подпиской» - разные тексты для разных причин), клик → пейволл с `onPaywall('expired')`, не `'homework'`.

7. Локально/на выделенном стенде поставить обе константы в `false` и пересобрать образы api+frontend. Фремиум-ученик - плитка домашки заблокирована («доступна с подпиской»), клик → пейволл `onPaywall('homework')`, прямой `/app/homework` → редирект на `/app/chat?paywall=homework`, API домашки → `403 { message, reason: 'homework' }`.
8. Ученик с прерванным доступом - поведение не должно отличаться от пункта 1.5 (`expired`/`'на паузе до оплаты'` не зависят от флага).

### 3. [Регрессионный риск, не проверить на текущем стенде, но стоит держать в уме] Рассинхрон двух копий константы

Из код-ревью (комментарий разработчика, за скоупом этой задачи, но важно для будущих раскаток тумблера):

11. **Blue-green риск.** Образы api и frontend катятся не атомарно - в промежуточном состоянии одна копия константы может быть `true`, а другая ещё `false` (в любую сторону). Если фронт думает, что домашка открыта (`homeworkOpen === true` на его копии), а бэк её всё ещё запрещает - при заходе на страницу домашки редиректа не будет (клиентская проверка пропустит), а любой запрос к API домашки получит `403 {reason: 'homework'}`. Общий интерцептор `frontend/composables/use-api.ts` авто-редиректит на пейволл только при `code === 'PAYWALL'` в ответе - у домашки в теле ошибки такого поля нет (`reason: 'homework'`, не `code`), значит автоматического восстановления не будет и экран может просто сломаться без объяснения. Проверить целенаправленно можно только искусственно рассинхронив константы на двух образах - не тест-кейс для обычного QA-раунда, скорее пункт для DevOps-чеклиста при первом реальном переключении флага.
12. **Путь через socket-gateway не проверяется тумблером вообще.** `/internal/homework/task`, `/interaction`, `/submission` (`api/src/routes/internal.routes.ts`) проверяют только `ownsSession`, без вызова `canAccessHomework`. Предсуществующая дыра (не создана и не расширена этой задачей - создание самой домашки всё ещё идёт через загейтенный REST, значит никогда не плативший ученик внутрь не попадёт), но ученик с **прерванной** подпиской, у которого уже есть созданная домашка, теоретически может продолжать решать её задания через сокет в обход `denyUnpaid`. Существовало до MIA-166, тумблер эту дыру не открывает и не закрывает - фиксировать отдельным тикетом, если решат чинить, не в рамках этого QA-раунда.

## Аналитика/API

Отдельного аналитического события на открытие/начало домашки фремиум-учеником задача не добавляет (в диффе изменений `analytics-events.ts` нет). API-контракт: `403 { message: string, reason: 'homework' }` на всех роутах домашки при закрытом доступе - для удобства тестирования можно точечно дёрнуть любой `GET`-роут домашки от лица фремиум-ученика и свериться с телом ответа, не проходя весь UI-флоу.

## Открытые вопросы

- **Флаг переключён в `true` отдельным коммитом `6d85a998` (14.09), не связанным с MIA-166 по тексту коммита и не упомянутым в комментариях тикета.** Текст задачи в Linear по-прежнему описывает дефолт `false`. Стоит уточнить у постановщика/разработчика, относится ли это включение к приёмке MIA-166 или это отдельное неучтённое в Linear решение - см. «Обновление».
- **Рассинхрон констант при blue-green выкате** (см. тест-кейс №11) - фронтенд ловит только `code: 'PAYWALL'`, домашка отвечает `reason: 'homework'` без `code` - в переходном состоянии экран может остаться без объяснения. Из ревью разработчика: «если тумблер будут щёлкать часто, дешевле отдавать его с бэка полем рядом с `access.level` в `/me`» - решение не принято, задача не в скоупе MIA-166.
- **Путь через socket-gateway без проверки доступа** (см. тест-кейс №12) - предсуществующий пробел, не создан этой задачей, требует отдельного тикета, если будет решено чинить.
- Проверка самого включённого состояния тумблера (пункты 8-10) недоступна на общем тестовом стенде в этом раунде - требует отдельного захода с изменёнными константами и пересборкой образов, по словам разработчика.
