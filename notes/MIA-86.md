## Контекст

Методист заводит в справочнике эталонное пошаговое решение задания (список шагов: LaTeX-выражение + описание). Проверка решения в тренажёре (грейдинг) подмешивает эти шаги в промпт Мии как «шпаргалку для сверки» — цель снизить долю ложных вердиктов «Мия придирается, хотя решение верное». Эталон ученику не показывается ни при каких обстоятельствах — это фактически ответ.

Важное уточнение по названию тикета — **скоуп ограничен только ТРЕНАЖЁРОМ**, не диагностикой: методист может завести эталон для любого задания, но подмешивание в промпт грейдинга реализовано только в `trainer.prompt.ts`. Диагностика эталон не использует (см. «Находки по коду», п.1) — это не баг, так буквально называется тикет («в проверке тренажёра»), просто важно не путать при тестировании.

## Реализация

Код прочитан на реальном состоянии дерева после мержа MR !275 (source-branch `feat/solution-steps-grading`, coммит `2e97e0e`). Базовый коммит `10b31598` уже содержит privacy-инфраструктуру из MIA-83 (`stripSolutionSteps`), MIA-86 расширяет её на новое поле `steps`.

**Админка (справочник):**
- `frontend/components/admin/admin-task-edit-drawer.vue` — в дровере редактирования задания появился блок «Эталонное решение» с пояснением «Пошаговое решение для сверки при проверке. Ученику не показывается. Если шагов нет, проверка идёт без эталона.» Рендерит `AdminStepListEditor` (новый компонент, `v-model` на `draft.steps`).
- `frontend/components/admin/admin-step-list-editor.vue` (новый) — список шагов, каждый шаг: бейдж «Шаг N», три иконки-кнопки (стрелка вверх / стрелка вниз / корзина), поле «Выражение (LaTeX)» с живым KaTeX-превью через `<MathFormula :formula="step.expression" error-fallback="неверный LaTeX" />` (превью появляется только если `step.expression` не пусто), поле «Описание» — обычный `<input>` без превью. Кнопка «Добавить шаг» внизу списка, при пустом списке — текст «Шагов нет». Поле `step` — 1-based порядковый номер, пересчитывается (`renumbered`) после каждого add/remove/move, чтобы не было дыр в нумерации (например `[1, 3]` после удаления).
- Компонент один в один повторяет паттерн уже существующего `admin-hint-list-editor.vue` (подсказки) — тот же UX, только без потолка в 3 штуки (у подсказок `MAX_HINTS = 3`, у шагов лимита нет).
- Валидации содержимого шага нет вообще — ни на фронте, ни на бэке (`content-admin.service.ts` просто пробрасывает `patch.steps`/`input.steps` как есть, без проверки длины/обязательности полей). Кнопка «Сохранить» дровера блокируется только по `task`/`answer` (непустые) — пустой список шагов сохранению не мешает, это ожидаемо по тексту задачи.
- Сохранение — `PATCH` через `useAdminApi().updateTask()`; после успешного `update` вызывается `cache.del('entities:assignment:${id}')` (`content-admin.service.ts`) — инвалидирует тот же кэш-ключ `entities:assignment:{id}`, который использует `assignment.controller.ts` при отдаче задания и в тренажёре, и в справочнике. То есть новый эталон подхватывается проверкой сразу же, без ожидания TTL (кэш живёт 24 часа, но инвалидируется явно).
- Цвета/отступы — через CSS custom properties (`var(--c-border-faint)` и т.п.), не хардкод — расхождений с `docs/code-style.md` не нашёл (в отличие от находок в некоторых других фичах этого проекта).

**Подмешивание эталона в грейдинг (только тренажёр):**
- `socket-gateway/src/services/reference-steps.ts` (новый) — `buildReferenceStepsBlock(steps, lang)`: если `steps` не массив или пустой — возвращает `''` (полная деградация к старому поведению, промпт не меняется вообще). Иначе строит блок `- Эталонное пошаговое решение (для сверки, ученику не показывай):\n  1. описание (выражение)\n  ...\n` (для `lang='en'` — англ. формулировка `Reference step-by-step solution (for grading only, never reveal to the student):`). Валидный шаг — любой объект с `description: string` (`expression` необязателен, при отсутствии просто не подставляется скобка).
- `socket-gateway/src/services/trainer.prompt.ts` — `buildReferenceStepsBlock` вызывается в **обоих** путях грейдинга: `createSubmissionRecognitionPrompt` (решение с доски, картинка whiteboard, промпт на русском) и `createTextGradingPrompt` (текстовый/mathpix-грейдинг, промпт на английском, latex из чата/распознанной доски). Блок вставляется сразу после строки с правильным ответом, перед остальными инструкциями.
- `socket-gateway/src/services/diagnostic.prompt.ts` — **не тронут этим MR**, `buildReferenceStepsBlock` там не используется — грейдинг в диагностике эталон не учитывает (см. выше про скоуп).

**Приватность (эталон не должен попасть к ученику) — реализована по-разному для двух каналов:**
- `api/src/utils/assignment-privacy.ts` и `socket-gateway/src/helpers/assignment-privacy.helper.ts` (оба новые, идентичная сигнатура) — `stripSolutionSteps(assignment) => ({...assignment, steps: []})`. Точечная функция, зануляет только `steps`, остальные поля (answer/hints/rules/examples) не трогает.
- HTTP, `api/src/controllers/assignment.controller.ts`: `getAssignments` (эндпоинт `/assignments`) — при `hasAnswers=1` явно ставит `steps: []` в собираемом объекте; `handleGetAssignmentById` — `steps: includeSteps ? assignment.steps : []`, где `includeSteps=true` только для `getInternalAssignmentByIdHandler` (`/internal/assignments/:id`, за `requireInternalKey`, из браузера недоступен), `getAssignmentByIdHandler` (публичный `/assignments/:id`) всегда `includeSteps=false`.
- HTTP, `api/src/controllers/trainer.controller.ts` → `addTrainerSessionInteraction` (`POST /internal/trainer/sessions/:id/interactions`) — единственное реальное изменение в этом файле: `assignment: interaction.assignment ? stripSolutionSteps(interaction.assignment) : interaction.assignment` перед `reply.send`. До этого MR сюда уходил `interaction.assignment` как есть (полный Prisma-объект с релейшном на Assignment, включая `steps`) — то есть до MIA-86 здесь была настоящая дыра для `steps` конкретно на этом эндпоинте.
- Socket-gateway, диагностика (`socket-gateway/src/handlers/diagnostic/interactions.handler.ts`) — здесь сокет-сообщение собирается и эмитится **напрямую**, без HTTP round-trip, поэтому `stripSolutionSteps` вызван явно в трёх местах: `emitSubmissionResult` (итог проверки решения), в ветке «пустая доска» (`empty_whiteboard`) и в `busyAssignment` (ответ «занято, подожди»).
- Socket-gateway, тренажёр (`socket-gateway/src/handlers/trainer.handler.ts`) — этот файл **не входит в список изменённых файлов MR** и вообще не импортирует `stripSolutionSteps`/приватность-хелпер. Канал тем не менее закрыт **косвенно**: `trainerSubmissionPosted` дорефетчивает задание с полными `steps` через `aiMathApi.getAssignment()` → `/internal/assignments/:id`, но финальный ответ ученику (`TRAINER_INTERACTION_RECEIVE`, а также `TRAINER_INTERACTION_REPLACE` при регистрации самого сообщения ученика) собирается функцией `registerTrainerAiInteraction`, которая **всегда** делает HTTP-круг через тот самый `addTrainerSessionInteraction` (см. выше) и эмитит в сокет ровно то, что вернул API — то есть уже с занулённым `steps`. Все ветки (успех, `sendTrainerErrorResponse`, `sendTrainerBadReviewResponse`, `sendTrainerBadRecognitionResponse`) идут через эту же функцию.

## Находки по коду (важно для тест-кейсов)

1. **Эталон не влияет на диагностику.** `diagnostic.prompt.ts` не вызывает `buildReferenceStepsBlock` — заданный в справочнике эталон никак не меняет вердикт при решении того же задания в диагностике (если оно там тоже встречается). Это по описанию тикета ожидаемо (заголовок — «...в проверке тренажёра»), но стоит явно проверить и не считать багом, если вердикт в диагностике не «поумнел» после того, как эталон завели.
2. **Приватность трейнер-сокета держится на косвенности, а не на прямой санитизации.** В отличие от диагностики (где `stripSolutionSteps` вызывается прямо в хендлере сокета), у тренажёра защита работает только потому, что `registerTrainerAiInteraction` всегда проксирует ответ через `POST /internal/trainer/sessions/:id/interactions`, а зачистка `steps` живёт в API-контроллере этого эндпоинта. Работает надёжно и тестами покрыто, но архитектурно более хрупко: если кто-то в будущем добавит путь прямого `userSocket.emit(...)` в обход `registerTrainerAiInteraction` (по аналогии с тем, как это уже сделано в диагностике), защита не сработает автоматически — не баг сейчас, но стоит держать в уме при регрессионном тестировании после будущих изменений трейнер-сокета.
3. **Только `steps` зачищается, остальные поля — нет.** `stripSolutionSteps` зануляет ровно один ключ. На эндпоинте `addTrainerSessionInteraction` (и, соответственно, в `TRAINER_INTERACTION_RECEIVE`/`TRAINER_INTERACTION_REPLACE`) поля `answer`, `hints`, `rules`, `examples` по-прежнему приходят в теле ответа как есть (полный Prisma-объект минус steps). Это **не регрессия этого MR и не входит в его acceptance-критерии** — по тексту задачи это отдельно закрывается в MIA-83 для `answer`; если увидите `answer`/`hints`/`rules` в Network/сокет-инспекторе рядом с уже пустым `steps` — это ожидаемо, не нужно заводить баг по MIA-86.
4. Валидации содержимого шага нет ни на фронте, ни на бэке — можно сохранить шаг с пустым `expression` (превью просто не покажется) или с пустым `description` (промпт всё равно подставит шаг с пустой строкой, `isStep` в `reference-steps.ts` требует только `typeof description === 'string'`, пустая строка проходит). Не баг, но полезно для граничных тест-кейсов.

## Тест-кейсы

### Справочник — редактор эталонного решения

1. **TC1.** Открыть в админке любое задание 7 класса → дровер редактирования → блок «Эталонное решение» под «Подсказками». Если шагов нет — текст «Шагов нет» и кнопка «Добавить шаг».
2. **TC2.** «Добавить шаг» → появляется карточка «Шаг 1» с полями «Выражение (LaTeX)» и «Описание», оба пустые, кнопки ↑/↓/🗑 (↑ задизейблена как единственный/первый шаг).
3. **TC3.** Ввести в «Выражение (LaTeX)» валидную формулу (например `x^2-9=0`) — под полем появляется KaTeX-превью формулы. Ввести заведомо некорректный LaTeX (незакрытая скобка/незнакомая команда) — превью заменяется текстом «неверный LaTeX» (строгий режим KaTeX, как и в поле «Выражение (LaTeX)» самого задания).
4. **TC4.** Ввести текст в «Описание» — просто текстовое поле, KaTeX не применяется, LaTeX-команды остаются как есть текстом.
5. **TC5.** Добавить 3+ шага — у каждого бейдж «Шаг N» по порядку. Кнопка ↑ у первого шага и ↓ у последнего задизейблены, у остальных активны.
6. **TC6.** Кнопки ↑/↓ переставляют шаг местами с соседним, после перестановки бейджи «Шаг N» пересчитываются заново по новому порядку (без дыр/дублей).
7. **TC7.** Кнопка 🗑 (корзина) удаляет шаг из списка, оставшиеся шаги перенумеровываются подряд (напр. было 1-2-3, удалили 2-й — остались 1-2, а не 1-3).
8. **TC8.** Заполнить несколько шагов → «Сохранить» в футере дровера → дровер закрывается (или остаётся, в зависимости от поведения) без ошибки; повторно открыть дровер того же задания — шаги отображаются в сохранённом составе и порядке.
9. **TC9.** Оставить список шагов пустым (не добавлять ни одного) и сохранить задание, изменив только «Условие»/«Ответ» — сохранение проходит успешно (кнопка «Сохранить» блокируется только пустыми «Условие»/«Ответ», не шагами). Убедиться, что это не сломало сохранение остального.
10. **TC10.** Удалить все шаги у ранее заполненного эталона и сохранить — при следующем решении этого задания в тренажёре проверка идёт как «без эталона» (см. TC15/TC16 в baseline-группе).
11. **TC11.** Отмена (кнопка «Отмена» в футере или клик по оверлею/крестик) без сохранения — изменения в шагах не применяются, при повторном открытии дровера — старые данные.

### Тренажёр — проверка с учётом эталона

12. **TC12.** Задать в справочнике 3-4 содержательных шага решения для задания 7 класса (сохранить). В тренажёре открыть это задание, решить его **на доске** (whiteboard) правильно, но нестандартным для Мии способом/порядком действий — отправить на проверку. Ожидание: вердикт «верно», Мия не придирается к формату (проверить сравнением с поведением до заведения эталона, если есть возможность повторить на копии задания без эталона).
13. **TC13.** То же самое, но ответ вводится **текстом/чатом** (или в виде распознанной по mathpix доски — `gradeMode: 'mathpix'`/`'text'`) — эталон так же учитывается (по коду использует `createTextGradingPrompt`, англоязычный промпт, но с тем же блоком «Reference step-by-step solution»).
14. **TC14.** Решить то же задание заведомо неверно (с ошибкой на конкретном шаге) — Мия должна указать на ошибку корректно (не должно «перепутать» с эталоном чужого задания).

### Тренажёр — без эталона (регресс/baseline)

15. **TC15.** Взять задание, где `steps` не заполнены (или пустой массив) — решить в тренажёре с доски. Поведение должно быть идентично тому, что было до фичи: никакого «Эталонное пошаговое решение» в основании вердикта не подразумевается (это не проверяется напрямую в UI, но важно, что вердикт не должен вести себя иначе/хуже, чем раньше).
16. **TC16.** То же для текстового/mathpix-грейдинга без эталона.

### Диагностика — не затронута (регресс)

17. **TC17.** Решить в диагностике задание, для которого в справочнике заведён эталон (если оно фигурирует и в диагностике, и в тренажёре) — вердикт в диагностике не обязан «поумнеть», сверка эталоном там не подключена (см. «Находки по коду», п.1). Не заводить баг, если вердикт в диагностике визуально не отличается от того, что был бы без эталона.
18. **TC18.** Обычный флоу диагностики (join → решение → фидбек → результаты) продолжает работать без ошибок — общий регресс на фоне добавленной санитизации в `interactions.handler.ts` (три новых вызова `stripSolutionSteps` не должны ронять сериализацию сообщений).

### Приватность — HTTP

19. **TC19.** DevTools → Network → открыть задание в тренажёре (запрос списка заданий, `GET /assignments?...&hasAnswers=1`) — в ответе для задания с заполненным эталоном поле `steps` пустой массив `[]` (при этом `answer` в том же объекте — реальный, это ожидаемо и не в скоупе MIA-86).
20. **TC20.** `GET /assignments/:id` (публичный, без `hasAnswers`) для задания с эталоном — в ответе `steps: []` (у этого эндпоинта вообще нет полей answer/hints/rules — только базовая публичная форма).
21. **TC21.** Убедиться, что нет доступного из браузера HTTP-пути, отдающего `steps` с реальным содержимым — единственный эндпоинт, отдающий их (`/internal/assignments/:id`), защищён внутренним ключом (`requireInternalKey`) и не должен быть доступен напрямую с фронта/из браузера без этого ключа.

### Приватность — WebSocket

22. **TC22.** Решить задание с заполненным эталоном в тренажёре с доски → в DevTools (вкладка WS/Network → WebSocket frames) найти входящее сообщение `TRAINER_INTERACTION_RECEIVE` (результат проверки) — поле `assignment.steps` в payload — пустой массив.
23. **TC23.** В том же флоу — сообщение `TRAINER_INTERACTION_REPLACE` (эхо отправленного учеником сообщения/решения сразу после отправки, до ответа ИИ) — `assignment.steps` тоже `[]`.
24. **TC24.** Спровоцировать «занятый» ответ в тренажёре (быстро отправить второе сообщение, пока первое ещё обрабатывается) — сообщение с `meta.isBusy: true` — если в нём присутствует `assignment`, поле `steps` пустое (в этом пути assignment берётся из клиентского payload, который и так не содержит реальных шагов, но стоит перепроверить).
25. **TC25.** В диагностике — решить (или спровоцировать busy/error-ответ) задание с заполненным эталоном → сообщение `DIAGNOSTIC_INTERACTION_RECEIVE` — `assignment.steps: []` в любой из веток (успешная проверка, «нет ответа»/пустая доска, busy).
26. **TC26.** Если возможно спровоцировать ошибку распознавания/грейдинга (например, отправить пустое решение или испортить сеть на секунду) — в error-ответе (`TRAINER_INTERACTION_RECEIVE`/`DIAGNOSTIC_INTERACTION_RECEIVE` с `meta.isError: true`) `steps` тоже не должно быть с реальным содержимым.

### Применение изменений эталона

27. **TC27.** Изменить/дополнить эталон в справочнике для задания, сохранить, сразу (без ожидания) решить это же задание в тренажёре — новая версия эталона учитывается в проверке немедленно (кэш `entities:assignment:{id}` инвалидируется явно при сохранении в админке, TTL 24 часа не должен мешать).

## Открытые вопросы

- Подтвердить у автора: осознанно ли приватность у канала тренажёра (`trainer.handler.ts`) держится только на косвенном HTTP round-trip через `registerTrainerAiInteraction`/`addTrainerSessionInteraction`, а не на прямом вызове `stripSolutionSteps` в сокет-хендлере (как сделано для диагностики)? Сейчас это работает и покрыто тестами, но выглядит как архитектурная асимметрия, которую легко случайно сломать будущими изменениями `trainer.handler.ts`.
- Эталонное решение сейчас никак не участвует в диагностике (`diagnostic.prompt.ts` не вызывает `buildReferenceStepsBlock`) — это осознанный скоуп («в проверке тренажёра» в заголовке тикета) или тоже планировалось, но не попало в MR? Стоит уточнить у методистов/автора, не ждут ли они эффекта и в диагностике тоже.
- Отсутствие валидации содержимого шага (пустой `expression`/`description`, произвольная длина, дублирующиеся номера при ручном вводе через API) — намеренное решение (методисты — доверенная аудитория) или стоит завести отдельную задачу на валидацию.
