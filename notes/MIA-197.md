## Контекст

Модель (в описанном на стенде случае - gpt-5.4-mini) иногда вместо того, чтобы реально вызвать инструмент, печатает служебную разметку харнесса словами прямо в тексте ответа - например:

```
to=functions.remember  彩神争霸是不是json
{"fact":"любит подробные объяснения"}
```

Ученик читал эту строку как реплику Мии. Провайдер отвечает на такой запрос `status=ok` с полным usage - ошибки нет, алерта нет, только жалоба «Мия написала непонятное». Факт (в примере - `remember`) при этом не сохранялся, потому что реального вызова инструмента не было.

Код прочитан целиком в `/tmp/repo` на коммите `e76ced24` (родитель мерж-коммита `0164cd7a`).

## Что изменено

### Детектор - `socket-gateway/src/helpers/tool-call-leak.helper.ts` (новый файл)

Не структурный парсинг, а три регулярки по паттернам чужого формата (harmony-разметка OpenAI):

```ts
const LEAK_PATTERNS: RegExp[] = [
  /\bto=functions\b/i,                 // to=functions.remember, commentary to=functions.skip
  /<\|[a-z_]+\|>/i,                    // <|start|>, <|channel|>, <|message|>, <|end|> и т.п.
  /assistantfinal/i,                   // склеенное имя канала, если сепараторы вообще потерялись
];
export const looksLikeToolCallLeak = (text: string): boolean =>
  !!text && LEAK_PATTERNS.some((pattern) => pattern.test(text));
```

Юнит-тест (`tool-call-leak.helper.test.ts`) отдельно проверяет, что математика/код/JSON в кавычках/упоминание «умею открывать темы» НЕ ловятся - паттерны привязаны к синтаксису харнесса, не к словам «функция»/«инструмент».

### Поток (стриминг) - `ConversationHandlers.handleChunk` (`conversation.handlers.ts`)

Разметка может быть разбита на несколько дельт, поэтому на каждый чанк детектор смотрит не на сам чанк, а на скользящее окно `LEAK_WINDOW = 200` символов (`streamedText.slice(-200) + delta`) - без окна пришлось бы пере-сканировать весь текст на каждой дельте (квадратично по длине, а потоков много одновременно). Как только окно даёт совпадение:
- `this.garbled = true`, дальнейшие дельты этого прохода молча дропаются (`if (this.garbled) return;`);
- в сокет уходит один пустой чанк с `reset: true` - фронт стирает уже показанный текст, но остаётся в состоянии «печатает» (`streaming.value = true`), а не завершает ход.

На `OUTPUT_TEXT_FULL` (финал прохода) проверка повторяется на полном тексте - на случай, если разметка не попала под скользящее окно дельт.

### Один повтор за ход, а не за проход

`isGarbledRetry` - флаг у самого **хода** (turn), а не у прохода (pass): `ConversationPool.start` передаёт его дальше и в `continueTurn` (follow-up после реального tool-call), и в `retryTurn` выставляет `true`. Без этого разметка на каждом проходе tool-loop получала бы свежий повтор и ход не завершался бы никогда.

`handleGarbledAnswer(prompt)`:
```ts
if (!this.isGarbledRetry && !this.pendingCall && !this.optionsCall) {
  const started = await this.retryTurn(prompt, { card, firstPassText, suggests, introAsks, offered, retriedMemory });
  if (started) { chatGarbledAnswerTotal.labels(surface, 'retried').inc(); return true; }
}
chatGarbledAnswerTotal.labels(surface, pendingCall||optionsCall ? 'tool_pass' : 'fallback').inc();
return false;
```
`retryTurn` шлёт **тот же промпт** ещё раз (`ConversationPool.retryTurn: (samePrompt, seed) => this.start(samePrompt, userData, { isGarbledRetry: true, seed })`).

### Настоящий вызов инструмента не переспрашивается

Если в проходе был реальный tool-call (`this.pendingCall || this.optionsCall` - см. тест «keeps a tool loop going and drops only the garbled words»), а текст той же реплики оказался разметкой - `retryTurn` НЕ вызывается (условие `!this.pendingCall && !this.optionsCall`), потому что вызов уже отработал (факт уже сохранён/тема уже открыта) и повторный проход задвоил бы его. Из ответа выбрасываются только слова: второй, «настоящий» проход отвечает пользователю штатно (`continueTurnCalls[0].seed.firstPassText === ''`), метка исхода - `tool_pass`, а не `retried`/`fallback`.

### Второй провал - заглушка

Если и повторный проход (`isGarbledRetry === true`) снова словил разметку, `retryTurn` не вызывается вообще (условие `!this.isGarbledRetry`), ход закрывается штатным путём с заглушкой:
- home chat: `Я тебя поняла. Спрашивай дальше.`
- тренажёр: `Секунду — я не успела ответить. Напиши ещё раз, пожалуйста.`

(тексты см. `stored[0].text` в тестах `falls back to the stub...` и `protects the trainer the same way`).

### Ход не наследует испорченный ответ

`anchorId(responseId)` возвращает `undefined`, если `this.garbled === true`, и это значение уходит в `aiResponseId`, который следующий ход передаёт провайдеру как `previousResponseId`. Без этого модель на следующем ходу читала бы собственную разметку как «последнее, что она сказала», и разметка могла тиражироваться дальше по диалогу (тест `does not anchor the next turn to the derailed response`).

### Лендинг (демо, `DemoHandlers`) - без второго прохода

У демо на лендинге один проход на ход, второй прогон делать нечем (нет tool loop, нет follow-up), поэтому при разметке сразу идёт извинение (`ErrorResponsesRu.PROXY_ERROR`), которое и сохраняется в переписку (иначе жалоба выглядела бы как вопрос без ответа):
```ts
await aiMathApi.addDemoInteraction({ ..., text: ErrorResponsesRu.PROXY_ERROR, meta: { streamId, garbled: true } });
await this.sendDemoResponse(prompt, ErrorResponsesRu.PROXY_ERROR);
```

### Сигнал "сбросить экран" (`reset: true`) - по всем поверхностям

Фронт (`frontend/cabinet/chat/use-home.ts`, `use-demo-board.ts`, `use-demo-chat.ts`, `diagnostic-handlers.ts`, `homework-handlers.ts`, `trainer-handlers.ts`) везде добавил обработку `payload.reset`: очищает показанный стрим-текст, но не завершает "печатает"/`busy`. Для домашки `reset` дополнительно несёт `taskId` - без метки сброс с только что покинутой задачи стёр бы ответ той, что открыта сейчас (тест `names the task on a homework reset...`).

### Новая метрика

`socket-gateway/src/metrics.ts`:
```ts
const chatGarbledAnswerTotal = new Counter({
  name: 'sgw_chat_garbled_answer_total',
  help: 'Turns whose text carried a leaked tool call, by surface and what was done about it',
  labelNames: ['surface', 'outcome'] as const,
  registers: [registry],
});
```
`surface` - `home` / `trainer` / `diagnostic` / `homework` / `demo`. `outcome` - `retried` (повтор запущен) / `tool_pass` (реальный вызов уже был, переспроса не было) / `fallback` (второй провал или демо - закрыто заглушкой).

## Как перепроверить

**Живьём воспроизвести баг сложно.** По коду это происходит «раз в несколько сотен ходов» (комментарий в `tool-call-leak.helper.ts`), детерминированного триггера нет - модель редко ошибается так. Разово гонять чат в надежде поймать разметку - не рабочий способ регресса; ниже - реалистичный путь проверки.

### 1. Юнит-тесты как основной источник уверенности

Все перечисленные выше сценарии уже покрыты юнитами, стоит свериться с ними напрямую, не пересоздавая вручную:
- `socket-gateway/src/helpers/__tests__/tool-call-leak.helper.test.ts` - сам детектор: харизматичная разметка ловится (`to=functions...`, `<|start|>...<|end|>`, `assistantfinal`), а математика/код/упоминание слова «функция» - нет.
- `socket-gateway/src/handlers/pools/__tests__/conversation.handlers.test.ts`, блок `ConversationHandlers - a tool call leaked into the text` (9 кейсов): повтор хода вместо сохранения разметки; заглушка на втором провале; сброс стрима с пустым `reset: true` до того, как что-то читаемое ушло студенту; **реальный tool-call не переспрашивается** (`keeps a tool loop going and drops only the garbled words` - факт сохраняется один раз, `retried: 0`, `continueTurnCalls: 1`); то же для тренажёра (`protects the trainer the same way`); разметка ловится и после 20 нормальных дельт (окно `LEAK_WINDOW`); `reset` для домашки несёт `taskId`; следующий ход не наследует `aiResponseId` сорванного ответа.
- `socket-gateway/src/handlers/pools/__tests__/demo.handlers.test.ts` (новый файл): на лендинге разметка не показывается, сохраняется извинение с `meta: { garbled: true }`; обычный ответ не трогается.
- `frontend/tests/cabinet-home-stream-pulse.test.ts` (кейс `drops what was already shown when the gateway resets a garbled answer, and keeps waiting`): фронт стирает уже показанный текст и остаётся в `streaming: true`.

### 2. Метрика перехвата за период

`sgw_chat_garbled_answer_total{surface, outcome}` - до фикса такой метрики не было вообще (баг ловился только по жалобам учеников, без единой цифры). После деплоя стоит смотреть график по `outcome`:
- `retried` - сколько раз шлюз сам переспросил модель и она поймала себя со второго раза (успешный сценарий, ученик вообще не должен был это заметить);
- `fallback` - сколько раз дошло до заглушки «я тебя поняла, спрашивай дальше» / «секунду, не успела ответить» (второй провал подряд, либо демо-лендинг без второго прохода) - это тот случай, когда ученик всё-таки увидел вырожденный ответ, а не саму разметку. Рост этого лейбла стоит подсвечивать отдельно;
- `tool_pass` - реальные вызовы инструмента, у которых из текста выбросили только слова (регресс не должен показывать рост этого лейбла как проблему - это штатная работа, просто теперь видно, как часто она случается).

Абсолютных чисел «до фикса» в коде/логах нет - раньше метрики не было в принципе, единственный зафиксированный кейс - жалоба на стенде 16.09.2026 (тот самый пример с `彩神争霸`), упомянутый прямо в комментарии к тесту. Поэтому при проверке смотреть не на «выросло/упало относительно чего-то», а на сам факт, что счётчик появился и растёт (значит перехват действительно срабатывает), и что доля `fallback` в нём не доминирует (если `fallback` почти всегда - значит повтор `retryTurn` не помогает, и это стоит эскалировать разработчику отдельно, а не считать успешной проверкой).

### 3. Регресс, который проверяем вживую

Обычный (не поддельный) вызов инструмента должен продолжать работать как раньше - этот путь как раз воспроизводим руками:
1. Чат кабинета - попросить Мию запомнить факт о себе («запомни, что я люблю рисовать») или сменить тему/открыть тренажёр так, чтобы она законно вызвала инструмент (`remember`, `open_topic` и т.п.).
2. **Ожидается:** инструмент отрабатывает, факт/переход виден в UI как раньше (карточка памяти, открытая тема), ответ приходит одним связным текстом без служебной разметки, задержка не выросла заметно (двойного прохода тут быть не должно - код специально не переспрашивает при реальном tool-call).
3. Дополнительно - тренажёр и домашка: попросить Мию показать шаг решения (частый случай легитимного вызова инструмента отображения) и убедиться, что ответ приходит целиком, без обрывов и без `reset` посреди нормального текста.
4. Если случайно поймать реальную разметку на стенде (маловероятно, но возможно) - убедиться, что: (а) в чате студента её не видно вообще ни на миг; (б) в логах `conversation.handlers` есть `msg: 'conversation.handlers: tool call leaked into the answer text'` с `surface`; (в) счётчик `sgw_chat_garbled_answer_total` увеличился с соответствующим `outcome`.

### Граничные случаи, которые стоит держать в уме

- Разметка в самом начале ответа (до единого читаемого слова) vs в середине/конце длинного ответа - оба случая покрыты тестами (`stops streaming the moment...` и `still catches the markup after a long, perfectly normal answer`), но стоит знать, что окно детектора - 200 символов, и в теории разметка длиннее этого окна теоретически может не поймать себя целиком (маловероятно на практике, все три паттерна короткие).
- Домашка: сброс должен относиться к задаче, на которой случился (`taskId`), не к той, что открыта сейчас, если ученик успел переключиться, пока шёл повтор.
- Лендинг/демо не имеет второго прохода принципиально - если увидите там `retried` в метрике, это баг (демо шлёт только `fallback`).
