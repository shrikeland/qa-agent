# MIA-83: правильный ответ задания доступен студенту через API (списывание)

Дев-фикса на это расхождение в истории коммитов ветки ещё нет — проверено напрямую по коду `master` (см. ниже): `api/src/utils/assignment-privacy.ts` не менялся с коммита `9e61ca59`, которым и была внесена регрессия. **Перед прогоном стоит свериться с автором, взят ли фикс в работу** — документирую то, что фактически задеплоено на test-1 сейчас, чтобы прогон не терял времени на уже известное.

## Контекст (все три раунда)

**Раунд 1 (MR — коммит `3c5665cf`, «fail-closed выдача задания»).** Эндпоинт выдачи заданий отдавал студенту `answer` (правильный ответ) под `requireAuth` — можно было списать в тренажёре и, что важнее, в диагностике, обесценив честность замера уровня. Закрыто fail-closed белым списком полей (`toStudentAssignment` в `assignment-privacy.ts`) на HTTP и WS. QA (21.07) — PASS по всем каналам.

**Раунд 2 (MR !296, «владение сессией», коммит `cc93830d`).** При ре-тесте всплыло: посторонний ученик мог читать/менять чужую диагностическую и тренажёрную сессию (переключать задание, удалять/подтверждать чужие сабмишены) — порча состояния, не утечка ответа, но тот же класс уязвимости (IDOR). Закрыто общим хуком `requireOwnTrainerSession`/аналог для диагностики + называние пользователя на каждом internal-вызове гейтвея. Второй под-раунд (MR !336, коммит найден по истории — «чужую сессию тренажёра больше нельзя переключить») добил последнюю дыру: `POST /trainer/next-assignment` и WS `trainer:session:next-assignment` не проверяли владение, плюс легаси-вход `POST /trainer/join` **сам отдавал** чужой `trainerSessionId` по одному только `userId`. Оба легаси-входа удалены целиком (нулевой трафик по ним за всю историю), проверка владения встала на все каналы разом. QA (18.08) подтвердила: сценарий B→A по HTTP и WS — отказ, задание A не двигается.

**Раунд 3 (текущий, НЕ ЗАКРЫТ) — правильный ответ снова доступен, другим полем.** При широком прогоне (не точечном) QA нашла: `rules` (карточка «Разбор ошибки»), возвращённая в студенческую тренажёрную выдачу более поздней фичей «теория в кабинете v2» (коммит `9e61ca59`, **после** раунда 1), у заданий `kind: find_error` в `rules[0].text` содержит правильный ответ дословным текстом. Масштаб по данным QA: из 3338 заданий у 2740 непустой `rules`, у **282** текст правила формулирует ответ (выборочная сверка 40 штук — в 38 из 40 ответ назван буквально).

## Реализация — что сейчас в коде (проверено на master)

`api/src/utils/assignment-privacy.ts`:

```
export const toTrainerAssignment = (assignment: Assignment): IAssignmentPublic => ({
  ...toStudentAssignment(assignment),
  rules: toStudentRules(assignment.rules),
});
```

`toStudentRules` не различает `kind` задания — отдаёт `rules` как есть (только чистит записи без `text`). `toTrainerAssignment` используется в двух местах, оба **без ограничения по `kind`**:

- `api/src/controllers/assignment.controller.ts:51` — `serialize = trainerId ? toTrainerAssignment : toStudentAssignment`, то есть **весь** тренажёрный список (`GET /api/assignments?trainerId=…`) отдаётся с `rules`, включая `find_error`-задания.
- `api/src/services/trainer-session.service.ts:207` — тот же `toTrainerAssignment` в payload `trainer:session:init` (WS), то есть утечка дублируется и в сокет-канал.

На клиенте это не мёртвое поле: `frontend/components/app-v2/cabinet-task.ts:45` (`rules: assignment.rules ?? []`) прокидывает его в `theory-modal.vue`, секцию «Правила для этой задачи» — то есть при определённой прогрессии (ML3/ML5, до такого задания ученик доезжает не сразу) ответ **будет показан в интерфейсе**, а не только доступен через сырой API-ответ.

Раунды 1 и 2 (fail-closed по `answer`/`steps`/`hints`/`examples`, владение сессией) на master подтверждены кодом и держатся — регрессии по ним не найдено.

## Как перепроверить (пока не исправлено — подтвердить, что расхождение воспроизводится)

1. Свежий ученик, ничего не решавший → в браузере (не только curl) выполнить `fetch('/api/assignments?trainerId=<id темы с find_error-заданиями>')` из консоли на странице тренажёра → в ответе есть задания `kind: 'find_error'` с непустым `rules[0].text` → текст правила называет число/выражение, совпадающее с `answer` этого задания в админке.
2. То же по WebSocket: подключиться к теме с `find_error`-заданиями, дождаться `trainer:session:init` (или переподключиться) → `currentAssignment.rules` присутствует у `find_error`-задания с тем же текстом.
3. Отрицательный контроль: у заданий **не** `find_error` (обычный `task`) в `rules` не должно быть карточки, называющей числовой ответ, — так по природе контента (правило — теория темы, не разбор конкретной ошибки).
4. Если фикс придёт — перепроверить, что `answer`/`steps`/`hints`/`examples` по-прежнему не текут ни по одному каналу (быстрый регресс раунда 1), и что владение тренажёрной/диагностической сессией по-прежнему держится (быстрый регресс раунда 2: студент B с `trainerSessionId` студента A → 403/без эффекта, и по HTTP `POST /trainer/next-assignment`, и по WS `trainer:session:next-assignment`).

## Что посмотреть рядом (регресс)

- **Продуктовая развилка** (озвучена в самом отчёте QA, требует решения, не правки кода вслепую): не отдавать `rules` для `find_error` до отправки решения / почистить контент 282 карточек / отдавать разбор только после сабмишена (по аналогии с `result-assignments` в диагностике). Само по себе решение «правило — часть задачи в тренажёре» (комментарий в коде `9e61ca59`) разумно — ломает его контент конкретных карточек `find_error`, а не архитектура.
- Не путать с раундом 2: если при перепроверке всплывёт что-то про смену чужого задания/сессии — это уже закрытый класс, отдельная регрессия, не тот же баг.
- `userId` в `POST /trainer/sessions/:id/interactions` по-прежнему берётся из тела запроса без сверки (открытое наблюдение, не блокер, не в скоупе этого тикета) — не мешает текущей проверке, но всплывёт при любом сквозном прогоне тренажёра.
