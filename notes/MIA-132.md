## Контекст

Исходный баг (label `Bug`): у ученика с силой 94% ML1 не пропускался, хотя должен был. Разбор разработчика (со скриншотами «до/после», PDF недоступен агенту напрямую) показал: само правило пропуска ML1 - «сила > 80 и первые две задачи ядра решены точно» - работало как было написано. Механику скрывали шесть сопутствующих дефектов, из-за которых пропуск был не виден ученику или ломался раньше, чем срабатывал:

1. Полоса блока показывала старое правило («нужно 4 из 5»), пока «проверочный вход» уже был жив.
2. Про сделку («решишь две задачи - пропустим остальное») объявляла модель греетинга сама, и в 82% случаев она это не делала (сделка «терялась»).
3. Про проваленную проверку продукт молчал вовсе - ученик не понимал, почему вернулся к обычному пути.
4. Бейдж «можно перескочить» на карте знаний считался не тем счётчиком, что реальное условие пропуска.
5. Строгое равенство `coreTouched === PROBE_CORE_TASKS` в зачёте пробы сжигало шанс на легаси-блоках (доассайненные задачи, перегрейд сдвигали счётчик сразу на 2 и больше - кадр с равенством просто проскакивался).
6. Не было событий воронки - нельзя было отследить ни предложение пробы, ни её провал, ни зачёт.

Все шесть исправлены в MR !376 (`feat/MIA-132-ml1-probe-visibility` → `master`, merge-commit `86561946294d39c2964c810dda3fde62ee3d8be5`, автор и он же смерджил - Kirill Verzhitskii). Затронуты `api/src/services/scoring/v3-strategy.ts`, `api/src/services/topic-ml-progress.service.ts`, `api/src/services/diagnostic-session.service.ts`, `api/src/constants/analytics-events.ts` (+ дублирующий frontend-контракт), `api/src/services/prompts/greeting.prompt.ts`, `socket-gateway/src/services/greetings.ts`, `socket-gateway/src/handlers/trainer.handler.ts`, `frontend/components/cabinet/chat/chat-task-strip.vue`, `frontend/cabinet/chat/{task.ts,use-session.ts}`, `frontend/cabinet/shell/use-cabinet.ts`.

**Ключевая переписка после мержа.** Первый раунд разбора закончился открытым вопросом к методологу: «ТЗ "Тренажёр" (проверка на двух задачах) против ТЗ "Силы" (значок по силе без единой задачи)» и «порог > 80 или ≥ 80». ## ГЛАВНОЕ: открытое расхождение ТЗ vs реализация

Прочитано целиком в `/tmp/repo` на `master` (`86561946`): `api/src/services/scoring/v3-strategy.ts` (правило) и `api/src/services/topic-ml-progress.service.ts` (`probeState`/`probeLeft`, использование в зачёте блока).

Буквально по коду (`api/src/services/scoring/v3-strategy.ts`):

```ts
export const AUTO_ML1_RATING = 80;
export const PROBE_CORE_TASKS = 2;

export function isProbeOffered(p: { mlLevel: MlLevel; rating: number | null; coreAvailable: number }): boolean {
  return (
    p.mlLevel === 1
    && p.rating !== null
    && p.rating > AUTO_ML1_RATING          // строго БОЛЬШЕ 80, не >=
    && p.coreAvailable > PROBE_CORE_TASKS
  );
}

export function isProbePassed(p: { ...; coreTouched: number; coreAccurate: number }): boolean {
  return (
    isProbeOffered(p)
    && p.coreTouched <= PROBE_CORE_TASKS
    && p.coreAccurate >= PROBE_CORE_TASKS   // зачёт только после 2 точных ответов
  );
}
```

Зачёт ML1 (`ML_STATUS.CREDITED`) на уровне сервиса (`topicMlProgressService.probeState`) требует, чтобы блок дошёл до статуса `active` и прошёл `isProbePassed` - то есть **всегда** нужны минимум две решённые задачи ядра, ни один путь не даёт мгновенный `credited` по одной только силе. Инстант-кредит по силе без единой задачи в коде не встречается вообще (единственный существующий мгновенный `CREDITED` в файле - это перенос зачёта с диагностики на ML1/ML2 при завершении стартовой диагностики, отдельный код-путь, не связанный с порогом силы для обычных тем).

Это ровно то, что нашёл QA на стенде (test-1.mia360.ru, коммит `86561946`):

| Сила | Фактический ML1 (стенд) | Ожидание по актуальному ТЗ Романа |
|---|---|---|
| 100% | `active`, `probe: "pending"`, `probeLeft: 2` - предложены 2 задачи | `credited` сразу, без единой задачи |
| 80% (ровно) | `active`, проверка/проба даже не предложена (`rating > 80` не выполняется при `rating === 80`) | `credited` сразу, без единой задачи |

Расхождение двойное:
- **Порог**: код - строго `> 80`; актуальное ТЗ - `>= 80` (граница 80% не пропускает вообще ничего, даже пробу).
- **Механика**: код - «проверочный вход» на двух точных задачах (`isProbeOffered` + `isProbePassed`); актуальное ТЗ - мгновенный зачёт по одной силе, без единой задачи.

Это два независимых изменения, оба ещё не в коде. Пофиксить нужно и `AUTO_ML1_RATING`/оператор сравнения, и убрать саму пробу как условие зачёта (заменить её другим путём credited, аналогичным переносу с диагностики), плюс синхронно поправить всё, что построено вокруг пробы в MR !376 (полосу, сделку модели, событие `trainer_block_probe_offered` - при мгновенном зачёте «предлагать» уже нечего, вся воронка пробы становится нерелевантной для этого сценария).

## Как перепроверить

Предусловие: новый ученик, у которого сила сформирована **завершённой стартовой диагностикой** (5/5 → `currentRating = 100`, либо подобрать ответы так, чтобы `currentRating` вышел ровно на 80). Важно открывать тему, которой **не было** в диагностическом наборе - темы из диагностики получают `ML1 credited` отдельным путём (перенос с диагностики) и не проверяют интересующую нас логику.

1. Завести ученика A с силой 100% (5/5 верных на диагностике), ученика B - с силой ровно 80%.
2. Для каждого открыть НОВУЮ тему вне диагностического набора (первый вход в тренажёр по этой теме).
3. Сразу дёрнуть `GET /api/me` (или дождаться первого кадра тренажёра) и посмотреть блок ML1/ML2 у этой темы.
4. **По актуальному ТЗ (Roman, после мержа !376)**: ML1 = `credited`, `issuedTotal: 0`, `coreSolved: 0`, ML2 сразу `active`. Ни одна задача не выдаётся до зачёта.
5. **Фактически на коде `86561946` будет** (это и есть открытый баг, а не то, что нужно чинить QA-действиями): ML1 = `active`, для силы 100% - `probe: "pending"`, `probeLeft: 2` (предложены 2 задачи), для силы 80% - проба даже не предложена (`probe: null`), обычный путь без пропуска. ML2 - `locked` в обоих случаях.
6. Если разработчик подтвердит, что фикс уже выкатан - перепроверять именно эти два значения силы (100% и ровно 80%, граница) плюс проверить, что «недостаточная» сила (например, 79%) по-прежнему НЕ пропускает ML1 вообще (регресс на обычный путь не должен сломаться).

## Что посмотреть рядом (отдельное наблюдение, не блокер этой задачи)

QA-прогон зафиксировал в обоих тренажёрных WS-прогонах кадр `trainer:session:init`, где `currentAssignment.rules` не пуст (по одной находке в кадрах 35 и 45; в диагностических кадрах поле не встречалось).

По коду (`api/src/utils/assignment-privacy.ts`) это, судя по всему, ожидаемое поведение белого списка, а не случайная утечка отдельно от этого фикса:

```ts
// Trainer view: the white list plus the theory behind the task...
export const toTrainerAssignment = (assignment: Assignment): IAssignmentPublic => ({
  ...toStudentAssignment(assignment),
  rules: assignment.kind === FIND_ERROR ? [] : toStudentRules(assignment.rules),
});
```

`toTrainerAssignment` (используется в `trainer-session.service.ts` для кадра `trainer:session:init`/`nextAssignment`) сознательно кладёт в `rules` теорию задачи (`{title, text}` через `toStudentRules`) для всех типов задач, КРОМЕ `find_error`, где `rules` хранит разбор с ответом и поэтому явно обнуляется. То есть непустой `rules` в обычной (не `find_error`) задаче - по всей видимости не баг этого MR, а осознанный дизайн («теория - часть задачи в тренажёре»). Фиксирую как отдельное наблюдение по приватности, а не как часть этого бага - требует отдельного решения продукта/безопасности, воспроизводится независимо от MR !376 и не блокирует эту задачу. Стоит уточнить у продукта/разработчика: ожидается ли показывать теорию ДО того, как ученик решил задачу, или `rules` должен подгружаться только после сдачи (аналогично `toStudentAssignmentWithAnswer`).
