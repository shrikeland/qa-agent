## Контекст

Контентная/методическая задача (label `Improvement`), а не типичная UI-фича. Автор сам пишет, что критерии приёмки ещё не определены и работа идёт в две фазы:

- **Фаза 1** — оцифровка структуры заданий 7-8 (темы → задачи → уровни → эталонные шаги → подсказки → привязка контрольных/диагностик к темам) со сверкой по трём внешним источникам (доки Ксюши, учебники Макарычева, раскладка Ромы). Результат этой сверки — карта тем с 1 сентября по ~30 мая — методический документ вне кодовой базы (гуглодок/таблица); в репозитории её нет и по названию/содержанию найти не удалось.
- **Фаза 2** — генерация задач 5-6 классов по шаблону 7-8, начинается только после ревью 7-8 Кириллом. Из последнего комментария Кирилла прямо следует, что 5-6 классы в текущую поставку не входят.

По факту в `Ready for Test` попала не вся фаза 1 целиком, а её видимая в проде/тесте часть — импорт эталонных пошаговых решений (`Assignment.steps`) для 595 заданий 7-8 классов + 10 старых заданий без `source_key` (только на тесте). Ветки `andreichepurchenko/mia-84-...` в GitLab нет (проверено, `git fetch` не находит), и по source_branch тоже ничего не нашлось. Реальный код найден через поиск MR по тексту — **MR !294** «chore(content): импорт сгенерированных эталонных решений в задачи тренажёра» (ветка `chore/import-generated-steps`, автор и мерджер — Kirill Verzhitskii, смёржен 2026-07-28), в описании которого есть прямая ссылка на MIA-84.

## Реализация

**MR !294** (файлы: `api/src/services/content/generated-steps-import.service.ts`, `api/scripts/import-generated-steps.ts`, `api/scripts/data/generated-steps/{steps-grade-7,steps-grade-8,steps-no-source-key}.json`, `docs/superpowers/specs/2026-07-28-import-generated-steps-design.md`):

- Разовый скрипт-импортёр читает JSON-пакеты, адресует записи по `source_key` (595 записей) либо по `id` (10 старых записей без `source_key`), находит соответствующие `Assignment` (только `deletedAt: null`) и **пишет `steps` только туда, где они пусты** (`isEmptySteps`) — ручные эталоны (в частности, 25 задач диагностик/контрольных на локальной базе и часть эталонов на `test-1`, о которых говорит описание тикета) не затираются никогда, это явный гард, а не декорация.
- После записи инвалидируется кэш `entities:assignment:<id>` (задание кэшируется на сутки — без сброса проверка решения ещё день не видела бы новый эталон).
- Пишется файл отката (список затронутых `id`) и печатается готовая команда для отката — режим отката не встроен в сам скрипт, это одноразовая операция.
- `DRY_RUN=1` — только отчёт (найдено / к обновлению / пропущено как «уже есть шаги» / не найдено / с некорректной формой шага), без записи.
- Согласно дизайн-доку в этом же MR, реальный прогон (не сам мерж кода) — на прод/тест — выполнялся отдельно, по факту прогнан на обоих: 10 записей по `id` на проде не найдены (там этот контент не сеялся отдельно) — совпадает с формулировкой из последнего комментария Кирилла.
- 3 задачи, не прошедшие тройную проверку генерации (упомянуты автором как «пришлю списком отдельно»), в пакет не входят и в диапазон этого MR не включены — они out of scope самого дизайн-дока.

**Где смотреть в админке.** `/admin/content` → дерево класс → предмет → тема → вкладки «Тренажёр»/«Диагностика» (последняя различает обычную диагностику и «Контрольная работа» по `type: CONTROL_TEST`, т.е. привязка контрольной к теме в коде — это её собственный `topicId`, «карту» строить не из чего отдельного) → открыть задание → drawer `admin-task-edit-drawer.vue` → блок **«Эталонное решение»** (`AdminStepListEditor`, компонент `admin-step-list-editor.vue`). У каждого шага — поле «Выражение (LaTeX)» с живым KaTeX-превью (`MathFormula`, `error-fallback="неверный LaTeX"`) и поле «Описание». Если шагов нет — подпись «Пошаговое решение для сверки при проверке... Если шагов нет, проверка идёт без эталона» (плейсхолдер «Шагов нет»).

**Отдельная находка — правка `\cdot` (соответствует `legacy-latex-patch.md` из комментария автора).** Не входит в MR !294 и не привязана к MIA-84 явно, но по содержанию совпадает: **MR !308** «Нормализация отлепляет букву от макроса `\cdot`» (смёржен 2026-07-30, follow-up к !307/MIA-100) — `expression-normalizer.ts` теперь вставляет пробел после `\cdot` перед буквой (`\cdota` → `\cdot a`, тест `unglues a letter from the cdot macro`). Уже существующие сломанные данные (**3 шага на тесте и 3 на проде** — совпадает с «3 места» из `legacy-latex-patch.md`) поправлены отдельным прогоном `scripts/normalize-expressions.ts` напрямую в БД, вне диффа самого MR — то есть точный список конкретных заданий по коду не восстановить, нужно смотреть глазами.

## Чек-лист

**1. Блок «Эталонное решение» в админке**
- `/admin/content` → класс 7 или 8 → любая тема → вкладка «Тренажёр» → открыть задание → в drawer должен быть блок «Эталонное решение» со списком шагов (LaTeX-выражение + превью + описание).
- Пройтись по нескольким заданиям в разных темах 7 и 8 класса — раньше эталон был у 1 задачи из 698, теперь ожидается: 595 по `source_key` + 10 по `id` (последние — только на тестовом стенде, на проде таких заданий нет).
- Убедиться, что превью реально рендерит формулу, а не показывает `неверный LaTeX`.
- Задания, где эталон стоял вручную (диагностики/контрольные, отдельные задачи тренажёра на `test-1`) — не должны были измениться этим импортом; стоит выборочно свериться, что старый ручной эталон не перезаписан.

**2. Регресс LaTeX (`\cdot` + буква)**
- Проверить `/admin/latex` → вкладка «Задания» → фильтр «только с ошибками» на тесте и на проде — ожидается 0 ошибок рендера после патча (MR !308).
- Точечно поискать формулы вида `\cdot a`, `\cdot b` и т.п. среди эталонных решений/условий 7 класса (упоминается `control-work-7.json` в описании MR) — визуально формула должна рендериться слитно и правильно (`3b·a`, а не разрыв/ошибка).

**3. Сверка структуры («карта тем») — критерии приёмки автором ещё не зафиксированы, чек-лист общий**
- Для каждой темы 7-8 класса в `/admin/content` — убедиться, что есть хотя бы одно задание в тренажёре (`trainerCount > 0`).
- Проверить, что контрольные/диагностики реально привязаны к теме (не «висят» без `topicId`, задачи внутри не потеряны при просмотре по теме).
- Если автор приложит саму карту тем (гуглодок/таблица, в репозитории её нет) — сверить выборочно список тем 7-8 в админке с ней и с оглавлением учебников Макарычева; отметить дыры: тема без заданий, контрольная без темы, тема из учебника, которой нет в базе.

**4. Хвосты (зафиксировать, не блокируют приёмку)**
- 3 задачи, не прошедшие автоматическую проверку генерации, остались без эталонного решения — список этих 3 задач автор ещё не прислал («пришлю списком отдельно» в комментарии от 22.07); нужно уточнить, дописывать их вручную или оставить как есть.
- 10 старых заданий без `source_key` применены на тесте по `id`; на проде таких заданий нет — переносить нечего, это ожидаемое поведение, не баг.

**5. Явно вне скоупа**
- Фаза 2 (задачи 5-6 классов) в эту поставку не входит — код/данные для неё в репозитории отсутствуют, тестировать нечего. Начнётся отдельным заходом после ревью 7-8 Кириллом (это и подтверждено его последним комментарием).
- Карта тем как методический артефакт (структура тем 1 сентября — 30 мая) сама по себе не тестируется в коде/UI — это документ для сверки методистом, вне контура ручного QA продукта.

## Открытые вопросы

- Список 3 заданий без эталонного решения (не прошли автопроверку) — не прислан на момент написания заметки, у автора его нужно запросить отдельно.
- Точный список 3+3 заданий, задетых `\cdot`-патчем (MR !308) — фикс данных прогнан скриптом напрямую в БД, вне диффа коммита, поэтому конкретные `id`/`source_key` по коду не восстановить; для точечной регрессионной проверки эти задания нужно либо найти вручную через `/admin/latex`, либо запросить у автора MR !308.
- Сама карта тем (структура 1 сентября — 30 мая, темы → контрольные, сверка с доками Ксюши/Макарычевым/раскладкой Ромы) как артефакт не найдена ни в репозитории, ни в приложениях к тикету на момент заметки — вероятно, отдельный документ, который ещё предстоит получить для полноценной сверки по пункту 3 чек-листа.
