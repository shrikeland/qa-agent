## Контекст

Ветка `feat/admin-period-picker-rollout` в origin уже не существует (обычная зачистка после мержа) - код прочитан по merge-коммиту `5bd41c5d` (`Merge branch 'feat/admin-period-picker-rollout' into 'master'`, MR !454, родители `2a94d951`/`ed4678ab`), diff смотрен как `git diff 2a94d951 ed4678ab`.

Баг-репорт: на страницах обратной связи (3 страницы) период задавался парой нативных `<input type="date">` - системный календарь на английском, обе даты руками, без пресетов, без возможности поделиться ссылкой на выбранный период (диапазон нигде не кодировался в URL). Отдельно на странице «Челленджи» пояснение «Как это работает» рендерилось как обычная `AdminCard` в конце потока страницы (за пределами первого экрана - надо было проскроллить) и было завёрнуто в ту же ветку `v-else-if="data && today"`, что и весь контент, поэтому при ошибке загрузки (`loadError`) пропадало вместе с данными.

## Что изменено

**Общий пикер периода вынесен в переиспользуемый модуль:**
- `frontend/utils/admin-period.ts` (новый файл) - список пресетов `ADMIN_PERIODS` (`today`, `yesterday`, `7d`, `week`, `lastweek`, `30d`, `mtd`, `lastm`, `90d`, `qtd`, `ytd`, `all`), функция `adminPeriodRange(key, now)` (MSK-anchored границы) и `isAdminPeriodKey()` - type guard, отклоняющий значение, не входящее в список (написан и покрыт тестом специально для случая «URL правили руками»).
- `frontend/components/admin/admin-period-picker.vue` - логика диапазонов вынесена в `admin-period.ts`; добавлен **controlled-режим**: пропсы `period` (родитель владеет пресетом, обычно из URL) и `hidePresets` (список пресетов, которые на конкретной странице не предлагать); событие `update:period`. В controlled-режиме пикер не читает/не пишет `localStorage` (`onMounted` не восстанавливает сохранённое, если `props.period` задан) - владение полностью у родителя через URL.

**Все 3 страницы обратной связи переведены на пикер, значение пресета - в URL как `?period=<key>`:**
- `frontend/pages/admin/feedback/index.vue` (список ответов опроса) - `filters: ['period']`, `periodKey` по умолчанию `'all'`, `hidePresets` не задан (пресет «за всё время» доступен и является дефолтом).
- `frontend/pages/admin/feedback/engagement.vue` (отчёт активности) - `periodKey` по умолчанию `'7d'`, `:hide-presets="['all']"`.
- `frontend/pages/admin/feedback/topics.vue` (закрытые темы) - аналогично `engagement.vue`: дефолт `'7d'`, `hide-presets=['all']`.
- Во всех трёх убраны инлайновые `<input type="date">`, кнопка «Сбросить» и связанный CSS (`.fb-date`).

**Важный нюанс (асимметрия между страницами, не баг, а следствие разных бэкендов):** «за всё время» скрыт только на `engagement.vue` и `topics.vue`, потому что их данные идут через `feedbackReportAdminService` (`api/src/admin/feedback-report.admin.service.ts`), где `resolvePeriod()` уже **до** этой задачи содержал `MAX_PERIOD_DAYS = 92` и молча обрезает более длинный запрошенный диапазон (`if (span > MAX_PERIOD_DAYS) return { from: ..., to }` - без ошибки, без сигнала клиенту). Страница `feedback/index.vue` ходит в `topicFeedbackAdminService` (`api/src/admin/topic-feedback.admin.controller.ts`), у которого такого потолка нет (`from`/`to` необязательны, без верхней границы) - поэтому там «за всё время» оставлено и стоит дефолтом. Т.е. сам 92-дневный потолок в API не новый в этой задаче, новое - что фронт **больше не предлагает** пользователю период, который сервер тихо обрежет, ровно на тех страницах, где это релевантно.

**Челленджи (`frontend/pages/admin/challenges/index.vue`):** пикера периода здесь нет и не появилось - у страницы свой отдельный selector `AdminChipGroup` с трендом за 7/14/30 дней (`PERIODS`), эта задача его не трогает. Изменения тут только про модалку:
- Блок «Как это работает» вынесен из потока страницы в `<Teleport to="body">` с оверлеем `.ovl` (`display: grid; place-items: center`, `frontend/assets/scss/admin-overlays.scss`) - модалка теперь центрируется во весь viewport, а не рендерится инлайн в конце карточек.
- Teleport-блок стоит **вне** `<template v-if="loading"> / <AdminCard v-else-if="loadError"> / <template v-else-if="data && today">` цепочки (был раньше внутри последней ветки) - значит рендерится независимо от состояния загрузки, в том числе при `loadError`.
- Добавлена обработка `Escape` (`onKeydown`, слушатель вешается/снимается в `onMounted`/`onBeforeUnmount`) и закрытие по клику на подложку (`@mousedown.self="howOpen = false"`).
- Кнопка «Как это работает» (`AdminBtn icon="info"`) не менялась - как открывала `howOpen = true`, так и открывает; поменялось только куда и как рендерится содержимое.

## Тест-кейсы

### 1. Пикер с пресетами вместо нативных date-инпутов

| # | Страница | Ожидается |
|---|---|---|
| 1.1 | `/admin/feedback` (Опросы) | Кнопка-пикер периода вместо двух `<input type="date">`; список пресетов включает «За всё время», дефолт при чистом URL - «За всё время» |
| 1.2 | `/admin/feedback/engagement` (Активность) | Пикер периода; в списке пресетов **нет** «За всё время»; дефолт при чистом URL - «7 дней» |
| 1.3 | `/admin/feedback/topics` (Закрытые темы) | Пикер периода; «За всё время» отсутствует; дефолт - «7 дней» |
| 1.4 | `/admin/challenges` | Пикер периода **не ожидается** (не относится к этой задаче) - здесь на месте остаётся переключатель 7/14/30 дней; проверить, что он не сломан заодно |

Также на всех трёх страницах обратной связи: нативных `type="date"` полей в DOM быть не должно вообще (проверить через devtools/инспектор, что `.fb-date` не рендерится).

### 2. Пресет → URL → шаринг ссылки → тот же период в новой вкладке/инкогнито

Проверять отдельно на каждой из 3 страниц (index/engagement/topics):
1. Выбрать любой непустой пресет (например «30 дней») - в адресной строке должен появиться параметр `?period=30d` (ключ именно `period`, значение - код пресета из `ADMIN_PERIODS`, не текст лейбла).
2. Скопировать URL целиком, открыть в новой вкладке / в режиме инкогнито (без localStorage предыдущей сессии).
3. **Ожидается:** пикер на новой странице сразу показывает тот же пресет («30 дней»), а не дефолт страницы, и данные в таблице соответствуют этому диапазону (сверить хотя бы по количеству строк/датам).
4. Проверить также переход по кнопке «назад»/«вперёд» браузера между двумя разными пресетами на одной странице - пикер должен переключаться синхронно с URL (это покрывает `watch(() => props.period, ...)` в `admin-period-picker.vue`).
5. Отдельно стоит проверить **страницу `feedback/index.vue` с пресетом `all`**: URL `?period=all` - при открытии в новой вкладке должен подтянуть «За всё время», а не свалиться в дефолт по перезагрузке localStorage (тут пикер в controlled-режиме, localStorage не должен использоваться вообще).

### 3. Ограничение окна 92 днями (только engagement и topics)

- На `engagement.vue` и `topics.vue`: в списке пресетов физически нет ничего длиннее «90 дней» ни через UI, ни явно через ручной ввод (custom-режим сейчас выключен флагом `SHOW_CUSTOM_RANGE = false`, так что подобрать произвольный диапазon через UI нельзя вовсе - это ограничивает лучше, чем клэмп).
- Регрессионная проверка через URL (эмулирует «клэмп молча режет»): открыть `engagement.vue` или `topics.vue` с `?period=all` вручную вписанным в адресную строку. Так как `hidePresets` работает только на уровне UI-меню, а `periodKey` в коде читается как `(state.value.period as AdminPeriodKey | undefined) ?? '7d'` **без** проверки через `isAdminPeriodKey`, стоит проверить, что страница не падает и не показывает мусор - `adminPeriodRange('all')` в самой функции обработан (`case 'all': return { from: new Date(0), to: now }`), но дальше `mskDayKey(...)` уйдёт в `from`/`to` отчёта, а серверный `resolvePeriod` всё равно обрежет диапазон до `MAX_PERIOD_DAYS = 92` (`api/src/admin/feedback-report.admin.service.ts:12,30-44`) - значит даже если фронт случайно отправит слишком широкий диапазон, данные придут корректно урезанными, а не «за всё время». Это стоит зафиксировать как PASS/FAIL отдельно от UI-теста, так как это два независимых слоя защиты (frontend прячет пресет, backend всё равно клэмпит).
- Дополнительно (edge case, не описан в постановке, но стоит проверить на регресс): открыть любую из 3 страниц с заведомо мусорным `?period=xyz` в URL. `isAdminPeriodKey()` в коде существует и покрыт юнит-тестом именно на этот случай (`frontend/tests/admin-period.test.ts` - `'accepts presets and rejects a hand-edited URL'`), но **не вызывается** ни на одной из трёх страниц - `periodKey` получается прямым приведением типа (`as AdminPeriodKey`) без реальной проверки. Не факт, что это баг (возможно, `adminPeriodRange` тихо не упадёт), но стоит перепроверить руками, не белый ли экран/консольная ошибка при заведомо невалидном значении - если ловится, это находка для отдельного тикета.

### 4. «За всё время» отсутствует в списке пресетов - только там, где это применимо

- `engagement.vue`, `topics.vue`: пресета «За всё время» быть не должно (см. п.3 в «Что изменено» - там сервер клэмпит диапазон, поэтому предлагать его смысла нет).
- `feedback/index.vue`: «За всё время» **должен** присутствовать и быть дефолтом (там нет клэмпа на бэкенде) - если этот пресет вдруг тоже спрятан, это стоит трактовать как регрессию, а не как ожидаемое поведение по формулировке задачи «убрано на всех страницах» - по коду убрано целенаправленно только там, где сервер режет диапазон.

### 5. Модалка пояснения на Челленджах

1. Открыть `/admin/challenges`, дождаться загрузки данных, нажать «Как это работает».
2. **Ожидается:** модалка появляется по центру экрана (затемнённый оверлей на весь viewport, карточка по центру - не в конце страницы), закрывается по клику на подложку, по крестику и по `Escape`.
3. **Форсировать ошибку загрузки**, чтобы проверить независимость модалки от данных - варианты: заблокировать в devtools (Network → Block request URL) соответствующий admin-API запрос челленджей, либо временно посадить сеть в offline при заходе на страницу, либо (если стенд позволяет) протухший/невалидный админ-токен. После того как страница показывает карточку `AdminEmpty` с текстом «Не удалось загрузить данные» и кнопкой «Попробовать снова»:
   - Кнопка «Как это работает» в хедере всё ещё должна быть кликабельна и открывать ту же модалку с тем же текстом - **это ключевая проверка регрессии**, раньше блок был внутри `v-else-if="data && today"` и полностью пропадал вместе с ошибкой.
4. Дополнительно - при `loading` (скелетон, самое начало открытия страницы до ответа API) кнопка «Как это работает» тоже видна в хедере (хедер не завёрнут в `v-if="loading"`) - проверить, что клик по ней в этот момент тоже открывает модалку, а не игнорируется.
