**Важный нюанс (асимметрия между страницами, не баг, а следствие разных бэкендов):** «за всё время» скрыт только на `engagement.vue` и `topics.vue`, потому что их данные идут через `feedbackReportAdminService` (`api/src/admin/feedback-report.admin.service.ts`), где `resolvePeriod()` уже **до** этой задачи содержал `MAX_PERIOD_DAYS = 92` и молча обрезает более длинный запрошенный диапазон (`if (span > MAX_PERIOD_DAYS) return { from: ..., to }` - без ошибки, без сигнала клиенту). Страница `feedback/index.vue` ходит в `topicFeedbackAdminService` (`api/src/admin/topic-feedback.admin.controller.ts`), у которого такого потолка нет (`from`/`to` необязательны, без верхней границы) - поэтому там «за всё время» оставлено и стоит дефолтом. Т.е. сам 92-дневный потолок в API не новый в этой задаче, новое - что фронт **больше не предлагает** пользователю период, который сервер тихо обрежет, ровно на тех страницах, где это релевантно.

**Челленджи (`frontend/pages/admin/challenges/index.vue`):** пикера периода здесь нет и не появилось - у страницы свой отдельный selector `AdminChipGroup` с трендом за 7/14/30 дней (`PERIODS`), эта задача его не трогает. Изменения тут только про модалку:

## [БАГ, ПОДТВЕРЖДЁН ЧТЕНИЕМ КОДА] Дефолт периода "30 дней" на всех трёх страницах + необработанный TypeError на чистом URL

Найдено QA (комментарий Андрея Чепурченко, 2026-09-21, тестировался тот же merge-коммит
`5bd41c5d` / MR !454 на стенде test-1) и подтверждено чтением кода на этом же коммите.

**Прошло по коду и не относится к этому багу** (перепроверено, расходится с "Что не прошло" в
комментарии): пресеты «За всё время» скрыты только на `engagement.vue`/`topics.vue` (см. выше),
модалка «Как это работает» вынесена из потока и переживает `loadError`, ручной `?period=all` для
`engagement`-отчёта действительно клэмпится сервером до 92 дней (`resolvePeriod`,
`api/src/admin/feedback-report.admin.service.ts:12,30-44`) - это всё уже описано в «Что изменено»
и «Тест-кейсах» ниже и подтверждается заново.

**Корень обоих сбоев из "Не прошло" - один и тот же, и он не в `admin-period.ts`, а в чужом,
не тронутом этой задачей composable `frontend/composables/use-admin-list-query.ts` (последний раз
менялся в `b4462ab2`, до MIA-195):**

```ts
// use-admin-list-query.ts, state computed
const filters = {} as Record<F, string>;
for (const key of spec.filters ?? []) filters[key] = q(key) ?? '';
```

Когда в URL нет `?period=...`, `q('period')` возвращает `undefined`, и `?? ''` подставляет
**пустую строку**, а не `undefined`. Это старое, устоявшееся поведение composable (используется и
другими фильтрами) - само по себе не баг этой задачи. Баг в том, что все три страницы,
добавленные в MIA-195, предполагают ровно противоположный контракт - что отсутствующий фильтр
придёт как `undefined`:

```ts
// feedback/index.vue
const periodKey = computed(() => (state.value.period as AdminPeriodKey | undefined) ?? 'all');
// engagement.vue / topics.vue - идентично, только дефолт '7d'
const periodKey = computed(() => (state.value.period as AdminPeriodKey | undefined) ?? '7d');
```

`state.value.period` на самом деле `''` (пустая строка), а не `undefined` - `??` его не ловит
(`'' ?? 'all'` даёт `''`, не `'all'`). `periodKey.value` на чистом URL равен `''` на всех трёх
страницах, а не ожидаемому `'all'`/`'7d'`.

**Почему на экране именно "30 дней", а не пусто.** `''` уходит в пикер как `:period="periodKey"`.
В `admin-period-picker.vue`:

```ts
const period = ref<AdminPeriodKey>(props.period ?? '30d'); // '' ?? '30d' -> '' (та же ловушка)
...
const periodLabel = computed(() => {
  if (period.value === 'custom') return fmtRange(rangeFrom.value, rangeTo.value);
  return PRESETS.find((p) => p.v === period.value)?.label ?? '30 дней';
});
```

Ни один пресет из `ADMIN_PERIODS` не имеет `v === ''`, поэтому `PRESETS.find(...)` даёт
`undefined`, и срабатывает **второй**, уже пикеровский, жёстко зашитый фолбэк-лейбл `'30 дней'`
(он же дефолт `modelValue` пикера вне контролируемого режима) - он никак не связан с
page-specific дефолтом страницы. Отсюда одинаковая надпись «30 дней» сразу на всех трёх страницах
вместо «За всё время» / «7 дней» / «7 дней» - две независимые `??`-ловушки на пустой строке,
одна поверх другой.

**Почему `engagement.vue`/`topics.vue` дополнительно падают в `TypeError`, а `feedback/index.vue` -
нет.** `adminPeriodRange()` (`frontend/utils/admin-period.ts`) - `switch` по `AdminPeriodKey` без
`default`-ветки; при вызове с рантайм-значением `''`, которое не совпадает ни с одним `case`,
функция проваливается через весь `switch` и неявно возвращает `undefined` (TS это не ловит,
потому что `key` статически типизирован как `AdminPeriodKey`, а `''` попадает туда только через
рантайм-каст `as AdminPeriodKey` в `periodKey`).

- `feedback/index.vue`: `range = computed(() => periodKey.value === 'all' ? null : adminPeriodRange(periodKey.value))`.
  `'' !== 'all'`, поэтому вызывается `adminPeriodRange('')` → `range.value === undefined`. Дальше
  `range.value?.from.toISOString()` - опциональная цепочка на **первом** `?.` схлопывает весь
  доступ целиком, включая `.toISOString()`, так что здесь не падает: страница молча уходит в
  `listTopicFeedback({ from: undefined, to: undefined, ... })`. Внешне это выглядит только как
  неверный лейбл «30 дней» - без ошибки в консоли, что совпадает с наблюдением QA (FAIL только по
  лейблу на этой странице).
- `engagement.vue` / `topics.vue`: `range = computed(() => adminPeriodRange(periodKey.value))` -
  без проверки на `'all'`. `range.value === undefined`. А следом:
  ```ts
  const from = computed(() => mskDayKey(range.value.from));
  const to = computed(() => mskDayKey(range.value.to));
  ```
  (`frontend/pages/admin/feedback/engagement.vue:32-33`, дословно то же в `topics.vue:32-33`) -
  здесь `?.` уже нет, `range.value.from` на `undefined` кидает ровно
  `TypeError: Cannot read properties of undefined (reading 'from')`. Эти computed читаются внутри
  `loadItems()` при сборке параметров `listEngagementReport`/`listTopicCompletions` - отсюда
  ошибка в консоли именно с этими именами функций и отсутствие данных на странице, дословно как в
  комментарии QA.

**`isAdminPeriodKey()` и почему живой роут его не применяет.** Функция объявлена и экспортирована
из `frontend/utils/admin-period.ts` (`export const isAdminPeriodKey = (v: unknown): v is
AdminPeriodKey => typeof v === 'string' && (v === 'custom' || ADMIN_PERIODS.some((p) => p.v ===
v));`) и покрыта юнит-тестом (`frontend/tests/admin-period.test.ts`, `describe('isAdminPeriodKey'
...)`). Поиск по фронтенду (`grep -rn isAdminPeriodKey frontend`) показывает ровно два места, где
имя встречается: файл объявления и файл теста - **ни одна из трёх страниц и сам
`use-admin-list-query.ts` эту функцию не импортируют и не вызывают.** Вместо валидации везде стоит
непроверяющий рантайм-каст `state.value.period as AdminPeriodKey | undefined`. Это не просто
пропущенная защита от ручного мусора в URL (`?period=xyz` - тот же незамеченный `TypeError`, что
и наблюдение QA "не блокер"), а прямая причина обоих багов выше: если бы страницы делали
`isAdminPeriodKey(state.value.period) ? state.value.period : 'all'`/`'7d'` вместо `?? 'all'`/`??
'7d'`, пустая строка `''` не прошла бы проверку типа и корректно откатилась бы на page-specific
дефолт - тогда ни неверный лейбл, ни `TypeError` не воспроизводились бы.

**Итог:** это один и тот же класс бага (не примененная валидация `period` из URL/query), который
проявляется по-разному в зависимости от страницы: тихий неверный дефолт на `feedback/index.vue`,
падение с `TypeError` и незагружаемые данные на `engagement.vue`/`topics.vue`. Фикс на уровне
одной страницы (например, поправить только `feedback/index.vue`) не закроет остальные - нужно
либо чинить `useAdminListQuery` (отдавать `undefined`, а не `''`, для отсутствующего фильтра, с
проверкой, не сломает ли это другие фильтры, которые уже полагаются на `''`-семантику), либо
применить `isAdminPeriodKey()` в `periodKey` на каждой из трёх страниц.

### 3. Ограничение окна 92 днями (только engagement и topics)

- На `engagement.vue` и `topics.vue`: в списке пресетов физически нет ничего длиннее «90 дней» ни через UI, ни явно через ручной ввод (custom-режим сейчас выключен флагом `SHOW_CUSTOM_RANGE = false`, так что подобрать произвольный диапазon через UI нельзя вовсе - это ограничивает лучше, чем клэмп).
- Регрессионная проверка через URL (эмулирует «клэмп молча режет»): открыть `engagement.vue` или `topics.vue` с `?period=all` вручную вписанным в адресную строку. Так как `hidePresets` работает только на уровне UI-меню, а `periodKey` в коде читается как `(state.value.period as AdminPeriodKey | undefined) ?? '7d'` **без** проверки через `isAdminPeriodKey`, стоит проверить, что страница не падает и не показывает мусор - `adminPeriodRange('all')` в самой функции обработан (`case 'all': return { from: new Date(0), to: now }`), но дальше `mskDayKey(...)` уйдёт в `from`/`to` отчёта, а серверный `resolvePeriod` всё равно обрежет диапазон до `MAX_PERIOD_DAYS = 92` (`api/src/admin/feedback-report.admin.service.ts:12,30-44`) - значит даже если фронт случайно отправит слишком широкий диапазон, данные придут корректно урезанными, а не «за всё время». Это стоит зафиксировать как PASS/FAIL отдельно от UI-теста, так как это два независимых слоя защиты (frontend прячет пресет, backend всё равно клэмпит).
- [БАГ, ПОДТВЕРЖДЁН ЧТЕНИЕМ КОДА, см. раздел выше] Ручной мусорный `?period=xyz` (и, что важнее, **отсутствие** `period` в URL вовсе) на `engagement.vue`/`topics.vue` даёт не «белый экран», а конкретно `TypeError: Cannot read properties of undefined (reading 'from')` в консоли и незагруженные данные - подтверждено чтением кода: `isAdminPeriodKey()` существует и покрыт юнит-тестом (`frontend/tests/admin-period.test.ts` - `'accepts presets and rejects a hand-edited URL'`), но **не вызывается** ни на одной из трёх страниц - `periodKey` получается прямым приведением типа (`as AdminPeriodKey`) без реальной проверки, а `adminPeriodRange()` на невалидном ключе падает в `undefined` (нет `default`-ветки в `switch`). Подробный разбор и тест-кейсы на регресс - в новом разделе «[БАГ, ПОДТВЕРЖДЁН ЧТЕНИЕМ КОДА] Дефолт периода "30 дней"…» и в разделе 6 ниже.

### 6. [БАГ, ПОДТВЕРЖДЁН ЧТЕНИЕМ КОДА] Регресс дефолта периода на чистом URL (без `?period=`)

Повторяет шаги 1-2 из комментария QA (Андрей Чепурченко, 2026-09-21); баг подтверждён чтением
кода (см. разбор выше) - `state.value.period` приходит `''`, а не `undefined`, из-за чего

1. Открыть `/admin/feedback` в новой чистой сессии (инкогнито/без localStorage), без `?period=` в
