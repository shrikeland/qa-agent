## Контекст

Фундаментальный рефакторинг связи «Родитель → Ученик»: доступ к платному контенту раньше считался по последней подписке родителя (`subscriptionRepository.findLatestForParent`), из-за чего второй и последующие дети семьи занимались бесплатно на подписке первого. MR !381 (`feat/MIA-96-family-slots`, смержен в master `0164cd7a`) вводит сущность **оплаченного места** (`subscription_slot`): у обычной подписки одно место, у будущего семейного тарифа - пять (`Plan.slots`, семейный тариф - отдельная задача, здесь только фундамент). Доступ ученика теперь читается с его собственного места, а не с подписки семьи.

Заодно в этот же MR попала смежная фича - самостоятельная регистрация ученика: форма регистрации больше не спрашивает имя ребёнка (спрашивала и продолжает спрашивать email родителя + класс ученика), а второй и следующие дети заводятся из кабинета родителя и сами вводят класс на экране первого входа `/hello`.

**Важно про расхождение в комментариях разработчика.** Комментарий от 07.09 говорил «форма регистрации не спрашивает ни имя, ни класс - остаётся только email». Комментарий PM от 16.09 попросил вернуть класс на форму («оставляем email и выбор класса, как сейчас»). Финальный комментарий от 18.09 и код это подтверждают: **регистрация (`frontend/pages/register.vue`) спрашивает email родителя и класс ученика (кнопки 5-9), имя не спрашивает никогда** - ни на форме, ни на экране `/hello`. Имя ребёнка вообще не собирается формами MIA-96: его пишет сама Мия в диалоге (это уже было в master до этой задачи, `registerBodySchema.student.name` в схеме остался, но необязателен и никаким UI не заполняется). Разница между «первым» и «вторым+» ребёнком не в имени, а в классе: первый ребёнок получает класс от родителя на регистрации и попадает сразу в кабинет; второй и следующие создаются с `grade = null` и обязаны выбрать класс сами на `/hello`, прежде чем кабинет откроется. Раздел «Реализация» ниже подтверждает это построчно по коду.

Платёжный путь для второго и последующих детей **не входит в этот релиз** (`out of scope`, подтверждено кодом): весь биллинг (`parent-billing.service.ts`) работает через `subscriptionRepository.findLatestForParent`, `PaymentLink` не знает про `studentId`, новая подписка на второго ребёнка не создаётся.

## Реализация

Код прочитан целиком на текущем HEAD (`master`, коммит `0164cd7a`).

### Модель данных - `subscription_slot`

`api/prisma/migrations/20260907120000_subscription_slot/migration.sql`:
- Новая таблица `subscription_slot` (`id`, `subscription_id`, `student_id` nullable, `occupied_at`, `released_at`, `created_at`), индексы `(student_id, released_at)` и `(subscription_id)` (строки 3-16).
- `subscription.student_id` становится nullable (строка 22) - legacy-поле, не дропается, служит источником для бэкфилла и путём отката.
- `plan.slots INTEGER DEFAULT 1` (строка 24).
- **Бэкфилл вшит прямо в миграцию** (строки 29-32): `INSERT INTO subscription_slot ... SELECT ... FROM subscription WHERE student_id IS NOT NULL` - по месту на каждую существующую подписку. Комментарий в файле объясняет почему: «доступ ученика читается из мест, стек, стартовавший до ручного скрипта, отправил бы каждого платящего ребёнка во фримиум». Ручной скрипт `api/scripts/backfill-subscription-slots.ts` остаётся страховкой: идемпотентен (`where: { studentId: { not: null }, slots: { none: {} } }`), поддерживает `DRY_RUN=1` (строка 3), при сухом прогоне только логирует количество без записи (строки 11-12).

### Доступ - `AccessService.subscriptionForAccess` (`api/src/services/access.service.ts:70-84`)

```ts
private async subscriptionForAccess(user): Promise<Subscription | null> {
  if (user.role === Role.PARENT) {
    const subs = (await subscriptionSlotRepository.listForParent(user.id)).map((slot) => slot.subscription);
    const byRecency = [...subs].sort((a, b) => b.expiresAt.getTime() - a.expiresAt.getTime());
    return byRecency.find((sub) => isAllowed(sub)) ?? byRecency[0] ?? null;
  }
  if (user.role !== Role.STUDENT) return null;
  const slot = await subscriptionSlotRepository.findActiveForStudent(user.id);
  return slot?.subscription ?? null;
}
```
Ключевое изменение: **студент** проверяется только по своему месту (`findActiveForStudent`, репозиторий `api/src/repositories/subscription-slot.repository.ts:14-20`, `where: { studentId, releasedAt: null }`, сортировка `orderBy: { subscription: { expiresAt: 'desc' } }` - при двух живых местах, например апгрейд на семейный тариф, побеждает то, у которого позже `expiresAt`). **Родитель** по-прежнему проверяется по любому живому месту семьи (`listForParent`), с fallback на самую свежую просроченную подписку, если живых нет (чтобы `/me` не сказал «никогда не подписывались» семье, у которой доступ просто кончился). `isAllowed()` (строки 50-65) не тронута - вся семантика статусов (`charging` держит доступ, `cancelled` доживает до `expiresAt`) осталась прежней, поменялась только подписка, которую к ней подставляют.

Регрессия, которую чинит этот MR, зафиксирована тестами `api/src/services/__tests__/family-access.scenario.test.ts` (сценарий «до бэкфилла» и «после») и `api/src/services/__tests__/access.slot.test.ts`: раньше `accessService.canAccessTrainer(SECOND_CHILD)` отвечал `full` на подписке первого ребёнка, теперь - `freemium`, пока у второго нет своего места (`family-access.scenario.test.ts:84-92`, комментарий в тесте: «Before this change the same call answered "full": every extra child in a paying family studied for free»).

### Регистрация - `frontend/pages/register.vue`

Форма (строки 349-368) содержит **только** email родителя (строки 310-321) и выбор класса кнопками `SUPPORTED_GRADES` (5-9, `frontend/constants/grades.ts:1`) - поля имени ребёнка в разметке нет вообще. Валидация в сторе `frontend/stores/auth-modal.ts:85-96`: `isRegisterEmailValid` (regex `EMAIL_REGEX`, строка 72), `isRegisterGradeValid` (`isSupportedGrade`), `isRegisterValid` = оба плюс чекбокс `consentPdn`. `registerPayload` (строки 98-113) отправляет на бэкенд `{ parent: { email }, student: { grade } }` - имя не передаётся никогда, поле `RegisterFormData.student` с комментарием «Имя ребёнка форма не спрашивает - его собирает Мия в чате» (строка 9).

Бэкенд: `api/src/routes/auth.routes.ts` - `registerBodySchema.student` (строки 55-64) требует только `grade` (`required: ['grade']`), `name`/`email` остались в схеме как необязательные (для инвайт-флоу и обратной совместимости), но UI их не шлёт. `registerHandler` (`api/src/controllers/auth.controller.ts:60-197`) передаёт тело в `authService.registerParentWithChild` без изменений в логике этой части - создаёт родителя и ребёнка с `grade` из формы и `name: null` (`api/src/services/auth.service.ts:114-121`).

### Первый вход и `/hello` - гейт по классу, а не по имени

`api/src/routes/auth.routes.ts:27-36` - `studentProfileBodySchema` для `PATCH /me/profile` требует **только `grade`** (`required: ['grade']`, `minimum: 5, maximum: 9`), с комментарием в коде: «Класс - единственное, чего может не быть у ребёнка, заведённого из кабинета родителя: имя собирает Мия в чате». Обработчик `updateStudentProfileHandler` (`api/src/controllers/auth.controller.ts:471-489`) проверяет роль (`403`, если не `STUDENT`) и пишет `grade` без проверки его текущего значения - **см. «Открытые вопросы» про повторный вызов**.

`frontend/pages/hello.vue` (полностью прочитан) - экран «Привет! Я Мия» спрашивает **только класс** (строки 41-67, кнопки `SUPPORTED_GRADES`), поля имени нет. По сабмиту (`submit()`, строки 26-38): `PATCH /me/profile` c `{ grade }`, событие аналитики `STUDENT_PROFILE_COMPLETED` с параметром `{ grade }` (строка 32), затем `userStore.loadMe()` и редирект на `ROUTES.dashboard`. Состояния: `idle` / `saving` (кнопка «Сохраняем…», задизейблена) / `error` (текст «Не получилось сохранить. Попробуй ещё раз.», строка 69) - retry просто нажатием кнопки снова, отдельного действия retry нет.

Гейт нельзя обойти прямой ссылкой - тройная защита:
1. `frontend/pages/ref/[token].vue:33-37` - после активации ссылки: `needsProfile = me?.role === 'STUDENT' && !me.grade`, редирект на `ROUTES.hello` вместо `ROUTES.dashboard`.
2. `frontend/middleware/auth.global.ts:16-18,78,96,127` - глобальный роут-гвард: `studentNeedsProfile(user)` (`role === STUDENT && !user.grade`) редиректит на `/hello` с **любого** URL кабинета, если текущий путь не `/hello` - проверяется во всех трёх ветках входа (уже залогинен, `/me` успешен, хендшейк по фингерпринту). Комментарий в коде явно фиксирует, что имя в гейт не входит: «The name is not part of the gate: Mia asks for it in the chat».
3. Бэкенд деградирует сам: `meHandler` (`api/src/controllers/auth.controller.ts:335-361`) - при `role !== STUDENT || grade === null` отдаёт **тот же урезанный ответ, что и родителю** (без дашборда, тем, диагностик), то есть даже если фронтовый гейт как-то обойти через прямой вызов API, дашборд-данные всё равно не приходят.

Важно: `middleware/auth.global.ts:29` - `if (import.meta.server) return;` - гейт `/hello` целиком клиентский (as и весь этот middleware), реальная защита от «увидеть чужие данные» лежит на пункте 3 (`meHandler`), а не на редиректе.

### Кабинет родителя - «Добавить ребёнка» (`api/src/services/family.service.ts`, `frontend/components/parent/parent-billing.vue`)

`FamilyService.addChild` (строки 19-42, полностью прочитан):
```ts
async addChild(parentId: string): Promise<AddChildResult> {
  const seats = await subscriptionSlotRepository.listForParent(parentId);
  const free = seats.find((seat) => seat.studentId === null && isAllowed(seat.subscription));
  const parent = await userRepository.get(parentId);
  const child = await userRepository.createStudent({ name: null, email: null, grade: null, parentId, abVariant: parent.abVariant ?? 'a' });
  if (free) await subscriptionSlotRepository.occupy(free.id, child.id);
  const token = generateAccessToken();
  await accessLinkRepository.create({ studentId: child.id, token, expiresAt: ... });
  return { childId: child.id, linkToken: token, seated: !!free };
}
```
Свободное место ищется **только среди мест с `isAllowed(seat.subscription) === true`** - место на просроченной/`freemium` подписке не считается свободным (тест `family.service.test.ts:62-71`: «a free seat on a drained subscription is not a seat»). Число детей у семьи ничем не ограничено (нет проверки лимита в коде и тестах) - можно добавлять сколько угодно детей без мест, все сверх лимита сядут на фримиум.

Роут: `POST /parent/children` → `parentAddChildHandler` (`api/src/controllers/parent-cabinet.controller.ts:30-31`) → `familyService.addChild(request.currentUser!.id)`. Защищено `requireAuth` + `requireParent` хуками на весь `parentRoutes` (`api/src/routes/parent.routes.ts:51-52`).

UI (`frontend/components/parent/parent-billing.vue`, раздел «Дети и места», строки 515-564):
- Список мест `billing.seats` (строки 518-525): `seatLabel()` (строки 89-90) - `childName ?? 'Без имени'` для занятого места, `'Свободное место'` для пустого; статус занятого места - через тот же `STATUS_LABEL` словарь, что и у обычной подписки (строки 118-129), у свободного - фиксированный текст «Оплачено, ребёнок не заведён».
- Кнопка «Добавить ребёнка» (строки 532-539), состояния `idle`/`sending` (текст «Добавляем…», задизейблена)/`error` (текст «Не получилось добавить ребёнка — попробуйте ещё раз.», строка 541-543, retry - повторный клик).
- После успеха (строки 545-563): если `addedChild.seated` - зелёная ветка «Ребёнок добавлен на свободное оплаченное место»; если нет - «Свободного оплаченного места нет, поэтому пока он занимается бесплатно — оплатите место» + ссылка **«Оплатить место» → `ROUTES.selectTariff`**. Ссылку можно только **скопировать** (`copyChildLink`, строки 79-85, `navigator.clipboard.writeText`, текст кнопки меняется на «Ссылка скопирована»); отправки на почту из кабинета нет (в исходном описании задачи и в спеке упоминалась опция «отправить на почту», в реализации её нет - только копирование).
- `PARENT_CHILD_ADDED` событие аналитики шлётся сразу после успешного добавления с параметром `{ seated: addedChild.value.seated }` (строка 73) - **до** повторного запроса `/parent/billing` (`refresh()`, строка 74), то есть событие уходит независимо от результата обновления списка.

**Важно про кнопку «Оплатить место».** Она ведёт на `/select-tariff`, но весь код `parent-billing.service.ts` (`changePlan`, `setRenewal`, `startCardBinding`, `summary` - все читают `subscriptionRepository.findLatestForParent(parentId)`, строки 166, 261, 306, 381) работает с **последней подпиской семьи**, а не с новой подпиской под конкретного ребёнка. `PaymentLink`/`activateFromPaymentLink` не несёт `studentId` (подтверждено в `docs/superpowers/specs/2026-09-07-family-slots-design.md:149-162`, раздел «Что из R1 осталось несделанным»). Практический эффект: если у семьи уже есть активная подписка на первого ребёнка, клик «Оплатить место» для второго уводит на экран смены/продления **этой же** подписки, а не на покупку отдельного места для нового ребёнка - см. тест-кейс №9.

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Happy path: регистрация первого ребёнка

1. Открыть `/register`. На форме - поле email родителя и ряд кнопок классов 5-9. Убедиться, что поля «Имя ребёнка» и «Телефон» на форме нет.
2. Ввести валидный email, выбрать класс (например, 7), отметить оба чекбокса согласий, нажать «Открыть доступ».
3. Ожидаемо: письмо с приветствием отправлено (или хотя бы не блокирует ответ, если SMTP недоступен на стенде - `SuccessModal` всё равно должен показать ссылку доступа для копирования).
4. Открыть письмо - в нём ровно две ссылки: «Открыть тренажёр» (персональная ссылка ребёнка) и «Войти в кабинет родителя» (со сноской «действует неделю»). Имени ребёнка нигде в письме нет.
5. Открыть персональную детскую ссылку в новом браузере/инкогнито - сразу дашборд ученика (`/dashboard`), экран `/hello` **не показывается**, потому что класс уже указан на форме регистрации.
6. Проверить `grade` ученика в кабинете/на `/me` - соответствует выбранному на форме.

### 2. [ПРИОРИТЕТ] Добавление второго ребёнка без свободного места (freemium)

1. Зарегистрироваться как в кейсе 1 без выбора тарифа (обычная freemium-регистрация).
2. Войти в кабинет родителя по ссылке из письма, перейти в раздел «Подписка»/«Дети и места».
3. Убедиться, что список показывает одно место, занятое первым ребёнком, статус - «Бесплатный доступ» (соответствует `SUBSCRIPTION_STATUS.FREEMIUM` из `STATUS_LABEL`).
4. Нажать «Добавить ребёнка». Кнопка должна на время запроса показать «Добавляем…» и быть недоступной для повторного клика.
5. После ответа - блок с сообщением **«Ребёнок добавлен. Свободного оплаченного места нет, поэтому пока он занимается бесплатно — оплатите место, чтобы открыть полный доступ»**, ссылка на копирование и кнопка «Оплатить место».
6. Скопировать ссылку кнопкой «Скопировать ссылку» - текст должен смениться на «Ссылка скопирована».
7. Открыть скопированную ссылку в отдельном инкогнито-окне (эмулируя устройство ребёнка) - должен открыться экран **«Привет! Я Мия»** с выбором класса, БЕЗ поля имени.
8. Попробовать обойти экран прямым переходом на `/dashboard` или `/app/...` тем же ребёнком, пока класс не выбран - должен произойти редирект обратно на `/hello` (проверить на нескольких целевых URL кабинета).
9. Выбрать класс на `/hello`, нажать «Начать» - должен произойти `PATCH /me/profile`, редирект на дашборд ученика. Дашборд должен открыться в свежевыбранном классе/предметах.
10. Вернуться в кабинет родителя и обновить страницу - второй ребёнок в списке «Дети и места» теперь должен отображаться с реальным именем (если Мия уже собрала его в чате) или «Без имени», статус места по-прежнему «Бесплатный доступ».

## Аналитика/API

- `student_profile_completed` (`frontend/pages/hello.vue:32`) - шлётся с параметром `{ grade }` при успешном сохранении профиля на `/hello`.
- `parent_child_added` (`frontend/components/parent/parent-billing.vue:73`) - шлётся с параметром `{ seated: boolean }` сразу после успешного `POST /parent/children`, до повторного `refresh()` списка мест.
- Оба события заведены в `frontend/constants/analytics-events.ts:415-420` и `api/src/constants/analytics-events.ts` (с `// label:` комментариями для Метрики), но **цели в Яндекс.Метрике на них не заведены** - лимит целей исчерпан на обоих счётчиках (тест: 207, прод: 208), API Метрики отвечает `limit_exceeded`. Событие в GA/дата-слое фиксируется, но конверсию по нему в отчётах Метрики не будет видно до чистки старых целей. Это факт, зафиксированный разработчиком, не блокер для функционального тестирования самих событий (их можно проверить через сетевую панель/дебаггер аналитики, не дожидаясь целей в Метрике).

## Открытые вопросы

1. **Расхождение по регистрационной форме между раундами комментариев - разрешено кодом.** Комментарий от 07.09 говорил об удалении и имени, и класса с формы; PM (16.09) попросил вернуть класс; финальный код (18.09) подтверждает: email + класс на форме, имя нигде не спрашивается (ни на форме, ни на `/hello` - имя вообще не в скоупе MIA-96, это делает Мия в чате). Тестировать регистрацию нужно по факту кода: **email + класс на форме, класс на `/hello` для детей без класса**, а не по более раннему тексту тикета/комментария 07.09.
2. **`PATCH /me/profile` не защищён от повторного вызова уже онбоарженным учеником** (см. тест-кейс №16) - технически это открытая лазейка к «смене класса учеником», которая по тикету вынесена в отдельную задачу и явно в out of scope MIA-96. Через обычный UI это недостижимо (после выбора класса `/hello` больше не открывается middleware'ом), но прямой вызов API это не проверяет. Стоит уточнить у разработчика/продукта, осознанный ли это временный пробел (раз функциональность «смены класса» всё равно скоро появится отдельной задачей) или нужен фикс до релиза.
3. **Метод `SubscriptionSlotRepository.release()` реализован и покрыт тестами, но никуда не подключён** - ни API-роута, ни кнопки «отвязать ребёнка от места» в этом MR нет, хотя спека (`docs/superpowers/specs/2026-09-07-family-slots-design.md:99`) описывает эту возможность как часть выката. Стоит уточнить: это сознательно отложено на следующий MR, или это пропущенный кусок функциональности R1.
4. **Кнопка «Оплатить место» для второго ребёнка ведёт на общий `/select-tariff`, который работает с последней подпиской семьи, а не создаёт подписку под конкретного ребёнка** - подтверждено кодом и явно описано в спеке как незакрытый функциональный пробел («Что из R1 осталось несделанным»). На тесте стоит зафиксировать фактическое поведение (что произойдёт при клике) и убедиться, что оно не портит доступ первого ребёнка - см. тест-кейс №9. Оплата места второму+ ребёнку официально в этот релиз не входит, но кнопка на UI уже присутствует и ведёт куда-то - нужно решить, достаточно ли текущего поведения для релиза или кнопку/сообщение об оплате стоит скрыть/переформулировать до того, как платёжный путь реально появится.
5. **Опция «отправить ссылку ребёнка на почту» из спеки не реализована** - в UI кабинета есть только «Скопировать ссылку». Не блокер, но стоит подтвердить, что это осознанное урезание скоупа, а не забытая часть.
6. **Цели `student_profile_completed` и `parent_child_added` не заведены в Яндекс.Метрике** из-за исчерпанного лимита целей на обоих счётчиках (тест 207, прод 208) - до чистки старых целей эти события не попадут в отчёты по конверсиям, хотя сами события в коде отправляются корректно.
7. **За скоупом MIA-96 (подтверждено спекой и описанием задачи), не проверять как баги:** оплата места второму и последующим детям (нужен отдельный платёжный путь с `PaymentLink.studentId`); семейный тариф на 5 мест (фундамент `plan.slots` готов, ни одного оффера с `slots > 1` пока не существует - протестировать создание такого оффера через админку невозможно, пока продукт его не заведёт); смена класса учеником из его собственного кабинета (кроме первого выбора на `/hello`, который не является «сменой» в смысле тикета); пропорциональные доплаты/апгрейды; единый платёж за несколько обычных подписок.

## Обновление 2026-09-21 - баг: `slots` не сохраняется при создании/оффере тарифа через админ-API (гипотеза QA подтверждена по коду)

**QA-прогон 18.09 (Andrei Chepurchenko, test-1.mia360.ru) дал FAIL**: `POST /api/admin/plans` с `{ ..., slots: 2 }` отвечает `200`, но и в самом ответе, и в последующем `GET /api/admin/plans` сохраняется `slots: 1`; `PATCH /api/admin/plans/:id` с `slots: 2` - та же картина. QA исключил хранилище (GET отдаёт поле), кэш (перепроверено отдельным GET) и платёжку (тестовый оффер был `invite_only`) и предположил разрыв в DTO/маппинге админского каталога - `slots` доходит до HTTP-обработчика, но не передаётся в create/update `Plan`.

**Гипотеза подтверждена по коду, причём разрыв глубже, чем просто «не передаётся в Prisma» - поля `slots` нет вообще ни на одном слое админского каталога, кроме самой БД и `catalog.service.ts` (публичного чтения оффера):**

- `api/src/services/catalog-admin.service.ts:57-63` - интерфейс `CreatePlanInput`, который принимает `createPlanHandler`, объявляет только `slug`, `price`, `currency?`, `durationDays`, `isRecurring?`. **Поля `slots` в типе нет.** `UpdatePlanInput` (строка 64) - это `Partial<Omit<CreatePlanInput, 'slug'>>`, то есть тоже без `slots`, наследует пробел автоматически.
- `createPlan()` (строки 114-121) вызывает `planRepository.create({ slug, price, currency: input.currency ?? 'RUB', durationDays, isRecurring: input.isRecurring ?? true })` - `input.slots` нигде не читается и не пробрасывается, даже если фактически пришёл в теле запроса. То же для `updatePlan()` (строки 125-131) - явный список полей `price`/`currency`/`durationDays`/`isRecurring`, `slots` среди них нет.
- Валидации схемой на этих роутах нет вообще: `api/src/admin/admin.routes.ts:148-149` - `fastify.post('/plans', createPlanHandler)` и `fastify.patch('/plans/:id', updatePlanHandler)` зарегистрированы **без** третьего аргумента `{ schema }` (сравнить с соседними роутами, например `parent.routes.ts:110`, где `schema: { body: ... }` есть). Значит `slots: 2` в теле запроса **не срезается** Fastify'вым `removeAdditional` (это другой механизм, в этом файле в принципе не участвует) - тело долетает до `createPlanHandler`/`req.body` целиком, включая `slots`, но `catalogAdminService.createPlan`/`updatePlan` просто никогда не смотрят на это поле TypeScript-интерфейса, потому что оно не объявлено в `CreatePlanInput`/`UpdatePlanInput`. Итог - значение молча теряется на уровне сервисного маппинга, ответ `200`, а `planRepository.create()` пишет `Plan` без `slots` в `data`, из-за чего Prisma/Postgres подставляет `DEFAULT 1`, заданный миграцией `plan.slots INTEGER DEFAULT 1` (см. основной раздел заметки, `migration.sql:24`) - это и есть `slots: 1`, который потом отдаёт `GET`.
- Проблема **не ограничена бэкендом** - на фронтенде тот же пробел: `frontend/composables/use-admin-api.ts:898-905`, интерфейс `AdminPlan` (тип и для чтения, и для `createPlan`/`updatePlan` payload'а, строки 1760-1766) тоже не содержит `slots`. То есть в админ-панели (`frontend/pages/admin/catalog/index.vue` и её драфт `catalog-draft.ts`) в принципе **нет поля ввода количества мест** при создании/редактировании тарифа - функциональность создания семейного тарифа не реализована сквозным образом ни на одном слое (UI → composable-тип → бэкенд-DTO → сервис), а не просто "потеряна по пути". QA нашёл этот пробел через прямой вызов API именно потому, что через UI поле `slots` вообще не с чем было бы отправить.

**Вывод:** гипотеза QA о разрыве в DTO/маппинге - верна и точно локализована (`api/src/services/catalog-admin.service.ts:57-64` - типы, `114-131` - методы `createPlan`/`updatePlan`). Дополнительно к его находке: это не единичный забытый проброс поля, а отсутствие функциональности целиком, вплоть до UI - семейный тариф на 5 мест по-прежнему нельзя ни создать, ни отредактировать (см. также исходный пункт 7 «Открытые вопросы» этой заметки - «фундамент plan.slots готов, оффера нет», сейчас понятно ещё и почему: инструмента для создания такого оффера нет).

**Практическое следствие для регресса.** Приоритетный acceptance-путь MIA-96 «seated: true, второй ребёнок сразу получает полный доступ на свободном месте семейного тарифа» (тест-кейс №3 основного раздела заметки) **остаётся заблокированным** - пока в БД нет ни одного `Plan` с `slots >= 2` (и создать его через админку/API нельзя, пока не будет пофикшен этот пробел и не появится UI-поле), проверить этот путь можно только прямой записью в БД в обход API/UI, что и было указано как ограничение в тест-кейсе №3 ещё 18.09.
