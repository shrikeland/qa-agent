> **Приоритет этого раунда.** Прошлый QA-прогон (07.09) дал FAIL по acceptance «строка контрольной ведёт в контрольную»: открытие начатой контрольной из колонки роняет экран в `ReferenceError: Cannot access '…' before initialization`. QA предположил причину в `useCabinetThreads({ topicName: computed(() => session.topicName.value) })`, созданном до `const session = useCabinetSession(...)`. Код это подтверждает буквально — `session` действительно объявлен строкой позже своих использователей, — но конкретно этот путь безопасен: все обращения к `session` в файле обёрнуты в `computed(...)`, которые Vue не считает сразу. Я прошёл по всей цепочке и нашёл нужную для регресс-теста точку, где TDZ действительно стреляет — не через `session`, а через `activeTest`, и именно на маршруте `/app/control-test`. Подробности и точный тест-кейс — в «Реализации» и в тест-кейсе №0.

## Контекст

Задача (label нет, priority Medium): в боковой колонке кабинета показывался только тренажёр — вид `домашка` был заведён в `SessionKind` с акцентным цветом, но строка для него никогда не собиралась, а контрольная в колонке не появлялась вовсе, потому что `fromRoute()` умел читать только `route.params.topicId`, которого нет ни у `/app/homework`, ни у `/app/control-test`.

Сделано в трёх коммитах на `master`, двумя волнами:

1. **Домашка** — MR !369, коммиты `239c8a7d` (адрес `/app/homework/<id>`) и `059fab1d` (строка домашки в колонке + `GET /homework/open`).
2. **Контрольная** — MR !373, коммит `b0c07068` (своя строка и адрес `/app/control-test?diagnosticId=<id>`), затем ревью нашло три дыры и MR !374, коммит `49a0b29b` их закрыл (сданный вариант, `utm_*`, повторяющийся `?diagnosticId=`).

Ветки волн (`feat/MIA-145-homework-in-sessions`, `fix/MIA-145-control-test-row-review`) уже смержены и удалены — ожидаемая уборка, ссылки ниже даны на коммиты в `origin/master`.

## Реализация

### Домашка в колонке (MR !369)

**Адрес домашки, `239c8a7d`.** Раньше выбор шёл только на клиенте: `pickOpenable()` (`frontend/components/homework/use-homework-data.ts:90-92`) брал первую незакрытую домашку из списка, в URL жил только `?step=`. Теперь страница переехала с `frontend/pages/app/homework.vue` на `frontend/pages/app/homework/[[id]].vue` (необязательный параметр пути, один файл вместо дублирования раздела), а `use-homework.ts` завёл двух писателей адреса:
- `syncUrl()` (`use-homework.ts:116-125`) переписывает `?step=` через `router.push`/`replace`, всегда указывая путь целиком (`{ path, query }`), а не только query — иначе писатель, читающий `route.path` асинхронно устаревшим, откатывал только что проставленный id;
- `stampHomeworkPath()` (`use-homework.ts:132-144`) следует за `data.state.currentId` (`watch(() => data.state.currentId, stampHomeworkPath)`, строка 163) и всегда делает `replace`, не `push` — иначе «Назад» выглядело бы залипшим.

Обратное чтение — `applyUrlId()`/`homeworkFromUrl()` (`hw-types.ts:198-200`): id из адреса используется, только если он есть в списке домашек ученика, иначе — тихий фолбэк на `currentId` (тот же `pickOpenable`). Чужой или протухший id в адресе не даёт ошибку — просто открывается штатная домашка, а адрес перезаписывается.

**Строка в колонке, `059fab1d`.** Три новых куска:
- `GET /homework/open` (`api/src/controllers/homework.controller.ts:39-49`, роут в `api/src/routes/homework.routes.ts:47`) → `homeworkService.openSummariesForUser()` (`api/src/services/homework/homework.service.ts:160-190`). Отдаёт только счётчики (`toOpenSummary`, `homework.view.ts:107-137`) — id, `createdAt`, `activeAt`, `tasks`, `picked`, `solved`, без страниц/заданий/попыток. `activeAt` — максимум таймстемпов по домашке, страницам, заданиям и сабмишенам, а не `updatedAt` (Prisma двигает его только при записи в саму домашку, отметка задачи его не трогает). Решённость — тем же `readSolveFacts()` (`api/src/services/rating-award.service.ts:74`), на котором считает рейтинг; решёнными считаются только отмеченные (`picked`) задачи. Максимум `MAX_ACTIVE_HOMEWORKS = 3` (`homework.service.ts:19`), фильтр по активным статусам `DRAFT`/`IN_PROGRESS`. Без доступа (`accessService.canAccessTrainer` не разрешает) — пустой массив `[]`, не 403: сайдбар дёргает эндпоинт с любого экрана, и всплывающий пейволл на непрошенный список был бы паразитным; замок в колонке в принципе вешается только по теме, у домашки нет своего.
- Сборщик строк `toHomeworkRows()` (`frontend/cabinet/screen/sessions.ts:105-131`) рядом с уже существовавшим `toSessionRows()` (тот же файл, строки 60-98) — у домашки нет темы и ML-блоков, свой прогресс («осталось N заданий» / «все задания решены» / «задания ещё не отмечены», не «N из M» — это намеренно, см. ниже) и свой маршрут (`ROUTES.homeworkOne(id)`). Обе выдачи мёржатся и сортируются вместе по `at` (таймстемп активности) в `paused` computed внутри `useCabinetThreads` (`use-threads.ts:243-262`), общий потолок `ROWS_SHOWN = 8` считается по объединённому списку, а не по каждому источнику отдельно.
- `useCabinetThreads` (`frontend/cabinet/chat/use-threads.ts`) получил параллельный цикл загрузки для домашек: `reloadHomework()` (строки 88-105) вызывается через `watch(() => [!!userStore.getUser, isHomeworkPath(route.path)], ..., { immediate: true })` (строки 148-155) — перечитывает список при **выходе** из раздела домашек (пока ученик там, счётчики меняет он сам, и список, дёрнутый на каждое движение, спорил бы с экраном).

Прогресс домашки нарочно не имеет форму «N из M»: `count` в `use-threads.ts` (строка ~280) регуляркой достаёт это из `progress` строки, чтобы нарисовать полосу задачи над доской — если бы строка домашки тоже говорила «2 из 4», полоса перетёрла бы номер задачи тренажёра своим. QA это проверил (кейс из отчёта) и подтвердил: полоса остаётся от тренажёра.

### Контрольная в колонке (MR !373 + фикс MR !374)

**Первая волна, `b0c07068`.** До этого коммита `fromRoute()` в `use-threads.ts` читал только `route.params.topicId` — контрольная, у которой параметр в query (`?diagnosticId=`), не давала строки вовсе, а строка из карты (`map-row-vals.ts`, `onAction: () => input.onAskControlTest(...)`) создавалась без `route`, поэтому клик по ней уводил в общий чат через дефолт в `goTo()` (`sess?.route ?? VIEW_ROUTES.chat`).

Добавлено:
- `controlTestSession()` (`frontend/cabinet/screen/control-test.ts:141-172`) — берёт работу по `diagnosticId` из адреса, безымянный адрес шёл через `retakeControlWork` (это изменилось во второй волне, см. ниже);
- `fromControlTestRoute()` в `use-threads.ts` — новая ветка `fromRoute()`: `route.params.topicId` отсутствует → если путь `ROUTES.appControlTest`, зовёт `fromControlTestRoute()`;
- маршрут строки — `ROUTES.appControlTestStart(diagnosticId)` = `/app/control-test?diagnosticId=<id>` — вариант держится в адресе, а не выбирается заново сервером на каждый заход;
- `goTo()` на этот момент сравнивал `route.fullPath !== to` целиком (это будет исправлено ниже — контрольная в query ломала это сравнение для себя же).

**Ревью нашло три дыры, закрыто MR !374, `49a0b29b`:**
1. **Сданный вариант давал строку «идёт».** На адресе сданной работы сервер отвечает `redirectToResults` — экран должен показать разбор, а не работу, а строка «идёт» вдобавок продолжала подсовывать эту работу в главную кнопку кабинета (`nextStep`/`running`) до конца визита. Фикс — `handedIn()` (`control-test.ts:140-141`, `work.status === 'scored' && work.total != null && work.total > 0`) и условие `if (!work || (handedIn(work) && !work.openSessionId)) return null;` (строка 165) в `controlTestSession()`. Заодно безымянный адрес переключили с `retakeControlWork` на `nextControlWork` (`control-test.ts:164`) — у `retakeControlWork` есть намеренный фолбэк на сданную работу для плитки «пройти ещё раз», это не подходит строке идущего занятия.
2. **`utm_*` перетирался навигацией.** `goTo()` сравнивал `route.fullPath !== to` целиком — переход по ссылке из письма с `?utm_source=...` в тренажёр переписывался бы навигацией на адрес без метки. Теперь (`use-threads.ts:161-168`) сравнивается `route.path !== target.path` плюс только те query-параметры, которые называет сам адрес занятия (`Object.entries(target.query).every(([k, v]) => route.query[k] === v)`) — чужой хвост адреса не трогается.
3. **Повторённый `?diagnosticId=a&diagnosticId=b`.** vue-router отдаёt повтор ключа массивом; `controlTestSession` ждал строку, `find()` не находил работу, строка молча пропадала. Фикс в `fromControlTestRoute()` (`use-threads.ts:196-201`): `const asked = route.query.diagnosticId; ... Array.isArray(asked) ? asked[0] : asked`. **Важный нюанс для теста:** берётся буквально первый элемент массива, а не «первый существующий/валидный» — если первым идёт несуществующий id, строка исчезнет, даже если второй валиден. См. тест-кейс №6 ниже.

### Находка QA (07.09): TDZ при открытии контрольной — где на самом деле рвётся, а не где предположил QA

Прочитан целиком `frontend/cabinet/shell/use-cabinet.ts` (1300+ строк). QA верно опознал класс бага (TDZ, `const`, обращение до объявления) и верно нашёл, что `session` объявлен позже своих потребителей — это факт:

```ts
// use-cabinet.ts:133-138
const threads = useCabinetThreads({
  topicId: routeTopicId,
  topicName: computed(() => session.topicName.value),   // session ещё не объявлен
  access: accessOf,
  onNavigate: () => setDrawer(false),
});
...
// use-cabinet.ts:172
const session = useCabinetSession(routeTopicId);
```

Но это (как и такое же обращение в `useCabinetTheory` на строках 144-148 и в `useCabinetCurator` на 163-171) **не падает на практике**: `computed(() => session.topicName.value)` — ленивый геттер, тело стрелочной функции не выполняется в момент вызова `computed()`, а только при первом чтении `.value`, которое случится не раньше конца `setup()` (когда `session` уже присвоен). Я проверил все три модуля (`use-threads.ts`, `use-theory.ts`, `use-curator.ts`) на наличие `watch(...)`/`watchEffect(...)`, которые могли бы прочитать эти computed'ы немедленно — таких нет. Так что путь, который назвал QA, сейчас безопасен, хоть и хрупок (см. «Открытые вопросы»).

**Реальная точка разрыва — соседняя, тем же классом бага, но через `activeTest`:**

```ts
// use-cabinet.ts:154-159 — создаётся ДО объявления activeTest
const board = useCabinetBoard({
  sessionBusy: computed(() => isTrainer.value && (session.typing.value || session.locked.value)),
  shouldClose: computed(() => isTest.value && boardShouldClose(activeTest.value.phase.value)),
});
...
// use-cabinet.ts:216-222 — activeTest объявлен на 60+ строк позже
const diagnostic = useCabinetDiagnostic(isDiagnostic, { kind: 'diagnostic' });
const controlTest = useCabinetDiagnostic(isControlTest, { kind: 'control_test', diagnosticId: controlTestId });
const activeTest = computed(() => (isControlTest.value ? controlTest : diagnostic));
```

Ключевое отличие от `session`: `useCabinetBoard()` (`frontend/cabinet/board/use-board.ts:78-80`) сразу внутри себя делает

```ts
watch(input.shouldClose, (over) => {
  if (over && open.value) closeBoard();
});
```

Vue при вызове `watch(source, cb)` **всегда** читает `source.value` один раз синхронно в момент установки — чтобы получить `oldValue` для будущего сравнения, — независимо от `immediate`. Это происходит внутри вызова `useCabinetBoard({...})` на строке 154, то есть до строки 222. Чтение `input.shouldClose.value` исполняет тело `computed(() => isTest.value && boardShouldClose(activeTest.value.phase.value))`.

`isTest` (`frontend/cabinet/shell/where.ts:82-84`) — `computed(() => isDiagnostic.value || isControlTest.value)`, а `isControlTest` — `computed(() => route.path === ROUTES.appControlTest && !!userStore.getUser)`. То есть `isTest.value === true` **именно и только** на `/app/diagnostic` и `/app/control-test` — и как раз тогда короткое замыкание `isTest.value &&` не срабатывает, выражение доходит до `activeTest.value`, а `activeTest` в этот момент в TDZ → `ReferenceError: Cannot access 'activeTest' before initialization`.

На тренажёре и в домашке `isTest.value === false` — `&&` останавливается раньше, `activeTest` не читается, крэша нет. Это точно совпадает с наблюдением QA: тренажёр и чат работали в той же сессии браузера, падало только открытие контрольной. Диагностика (`/app/diagnostic`) должна падать тем же образом — в отчёте QA её не проверяли (шли через уже пройденную диагностику к контрольной), стоит перепроверить и её.

**Итог: причина названа QA верно по классу ошибки (TDZ в `use-cabinet.ts`) и почти верно по месту (та же функция, соседний блок), но не тот идентификатор и не тот механизм.** Не `session`/`useCabinetThreads`, а `activeTest`, срабатывающий через устройство `watch()` внутри `useCabinetBoard()`. Для разработчика это разные фиксы: `session` можно оставить как есть (или поднять исполнение выше просто для читаемости), а `board`/`shouldClose` требует либо переставить объявление `activeTest`/`diagnostic`/`controlTest` выше строки 154, либо не передавать в `useCabinetBoard` computed, зависящий от ещё не объявленной переменной.

## Тест-кейсы

### 0. Приоритет — регресс-тест TDZ-блокера (открытие контрольной из колонки)

Тот же сценарий, что дал FAIL 07.09, теперь с точным прицелом на найденный код:

1. Учеником с активной подпиской пройти диагностику полностью, начать контрольную (`?diagnosticId=<id>` в адресе, работа не сдана).
2. Уйти на дашборд/в тренажёр — строка контрольной должна появиться в «Идёт сейчас».
3. Кликнуть по строке контрольной (переход на `/app/control-test?diagnosticId=<id>`) **или** перезагрузить страницу прямо на этом адресе.
4. **Ожидалось (до фикса разработчика падало):** открывается контрольная с текущим заданием, без ошибки.
5. Если всё ещё падает — открыть консоль браузера и свериться с `ReferenceError`: если в тексте ошибки фигурирует `activeTest` — это точно описанный выше баг (`use-cabinet.ts:154-159` + `use-board.ts:78`), не тот, что предполагался в прошлом отчёте. Если текст ошибки называет другой идентификатор — версия выше требует пересмотра, стоит приложить точный текст ошибки и его нужно будет сверить заново с actual TDZ-местом в коде (в файле могло появиться что-то новое).
6. Дополнительно повторить тот же сценарий на `/app/diagnostic` (не пройденной ещё диагностике) — тот же `isTest.value === true`, тот же риск TDZ, в прошлом отчёте не проверялось.

### 1. Домашка — появление, открытие, адрес, перезагрузка

1. Иметь ручную домашку с хотя бы одним отмеченным, не решённым заданием (как в прошлом раунде).
2. Уйти с раздела домашки на дашборд/в другой раздел — строка домашки видна в «Продолжить» (или в «Идёт сейчас», если домашка сейчас открыта), с подписью «осталось N заданий».
3. Клик по строке — переход на `/app/homework/<id>`, тот же экран, на котором остановился ученик.
4. Перезагрузить страницу на `/app/homework/<id>` — открывается та же домашка (тот же id в адресе, не «первая незакрытая» по `pickOpenable`).
5. Отметить все задания и сдать домашку (статус уходит из активных) — строка должна пропасть из колонки на следующей перезагрузке списка (при выходе из раздела).

### 2. Домашка — граница в 3 штуки и мёрж с темами

1. Завести три активные домашки (лимит `MAX_ACTIVE_HOMEWORKS = 3`, попытка четвёртой должна давать `409 active_limit`, это существующее поведение, не в скоупе, но полезно для сетапа).
2. Поработать также в 2-3 темах тренажёра, чтобы они попали в «Продолжить».
3. Проверить, что список «Продолжить» — единый, отсортированный по времени последней активности (`activeAt`/`lastActivityAt`), а не «сначала все домашки, потом все темы» и не два отдельных блока.
4. С учётом `ROWS_SHOWN = 8` (общий потолок) — если тем+домашек больше восьми, обрезаются самые старые по активности, независимо от вида.

### 3. Контрольная — сданный вариант не даёт строку «идёт» (регресс из MR !374)

1. Полностью сдать контрольную (получить оценку — `status: 'scored'`, `total > 0`).
2. Вернуться на её адрес `/app/control-test?diagnosticId=<id>` вручную или через старую ссылку/закладку.
3. Строки «идёт» в колонке быть не должно (ни на этом экране, ни на других — `controlTestSession()` возвращает `null` для сданного варианта без `openSessionId`).
4. Открыть безымянный `/app/control-test` без query — должна выбраться следующая доступная работа через `nextControlWork` (незавершённая, если есть, иначе первая непройденная), а не через `retakeControlWork` (который мог бы вернуть уже сданную).

### 4. Сохранение `utm_*` и прочих чужих query-параметров при навигации по строке

1. Открыть тему тренажёра ссылкой с `?utm_source=qa&utm_campaign=x`.
2. Кликнуть по своей же строке в колонке (или дать её мёржиться заново через `goTo`) — метки должны остаться в адресе, не быть переписаны навигацией на «чистый» путь.
3. То же для контрольной — открыть `/app/control-test?diagnosticId=<id>&utm_source=qa`, убедиться, что переход по собственной строке не теряет `utm_source` (сравнение в `goTo` теперь по пути + именованным занятием параметрам, посторонний хвост не трогается).

### 5. Повторяющийся `?diagnosticId=` — оба порядка

vue-router отдаёт повтор ключа массивом, код берёт `asked[0]` без всякой проверки валидности — это asymmetричный кейс, стоит проверить оба порядка отдельно:

1. `?diagnosticId=<валидный>&diagnosticId=<несуществующий>` — валидный первый → строка находится и работает (это уже проверялось в прошлом раунде QA, прошло).
2. `?diagnosticId=<несуществующий>&diagnosticId=<валидный>` — несуществующий первый → **по коду строка должна пропасть/не найтись**, даже несмотря на то, что второй id валиден. Если строка всё же находит валидную работу — значит, поведение изменилось относительно прочитанного кода, стоит отдельно разобраться, что теперь выбирает `asked[0]` или откуда берётся id.

### 6. Пустая колонка без доступа — freemium/expired

1. Freemium-ученик (без подписки) — `GET /api/homework/open` даёt `200 []`, колонка не показывает домашку и не роняет 403 (уже проверено QA 07.09, включить в регресс).
2. Ученик с истёкшей подпиской (`expired`, был paid ранее) — то же самое: пустой список, не ошибка. Отдельно не проверялось в прошлом раунде — стоит покрыть, `canAccessTrainer` должен трактовать `expired` так же, как `freemium`, для этого списка.
3. Прямой заход на `/app/homework` под freemium/expired — редиректит на `?paywall=homework` (гейт на уровне страницы, `frontend/pages/app/homework/[[id]].vue`, отдельно от пустого списка в колонке).

### 7. Полоса задачи над доской — номер только у тренажёра

1. Открыть строку домашки или контрольной из колонки.
2. Полоса над доской не должна показывать «Задача N из M» — эта форма прогресса намеренно не используется в `progress` домашки/контрольной (`toHomeworkRows`/`controlTestSession`), чтобы не перетереть номер задачи тренажёра, если он там уже шёл.
3. Открыть тренажёр — полоса с номером задачи тренажёра работает как раньше (регресс).

### 8. Устаревший/чужой id в адресе домашки

1. Взять `/app/homework/<id>` с id несуществующей или уже удалённой домашки (или скопировать чужой id, если есть второй аккаунт).
2. Ожидается: не ошибка и не пустой экран — тихий фолбэк на `pickOpenable()` (первая незакрытая домашка ученика, либо первая по списку), адрес при этом должен переписаться на настоящий id (`stampHomeworkPath`).
3. Не покрыто прошлым QA-раундом кросс-аккаунтная проверка (см. «Открытые вопросы») — если есть возможность завести второго платного ученика, стоит явно попробовать открыть чужой id и убедиться, что `getForUser(id, userId)` на бэкенде не отдаёт чужую домашку (это существующая защита, не новая в этой задаче, но полезно перепроверить в связке с новым способом попадать на этот адрес).

## Аналитика/API

- `GET /api/homework/open` (`api/src/routes/homework.routes.ts:47`) — сводка для колонки; 401 без cookie, `200 []` без доступа, иначе до 3 объектов `{ id, createdAt, activeAt, tasks, picked, solved }`, без текстов заданий/страниц/сабмишенов (уже проверено QA).
- `ANALYTICS_EVENTS.HOMEWORK_OPEN` (`homework_open`, `frontend/constants/analytics-events.ts:389`) — трекается в `use-homework.ts` при каждом входе в раздел домашки (`watch(() => isHomeworkPath(route.path), ...)`), **не различает** источник входа (клик по строке в колонке vs кнопка внутри раздела vs прямая ссылка) — если нужна отдельная метрика «открыто из колонки», её сейчас нет.
- `ANALYTICS_EVENTS.CONTROL_TEST_START`/`CONTROL_TEST_TASK_VIEW`/... (`control_test_start` и т.д., `frontend/constants/analytics-events.ts:103-113`) — существующие события работы с контрольной, тоже не различают, что открыло экран: строка колонки, плитка `controlTestTile` или прямая ссылка.
- Никакого нового события конкретно на «клик по строке колонки» (ни для домашки, ни для контрольной) в этой задаче не заведено — если акцептанс подразумевал отдельную аналитику по колонке, её нет, но в тексте задачи такого требования не было.

## Открытые вопросы

- **[Блокер] TDZ при открытии контрольной из колонки.** См. тест-кейс №0 — приоритетный ретест. Код: `frontend/cabinet/shell/use-cabinet.ts:154-159` (`shouldClose: computed(() => isTest.value && boardShouldClose(activeTest.value.phase.value))`, передаётся в `useCabinetBoard`) при `activeTest` (`const`, строка 222) ещё не объявленном на момент вызова, реально читается сразу через `watch(input.shouldClose, ...)` в `frontend/cabinet/board/use-board.ts:78`. Проявляется только когда `isTest.value === true`, то есть на `/app/control-test` и, предположительно, на `/app/diagnostic` (это не проверялось в прошлом раунде — стоит покрыть).
- **Структурная хрупкость того же класса — `session` используется в `use-cabinet.ts` до объявления (строки 133-171), а объявлен на строке 172.** Сейчас безопасно, потому что все обращения — внутри ленивых `computed(...)`, и ни один модуль (`use-threads.ts`, `use-theory.ts`, `use-curator.ts`) не читает их немедленно через `watch`/`watchEffect`. Но это легко сломать будущей правкой (как и сломалось с `activeTest`) — стоит держать в уме при следующих изменениях этого файла, а лучше поднять объявление `session` (и, желательно, `diagnostic`/`controlTest`/`activeTest`) выше их первых потребителей, а не полагаться на то, что никто больше не добавит eager-чтение.
- **Диагностика по-прежнему не появляется в колонке** — это осознанно вне скоупа задачи (прямо сказано автором в первом комментарии), фиксируем как ожидаемое, не баг.
- **Кросс-пользовательская проверка ownership домашки не проводилась** предыдущим QA-раундом (не было второго платного ученика) — само по себе не новое в этой задаче (`getForUser(id, userId)` в `homework.service.ts` существовал и раньше), но раз задача добавила новый способ попадать на `/app/homework/<id>` по прямому адресу, стоит явно перепроверить хотя бы один раз с двумя аккаунтами.
- **Юнит-тесты в Docker не прогонялись** прошлым раундом (демон Docker был недоступен в среде QA) — если это по-прежнему так, стоит попытаться прогнать хотя бы `frontend/tests/cabinet-control-test.test.ts`, `frontend/tests/cabinet-sessions.test.ts`, `api/src/services/homework/__tests__/homework-open-summary.test.ts` локально без Docker, если возможно, поскольку они как раз покрывают код из этой задачи (но не покрывают найденный TDZ-баг — это интеграционная ошибка инициализации Vue-композабла, юнит-тест на чистых функциях её не поймает).
- **Нюанс дублей `?diagnosticId=`** (тест-кейс №5): код берёт `asked[0]` без проверки валидности, а не «первый существующий id» — при обратном порядке параметров (невалидный первый) строка, скорее всего, пропадёт даже если второй id рабочий. Формально это не противоречит акцептансу (задача просила не терять строку из-за дубля, а не разруливать порядок «умно»), но стоит явно зафиксировать результат на обоих порядках, чтобы не спутать с регрессом при следующей проверке.
