## Реализация

Источник формул — `docs/admin-dashboard-metrics.md` (полностью, прочитан целиком), плюс код:
`api/src/admin/dashboard-metrics.service.ts` (SQL), `api/src/admin/dashboard-metrics.ts`
(производные показатели, юнит-тесты), `api/src/admin/dashboard-funnel.ts` (воронка),
`api/src/admin/admin.service.ts#getDashboard` (сборка ответа), `frontend/pages/admin/index.vue`.

### Оперативные метрики (блок 1)

| Метрика | Формула (кратко) |
|---|---|
| MRR | сумма месячных стоимостей **платных** подписок на конец периода; годовая/недельная приводится к 30 дням через `COALESCE(renewal_duration_days, длительность тарифа оффера, 30)` — не через `expires_at - started_at` (продление сдвигает `expires_at` на месте) |
| Регистрации | родители с `created_at` в периоде |
| Новые подписки | подписки, чей **первый** успешный платёж попал в период |
| Продления / отвал платящих | продления — платежи в периоде, не первые для подписки; отвал платящих — отдельная карточка MIA-193, см. `notes/MIA-193.md` |
| Активные подписки | платные на конец периода; бесплатные (живой триал без единой оплаты) — отдельной строкой «+N бесплатных» под значением |
| ARPU | MRR / число платных подписок |

### Продукт и клиенты (блок 2)

| Метрика | Формула |
|---|---|
| LT | среднее `LEAST(COALESCE(cancelled_at, expires_at), to) - started_at` по подпискам, по которым были деньги; живые входят **текущим возрастом** (цензура, не выброс — иначе LT занижался бы тем сильнее, чем моложе продукт) |
| LTV | (вся выручка до `to` − AI-косты до `to` по курсу `USD_RUB_RATE`) / все подписки, что когда-либо платили |
| CAC | расходы на привлечение за период / новые платящие подписки; **пока расходов нет — прочерк, не ноль** (`cacOf`: `p.marketingSpend > 0 ? ratio(...) : null`) |
| AI-косты | `SUM(ai_usage.cost_usd_micros)` за период, в рублях по курсу env `USD_RUB_RATE` (по умолчанию 90) и подписью в $ |
| Retention | платные подписки на конец периода / все, что когда-либо платили (кумулятивно, не за период — знаменатель того требует) |
| CSI | среднее `topic_feedback.satisfaction` за период, шкала 1-10, рядом число оценок |

### Операционка (блок 3)

13-16: уникальные активные ученики за период по Диагностике/Тренажёру/Контрольным/Домашке
(начатые сессии своего типа для диагностики/контрольных, отправленные решения для
тренажёра/домашки — «начал и бросил» в счёт не идёт). 17: `SUM(engagement_time.seconds)` за
период / число уникальных активных (13-16 объединением). 18: `SUM(rating_award.points)` за
период / то же число активных.

### Воронка — финальное соответствие кодов (после !457 + !458)

`api/src/admin/dashboard-funnel.ts`:

| Код | Метка на дашборде | База (знаменатель) |
|---|---|---|
| С0 | Открыли форму | новые посетители |
| С0-1 | Зарегистрировались | открыли форму |
| С1 | Зарегистрировались | новые посетители |
| С1.1 | **Начали диагностику** | регистрации |
| С1.2 | Начали тренажёр | регистрации |
| С1.3 | Начали домашку | регистрации |
| С2 | Оплатили | регистрации |

С1.1 = «начали диагностику» от регистраций — дважды переезжало (в исходной задаче и в !457 было
«завершили диагностику»), окончательно исправлено только в !458. Шаг «открыт пейволл» ушёл из
воронки полностью (в файле недельного отчёта его нет); в файле `docs/admin-dashboard-metrics.md`
написано, что он «остаётся в стадиях пользователя (`funnel-stage.ts`), по которым фильтруется
список людей» — **при чтении `api/src/admin/funnel-stage.ts` это не подтвердилось**: там линейная
цепочка `registered → student_added → diagnostic_started → diagnostic_completed → training →
paid`, и комментарий в коде прямо говорит «Opening the paywall is intentionally NOT a stage: nearly
every user hits it, so it masked how far the family actually got» — то есть пейволла там нет и,
похоже, никогда не было в этом виде. Это расхождение документации с кодом, не баг воронки —
отметил как открытый вопрос, стоит сверить с автором при следующем контакте, но на прохождение
тест-кейсов не влияет.

Числа берутся у `unitEconomicsService.periodTotals()` (когорта: leads/diagStarted/trainerStarted/
homeworkStarted/paid) и `metrikaStatService.getPeriodTraffic()` (newVisitors/formOpened — источник
внешний, Метрика; при её отсутствии эти два шага показывают прочерк, остальные пять — нет,
см. юнит-тест `dashboard-funnel.test.ts` «без данных Метрики гаснут только шаги входа»). Границы
округлены до суток МСК (`admin.service.ts` — `funnelFrom`/`funnelTo` через `mskDayKey`). С2 делит
оплаты на **семьи**, а не подписки — у семьи с двумя оплатами доля может выйти больше 100%, это
осознанно (сходится с файлом отчёта, не с «чистой» математикой). Плашка сверху воронки —
`funnelConversion` — это всегда С2 (регистрация → оплата), доли остальных шагов **нельзя**
перемножать (разные знаменатели, задокументировано явно).

### Лента событий

Сведена в UI дашборда к трём видам: `GET /api/admin/activity` вызывается с
`kind: 'reg,pay,sub_cancelled'` (жёстко зашито в `frontend/pages/admin/index.vue`, не настраивается
пользователем на этой странице). Полный список видов событий (`student_added`, `consent`,
`link_issued`, `diag_*`, `trainer_started`, `trial_started`, `problem_report`) в SQL-объединении
`activityUnionSql()` остался — они просто не запрашиваются лентой дашборда; страница «События»
(`/admin/activity`) видит их все. `sub_cancelled` — новый вид, раньше отмена подписки не попадала
в ленту вовсе. У `pay` появился признак `extra.isRenewal` (продление показывается отдельным
текстом от первой оплаты) — логика в `activity-event-text.ts`/`activity-event-visuals.ts`
(вынесены в общие файлы специально, чтобы копии на дашборде и на странице событий не расходились:
в комментарии прямо сказано «отмена подписки рисовалась там оплатой, а тут регистрацией» — тот
баг уже устранён вынесением в общий модуль).

### CAC / расходы на привлечение

Таблица `marketing_spend` (миграция `20260917120000_marketing_spend`): день, канал, сумма (целые
рубли), комментарий. `GET/POST /api/admin/marketing-spend`, `DELETE /api/admin/marketing-spend/:id`
(`api/src/admin/marketing-spend.admin.controller.ts`, весь файл прочитан). Валидация POST: день —
`YYYY-MM-DD` и должен существовать как дата (`2026-02-31` отклоняется), сумма — `0 < amount ≤
2_000_000_000` (целое число, `MAX_SPEND` — защита от переполнения INTEGER-колонки), канал —
непустая строка после trim. DELETE — `deleteMany` (не `delete`), поэтому повторное удаление той же
записи отдаёт 404, а не 500. Список ограничен 200 строками (`PAGE_SIZE`), но сумма (`total`)
считается по всему диапазону агрегатом, не по возвращённой странице — в ответе есть `hasMore`.
Кнопка «Расходы на привлечение» открывает `admin-marketing-spend-drawer.vue`: кнопка «Добавить»
задизейблена, если канал пуст или сумма `<= 0`/не задана.

### AB-варианты

Убраны с дашборда визуально, но `abBreakdown` по-прежнему считается и возвращается в
`GET /api/admin/dashboard` (`admin.service.ts#getDashboard`, поле `abBreakdown`) — просто не
рендерится на `/admin/index.vue`. Отдельная страница `/admin/experiments` с z-тестом закрыта — но
это сделано другим тикетом (MIA-177, упомянуто как контекст, не проверяется здесь).

### Известное ограничение — cancelled_at как состояние, не событие

Задокументировано в `docs/admin-dashboard-metrics.md` дословно: «Отмены считаются по полю
`subscription.cancelled_at`, а это состояние, а не событие. Если родитель снова включит
автопродление, поле обнуляется — отмена исчезает и из счётчика за уже закрытый период, и из
ленты». Важно: это ограничение относится к **отдельному** полю `cancelled_at`, использованному в
ленте событий (`sub_cancelled`) — карточка «Отвал платящих» из MIA-193 считается **по-другому**
(по факту неоплаченного продления, окно 3 дня), см. `notes/MIA-193.md`. Не перепутать при
тестировании: у ленты и у новой карточки KPI разная механика для формально похожих вещей.

### `/api/admin/funnel` как отдельная ручка — не существует, это ожидаемо

В `admin.routes.ts` зарегистрирован только `GET /dashboard` (`fastify.get('/dashboard',
getDashboardHandler)`) — отдельного `/funnel` роута нет. Воронка приходит полем `funnel` внутри
ответа `/api/admin/dashboard`. QA 17.09 зафиксировал 404 на прямом обращении к `/api/admin/funnel`
как «не блокер» — подтверждено чтением кода: маршрута действительно нет и не планировалось, это
не регресс. Отдельная страница воронки/экспериментов выведена из навигации ранее, в MIA-177.

### 1. [ПРИОРИТЕТ] Воронка — перепроверить коды С0…С2 после !457 + !458

Дважды путали С1.1 (сначала в исходной реализации, затем в !457 «начали диагностику» снова
съехало на «завершили») — это главный кандидат на регресс в этом раунде.

1. Открыть `/admin` (дашборд), задать период с достаточным объёмом данных.
2. Свериться построчно с таблицей кодов из «Реализации» выше: С0 = открыли форму / новые
   посетители, С0-1 = регистрации / открыли форму, С1 = регистрации / новые посетители,
   **С1.1 = начали диагностику / регистрации (не «завершили»!)**, С1.2 = начали тренажёр /
   регистрации, С1.3 = начали домашку / регистрации, С2 = оплатили / регистрации.
3. В каждой строке воронки должны быть видны числитель, знаменатель и доля в формате вида
   «184 из 1180 · новые посетители» (текст знаменателя — `baseLabel` из `dashboard-funnel.ts`).
4. Плашка сверху воронки (`funnelConversion`) должна показывать именно С2 (регистрация → оплата) —
   не произведение долей остальных шагов.
5. При недоступности данных Метрики (или на окружении, где `getPeriodTraffic` вернул `null`) —
   С0 и С0-1 (и С1, так как использует `newVisitors`) должны показывать прочерк («нет данных»),
   при этом С1.1-С1.3 и С2 (не зависящие от Метрики) продолжают считаться нормально — не путать
   с общим падением воронки.
6. Сверить числа воронки с суммой соответствующих недель отчёта «Аналитика → Unit-экономика» за
   тот же период — построчно, а не приблизительно (в комментарии автора после исправления это
   уже делалось вручную: 219 регистраций, 36 диагностик, 106 тренажёров, 3 домашки, 1 оплата —
   ориентир для похожего прогона, не эталон для точного совпадения на текущих данных стенда).
7. Если объём живого трафика на стенде маленький (регистрации заводятся скриптами, посетителей
   Метрики почти нет) — доли типа С0-1/С1 могут показывать сотни/тысячи процентов. Это не баг:
   числитель и знаменатель не связаны отношением «подмножество», при малом знаменателе доля
   легко перевешивает 100%. Не заводить как дефект без проверки на более широком трафике.

### 3. Happy path по неизменной части (регресс блоков 1-3 после !445/!457/!458)

1. MRR, ARPU, LT, LTV, CAC, Retention, CSI, активные ученики по 4 поверхностям, время/рейтинг на
   активного — визуально присутствуют, значения не `NaN`/`undefined`, дельты к предыдущему периоду
   показываются только когда есть база сравнения (prev != 0/null).
2. Активные подписки — показывается только платное число крупным шрифтом, «+N бесплатных» — мелким
   текстом под значением, не смешано в одну цифру.
3. AI-косты — сумма в рублях + подпись «$X по курсу Y ₽» — курс должен совпадать с
   `USD_RUB_RATE` окружения (спросить у DevOps/проверить `.env`, если нужно точное значение).
4. AB-варианты не видны на `/admin` (ни блока, ни переключателя) — но это не регресс `/admin/
   experiments`, если он всё ещё редиректит/404 — это отдельный тикет MIA-177, не перепроверять
   здесь глубоко, только зафиксировать факт отсутствия AB-блока на самом дашборде.

### 4. Период — пресеты «эта неделя» / «прошлая неделя» / «за всё время»

1. Переключить пресет на «Эта неделя» — период должен начинаться с понедельника текущей недели
   по МСК (как в недельном отчёте), не с воскресенья и не с произвольного дня.
2. «Прошлая неделя» — с понедельника по воскресенье предыдущей недели.
3. «За всё время» — API не даёт периода без даты; на бэке нижняя граница поднимается до первой
   регистрации, но не дальше трёх лет назад (защита от 20 000 строк дневной серии) — если на
   стенде есть данные старше трёх лет, стоит проверить, что более старые дни не потеряны молча
   без предупреждения (либо это ожидаемо и не баг — сверить с docs).
4. Смена периода не должна требовать перезагрузки страницы — пересчёт на лету.

### 5. Открытые пункты этого раунда (перенесены из «не покрыто» QA 17.09 + новые из чтения кода)
