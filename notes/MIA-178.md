### Общая архитектура ответа `GET /admin/dashboard?from&to`

Метрики делятся на «за интервал» (`periodMetrics(from, to)` - платежи, отмены, косты, активность) и «на момент» (`snapshotMetrics(to)` - MRR, живые подписки, накопленные итоги). `adminService.getDashboard()` вызывает `dashboardMetricsService.collect(periodFrom, periodTo)`, который параллельно считает текущий и предыдущий период той же длины (`prevTo = from - 1мс`, `prevFrom = from - periodMs`) и снапшоты на `to` и на `from`. `deriveDashboardMetrics()` (`dashboard-metrics.ts`) сворачивает всё в плоский объект `metrics.*` вида `{value, prev}` - именно этот объект рендерит UI (`m.value` в `index.vue`).

**Важно для API-тестирования:** в том же ответе `/admin/dashboard` рядом с `metrics.*` остались старые верхнеуровневые поля `mrr`, `mrrPrev`, `arpu`, `activeSubscriptions` - это унаследованный расчёт (`prisma.subscription.aggregate` по статусу `ACTIVE`/`TRIAL`, без нормализации к 30 дням и без проверки факта оплаты) и он **не совпадает** с `metrics.mrr.value`/`metrics.arpu.value` на тех же данных - юнит-тест `admin.service.test.ts` фиксирует это явно: `res.mrr` = 70000 (старая формула), а `res.metrics.mrr.value` = 42000 (новая, нормализованная) на одном и том же фикстурном наборе моков. UI эти старые поля не рендерит (в `index.vue` использованы только `m.*` и `d.registrations.*`), но поля физически в ответе и может сбить с толку при ручной проверке через сеть/API - см. «Открытые вопросы».

### Операционные метрики

Цитаты формул - дословно из `docs/admin-dashboard-metrics.md` (написан разработчиком, ссылается на код):

- **MRR** - сумма «месячной стоимости» платных подписок на конец периода. Месячная стоимость = `COALESCE(renewal_amount, amount) * 30 / COALESCE(renewal_duration_days, длительность тарифа оффера, 30)` (`monthlyAmountSql` в `dashboard-metrics.service.ts`) - годовой тариф больше не задирает MRR в 12 раз. «Платная подписка на момент T»: началась ≤T, не истекла и не отменена к T, и есть ≥1 успешный платёж до T (проверяется факт платежа через `payment.status='succeeded'`, не статус подписки).
- **Регистрации** - без изменений, родители с `created_at` в периоде.
- **Выручка** (новое поле, не было в списке продакта явно, но упомянуто разработчиком) - сумма успешных платежей за период; по ней сверяются CAC и LTV.
- **Новые подписки** - подписки, чей **первый** успешный платёж попал в период (`first_pay` CTE, `MIN(paid_at)` по подписке).
- **Продления/отмены** - продления: успешные платежи в периоде, не первые для своей подписки; отмены: подписки с `cancelled_at` в периоде.
- **Активные подписки** - только платные на конец периода; бесплатные - отдельно строкой «+N бесплатных» мелким шрифтом (`AdminKpi sub="+${freeSubscriptions} бесплатных"` в `index.vue`). Бесплатная = живой триал (`status='trial'`), за который ещё не платили; **freemium намеренно не входит** - иначе «+N бесплатных» росло бы без остановки числом всех когда-либо заведённых семей (комментарий в коде и доке).
- **ARPU** = MRR / число платных подписок (`arpuOf`, `ratio(snap.mrr, snap.paidSubscriptions)`), не MRR / все живые.

### Продукт и клиенты

- **LT** - среднее время жизни подписок, по которым были деньги: `AVG(LEAST(COALESCE(cancelled_at, expires_at), to) - started_at)` в днях. Живые входят текущим возрастом (цензура), не выбрасываются - иначе метрика считалась бы только по ушедшим и была тем сильнее занижена, чем моложе продукт.
- **LTV** = `(вся выручка до to - AI-косты до to по курсу USD_RUB_RATE) / число подписок, которые когда-либо платили` (`ltvOf`, `ratio(revenueTotal - aiCostUsdTotal*rate, paidSubscriptionsEver)`). Кумулятивная, не за период - период влияет только через правую границу `to`.
- **CAC** = расходы на привлечение за период / новые платящие подписки за период (`cacOf`). **Если `marketingSpend === 0` (расходов не заведено) - CAC = `null` (прочерк), а не 0**: `p.marketingSpend > 0 ? ratio(...) : null` - явная проверка перед делением, не просто «0/0=null».
- **AI-косты** - сумма `ai_usage.cost_usd_micros` за период, переводится в рубли по курсу `USD_RUB_RATE` (env, дефолт 90, подписан в UI прямо в карточке).
- **Retention** = живые платные подписки (снапшот на конец периода) / все подписки, которые когда-либо платили. Кумулятивный знаменатель, как и LTV.
- **CSI** - среднее `topic_feedback.satisfaction` за период. **Важный нюанс:** форма отзыва (`topic-feedback.routes.ts`, схема `SCORE = {minimum: 1, maximum: 10}`) физически не допускает 0 - шкала фактически 1-10, документация разработчика это подтверждает («шкала 1-10»), хотя продакт в постановке просил «0 до 10» - см. «Открытые вопросы».

### Операционка

Активные ученики за период (уникальные `user_id`, отдельным `DISTINCT`-CTE на каждый тип + `UNION` для тотала):
- диагностика/контрольные - по начатым сессиям своего типа (`diagnostic_session.started_at`, `type = 'DIAGNOSTIC'`/`'CONTROL_TEST'`);
- тренажёр - по отправленным решениям (`trainer_submission.created_at`, join на `trainer_session`);
- домашка - по отправленным решениям (`homework_submission.created_at`, join на `homework`).

«Время на ученика» = `SUM(engagement_time.seconds за период) / activeUsers.total`; «Рейтинг на ученика» = `SUM(rating_award.points за период) / activeUsers.total`. Оба через общий `ratio()` - при 0 активных возвращают `null` (проверено юнит-тестом), UI рисует `-`. `rating_award.reason` в схеме - только положительные причины начисления (`trainer_task`, `topic_clean_bonus`, `topic_closed`, `topic_feedback`, `first_login`, `diagnostic`, `streak_day`, `challenge`) - механизма списания баллов в модели нет, то есть на практике метрика - именно «прирост», а не двунаправленное «изменение», см. «Открытые вопросы» (продакт просил пункт 18 именно «изменения рейтинга»).

### Воронка

`adminService.getFunnel`/когортный блок в `getDashboard` переименован в коды недельного отчёта: С0 (регистрация) → С0-1 (ребёнок зашёл, `device` создан) → С1 (диагностика начата) → С1.1 (диагностика завершена, `status='scored'`) → С1.2 (**новый шаг** «тренажёр начат» - закрывает дыру между диагностикой и пейволлом) → С1.3 (открыт пейволл, `paywall_first_shown_at IS NOT NULL`) → С2 (оплата, считается **семьями**, не подписками - `COUNT(DISTINCT u2.id)`, у одной семьи бывает несколько подписок). Все шаги - независимые срезы одной когорты (родители, зарегистрированные в периоде), не вложенные множества: платят и по прямой ссылке без пейволла, тренажёр v2 открыт без диагностики - поэтому нижний шаг иногда больше верхнего, и `drop = Math.max(0, prev - cur)` (отрицательного отвала не бывает), ширина полосы (`admin-funnel-view.vue`, `share()`) ограничена `Math.min(100, ...)`.

### Лента событий и AB-варианты

`activityUnionSql()` (`admin.service.ts`) получил новую ветку `sub_cancelled` (`subscription.cancelled_at IS NOT NULL`, `WHERE`-условие по этому же полю) - раньше отмена в ленте не отражалась вовсе. У `pay` появился признак `isRenewal` (подзапрос на более ранний успешный платёж той же подписки) - `activity-event-text.ts` рисует «оплатил(а)» / «продлил(а)» разным текстом. Дашборд (`loadDashboardFeed` в `index.vue`) запрашивает ленту с `kind: 'reg,pay,sub_cancelled'` - жёстко ограничен тремя типами. Страница `/admin/activity` (`pages/admin/activity/index.vue`) не урезана - там по-прежнему полный набор категорий фильтра (`pay`, `sub_cancelled`, `reg`, `diag`, `trainer`, `consent`, `link`, `problem_report`) - учебные события остались, просто ушли со стартового экрана дашборда.

`abBreakdown` по-прежнему считается и возвращается в ответе `/admin/dashboard` (комментарий разработчика подтверждает: «Данные остались в ответе ручки»), но в `index.vue` карточка с AB-разрезом из шаблона убрана целиком - на дашборде её нет, разбор остался на `/admin/experiments`.

### Расходы на привлечение (CAC) - таблица `marketing_spend`

Новая таблица (`day DATE`, `channel TEXT`, `amount INTEGER` - рубли, `comment TEXT?`), миграция `20260917120000_marketing_spend`. Роуты `GET/POST /admin/marketing-spend`, `DELETE /admin/marketing-spend/:id` (`marketing-spend.admin.controller.ts`):
- `parseDay()` разбирает **календарный день без времени** (`YYYY-MM-DD`, привязка к московским суткам, а не к моменту), с проверкой существования даты обратным сравнением (`2026-02-31` проходит regex, но не проходит `toISOString().slice(0,10) === v`);
- `amount` - целое число рублей, `0 < amount <= 2_000_000_000` (защита от переполнения `INTEGER`-колонки, иначе 500 вместо внятной 400);
- `channel` - обязателен, триммится;
- список ограничен 200 строками (`PAGE_SIZE`), но `total` (сумма `_sum.amount`) считается по **всему** диапазону, не только по отданной странице - специально, чтобы сумма в ящике не расходилась с CAC на дашборде;
- удаление - `deleteMany` (не `delete`): повторный клик или гонка с другим админом не валит 500, а тихо возвращает 404, если строки уже нет.

UI - кнопка «Расходы на привлечение» в блоке «Операционка» (`index.vue`) открывает `AdminMarketingSpendDrawer` с границами `from`/`to` = московский день текущего периода (`mskDayKey`, зеркалит бэкенд - иначе список в ящике и CAC на карточке считали бы разные сутки). После `submit`/`remove` дровер шлёт `changed` → родитель дёргает `loadDashboard()` заново, CAC должен пересчитаться без ручного обновления страницы.

### Периоды

`admin-period-picker.vue` - добавлены пресеты «Эта неделя» (`startOfMskWeek`, с понедельника - зеркалит недельный отчёт unit-экономики), «Прошлая неделя» (`startOfMskWeekOffset(-1)` до начала этой недели минус 1мс), «За всё время» (`from = new Date(0)`, `to = now`). Все границы считаются в московском поясе через новый `frontend/utils/app-timezone.ts` (зеркалит `api/src/constants/timezone.ts`, фиксированный оффсет +3ч без перехода на летнее время). На бэке `clampDashboardFrom()` поднимает нижнюю границу «за всё время» до первой регистрации и не дальше `DASHBOARD_MAX_SPAN_DAYS = 1100` дней (~3 года) назад от `to` - защита от двадцатитысячестрочной дневной серии. `from`/`to` уходят на бэк полным ISO-timestamp через `.toISOString()` (не голой датой) - в отличие от бага дат в MIA-147/`ai-cost`, здесь этот класс проблемы не воспроизводится по конструкции.

Дельта в карточке не показывается, если не с чем сравнивать (`deltaOf()` в `index.vue`: `value == null || prev == null || prev === 0` → `undefined`, карточка рисуется без стрелки/процента).

## Тест-кейсы

### Операционные метрики

1. Открыть `/admin`, период «30 дней» (дефолт). Убедиться, что показаны 7 карточек: MRR, Регистрации, Новые подписки, Выручка, Продления/отмены, Активные подписки, ARPU.
2. Взять подписку с годовым тарифом (`renewal_amount`/`amount` за год, `renewal_duration_days` не 30) - убедиться, что её вклад в MRR виден как **месячный** эквивалент (`amount * 30 / duration`), а не полная годовая сумма. Проверить на конкретной подписке через SQL/`/admin/users/:id`, свериться с картой на дашборде.
3. **ARPU не путает знаменатель**: если есть живые бесплатные триалы, ARPU не должен падать от их числа - `MRR / paidSubscriptions`, а не `MRR / (paid+free)`. По юнит-тесту (`dashboard-metrics.test.ts`): при MRR=40000, paidSubscriptions=20 → ARPU=2000, независимо от `freeSubscriptions=100`.
4. **«Активные подписки»** - карточка показывает число платных крупно, подпись мелким шрифтом «+N бесплатных». Убедиться, что freemium-аккаунты (никогда не платившие, срок «до 2099») **не** прибавляются к N - завести/найти чисто freemium-пользователя, число «+N бесплатных» не должно вырасти при его появлении (только живой триал `status='trial'` должен туда попасть).
5. **Новые подписки vs Продления**: найти подписку с двумя успешными платежами (первый - в прошлом периоде, второй - в текущем). Второй платёж должен попасть в «Продления» текущего периода, а не в «Новые подписки» (та учтена только с первым платежом в своём периоде).
6. **Отмены**: отменить (или найти уже отменённую) подписку с `cancelled_at` в текущем периоде - число в «Отмены» увеличивается на 1, и то же событие должно появиться в ленте (см. кейс ленты ниже).
7. Переключить период на «Вчера» и обратно на «30 дней» - все 7 карточек операционного блока пересчитываются без перезагрузки страницы (следят за `adminPollTick`/`onPeriodChange`).

### Продукт и клиенты

8. **LT**: сверить с формулой `AVG(LEAST(COALESCE(cancelled_at, expires_at), to) - started_at)` в днях - взять живую платную подписку без отмены, её вклад в LT = `to - started_at` (возраст на конец периода, не 0 и не «выброшена из расчёта»).
9. **LTV** по юнит-тесту: `revenueTotal=200000`, `aiCostUsdTotal=100`, `usdRubRate=90`, `paidSubscriptionsEver=50` → `(200000 - 100*90) / 50 = 3820`. Если есть тестовое окружение с контролируемыми данными - воспроизвести и сверить именно это число на дашборде.
10. **CAC с пустыми расходами**: выбрать период, в котором ни одной строки `marketing_spend` не заведено. Карточка CAC должна показать **прочерк** (`-`), подпись - «расходы за период не заведены», **не «0 ₽» и не «0»**. Дельта у CAC также не должна рисоваться.
11. **CAC с заведённым расходом**: через «Расходы на привлечение» добавить строку (дата внутри текущего периода, канал, сумма > 0). После сохранения и обновления дашборда (авто через `changed`→`loadDashboard`, либо переключить период туда-обратно) CAC должен показать число = `marketingSpend / newSubscriptions` за период, подпись - «расходы {сумма} за период». По юнит-тесту: `marketingSpend=50000`, `newSubscriptions=10` → CAC=5000.
12. Удалить только что добавленную строку расхода из ящика - CAC должен **вернуться к прочерку** (если это была единственная строка за период), сумма «за выбранный период» в ящике - к 0.
13. **AI-косты**: подпись под карточкой должна явно показывать курс (`$X по курсу {USD_RUB_RATE} ₽`), сумма в рублях = сумма в долларах × курс. Сверить с `/admin/ai-cost` (если доступен) на пересекающемся периоде - суммарные AI-косты не обязаны совпадать 1-в-1 (дашборд считает по всем поверхностям, включая анонимный демо-чат лендинга - см. `docs/admin-dashboard-metrics.md`, раздел «Чего эти цифры не покажут»), но порядок величины должен биться.
14. **Retention** по юнит-тесту: `paidSubscriptions(snapshot)=20`, `paidSubscriptionsEver=50` → 40.0%. Отменённая, но ещё действующая подписка (доступ есть, но `cancelled_at` уже проставлен и подписка уже не считается «платной на момент T» согласно `paidLiveAt`) не должна учитываться как активная - проверить конкретно на подписке в состоянии «оплачена, отменена, срок ещё не истёк»: она не в числителе Retention/MRR/«Активные подписки», но всё ещё в знаменателе (`paidSubscriptionsEver`).
15. **CSI**: карточка показывает среднюю оценку и число оценок «N оценок, шкала 1-10» рядом. Проверить, что среднее действительно среднее по `topic_feedback.satisfaction` за период (форма отзыва физически ограничена 1-10, см. «Открытые вопросы» - 0 в данных быть не может).
16. Период без единой оценки CSI - карточка должна показать `-`, а не `0` (проверить: `csi: null` при отсутствии строк, `avgCsi` в SQL - `AVG` от пустого множества даёт `NULL`).

### Операционка (активные ученики)

17. Ученик, начавший (но не завершивший) диагностику в периоде - должен попасть в «Диагностика», не должен попасть в «Тренажёр»/«Домашка», если там ничего не делал.
18. Ученик, только открывший тренажёр, но не отправивший ни одного решения - **не** должен попасть в «Тренажёр» (считается по `trainer_submission`, не по факту открытия страницы - осознанное решение, см. доку «Активность считается по факту работы, а не по открытой странице»).
19. Один и тот же ученик, активный по двум поверхностям (например, диагностика + домашка) - в «Активных всего» должен учитываться **один раз** (проверить через `UNION`, не `UNION ALL` - дублирования быть не должно).
20. «Время на ученика» и «Рейтинг на ученика» - при нулевом числе активных учеников за период (например, очень короткий/пустой период) карточки показывают `-`, не `NaN`/`Infinity`/`0` (по юнит-тесту: `activeUsers.total=0` → `avgSecondsPerActiveUser.value === null`, `avgRatingPerActiveUser.value === null`).
21. «Рейтинг на ученика» подписан «прирост баллов за период» - убедиться, что число неотрицательно на любых данных (учитывая, что модель `rating_award` не хранит отрицательных начислений - см. «Открытые вопросы» по формулировке из Linear «изменения рейтинга»).

### Воронка

22. Открыть блок «Воронка» на дашборде, период «30 дней». Должно быть ровно 7 шагов с кодами С0, С0-1, С1, С1.1, С1.2, С1.3, С2 и подписями «Регистрация», «Ребёнок зашёл», «Диагностика начата», «Диагностика завершена», «Тренажёр начат», «Открыт пейволл», «Оплата» - именно в этом порядке (С1.2 «Тренажёр начат» - новый шаг, которого раньше не было).
23. Найти/создать семью, оплатившую подписку по прямой ссылке без прохождения пейволла (если такой путь есть на стенде) - шаг «Оплата» (С2) в этом случае может оказаться **больше** предыдущего шага «Открыт пейволл» (С1.3). Ожидаемо: полоса шага С1.3 не «переливается» за 100% (`Math.min(100, share)`), а «Отвалилось» на этом шаге = 0, не отрицательное число.
24. Переключить период на «Эта неделя» - воронка и число «выпало» в подписи «X% общая конверсия» должны пересчитаться под ту же когорту (родители, зарегистрированные на этой неделе), а не показывать все данные подряд.
25. На дашборде AB-варианты **не отображаются** ни в воронке, ни отдельным блоком (карточка/таблица AB из шаблона убрана) - убедиться, что раздел с разбивкой по вариантам полностью отсутствует на странице `/admin` (данные остаются доступны через прямой запрос к API и на `/admin/experiments`, но не на дашборде).

### Периоды и дельты

26. Пресет «Эта неделя» - границы должны начинаться с понедельника текущей недели (московское время), не с воскресенья и не с произвольного дня недели.
27. Пресет «Прошлая неделя» - должен показывать данные полностью предыдущей календарной недели (пн-вс), не «последние 7 дней от сегодня».
28. Пресет «За всё время» - должен показать данные с первой регистрации в системе (не буквально с 1970 года - на бэке нижняя граница поднимается до `MIN(created_at)` среди родителей, но не дальше ~3 лет назад от `to`). Если на стенде данные моложе 3 лет - просто сверить, что дашборд не показывает пустоту/ошибку и число регистраций в этом периоде совпадает с общим числом родителей.
29. Для любого периода, где предыдущий период по этой метрике имеет `prev = 0` или отсутствует сравнимая база (например, «За всё время» - предыдущего периода той же длины физически может не быть содержательных данных) - дельта (стрелка/процент) у карточки **не показывается** вообще, не рисуется как «+∞%» или «+1000%».
30. Переключить период туда-обратно несколько раз подряд (например, «7 дней» → «30 дней» → «7 дней») - карточки должны каждый раз пересчитываться на актуальные числа, без залипания старых значений от предыдущего периода (гонка запросов не должна перетирать результат последним пришедшим, а не последним запрошенным - явно не проверялось чтением кода, стоит визуально проверить на медленной сети/троттлинге).

### Лента событий (дашборд)

31. Лента «Последние события» на дашборде должна содержать **только** три типа: регистрации, оплаты (новые/продления - подписаны разным текстом «оплатил(а)» / «продлил(а)»), отмены. Никаких учебных событий (диагностика, тренажёр, согласия, жалобы, выдача/активация ссылок) быть не должно.
32. Найти/создать свежее событие продления подписки (не первый платёж) - в ленте должна появиться запись с текстом «продлил(а) подписку «{тариф}»», отличным от текста «оплатил(а) подписку «{тариф}»» у первой оплаты, и суммой платежа рядом.
33. Найти/создать отмену подписки - в ленте появляется запись «подписка «{тариф}» отменена», **безличная формулировка** (не «родитель отменил») - это осознанно: тем же полем `cancelled_at` помечается и отказ родителя, и системная отмена после исчерпанных попыток списания, различить их в ленте нельзя.
34. Ссылка «Все» у блока ленты ведёт на `/admin/activity`, где по-прежнему доступны все категории событий, включая учебные (диагностика, тренажёр, согласия, ссылки, жалобы) и отдельный фильтр «Отмены» - урезание коснулось только виджета на дашборде, не самой страницы событий.

### Известное ограничение: отмена по `cancelled_at` (не событие, а состояние)

35. **[Ожидаемое поведение, не баг]** Отменить подписку (`cancelled_at` проставляется) в периоде T1 - убедиться, что отмена посчиталась в метрике «Отмены» за T1 и попала в ленту. Затем (в периоде T2, после T1) включить автопродление той же подписке заново (`cancelled_at` обнуляется). Проверить: (a) при повторном просмотре периода T1 счётчик «Отмены» за T1 **уменьшился** - отмена «исчезла» из уже закрытого периода задним числом; (b) запись в ленте событий для этой отмены тоже пропала. Это задокументированное разработчиком ограничение («честный счётчик потребовал бы отдельного журнала событий подписки») - подтвердить, что поведение именно такое, но **не заводить как баг**, только зафиксировать в отчёте как подтверждённое ограничение.

## Аналитика/API

Отдельных аналитических событий (`analytics-events.ts` на бэке и фронте) для дашборда или расходов на привлечение эта задача не добавляет - в обоих файлах констант нет ни `MARKETING_SPEND_*`, ни `DASHBOARD_*`. Логировать сохранение/удаление расхода или просмотр дашборда через аналитику не предполагается.

Для ускорения ручной проверки можно дёргать API напрямую (нужны админские куки/сессия, весь `/admin/*`-префикс защищён `requireAdmin`):

- `GET /admin/dashboard?from=<ISO>&to=<ISO>` - основная ручка. `from`/`to` - полный ISO-timestamp (не голая дата), при отсутствии `to` берётся `now()`, при отсутствии `from` - `to - 30 дней`. В ответе `data.metrics.*` - новые карточки (сверять с UI), `data.mrr`/`data.arpu`/`data.activeSubscriptions`/`data.mrrPrev` - **старые** поля другой формулы, не совпадают с `metrics.mrr`/`metrics.arpu` (см. «Реализация»), не путать при сверке чисел.
- `GET /admin/marketing-spend?from=YYYY-MM-DD&to=YYYY-MM-DD` - список расходов и сумма за диапазон; `from`/`to` тут, в отличие от dashboard, - **голые календарные даты**, не ISO-timestamp.
- `POST /admin/marketing-spend` `{day: 'YYYY-MM-DD', channel, amount, comment?}` - создание строки расхода, быстрее чем через UI-форму для набивки тестовых данных.
- `DELETE /admin/marketing-spend/:id` - удаление.
- `GET /admin/funnel?from&to&abVariant` - отдельная ручка воронки (не та, что зашита в `getDashboard`, хотя дашборд-воронка её «зеркалит» по комментарию в коде) - если числа на дашборде разойдутся с этой ручкой, это тоже повод для отдельной проверки, хотя в скоуп MIA-178 она не входит впрямую.
- `GET /admin/activity?kind=reg,pay,sub_cancelled&page=1&perPage=8` - тот же запрос, что дёргает дашборд для ленты; удобно проверить состав событий без UI.

## Открытые вопросы

Сверка построчно с 18 пунктами продакта:

1. **MRR** - вопрос «по какой формуле» закрыт документацией и кодом (нормализация к 30 дням, только платные). Закрыт.
2. **Регистрации** - без изменений. Закрыт.
3. **Новые подписки** - реализовано (первый успешный платёж). Закрыт.
4. **Продления/отмены** - реализовано. Закрыт, но см. известное ограничение по `cancelled_at` (п. 35 тест-кейсов).
5. **Активные подписки** - платные крупно + «+N бесплатных» мелким шрифтом. **Нюанс, стоит явно подтвердить с продактом:** «бесплатные» реализованы как «живой триал, ещё не плативший», freemium туда осознанно не включён (иначе число растёт без остановки). Продакт в постановке не различал триал/freemium явно - если под «бесплатными» подразумевался в том числе freemium, это разойдётся с ожиданием. Разработчик обосновал решение в доке, но явного согласования с продактом в тикете не видно.
6. **ARPU** - формула закрыта (MRR/платящие). Закрыт.
7. **LT** - реализовано, с цензурой живых подписок (осознанное смещение вниз относительно «истинного» LT, задокументировано). Закрыт.
8. **LTV** - формула ровно как в постановке. Закрыт.
9. **CAC за период** - реализовано, но потребовало ручного ввода расходов (в системе нет интеграции с рекламными кабинетами - зафиксировано как решение, не баг). Закрыт.
10. **AI-косты за период** - реализовано. Закрыт.
11. **Retention** - формула ровно как в постановке («живые/все, в т.ч. отменённые»). Закрыт.
12. **CSI** - **небольшое расхождение с текстом продакта**: постановка просит «оценки от 0 до 10», в коде и в подписи карточки - шкала «1-10» (форма отзыва `topic-feedback.routes.ts` физически не допускает 0, `minimum: 1`). Это ограничение существовавшей формы обратной связи, не создано этой задачей, но раз продакт явно написал «0 до 10» - стоит уточнить, было ли это опечаткой/неточностью формулировки, или ожидалась расширенная шкала (в рамках MIA-178 это не чинится, форма отзыва вне скоупа MR).
13-16. **Активные ученики по 4 поверхностям** - реализовано, по факту работы (сессия/решение), не по открытию страницы. Закрыто.
17. **Среднее время на активного пользователя** - реализовано. Закрыт.
18. **Изменения рейтинга в среднем на активного пользователя** - реализовано как **сумма положительных начислений `rating_award.points`, делённая на число активных**, подписано на дашборде «прирост баллов за период». Продакт написал именно «изменения» - в модели `RatingAward` нет причин списания баллов (только начисления: `trainer_task`, `topic_clean_bonus`, `topic_closed`, `topic_feedback`, `first_login`, `diagnostic`, `streak_day`, `challenge`), так что на практике «изменение» физически не может быть отрицательным при текущей модели данных - расхождение скорее терминологическое (продакт мог иметь в виду именно прирост), но стоит явно сверить с продактом, ожидался ли когда-либо отрицательный сценарий (штраф/сгорание баллов), который эта метрика не покроет.

Дополнительно, вне 18 пунктов:

- **Фильтр периода** - «за всё время», «эта неделя», «прошлая неделя» реализованы. Закрыт.
- **AB-варианты убраны с дашборда** - убраны из UI, но данные остаются в ответе `/admin/dashboard` (`abBreakdown`) - соответствует комментарию разработчика («разбор живёт на `/admin/experiments`»), не баг.
- **Воронка синхронизирована с кодами С0…С2** - реализовано, добавлен промежуточный шаг С1.2 «Тренажёр начат». Код явно предупреждает: если в отчёте unit-экономики коды означают другое - правится один список (`funnel: [...]` в `admin.service.ts`) - стоит свериться с последней версией Weekly-отчёта, что коды и их порядок совпадают буквально (не проверено этим чтением кода - недоступен сам Weekly-отчёт для сверки).
- **События сведены к регистрациям/оплатам/отменам** - реализовано на дашборде, полный список остался на `/admin/activity`. Закрыт.
- **Дублирующиеся `mrr`/`arpu`/`activeSubscriptions` верхнего уровня в ответе `/admin/dashboard`** (старая формула, не совпадает с `metrics.mrr`/`metrics.arpu` на тех же данных, подтверждено юнит-тестом) - в скоуп задачи это не входит и UI их не показывает, но стоит спросить разработчика, не стоит ли выпилить как мёртвый код: при прямой сверке через API легко перепутать поля и получить «расхождение», которого на самом деле нет на экране.
- **«За всё время» ограничено ~3 годами вглубь** - если у продукта на момент проверки данных больше 3 лет, пресет «За всё время» не покажет самые старые записи. Если продукту важна честность именно «всё время» без ограничения - стоит уточнить, устраивает ли компромисс с производительностью (задокументирован разработчиком как осознанный).
