## Контекст

Задача (label - нет, priority - No priority): месячный отчёт родителю (`type: 'monthly'`) был заметно беднее недельного (MIA-150) - только балл диагностики, список тем и абзац от Мии, без единого факта о том, что происходило в течение месяца. ТЗ методолога (`docs/educational-process/specs-source/mia360-report.md`, раздел «Фактические метрики») требует дни/часы/задачи, закрытые темы за период, плюс отдельно сильные стороны и зоны роста. «Качества ученика» (вовлечённость, внимательность и т.д.) и раздел «Бонус» ТЗ явно вынесены в Out of scope.

**Раунд QA от 08.09 (Andrei Chepurchenko) - FAIL.** API уже отдавал все поля MIA-156 (`daysActive`, `standing`, `strengths`, `growthAreas` и т.д.), а страница `/report/:token` рисовала старую вёрстку без карточек фактов, с `.topic__dot`/`.legend`/пунктиром «результат диагностики» - расхождение версий фронта и API на стенде. Само наблюдение и гипотеза QA («вероятно нераскатанная либо закэшированная сборка») по коду не опровергаются и не подтверждаются повторно этой заметкой - для этого нужен живой стенд, не чтение кода.

**Комментарий разработчика от 22.09** (после которого и всплыла задача в этом раунде): «Прогресс темы в отчётах считается по ML-блокам вместо mastery_score, который на v3 не пишется (на проде из 382 записей прогресса за 30 дней ненулевой mastery был у 22)». Это описывает как раз коммиты обзора, добавленные поверх исходного `d6c99dac` («наполнить месячный отчёт и убрать следы мёртвой шкалы») - и относится не только к месячному отчёту: недельный тоже переведён на новый источник прогресса и получил свой собственный UI-срез (см. «Реализация» и «Тест-кейсы» ниже, отдельный раздел про регресс недельного отчёта).

## Реализация

### Факты месяца - без изменений с прошлого чтения кода

`api/src/services/parent-report.service.ts`, `weeklyActivity()` (строка 669) по-прежнему единая функция для недельного и месячного отчёта (дни/задачи/время по МСК-суткам), `createMonthlyReport()` (1016) по-прежнему требует хотя бы одну `SCORED`-диагностику, иначе месячный отчёт не создаётся вовсе. `buildMonthlyReportPayload()` (410) собирает `daysActive`/`daysInPeriod`/`tasksSolved`/`timeSpentMinutes`/`standing`/`topicsClosedInPeriod`, `strengths`/`growthAreas` добавляются только когда непустые. Фронтенд, `frontend/pages/report/[token].vue`: единый `periodFacts` (computed, строка 391, `weeklyData ?? monthlyData`) обслуживает карточки `.wstats` и блок `.standing` для обоих типов отчёта - в этой части всё совпадает с прошлым чтением кода, конкретика не изменилась.

### Новое: и топикам, и отчёту в целом теперь нужна метка «чем измерено»

Это главное изменение поверх прошлой версии заметки. Причина - в комментарии разработчика: под scoring v3 `topic_user_progress.mastery_score` не пишется вовсе (`V3Strategy.computeMasteryScore` возвращает предыдущее значение без изменений), то есть прогресс темы в отчёте был заморожен на дате перехода на v3 - ноль для тем, тронутых после переключения, несмотря на реально закрытые ML-блоки.

- **`topicMlProgressService.topicProgressPct()`** (`api/src/services/topic-ml-progress.service.ts:736`) - новый метод: `(закрытых блоков + доля активного блока по решённым core-задачам) / 5 блоков × 100`, округление вниз до 100. Формула специально зеркалит `mlProgressPct` из `frontend/utils/ml-progress.ts` («бар в отчёте родителю и полоса в кабинете ученика обязаны совпадать»). Знаменатель активного блока берётся не из конфига уровня, а из фактического числа задач в БД (`coreAvailableByBlock()`, groupBy по `topicId`+`mlLevel`) - на уровне с бедным контентом это меньше, чем в конфиге, и кабинет ученика считает именно по факту. Юнит-тесты (`topic-ml-progress.service.test.ts`, `describe('topicProgressPct')`) отдельно проверяют регрессионный кейс «100% не превращается в 0 из-за отсутствия mastery».
- **`parent-report.service.ts`, `topicBlockMaps()`** (строка 804, приватный) - при активной v3-стратегии (`getActiveScoringStrategy().version === 'v3'`) одним запросом тянет ML-блоки студента и строит `progressPct`/`closedBlocks` по каждой теме; при v2/v1 возвращает `null`. `progressOf()` (489) - если блоков для темы нет вообще (в `progressPct` нет ключа - актуально и при v3, для тем без ML-строк, например легаси-контент, пройденный до перехода), используется старый способ - доля решённых заданий от общего числа (`solvedAssignments/totalAssignments`), а не сырой `mastery_score`. Это касается и недельного, и месячного отчёта одинаково.
- **`progressSourceOfTopic()`** (484) помечает тему как `'ml_blocks'` или `'mastery'` в зависимости от того, из какого источника взят её прогресс - поле пишется в payload (`WeeklyReportTopic.progressSource`), только для недельного (в месячном delta-сравнение с предыдущим отчётом вообще убрано, см. ниже).
- **`comparablePrevMastery()`** (289) - при сравнении с предыдущим недельным снапшотом теперь сверяет `progressSource` темы «тогда» и «сейчас»: если линейка изменилась (например, тема была измерена как `mastery`, а теперь есть её ML-блоки), прошлое значение в сравнение не попадает вообще (`continue`, не `0`). Комментарий в коде прямо называет баг, который это чинит: «сравнение через версию отчёта показало бы падение с 60% до нуля тому, кто просто начал тему» - то есть без этой правки переход темы на ML-блоки мог бы нарисовать родителю ложный регресс ребёнка.

### Месячный отчёт - тема теперь не «было X, стало Y», а «диагностика/N блоков»

`buildMonthlyReportPayload()` (410-433): `prevMasteryScore` у месячных тем теперь жёстко `null` (комментарий в коде: «пунктирная отметка "где было в начале" ушла со страницы - она рисовалась по mastery_score, который для всех тем стоял на нуле»), вместо неё - опциональные `blocksClosed`/`blocksTotal` (только когда есть ML-блоки, `ML_BLOCKS_TOTAL = 5`).

Фронтенд, `[token].vue`:
- `isTopicDone()` (406) - `blocksTotal != null && blocksClosed === blocksTotal` → тема помечена «Пройдена» (зелёным) вместо числовой дельты.
- Иначе для месячной темы с блоками - `N/5` блоков закрыто (`.topic__blocks`); без блоков (легаси, v2/v1 или тема вне ML) - старый статусный лейбл (`Освоено`/`Уверенно`/`Нужно подтянуть`).
- Подпись «в диагностике N/10» (`.topic__baseline`, строка 732) - без изменений с прошлого чтения, рендерится по `diagnosticScore != null`.
- Сортировка тем (`monthlyTopics`, 433) - без изменений: сначала пройденные полностью, затем начатые по убыванию прогресса, затем нетронутые.
- Точки статуса (`.topic__dot`, строка 722) и легенда трёх цветов (`.legend`, строка 768) теперь строго `v-if="diagnosticData"` - для `monthlyData` не рендерятся вовсе, как и раньше.
- Новое: строка распределения диагностики в шапке месячного отчёта (`monthly-anchor__dist`, «N освоено / N уверенно / N подтянуть») теперь показывает только ненулевые группы (`diagnosticSpread`, строка 376, `.filter(group => group.count > 0)`) - раньше показывались все три группы всегда, включая нулевые.

### Недельный отчёт - задет тем же MR, стоит зарегрессить заодно (не в исходном скоупе MIA-156, но в этом MR)

- Список тем недельного отчёта больше не показывает все темы курса подряд - только те, где `weeklyTasksSolved > 0` (новое поле, посчитано в `weeklyActivity()` через `tasksByTopicId` по `trainerSession.trainer.topicId`), максимум 6 (`TOPICS_SHOWN_WEEKLY = 6`, строка 404), отсортированных по убыванию числа задач. Хвост - строкой «и ещё N тем с работой на этой неделе» (`weeklyTopics.hidden`).
- Домашка (не имеет `topicId`, раньше нигде не учитывалась в разрезе по темам) - отдельная строка «плюс N задач в домашней работе» (`homeworkTasksSolved`, посчитан в `weeklyActivity()` отдельно от `tasksByTopicId`).
- Старые снапшоты без `weeklyTasksSolved` у тем (написанные до этого MR) - показываются целиком, без урезания до 6 (`if (topics.length && !topics.some(t => t.weeklyTasksSolved != null)) return { shown: topics, ... }`) - обратная совместимость учтена явно.
- Тема недели, полностью закрытая по блокам (`isTopicDone`) - тоже помечается «Пройдена» вместо дельты; иначе показывается «+N задач» (`weeklyTasksSolved`), а не дельта прогресса в процентах.

### Кабинет родителя (Acceptance: «месячный отчёт... теми же цифрами, что и кабинет») - гэп сохраняется, но сместился

Раньше (по старой версии заметки) `frontend/cabinet/screen/reports.ts` не показывал фактов для месячного отчёта, потому что `StudentReport.daysActive/tasksSolved/minutes` для месячного типа были жёстко `null` на бэкенде (`student-report.service.ts`). **Это изменилось в этом MR**: `fromMonthly()` (`api/src/services/student-report.service.ts:107`) теперь пробрасывает реальные `daysActive`/`tasksSolved`/`minutes` (строки 116-118, `numOrNull(p.daysActive)` и т.д., с комментарием «null пока в старом снапшоте этих полей нет - ноль обещал бы, что ученик ничего не делал»). То есть **данные до кабинета теперь физически доходят.**

**Но `frontend/cabinet/screen/reports.ts`, `monthlyCard()` (строки 120-132) этим MR не тронут вообще** - функция по-прежнему безусловно возвращает `facts: []` для месячного отчёта, никак не читая `r.daysActive`/`r.tasksSolved`/`r.minutes` (в отличие от `weeklyCard()`, строки 98-118, которая эти поля уже использует). Получается: бэкенд-контракт для карточки кабинета (в части дней/задач/времени) готов, но фронт кабинета его не подхватил - разрыв не «данных нет», а «данные есть, экран их не рисует». Ещё точнее: даже если починить `monthlyCard()`, `standing`/`topicsClosedInPeriod`/`strengths`/`growthAreas` в `StudentReport` (интерфейс, `student-report.service.ts:30-42`) по-прежнему не заведены вообще - для полного паритета с `/report/:token` не хватает и контракта, не только вёрстки. Итог сверки acceptance «теми же цифрами, что и кабинет» не изменился по сути: сравнивать физически почти нечем, только теперь по чуть более тонкой причине.

### Письмо vs страница - без изменений

`api/src/services/email/templates/parentMonthlyReport.mjml` не в дифе этого MR. `monthlyEmailLine()` (`parent-report.service.ts:456`) по-прежнему только один общий абзац без единой цифры месяца («Стартовали с X из 10 на диагностике. {Имя}: собрали прогресс по темам за месяц - подробности в отчёте.») - расходиться в цифрах с письмом физически нечем, акцептанс формально не может быть нарушен, но и не проверяется содержательно.

### AI-саммари и списки - в целом как в прошлой версии заметки, плюс два фикса ревью

`api/src/services/parent-report-ai.service.ts`: `generateMonthlySummary()` просит модель вернуть JSON `{summary, strengths, growthAreas}` (режим `jsonObject: true`), `parseMonthlySummary()` терпим к обёртке в \`\`\`json и к преамбуле, режет списки до 3 пунктов по 60 символов. Два новых момента поверх прежнего чтения:
- **Таймаут для месячного ответа увеличен отдельно** (`JSON_TIMEOUT_MS = 35_000` против `TIMEOUT_MS = 20_000` для остальных отчётов, `maxOutputTokens: 2400` вместо 1500) - комментарий в коде: «месячный ответ везёт абзац и шесть строк списков в JSON... с прежним таймаутом он рвался бы на середине».
- **Расход теперь пишется в `ai_usage` даже когда разбор JSON-ответа не удался** (`usage`/`responseId` попадают в `AiSummaryFailure` и при пустом `output_text`, и при нечитаемом JSON) - раньше неудачный парсинг просто ронял вызов без следа в учёте костов, хотя токены уже были списаны провайдером. Не входит напрямую в acceptance MIA-156, но напрямую касается корректности `ai_usage`/`/admin/ai-cost` (пересекается с MIA-147) - стоит держать в уме при регрессе costs-дашборда.
- При `parsed === null` (как и раньше) - весь `generateMonthlySummary()` возвращает `ok: false`, `aiSummary = null`, `strengths = []`, `growthAreas = []`, отчёт всё равно создаётся и уходит.

### Дополнительно в этой ветке: ссылка входа для родителя из админки

`api/src/admin/admin.service.ts` (`getParentLoginLink`) подписывает токен через `api/src/helpers/parent-login-token.helper.ts` (`signParentLoginToken`/`readParentLoginToken`, HMAC-SHA256, **TTL ровно 7 дней** - `PARENT_LOGIN_TOKEN_TTL_MS = 7 * 24 * 3600_000`). Одноразовость обеспечивает отдельный `api/src/services/parent-login-token.service.ts` (`ParentLoginTokenService.claim()`) - Redis-лок (`cache.lock`, `SET NX`) по хешу токена: первый, кто предъявил токен `/parent/enter?token=...`, забирает вход, повторное предъявление (в том числе второй вкладкой одновременно) - отказ; ошибка Redis тоже трактуется как отказ, а не как «пропустить». `GET /api/admin/users/:id/parent-login-link` - 404, если пользователь не `role: PARENT` (юнит-тест это подтверждает). Фронт - `frontend/composables/use-admin-link-copy.ts` (`copyParentLoginLink`), пункт меню в `frontend/pages/admin/users/[id].vue`/`index.vue`, симметрично уже существующей ссылке для ребёнка.

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Ретест FAIL от 08.09 на актуальной сборке

Шаги те же, что в отчёте QA от 08.09 - открыть месячный отчёт (preview-ссылку или свежий отчёт своего тестового ученика), проверить:
- три карточки фактов (дни/задачи/время) в `.wstats`, блок `.standing` (рейтинг с `+N`, серия дней, «+N тем за месяц», «X/Y тем курса»), два списка «Получается лучше всего»/«Над чем поработать» (`.takeaways`) при непустых `strengths`/`growthAreas`;
- отсутствие `.topic__dot`, `.legend`, текста «Пунктир - результат диагностики» - для месячного типа их не должно быть в DOM вообще;
- у тем из стартовой диагностики - подпись «в диагностике N/10»;
- **новое по сравнению с прошлым раундом**: у полностью закрытых тем - зелёная плашка «Пройдена»; у прочих тем с ML-блоками - «N/5» вместо прежней дельты в процентах; у шапки отчёта («Старт: диагностика X/10» + распределение) - строка распределения не показывает нулевые группы (если, например, красных тем на диагностике не было - строки «0 подтянуть» быть не должно).

### 2. [Не изменилось по сути, но причина другая] Сверка «отчёт vs кабинет родителя»

1. У тестового ученика с диагностикой и активностью за месяц открыть месячный отчёт, зафиксировать дни/задачи/время/рейтинг/«+N тем».
2. Через «Скопировать ссылку входа для родителя» (см. тест-кейс №7) открыть кабинет родителя → «Отчёты».
3. Сравнить карточку месячного отчёта в кабинете.

Ожидаемо по коду: карточка в кабинете по-прежнему пуста (`facts: []`, `frontend/cabinet/screen/reports.ts:130`) - несмотря на то, что `daysActive`/`tasksSolved`/`minutes` теперь реально доходят до `StudentReport` (см. «Реализация»). Зафиксировать как открытый гэп (см. «Открытые вопросы»), не как новый баг деплоя - код идентичен что на master, что в MR.

### 3. Топики месячного отчёта - блоки вместо дельты

Для ученика на v3-скоринге:
- тема, где закрыты все 5 ML-блоков → «Пройдена», без дельты и без прежнего пунктира;
- тема в процессе (часть блоков закрыта, активный блок начат) → «N/5», N меньше 5;
- тема, у которой ML-блоков нет вовсе (легаси-контент, пройденный до перехода на v3, либо тема вне ML-программы) → старый статусный лейбл («Освоено»/«Уверенно»/«Нужно подтянуть»), без «N/5» - проверить, что это не выглядит как ошибка, а как ожидаемый режим для немаппленной темы;
- сверить конкретное число `masteryScore`/«N% темы пройдено» в промпте Мии (см. «Реализация», `buildMonthlyPrompt`) с тем, что кабинет ученика показывает для той же темы по `mlProgressPct` - числа обязаны совпадать (общая формула, `topicProgressPct` зеркалит `frontend/utils/ml-progress.ts`).

### 4. Топики недельного отчёта - урезание до 6 + домашка (регресс MIA-150, задет этим MR)

1. У ученика, решавшего задачи по 8+ темам за неделю - недельный отчёт должен показать максимум 6 тем (те, где `weeklyTasksSolved > 0`, по убыванию), и строку «и ещё N тем с работой на этой неделе».
2. У ученика, решавшего домашку в течение недели - отдельная строка «плюс N задач в домашней работе», не растворённая в общем списке тем (у домашки нет `topicId`).
3. У ученика с недельной активностью только в старом снапшоте (написан до этого MR, если такой сохранился в тестовых данных) - список тем должен показаться целиком, без урезания до 6 (обратная совместимость).
4. Тема недели, полностью закрытая - плашка «Пройдена» вместо «+N задач»; тема с работой, но не закрытая - «+N задач».

### 5. Рейтинг, серия, «+N тем за месяц», позиция в курсе (без изменений с прошлого раунда, но стоит перепройти вместе с топ. 3-4)

- `standing.ratingTotal` + `+{{ratingGained}}` только при приросте `> 0`; серия (`streakDays`) - блок скрыт при `0`; «+N тем за месяц» (`topicsClosedInPeriod`) должно быть посчитано строго по периоду и, как правило, меньше «X тем курса пройдено» (за всё время) - оба тайла теперь гарантированно читают один и тот же список тем курса (`courseTopicIds()`, общий метод для обеих плиток - устраняет источник потенциального рассинхрона между «+N за месяц» и «X из Y»).

### 6. Списки «Получается лучше всего» / «Над чем поработать»

Без изменений с прошлого раунда: раздельные `<ul>`, до 3 пунктов, до 60 символов на пункт (обрезка с `…`), блок скрыт при пустых обоих списках. Дополнительно стоит проверить: JSON-ответ модели не рвётся на середине при большом количестве тем (новый таймаут 35 c/2400 токенов) - смотреть по факту наличия `aiSummary`/`strengths`/`growthAreas` на реальных отчётах с диагностикой из 30+ тем.

### 7. Проверка своими данными - ссылка входа для родителя из админки

1. В карточке пользователя-родителя в админке → «Скопировать ссылку входа для родителя».
2. Перейти по ссылке → кабинет родителя открывается без пароля.
3. Повторно открыть ту же (уже использованную) ссылку - вход должен быть отклонён (Redis-лок одноразовости, `parentLoginTokenService.claim()`).
4. Скопировать ссылку заново - должен прийти новый токен (не переиспользование старого).
5. Ссылке больше 7 дней (искусственно состарить/подождать, если тестовая среда позволяет) - токен должен быть отклонён по истечении `PARENT_LOGIN_TOKEN_TTL_MS`.

### 8. Намеренный провал JSON от модели (граница, как и в прошлом раунде)

Не воспроизводится без моков `openAiResponsesClient`. Ожидаемо: отчёт создаётся и письмо уходит, `aiSummary = null`, оба списка пустые, блок `.takeaways` скрыт. **Новое, стоит проверить отдельно**: строка в `ai_usage` для этого вызова всё равно должна появиться с непустым `cost_usd_micros` (списание идёт и при `status: 'error'` из-за нечитаемого JSON) - если раньше падение парсинга роняло вызов без следа в костах, теперь это регрессионный кейс специально для `/admin/ai-cost`.

### 9. Граничные состояния (без изменений с прошлого раунда)

Нулевая активность за месяц, МСК-границы периода, отсутствие диагностики (`createMonthlyReport()` не создаёт отчёт вовсе) - см. подробности в предыдущей версии заметки, логика этих трёх файлов (`weeklyActivity`, `mskPeriodRange`, `createMonthlyReport` guard) этим MR не задета.

## Открытые вопросы

- **[Сохраняется, но по другой причине] Кабинет родителя не показывает факты месяца.** `frontend/cabinet/screen/reports.ts:monthlyCard()` (120-132) по-прежнему жёстко возвращает `facts: []`, хотя данные (`daysActive`/`tasksSolved`/`minutes`) этим MR уже проброшены в `StudentReport` через `fromMonthly()` (`student-report.service.ts:107-119`). То есть починка этой функции для трёх из ~7 месячных метрик теперь тривиальна (данные уже есть, нужно только прочитать их в `monthlyCard()` по аналогии с `weeklyCard()`) - но `standing`/`topicsClosedInPeriod`/`strengths`/`growthAreas` в `StudentReport` всё ещё не заведены вообще, так что полный паритет с `/report/:token` потребует ещё и расширения интерфейса `StudentReport`. Открытый вопрос ровно тот же, что в прошлой версии заметки: это отдельная задача или недоделанная часть MIA-156 - решать постановщику.
- **Акцептанс «письмо и страница не расходятся в цифрах» проверяем только формально** - письмо не содержит цифр месяца, расходиться нечем (не изменилось).
- **MR фактически шире MIA-156**: тот же MR переводит топик-прогресс НЕДЕЛЬНОГО отчёта (MIA-150) на ML-блоки и меняет список тем в нём (топ-6 + домашка отдельной строкой). Это не упомянуто ни в скоупе, ни в Out of scope MIA-156 - стоит либо явно зарегрессить недельный отчёт в рамках этого же QA-раунда (тест-кейс №4 выше), либо уточнить у автора/постановщика, не требует ли это отдельного тикета для отслеживания.
- **Раздел «Бонус» ТЗ методолога не реализован** - как и раньше, вероятно осознанно опущено, стоит уточнить у автора/методолога.
- **Хеш задачи (title+description+комментарии) не совпал побайтово с сохранённым в state.json значением даже при точном текстовом совпадении содержимого** (перепроверено вручную) - формат сериализации, которым считался прежний hash, доподлинно не известен (вероятно другой join/включает доп. поля). Решение «изменена» принято по содержательному сравнению (появился комментарий от 22.09), не по совпадению/несовпадению хеша - см. итоговое сообщение агента.
- **Не покрыто чтением кода, нужен живой стенд**: реальная сверка чисел (тест-кейсы 1-6), фактическая генерация/отправка письма, намеренный провал JSON на реальном вызове модели (тест-кейс №8), МСК-границы на живых данных, аналитические события, а также сам ретест FAIL от 08.09 (расхождение версий фронта/API на стенде - это никогда не было вопросом кода, а вопросом раскатки).
