## Реализация

### A/B-раздача: `plans` (лендинг) и `h3` (тарифы) — фронт и бэк идентичны

`frontend/data/ab-tests.ts` и `api/src/data/ab-tests.ts` — два независимых объекта `AB_TESTS`, проверены построчно: набор вариантов, веса и `tariffs` совпадают. `landing.plans` — `weight: 1` (обычный случайный вариант классического рандомайзера, наравне с `classic`/`spot`/`old`), `pricing.h3` — `weight: 0, linkOnly: true` (`tariffs: ['all_in_month', 'basic_month']`) — сам по себе никогда не выпадает случайно, только через привязку к `plans` (комментарий в коде: «Never drawn on its own: the plans landing carries its visitors here»).

Связка `landing → pricing` — `frontend/utils/landing-variant.ts:pricingForLanding`: если тарифный вариант не пришёл явной ссылкой (`?ab=`), а лендинг — `plans`, тарифы принудительно становятся `h3`; если лендинг не `plans`, а бакет почему-то остался `h3` — откатывается на `defaultVariant` (`std`). Применяется в двух местах с одинаковой логикой: `frontend/server/middleware/ab-tests.ts` (SSR, куки `ab_landing`/`ab_variant`) и `use-landing-audience.ts:choose()` (после ответа в гейте аудитории на клиенте).

Флаг «это лендинг plans» — `frontend/composables/use-landing-plans.ts` (`shouldShowPlansLanding`): `variantKey === 'plans' && !isUz`. Узбекская витрина исключена явно (комментарий: «вариант собран под российскую витрину: на узбекской он читается как classic»).

**Коммит `be522d68` (последний в MR)** правит ровно то расхождение, которое отдельно проверял QA: `frontend/composables/use-variant-offers.ts` принимает `scope: 'surface' | 'billing'`. Для `'surface'` (публичные поверхности — лендинг, баннер, прайсинг) `variantKey`/`tariffs` теперь всегда берутся как `h3`, если `isPlans === true`, **независимо** от pricing-бакета аккаунта; для `'billing'` (всё, что реально списывает деньги — паывол, `/select-tariff`) поведение не менялось — там бакет аккаунта побеждает всегда. Это ровно то, что QA описал как «прошло»: вошедший пользователь с бакетом `std` на `?abl=plans` видит на самом лендинге тарифы `plans`, а на `/select-tariff` — свои настоящие тарифы.

### Форма звонка куратора — `landing-v2-callback-modal.vue`

Состояние: `email`, `phone`, `consent`, `submitting`, `sent`, `error`, `touched`. Валидация:
```ts
const emailValid = computed(() => /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(normalizedEmail.value));
const phoneValid = computed(() => isRuPhoneValid(phone.value));
const canSubmit = computed(() => emailValid.value && phoneValid.value && consent.value && !submitting.value);
```
`isRuPhoneValid`/`normalizeRuPhone` — из `frontend/utils/normalize-phone.ts`, используются только в **submit-путь** (проверка и тело запроса), не в самом поле ввода — см. раздел про баг ниже. Отправка: `POST /landing/callback` с `{ email, phone: normalizeRuPhone(phone.value), consent: true, abLanding: landingVariant.value }`. Ошибка (сетевая/`4xx`/`5xx`, всё через один `catch`) → единый текст «Не удалось отправить заявку. Попробуйте ещё раз.» — не различает 400/429/500 (см. «Открытые вопросы»). Успех → `sent = true` → экран «Спасибо!.. » → «Хорошо»; при повторном открытии (`watch(() => props.open)`) поля сбрасываются, если до этого была отправка; после ошибки — не сбрасываются (поля остаются как ввёл человек).

Примечание по неймингу, не баг: кнопка, открывающая модалку (`landing-v2-pricing.vue`), — «Хочу звонок от куратора»; кнопка отправки внутри самой модалки — «Жду звонка» (в состоянии отправки — «Отправляем…»). Разные подписи в одном сценарии, стоит свериться с макетом при следующем прогоне.

### Бэкенд формы звонка — валидация, rate-limit, интеграция с Telegram

`api/src/routes/landing.routes.ts`:
```ts
const callbackBodySchema = {
  type: 'object',
  required: ['email', 'phone', 'consent'],
  additionalProperties: false,
  properties: {
    email: { type: 'string', format: 'email', maxLength: 200 },
    phone: { type: 'string', pattern: '^\\+7\\d{10}$', maxLength: 16 },
    consent: { type: 'boolean', const: true },
    abLanding: { type: ['string', 'null'], maxLength: 32 },
  },
} as const;
```
`POST /landing/callback` — `config.rateLimit: { max: 5, timeWindow: '1 hour' }`. Регэксп `^\+7\d{10}$` требует ровно 10 цифр после `+7` **и не знает**, что цифры внутри могут быть искажённым номером с восьмёрки — искажённый `+78999123456` (10 цифр после `+7`: `8999123456`) формально проходит regex, поэтому баг маски не ловится ни на клиенте, ни на сервере (это и есть механизм молчаливой потери лида, описанный QA). `consent: { const: true }` — по умолчанию AJV/Fastify коэрсит типы (`coerceTypes` включён глобально, отдельного отключения в `api/src/index.ts` нет), поэтому строка `"true"` в теле запроса тоже пройдёт как `true` — совпадает с наблюдением QA №3.

`api/src/controllers/landing.controller.ts:submitCallbackRequest` → `landingService.submitCallbackRequest` (`api/src/services/landing.service.ts`):
```ts
async submitCallbackRequest(input: CallbackRequestInput): Promise<void> {
  await prisma.callbackRequest.create({ data: input });
  void telegramNotifier.callbackRequest({ email: input.email, phone: input.phone, abLanding: input.abLanding });
},
```
Запись в БД дожидается ответа (правильно, `204` реально означает «сохранено»), отправка в Telegram — `void`, fire-and-forget, ошибка в ней не откатывает и не логируется здесь явно (полагается на `telegramService`/лог внутри него — отдельно не проверялось, не в периметре MIA-207). `ipAddress`/`userAgent` берутся `extractConsentMeta(request)` → `request.ip`/`user-agent`, `request.ip` резолвится через `trustProxy: true` (`api/src/index.ts:60`, комментарий в коде: «Trust X-Forwarded-For from nginx so req.ip resolves to the real client IP») — это тот же механизм, из-за которого QA обошёл rate-limit подменой заголовка (см. «Открытые вопросы»).

`api/src/services/telegram/telegram-notifier.ts:callbackRequest()` шлёт в чат `'curator'` (`TELEGRAM_CHATS.curator`) — тот же чат, что и обычная заявка «Связаться с куратором» из тренажёра, подтверждает комментарий Kirill про «чат Mia 360 Product». `telegram-digest-scheduler.service.ts` отдельно считает `prisma.callbackRequest.count({ where: { createdAt: { gte: start, lt: end } } }))` за прошедшие сутки по МСК и добавляет строку «Звонок куратора (лендинг): N» в `dailyDigest`, но только при `N > 0` (`...(s.callbackRequests > 0 ? [...] : [])`) — на дне без заявок строка просто не появится, это ожидаемо, не баг.

### Баг маски телефона — `frontend/components/ui/phone-input.vue`

Компонент **не входит в список файлов MR !519** — он существовал раньше (использовался только в styleguide) и MIA-207 впервые вывел его в форме звонка куратора (`landing-v2-callback-modal.vue:86`, `<UiPhoneInput v-model="phone" ...>`), тем самым сделав существовавший баг маски продовым.

Полный код маски:
```vue
const FORMATS = {
  ru: { mask: '+7 (###) ###-##-##', placeholder: '+7 (999) 000-00-00', maxlength: 18 },
  uz: { mask: '+998 (##) ###-##-##', placeholder: '+998 (97) 000-00-00', maxlength: 20 },
} as const;
...
<input v-model="model" v-maska="format.mask" ... :maxlength="format.maxlength" />
```
Маска `'+7 (###) ###-##-##'` содержит ровно 10 символов `#` (3+3+2+2) — именно столько цифр она принимает; `+7 (` — статический литерал, который директива `v-maska` подставляет сама и **не** заполняет вводимыми символами. Директива `vMaska` (пакет `maska`, `frontend/plugins/maska.ts`) при вводе просто раскладывает набранные цифры по слотам `#` по порядку, слева направо, ничего не зная про то, что первая набранная цифра может быть телефонным префиксом «8» или «7», который по российской традиции набора нужно отбросить, а не поместить в слот кода города/оператора.

В результате при вводе в пустое поле `89991234567` (11 цифр, набор «по-старому», с восьмёрки) маска берёт **первые 10** цифр как есть — `8999123456` — и раскладывает их по слотам, отбрасывая 11-ю (`7`): поле показывает `+7 (899) 912-34-56`. Дальше эта строка уходит в `normalizeRuPhone` (`utils/normalize-phone.ts`) уже как значение поля:
```ts
export const normalizeRuPhone = (raw: string): string | null => {
  const digits = raw.replace(/\D/g, ''); // "78999123456" (11 цифр)
  if (digits.length === 11 && (digits.startsWith('7') || digits.startsWith('8'))) {
    return `+7${digits.slice(1)}`; // "+7" + "8999123456" = "+78999123456"
  }
  ...
};
```
`normalizeRuPhone` сама по себе написана правильно (отрезала бы ведущую 7/8, если бы та осталась первой цифрой сырой строки цифр) — но маска уже необратимо потеряла информацию о том, что «8» в начале была служебным префиксом, а не частью абонентского номера: к моменту, когда `normalizeRuPhone` видит строку, её 11 цифр — это `7` (из статического `+7` маски) + `8999123456` (10 «полезных» слотов, где первый на самом деле не код города, а исходная восьмёрка). Итог — `+78999123456` вместо верного `+79991234567`. Это в точности воспроизводит таблицу из отчёта QA.

Ключевое расхождение с регистрацией: `frontend/pages/register.vue` **не использует `UiPhoneInput`/маску `v-maska` вовсе** — обычный `UiInput` + собственная нормализация на `blur`:
```ts
// register.vue
const normalizePhoneInput = () => {
  const market = isUz.value ? 'uz' : 'ru';
  const normalized = normalizePhone(data.value.parent.phone, market); // utils/parent-phone.ts
  if (normalized && isValidPhone(normalized, market)) data.value.parent.phone = normalized;
};
```
`normalizePhone` (`frontend/utils/parent-phone.ts`, **третья**, отдельная от `normalize-phone.ts` копия похожей логики) работает над уже введённой пользователем сырой строкой целиком, а не посимвольно через маску:
```ts
export const normalizePhone = (raw: string, market: Market): string => {
  const digits = raw.replace(/\D/g, '');
  if (!digits) return '';
  if (market === 'uz') return digits.startsWith('998') ? `+${digits}` : `+998${digits}`;
  const ru = digits.startsWith('8') ? `7${digits.slice(1)}` : digits.startsWith('7') ? digits : `7${digits}`;
  return `+${ru}`;
};
```
Здесь `digits.startsWith('8') ? '7' + digits.slice(1) : ...` явно распознаёт и срезает ведущую «8», заменяя её на «7» **до** того, как строка вообще куда-то улетает — ровно то, чего не умеет маска в `phone-input.vue`. Поле ввода в `register.vue` при этом никак не маскируется во время печати (пользователь видит сырой текст, форматирование применяется только на `blur`), поэтому у поля регистрации в принципе нет промежуточного состояния, где посимвольная раскладка могла бы отрезать не ту цифру.

Итого в кодовой базе **три независимых утилиты нормализации телефона** с разной степенью корректности на входе с восьмёрки: `utils/normalize-phone.ts` (`normalizeRuPhone`, callback-модалка, submit-время — сама по себе верна), `utils/parent-phone.ts` (`normalizePhone`/`isValidPhone`, `register.vue`, `blur`-время — верна), и маска `v-maska` в `phone-input.vue` (callback-модалка, ввод-время — **не** верна и искажает данные раньше, чем любая из двух нормализаций успевает их увидеть).

Наводка QA (не проверялась отдельно, но логически верна по коду): фикс — либо научить маску понимать ведущие 8/7 (например, срезать первую цифру при попытке ввести 11-ю цифру в уже заполненные 10 слотов), либо в `landing-v2-callback-modal.vue` заменить `<UiPhoneInput>` на тот же паттерн, что в `register.vue` (`UiInput` + нормализация на `blur`, без посимвольной маски).

### 5. Форма «Хочу звонок от куратора» — happy path и валидации

15. Открыть модалку — заголовок «Звонок от куратора», поля Email/Телефон, чекбокс согласия со ссылкой на `/privacy-policy` (открывается, `200`, `target="_blank"`).
16. Пустая отправка (клик по «Жду звонка» без заполнения) — запрос не уходит, под кнопкой/над ней текст с ошибкой («Проверьте email и телефон.» либо про согласие — в зависимости от того, что не заполнено), поля подсвечены (`:error`).
17. Невалидный email (`без-собаки`, `a@b`), телефон короче/длиннее нормы, без галочки согласия — каждый случай отдельно не даёт отправить, `canSubmit=false`.
18. Валидные email+телефон (**набранный не с восьмёрки**, см. кейс «известный баг» ниже для восьмёрки отдельно), без согласия → сообщение именно про согласие («Нужно согласие на обработку данных.»).
19. Корректная отправка: кнопка «Жду звонка» → «Отправляем…», задизейблена на время запроса; успех → «Спасибо! Куратор перезвонит вам в ближайшее время.» → «Хорошо» закрывает модалку.
20. Открыть модалку повторно после успешной отправки — поля пустые (сброшены).
21. Смоделировать ошибку сети/сервера (devtools offline или временно сломать эндпоинт) — единый текст «Не удалось отправить заявку. Попробуйте ещё раз.», поля **не** сбрасываются (в отличие от успеха), после восстановления сети повторная отправка с теми же данными проходит.
22. На бэке (через API-клиент/Postman, не только форму): `consent: false` или отсутствие поля → `400`; телефон не по формату `^\+7\d{10}$` → `400`.
23. 6-й запрос за час с одного адреса → `429` — форма должна как-то дать понять, что лимит исчерпан (см. «Открытые вопросы» про формулировку).

### 6. [ЗНАЧИМО] Известный, ещё не исправленный баг — маска телефона с ведущей «8»

Отдельный прогон именно этого сценария нужен на каждом ретесте до фикса — самый быстрый способ подтвердить, чинили баг или нет.

24. Открыть модалку «Хочу звонок от куратора» на чистой странице (поле телефона пустое).
25. Набрать **подряд, без пауз и без вставки из буфера**, `89991234567` (11 цифр, с восьмёрки).
26. Зафиксировать, что показывает поле: ожидание по багу — `+7 (899) 912-34-56` (в поле осталась восьмёрка на месте кода города/оператора, последняя цифра «7» потеряна).
27. Заполнить валидный email, поставить согласие, перехватить тело запроса (devtools → Network) при отправке.
28. Сверить `phone` в теле запроса с таблицей:

| Набрано в пустое поле | Ожидается в поле (по коду) | Ожидается в `phone` запроса |
|---|---|---|
| `89991234567` | `+7 (899) 912-34-56` | `+78999123456` — **баг, искажённый номер** |
| `79991234567` | `+7 (999) 123-45-67` | `+79991234567` — корректно |
| `+79991234567` | `+7 (999) 123-45-67` | `+79991234567` — корректно |
| `9991234567` | `+7 (999) 123-45-67` | `+79991234567` — корректно |

29. Убедиться, что форма НЕ показывает ошибку валидации для искажённого номера из строки 1 — `canSubmit=true`, `204` от сервера (сервер тоже не отбивает, т.к. `+78999123456` формально проходит `^\+7\d{10}$`).
30. Если баг всё ещё воспроизводится — оставить тикет в текущем статусе/эскалировать, зафиксировав точное поведение по этой таблице; если исправлен — перепройти также вставку из буфера (`Ctrl+V`) с числом с восьмёрки и с международным `+7`, чтобы убедиться, что фикс не завязан только на посимвольный ввод.

## Аналитика/API

- `LANDING_PAY_CLICKED = 'landing_pay_clicked'` (`frontend/constants/analytics-events.ts:239`) — трекается и при клике по платной карточке (`{ tariff_id: slug }`, `landing-v2-pricing.vue:onPay`), и по бесплатной, если она есть (`{ tariff_id: null }`, `onFree`); стандартные поля `ab_variant`/`ab_landing`/`is_logged_in` добавляются на уровне `useLandingAnalytics` — сверить в Метрике, что для `plans` они приходят как `h3`/`plans` (по докладу QA — приходят).
- Дальше по воронке — `auth_signup_submit`, `binding_redirect`, `freemium_paywall_show` (общие события регистрации/оплаты, не специфичные для MIA-207, но участвуют в конверсии `plans`).
- **Форма «Хочу звонок от куратора» не трекается отдельным событием вовсе** — ни открытие модалки, ни попытка отправки, ни успех/ошибка не идут в `useLandingAnalytics`/Метрику (в `landing-v2-callback-modal.vue` нет ни одного вызова `track(...)`, проверено). Видимость воронки по этой кнопке есть только через сырое количество записей в БД/Telegram-дайджест (`callbackRequests`), без промежуточных шагов «открыл → начал вводить → отправил». Если аналитика ожидает сравнивать варианты по этой кнопке в Метрике — сейчас нечем; стоит уточнить у автора задачи/аналитика, ожидалось ли отдельное событие.
- `POST /landing/callback` — контракт: `{ email, phone: '+7XXXXXXXXXX', consent: true, abLanding?: string|null }` → `204`; `400` на невалидной схеме; rate-limit `5/час` (`config.rateLimit`, роут `api/src/routes/landing.routes.ts`); телефон валидируется только regex-ом `^\+7\d{10}$`, который не отличает корректный номер от искажённого маской (см. «Реализация» → баг).
- Заявка пишется в `prisma.callbackRequest` (новая таблица, `api/prisma/migrations/20260924120000_add_callback_request`) и параллельно (`void`, не блокирует ответ) уходит в Telegram-чат `curator` тем же каналом, что и обычные заявки «Связаться с куратором» из тренажёра; за сутки МСК считается `telegram-digest-scheduler.service.ts` и показывается в дневной сводке строкой «Звонок куратора (лендинг): N» (только если `N > 0`).
- `api/src/data/ab-tests.ts` и `frontend/data/ab-tests.ts` сверены построчно на этом коммите — расхождений в наборе вариантов/весов/`tariffs` для `pricing.h3` и `landing.plans` нет.

## Открытые вопросы

- **Блокер, не исправлен на момент записи**: маска телефона в `frontend/components/ui/phone-input.vue` (`v-maska="'+7 (###) ###-##-##'"`) искажает номер, набранный с ведущей «8» (`89991234567` → в запросе уходит `+78999123456` вместо `+79991234567`); ни клиентская, ни серверная валидация (`^\+7\d{10}$`) это не ловят, т.к. искажённый номер формально корректен по формату — заявка реально уходит куратору на чужой номер, форма не даёт об этом знать. Подробное воспроизведение — тест-кейс 6. Компонент существовал до MIA-207 (использовался только в styleguide), тикет впервые вывел его в продовый сценарий через `landing-v2-callback-modal.vue`.
- **Обход rate-limit подменой `X-Forwarded-For`** (наблюдение QA, не блокер MIA-207 как такового, но касается конкретно этого анонимного роута особенно остро — он пишет в чат кураторов и в БД): в `api/src/index.ts:60` `trustProxy: true`, а nginx перед бэкендом, по всей видимости, **дописывает** адрес в существующий заголовок, а не заменяет его — то есть клиент может подставить свой `X-Forwarded-For` и остаться доверенным первым адресом в цепочке. Похоже, касается вообще всех rate-limit роутов проекта (все они читают `request.ip`), но здесь особенно критично из-за интеграции с Telegram/БД без авторизации. Кандидат на отдельный тикет вне MIA-207.
- 429 на форме звонка показывается тем же текстом, что и обычная ошибка — «Не удалось отправить заявку. Попробуйте ещё раз.» — хотя повтор технически не пройдёт ещё до часа. Стоит завести отдельный текст для 429, раз уж лимит жёсткий (5/час).
- По наблюдению QA, невалидные запросы (400/415) тоже расходуют лимит в 5/час — если это подтвердится (rate-limit hook у `@fastify/rate-limit` по умолчанию срабатывает раньше схемной валидации), пользователь, несколько раз ошибившийся с форматом телефона/email, рискует упереться в лимит раньше, чем отправит валидную заявку.
- `consent: "true"` строкой (а не булевым) на бэке проходит как `204` — AJV/Fastify коэрсит типы по умолчанию, `const: true` в схеме не защищает от строкового значения так строго, как могло задумываться.
- UZ-витрина всё равно ставит куки `ab_landing=plans`/`ab_variant=h3`, хотя фактически рендерит `classic` — при разборе результатов теста конверсии `plans` нужно фильтровать по рынку, иначе UZ-регистрации попадут в когорту `plans`/`h3`, которую они по факту не видели (аналогично уже известному механизму бага MIA-204, но здесь это не блокер для UI — сам `plans`-лендинг на UZ не показывается некорректно, просто когорта в аналитике может быть «грязной»).
- С `/select-tariff` после регистрации можно уйти по «Позже, перейти к занятиям» во freemium — так и задумано архитектурно, но при чтении конверсии `plans` (где по описанию тарифа «бесплатного тарифа якобы нет») об этом стоит помнить: часть «конверсии `plans`» на самом деле может быть freemium-обходом, а не оплатой одного из двух тарифов.
- Форма звонка не трекается ни одним analytics-событием (см. «Аналитика/API») — если для сравнения вариантов ожидалась воронка «открыл модалку → отправил → успех», сейчас её взять неоткуда кроме сырого счётчика в БД/дайджесте.
- Не покрыто в этом прогоне ни QA, ни этим ревью кода: фактическая доставка сообщения в Telegram-чат кураторов и в дневную сводку (нет внешнего канала для чтения чата; косвенно подтверждается только тем, что API отвечает `204` и запись реально появляется в БД) и проверка каталога тарифов на проде — вне периметра QA.
- Мелкое несоответствие подписей (не баг, к сведению): кнопка, открывающая модалку — «Хочу звонок от куратора», кнопка отправки внутри неё — «Жду звонка»; стоит свериться с макетом, ожидалась ли единая формулировка.
