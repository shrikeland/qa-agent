## Контекст

До этой задачи добавить второго (и далее) ребёнка можно было только из раздела «Подписка» кабинета родителя — кнопка жила внутри блока с местами, который рендерился только при `billing.status !== null`, то есть родитель без записи о подписке кнопки вовсе не видел. Пустой кабинет (ни одного ребёнка) вёл на публичную регистрацию, а не в тот же флоу.

Скоуп MIA-200 (`## Скоуп`/`## Acceptance` в тикете): кнопка «Добавить ребёнка» в меню кабинета под списком детей — всегда, а не только из «Подписки»; общий диалог добавления (подтверждение → ссылка ребёнка с копированием/шарингом → статус места: сел на оплаченное / пока бесплатно + переход к оплате); пустой экран кабинета ведёт в тот же диалог; кнопка в «Подписке» открывает его же.

## Реализация

### Общий диалог — `frontend/components/parent/parent-add-child-modal.vue`

`props: { open: boolean; source: 'sidebar' | 'billing' | 'empty' }`, шаг `step: 'confirm' | 'sending' | 'done' | 'error'`.

- **Создание** (`create()`): гард от повторного клика; `POST /parent/children` → `{ childId, linkToken, seated }`; трек `ANALYTICS_EVENTS.PARENT_CHILD_ADDED` c `{ seated, source }`; **с MR !509** `emit('added', result)` передаёт наружу весь ответ (раньше эмитился пустой `added: []`, шелл просто перечитывал список, не зная, кого добавили).
- **Ссылка**: `computed` из `linkToken`, приходит сразу в ответе — отдельного запроса не требуется.
- **Нельзя закрыть во время запроса**: `UiModal :closable="step !== 'sending'"` — гасит `Escape`, клик по фону и убирает крестик из разметки (`v-if="closable"`); кнопки «Отмена»/«Добавить ребёнка» задизейблены тем же условием.
- **Экран `'done'`**: `AuthStudentLinkSuccess` (переиспользованный компонент регистрации, ссылка+«Копировать»+WhatsApp/Telegram) с заголовком «Ребёнок добавлен»; в слоте `#reminders`:
  - `added.seated === true` → «Ребёнок сел на свободное оплаченное место — курс открыт полностью.», без кнопки оплаты;
  - `added.seated === false` → «Свободного оплаченного места нет, поэтому пока он занимается бесплатно — открыта одна тема.» + `UiButton «Оплатить место»` (`goBilling()` → `emit('go-billing')` + `emit('close')`);
  - в обоих случаях: «Ссылку можно скопировать позже — в разделе «Подписка», рядом с каждым ребёнком.» — **текст сменился** с версии MR !459 («она лежит в разделе «Обзор» этого ребёнка»); правку внёс не MIA-200, а `06c676dd`, но она формирует ожидание для теста повторного получения ссылки.
- **Ошибка**: «Не получилось добавить ребёнка — попробуйте ещё раз.», кнопка → «Повторить», диалог остаётся закрываемым.

### Точки входа — три источника, один диалог (`frontend/pages/parent/index.vue`)

Состояние диалога (`addChildOpen`/`addChildSource`) поднято в шелл; `<ParentAddChildModal>` — вне веток `state`, чтобы переход `no-children → ready` не размонтировал диалог со ссылкой.

1. **Меню (сайдбар)** — `frontend/components/parent/parent-sidebar.vue`, кнопка «Добавить ребёнка» (иконка `UserPlus`, класс `.parent-kid--add`) лежит **внутри** `<div v-if="props.children.length" class="parent-sidebar__kids">`, визуально под списком детей → `emit('add-child')` → `openAddChild('sidebar')`. Сайдбар не рендерится в `no-children`, так что условие `v-if` не мешает: кнопка в меню видна ровно когда видно меню, т.е. у семьи есть хотя бы один ребёнок.
2. **Пустой экран** — `index.vue`, ветка `state === 'no-children'`: «Ребёнок ещё не добавлен» + `<button @click="openAddChild('empty')">Добавить ребёнка</button>` — публичная регистрация больше не задействована.
3. **«Подписка»** — `frontend/components/parent/parent-billing.vue`, низ секции «Дети и места»: `<button @click="emit('add-child')">Добавить ребёнка</button>` → `openAddChild('billing')`. Ветка `billing && billing.status === null` (подписки вообще нет) по-прежнему выше и без блока «Дети и места»/кнопки — этот код ни MR !459, ни MR !509 не трогали (см. «Открытые вопросы» — практически недостижимый край).

### После добавления — куда попадает родитель (правка MR !509, `index.vue:onChildAdded`)

```
const onChildAdded = async (added: ParentAddChildResponse) => {
  const opensNewChild = addChildSource.value !== 'billing';
  if (opensNewChild) { setChild(added.childId); setSection('overview'); }
  await refresh();
  if (opensNewChild) setChild(added.childId);
  await billingSection.value?.refresh();
};
```

- Источники `'sidebar'` и `'empty'` → кабинет переключается на «Обзор» **нового** ребёнка (до MR !509 модалка просто эмитила `added: []` без id, и `index.vue` только обновлял список — активным оставался прежний ребёнок/раздел).
- Источник `'billing'` → раздел не меняется, родитель остаётся в «Подписке» (там же кнопка и была нажата), список «Дети и места» обновляется через `billingSection.value.refresh()`.
- `setChild` вызывается дважды (до и после `refresh()`) намеренно: если `refresh()` попадает на уже летящий запрос списка детей (стартовавший до создания), тот ответ не может содержать нового ребёнка и переключил бы `childId` обратно на первого — второй `setChild` после `refresh()` это перекрывает.

### Статус места ребёнка в «Дети и места» (правка MR !509, бэкенд)

`api/src/services/parent-billing.service.ts`, `buildChildren()`: раньше подписка строки ребёнка искалась по `subscription.studentId` (`byStudent`) — у ребёнка на **чужом** (семейном) месте `studentId` подписки указывает на первого ребёнка, поэтому второй получал `subscriptionId: null, status: null` и в интерфейсе выглядел неоплаченным, хотя фактически имел полный доступ через `subscriptionSlot`. Теперь добавлена карта `bySeat` — соответствие `studentId → его подписка через seat.subscriptionId`, и подписка строки берётся `bySeat.get(id) ?? byStudent.get(id)`. Новое булево поле `BillingChild.ownsSubscription` (`sub?.studentId === student.id`) отличает «владельца» подписки от «сидящего на чужом месте»:
- `childStatusLine()` во `frontend/components/parent/parent-billing.vue` теперь для ребёнка на семейном месте показывает тот же статус/«доступ до», что и у владельца, вместо «Без подписки — занимается бесплатно»;
- `nextChargeAt`/`nextChargeAmount` (сумма и дата следующего списания) показываются **только** в строке владельца (`ownsSubscription`) — одно семейное списание не дублируется на каждой строке;
- `canBuySeat()` — кнопка «Оплатить место»/«Повторить оплату» теперь требует `ownsSubscription`, иначе покупка с чужой строки открыла бы вторую подписку вместо оплаты семейной;
- `canDeleteChild()` — раньше `!signedIn && !status`, теперь `!signedIn && !ownsSubscription` — ошибочно добавленного ребёнка на свободном семейном месте по-прежнему можно удалить (место возвращается семье), но того, кто уже открыл **собственную** подписку, — нет.

Тесты (`api/src/services/__tests__/parent-billing.service.test.ts`, `frontend/tests/parent-billing.test.ts`) добавлены именно под эти три пункта.

### Бэкенд создания ребёнка (не менялся ни в MR !459, ни в MR !509)

`FamilyService.addChild(parentId)` (`api/src/services/family.service.ts`): ищет свободное место семьи, создаёт «пустого» ученика, при наличии места занимает его, выпускает `accessLink` (TTL `ACCESS_LINK_TTL_DAYS`), возвращает `{ childId, linkToken, seated: !!free }`. Контракт `POST /parent/children` не менялся.

### Известный, ещё не исправленный баг: онбординг перекрывает «Обзор» нового ребёнка

`frontend/pages/parent/index.vue`:
```
const showOnboarding = computed(() => state.value === 'ready' && !onboardingDone.value);
...
<ParentOnboarding v-if="showOnboarding" ... @finished="onOnboardingFinished" />
```
`ParentOnboarding` (`frontend/components/parent/parent-onboarding.vue`) — полноэкранный оверлей (`position: fixed; inset: 0; z-index: 40`), рендерится в шаблоне **до** веток `state`, то есть поверх всего кабинета, включая только что открытый «Обзор». `onboardingDone` инициализируется из `userStore.getUser?.onboarding?.parentCabinetDoneAt` — у семьи, которая до этого была в `no-children`, кабинет ни разу не показывался в `ready`, флаг не проставлен. Когда родитель с пустого экрана добавляет первого ребёнка, `state` переключается на `'ready'` ровно в тот момент, когда MIA-200 пытается открыть «Обзор» этого ребёнка — и `showOnboarding` становится `true` одновременно с этим, перекрывая экран с только что созданной ссылкой. Кнопки онбординга «Понятно»/«Пропустить» обе ведут в `finish()` → `markOnboarding('parentCabinetDoneAt')` + `router.push('${ROUTES.selectTariff}?from=register')` — то есть родитель не просто теряет вид «Обзора», а вообще уводится со страницы кабинета на выбор тарифа, минуя и ссылку, и сам кабинет.

Это не регрессия MR !459/509 в узком смысле (онбординг существовал и раньше), но именно MIA-200 впервые создал ситуацию «пустая семья → добавление ребёнка → кабинет остаётся открытым на „Обзоре"», в которой этот оверлей стал заметен и превратился в блокер acceptance-критерия «ссылка ребёнка видна сразу». Ребёнок и ссылка при этом реально создаются и доступны в API/DOM за оверлеем — баг чисто в навигации/UI, не в данных.

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Добавление ребёнка из меню кабинета (happy path)

1. Родитель с ≥1 ребёнком (сайдбар виден). Под списком детей в меню — «Добавить ребёнка» (пунктирный аватар, приглушённый текст). Кликнуть.
2. Открывается диалог «Добавить ребёнка»: текст про создание аккаунта и про место/бесплатный доступ, кнопки «Отмена» / «Добавить ребёнка».
3. Нажать «Добавить ребёнка». Во время запроса: подпись кнопки → «Добавляем…», обе кнопки задизейблены, крестика закрытия в шапке нет вовсе.
4. Экран успеха: заголовок «Ребёнок добавлен», персональная ссылка сразу показана, поле+«Копировать»+иконки WhatsApp/Telegram, текст «...в разделе «Подписка», рядом с каждым ребёнком.».
5. «Готово» → диалог закрывается. Ожидается: новый ребёнок сразу в списке детей сайдбара, без `F5`. Так как открыт был не пустой экран (`source='sidebar'`), активный раздел/ребёнок **не переключается** — родитель остаётся там, где был.

### 2. Добавление с пустого экрана кабинета — навигация после закрытия (ЗНАЧИМО: связано с открытым багом)

6. Родитель без единого ребёнка (`state === 'no-children'`). «Ребёнок ещё не добавлен», кнопка «Добавить ребёнка» — не ссылка на `/register`, URL не меняется.
7. Клик → тот же диалог, что в кейсе 1.
8. Пройти happy path, получить ссылку, нажать «Готово».
9. **Ожидается по коду/скоупу MR !509**: кабинет переключается из пустого экрана на «Обзор» только что созданного ребёнка, без перезагрузки, ссылка видна.
10. **Фактически (открытый баг, воспроизвести и подтвердить статус на билде QA)**: если у аккаунта ещё не был показан онбординг кабинета (`user.onboarding.parentCabinetDoneAt` не проставлен — типичный случай для семьи, которая только что была `no-children`), поверх «Обзора» появляется приветственный оверлей (3 слайда, «Дальше»/«Понятно»/«Пропустить»). Нажатие «Пропустить» **или** «Понятно» на последнем слайде уводит на `/select-tariff?from=register` вместо того, чтобы оставить родителя на «Обзоре» со ссылкой. Зафиксировать: ссылку в принципе на этом пути увидеть не удаётся, не покинув «Обзор» одним из способов ниже.
11. Обходной путь для проверки, что ребёнок и ссылка реально созданы: со страницы `/select-tariff` вернуться в кабинет (например, по прямому URL `/parent`) — сайдбар должен показывать нового ребёнка; открыть его «Обзор» вручную → должен показать «Ребёнок ещё не заходил в тренажёр» + «Скопировать ссылку» (см. кейс 8).
12. Если у аккаунта `parentCabinetDoneAt` уже проставлен (родитель у которого до этого уже были дети, потом всех удалили, либо тестовый флаг выставлен вручную) — онбординг не покажется, и navigation-фикс MR !509 должен отрабатывать чисто: проверить этот сценарий отдельно, чтобы отделить «баг онбординга» от возможной регрессии в самой навигации.

### 3. Добавление у семьи без активной/просроченной подписки

13. Родитель с истёкшей/отменённой/ещё не купленной подпиской, но с ≥1 ребёнком — кнопка в меню видна и кликабельна, диалог работает как в кейсе 1 (раньше при отсутствии активной подписки в «Подписке» блока с кнопкой не было вовсе — вход через меню от статуса подписки не зависит).
14. Отдельно (маловероятный край, не блокер): семья вообще без записи о подписке (`billing.status === null`) — «Подписка» показывает только «Подписки пока нет...» + «Выбрать тариф», без «Дети и места» и без кнопки добавления (код не менялся). Кнопка в сайдбаре при этом всё равно должна работать.

### 4. Свободное оплаченное место → ребёнок садится на него, отображается как «покрытый»

15. Семья с двухместным (и более) тарифом, где занято меньше мест, чем куплено. Добавить ребёнка любым способом.
16. Экран успеха: «Ребёнок сел на свободное оплаченное место — курс открыт полностью.», без кнопки «Оплатить место».
17. Открыть «Подписка» → у нового ребёнка в «Дети и места»: статус **такой же, как у владельца подписки** (например «Пробный период · доступ до …» или «Активна · доступ до …»), **без** «Оплатить место»/«Повторить оплату», **без** собственной суммы следующего списания (сумма и дата — только в строке владельца подписки). Есть «Ссылка для входа», «Изменить имя», «Указать класс» (если класс не указан). Проверить также «Удалить» — для ребёнка на чужом месте, который ещё не заходил, кнопка должна остаться доступной (это не «своя» подписка), после удаления — место возвращается в «Свободное место».

### 5. Свободного места нет → «пока бесплатно» + переход к оплате

18. Семья без свободных мест (места заняты либо подписки не было). Добавить ребёнка любым способом.
19. Экран успеха: «Свободного оплаченного места нет, поэтому пока он занимается бесплатно — открыта одна тема.» + кнопка «Оплатить место».
20. Нажать «Оплатить место» → диалог закрывается, кабинет переключается на «Подписку» (внутренний `setSection('billing')`, без перехода на отдельный домен/страницу).
21. В «Подписке» у нового ребёнка: «Без подписки — занимается бесплатно» (или «Место не оплачено — занимается бесплатно», если статус `awaiting_payment`/`binding_failed`) + кнопка «Оплатить место»/«Повторить оплату» (эта кнопка реально инициирует покупку через `POST /parent/children/:id/subscription`, в отличие от кнопки в диалоге, которая только переключает раздел).

### 6. Кнопка в «Подписке» открывает тот же диалог и не меняет раздел

22. В «Подписке» нажать «Добавить ребёнка» внизу блока «Дети и места». Диалог визуально идентичен варианту из меню/пустого экрана.
23. Пройти happy path. Ожидается: новый ребёнок появляется и в сайдбаре, и строкой в «Дети и места» без ручного обновления страницы; **раздел остаётся «Подписка»** (в отличие от кейсов 2/6.1 — навигация на «Обзор» происходит только для источников `sidebar`/`empty`, не для `billing`).

### 7. Диалог нельзя закрыть во время запроса

24. Открыть диалог, нажать «Добавить ребёнка», сразу (по возможности придушить сеть до Slow 3G в devtools):
    - `Escape` — диалог остаётся открытым;
    - клик по затемнённому фону — остаётся открытым;
    - крестика закрытия в шапке нет вовсе (не задизейблен — отсутствует в DOM).
25. После ответа сервера — ребёнок создан (проверяется списком детей), ссылка показана; `Escape`/фон/крестик снова закрывают диалог штатно.

### 8. Ошибка при создании

26. Смоделировать сетевую/серверную ошибку на `POST /parent/children` (devtools offline/block) → диалог остаётся на форме, текст «Не получилось добавить ребёнка — попробуйте ещё раз.», кнопка → «Повторить», диалог закрываем.
27. Снять блокировку, нажать «Повторить» — обычный happy path.

### 9. Повторное получение ссылки — обновлённый путь через «Подписку» + старый путь через «Обзор»

28. Добавить ребёнка, закрыть диалог сразу, ссылку не копировать.
29. В «Подписке», в строке этого ребёнка нажать «Ссылка для входа» → подпись меняется на «Ссылка скопирована», в буфере — рабочая ссылка того же ребёнка (эндпоинт `POST /parent/children/:id/login-link`, отдельный от диалога добавления — может выпустить **новую** ссылку, если прежняя уже сгорела при входе ребёнка; для только что созданного, ещё не заходившего ребёнка должна вернуть ту же ссылку, что показал диалог).
30. Отдельно проверить старый путь (если баг из кейса 2 не мешает добраться до «Обзора»): выбрать ребёнка → «Обзор» → пока `lastSeenAt === null`, показывается «Ребёнок ещё не заходил в тренажёр» + «Скопировать ссылку» (без похода в «Подписку»/без нового запроса — читает уже выданный `accessLink`). После первого входа ребёнка по ссылке этот блок в «Обзоре» пропадает.

### 10. Шаринг ссылки в WhatsApp/Telegram — персональная, не общая

31. На экране успеха нажать иконку WhatsApp → открывается `wa.me` с текстом, содержащим ссылку именно этого ребёнка.
32. Аналогично Telegram (`t.me/share/url`).
33. Добавить подряд двух детей — ссылки в шаринге не должны совпадать и не залипать на предыдущем ребёнке.

### 11. Состояния и адаптив

34. Пустое состояние (кейс 2), загрузка («Загружаем…» в «Подписке»/«Обзоре»), ошибка сети при открытии «Подписки»/«Обзора» («Не удалось загрузить...» + «Повторить»), ошибка при добавлении (кейс 8) — все проверить визуально.
35. Мобильная ширина (≤1079px — брейкпоинт сайдбара, `NARROW_MAX_WIDTH`): кнопка «Добавить ребёнка» доступна в выезжающем drawer, после клика drawer закрывается (`closeDrawer()` в `openAddChild`); диалог добавления корректно рендерится на узком экране (сетка кнопок `1fr/1.7fr` в `.add-child__actions`).
36. Десктоп: диалог, сайдбар и раздел «Подписка» — стандартная раскладка, без ограничения по ширине специфичного для этой фичи кода.

## Аналитика/API

- `PARENT_CHILD_ADDED = 'parent_child_added'` (`frontend/constants/analytics-events.ts:426`, зеркалом в `api/src/constants/analytics-events.ts:426`) — существует с MIA-96/451, в MIA-200 добавлено поле `source: 'sidebar' | 'billing' | 'empty'` в пейлоад (`{ seated, source }`) — сверить в трекере, что параметр долетает и соответствует точке входа.
- `PARENT_CHILD_LOGIN_LINK_COPIED = 'parent_child_login_link_copied'` (`:432`) — из соседнего коммита `06c676dd`, трекается при клике «Ссылка для входа» в «Подписке» с `{ result: 'success' | 'fail' }`; не самого MIA-200, но относится к тест-кейсу 9 (повторное получение ссылки) — стоит свериться заодно.
- `PARENT_CHILD_SEAT_PAID = 'parent_child_seat_paid'` (`:430`) — трекается при клике «Оплатить место»/«Повторить оплату» в самой «Подписке» (`buySeat()`), с `{ plan_slug, result }`; не путать с переходом «Оплатить место» из диалога добавления — тот раздела не меняет само событие, а лишь переключает `setSection('billing')`, отдельного события на этот клик в модалке не заведено (проверить, не ожидается ли аналитиками отдельная метка перехода — в коде её нет).
- `PARENT_CHILD_DELETED = 'parent_child_deleted'` (`:436`) — трекается при удалении ребёнка из «Дети и места», актуально для кейса 4 (удаление ребёнка с чужого места).
- Контракт `POST /parent/children` не менялся: `200 { childId, linkToken, seated }`.
- Новый для этой пары MR эндпоинт `POST /parent/children/:childId/login-link` (из `06c676dd`, не MIA-200) — используется кейсом 9; на аналитику и API-контракты MIA-200 не влияет напрямую, но участвует в проверке acceptance «ссылка доступна повторно».

## Открытые вопросы

- **Онбординг перекрывает «Обзор» нового ребёнка и уводит на `/select-tariff`** (см. «Реализация» → «Известный, ещё не исправленный баг»). Это последняя находка QA (комментарий от 2026-09-24 18:46), из-за которой тикет и был возвращён в `Testing`; фикса под неё в `master` на момент записи нет. Нужно подтвердить репродукцию по кейсу 2 и, если воспроизводится, оставить тикет открытым/эскалировать на разработчика — сам разработчик пока не комментировал эту находку.
- Раздел «Подписка» у семьи с `billing.status === null` (совсем без записи о подписке) по-прежнему не показывает ни «Дети и места», ни кнопку «Добавить ребёнка» — код этой ветки не менялся ни в MR !459, ни в MR !509; по бизнес-логике такая комбинация (дети есть, подписки нет вовсе) практически недостижима, так как подписка заводится вместе с регистрацией первого ребёнка.
- Часть UI, задействованного тест-кейсами (карточная «Подписка», «Ссылка для входа»/«Указать класс»/«Изменить имя» на строке ребёнка), пришла не из MIA-200, а из параллельного `06c676dd`. Формально это другой тикет, но он настолько плотно переплетён с добавлением ребёнка (тот же файл, тот же текст про повторное получение ссылки), что тестировать MIA-200 в отрыве от него не получится — при расхождениях с ожиданиями по этим элементам стоит уточнять, к какой задаче относится баг, прежде чем заводить его на MIA-200.
- Ветка `andreichepurchenko/mia-200-...`, указанная в `gitBranchName` тикета, в `origin` репозитория не существует — фактические ветки: `feat/MIA-200-parent-add-child` (MR !459) и `fix/MIA-200-seat-holder-billing` (MR !509), обе уже смержены в `master`; вся проверка кода в этой заметке сделана по `master`.
