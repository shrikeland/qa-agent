## Контекст

Баг: когда ответ модели на распознавание решения (доска/фото, `RecognitionStream`) не удавалось разобрать как JSON, ученик видел реплику «Возникла проблема с разбором ответа», сабмишен уходил в ошибку с пустым вердиктом — и разбирать случай было не по чему: ветка parse-fail не писала вообще ничего в БД, сырой текст ответа модели жил только в логах контейнера до ближайшего рестарта. Жалобу «Мия не приняла решение» нельзя было проверить постфактум.

**Раунд Testing 21.09 — FAIL, не по делу фикса.** QA (Andrei Chepurchenko) прогнал полную регрессию по HTTP-контракту `/api/internal/ai-usage`, диагностическому распознаванию через Socket.IO, ownership и UI — всё это прошло. Но **основной acceptance-кейс не был живьём подтверждён**: за период 18-22.09 в проде/на тесте не случилось ни одного реального парс-фейла модели, исторической строки для проверки не нашлось, а детерминированного способа заставить провайдера вернуть неразбираемый JSON в коде нет — воспроизвести баг на стенде по требованию не удалось. Формально это не FAIL по дефекту фикса, а невозможность его подтвердить без реального сбоя модели.

**23.09 — статус вернули в Ready for Test.** Разработчик (Kirill Verzhitskii) закрыл именно этот пробел не через живой сбой модели, а обойдя цепочку сбоку: отправил тестовый вызов **напрямую во внутреннюю ручку учёта** `/internal/ai-usage` со `status: 'parse_error'` и текстом в 9018 символов, и получил ожидаемую строку в `ai_usage` (усечение до 8000, цена посчитана, видна в `/admin/ai-cost` как `errors=1`); тестовую строку после проверки удалил. Отдельно оговорено: событие Sentry шлёт сам `socket-gateway` в момент живого срыва разбора, и его «искусственно не вызвать без настоящего сбоя модели» — эта часть цепочки подтверждена только юнит-тестами, не живым прогоном. Параллельно смёржен MR **!486** `test(ai-usage): покрытие записи parse_error` — юнит-тесты на api-сторону (усечение до 8000, цена не теряется).

**Важно для перепроверки:** способ подтверждения от 23.09 доказывает, что путь «status=parse_error → строка в ai_usage → видна в /admin/ai-cost» работает — но не доказывает, что реальный сорванный ответ модели действительно долетает до этого пути тем же способом, как раньше не долетал ни разу. Ключевой недостающий кусок с 21.09 не изменился: **детерминированного переключателя, чтобы заставить провайдера вернуть неразбираемый JSON, в коде по-прежнему нет.**

## Реализация

Код прочитан целиком на HEAD master (MR !455, sha `6bd95a547c9` — реализация; MR !486, sha `dea6e0de99a` — тесты api-стороны, применяется поверх).

### Откуда берётся `parseFailure`

`socket-gateway/src/sockets/helpers/recognition-response.helper.ts` — `recognitionResponseHelper()`. При неудачном `JSON.parse(chunk.text)` возвращает объект с `error: 'Возникла проблема с разбором ответа'` и **новым полем** `rawText: originalText` — исходный (не подчищенный от `\n`) текст, который прислала модель. Второй `catch` (уже после успешного `JSON.parse`, но при несовпадении со схемой) тоже несёт `rawText`, только это ветка не парс-фейла, а невалидной структуры.

`socket-gateway/src/handlers/pools/recognition.handlers.ts`, `RecognitionHandlers`:
```ts
parseFailure: ParseFailure | null = null;
...
this.parseFailure =
  parsedResponse.error && parsedResponse.rawText !== undefined ? { rawText: parsedResponse.rawText } : null;
```
Комментарий в коде объясняет намеренную логику: «Разобранный ответ снимает подозрение с предыдущего чанка» — ответ модели может прийти несколькими частями, и если поздний чанк распарсился, `parseFailure` каждый раз перезаписывается (в т.ч. в `null`), так что поток не помечается сорванным целиком из-за одной неудачной промежуточной части. Покрыто тестом `stream-abort-usage.test.ts` («a later well-formed part clears an earlier parse failure»).

### Переживание `unbind()`

`socket-gateway/src/sockets/streams/recognition.stream.ts`, `unbind()`:
```ts
// unbind подменяет handlers пустыми, и вместе с ними пропал бы сорванный разбор ответа:
// finish() пишет строку ai_usage уже после этого, а abort() - и вовсе следующим шагом.
this.parseFailure = this.handlers.parseFailure ?? this.parseFailure;
this.handlers = new RecognitionHandlers(this.id, this.userData, () => {}, () => {});
```
Это ключевой архитектурный момент фикса: `unbind()` вызывается и из `finish()`, и из `abort()` **до** записи usage, и раньше заменял `handlers` (а вместе с ним и состояние `parseFailure`) пустой заглушкой — так сорванный разбор физически не мог дожить до записи в `ai_usage`. Теперь `parseFailure` сохраняется на сам `RecognitionStream` до подмены. Покрыто тестом `stream-abort-usage.test.ts` («an unparsable answer survives unbind and reaches ai_usage»).

### Запись в `ai_usage` и Sentry-сигнал

`socket-gateway/src/sockets/streams/recognition.stream.ts`, `finish()`:
```ts
recordStreamAiUsage(this, endPayload, 'recognition', failure, this.parseFailure);
if (this.parseFailure) {
  captureError(new Error('recognition answer did not parse'), {
    kind: 'recognition_parse_error',
    streamId: this.id,
    model: endPayload?.model ?? this.model.id,
    responseId: endPayload?.responseId ?? null,
    contentLength: this.parseFailure.rawText.length,
  });
}
```
`socket-gateway/src/helpers/ai-usage.helper.ts`, `recordStreamAiUsage()`:
```ts
const rawResponse = parseFailure ? parseFailure.rawText.slice(0, RAW_RESPONSE_MAX) : null; // RAW_RESPONSE_MAX = 8000
const status = failure ?? (parseFailure ? 'parse_error' : 'ok'); // failure ('error'/'timeout') важнее parse_error
```
Явный приоритет: обрыв/таймаут важнее сорванного разбора в поле `status` (их считают отдельные счётчики отказов), но `raw_response` всё равно пишется — сорванный разбор виден по непустой колонке независимо от итогового `status`.

`api/src/services/ai-usage/ai-usage.service.ts`, `record()` режет текст ещё раз на api-стороне (`RAW_RESPONSE_MAX = 8000`, тот же лимит продублирован в двух местах — socket-gateway и api) — по комментарию в коде это намеренно: «режется здесь, а не валидацией роута: иначе длинное тело отбило бы всю строку учёта вместе с расходом». Строка **всегда** попадает в `accrueDemoSpend`/подсчёт стоимости наравне с обычным вызовом — деньги за вызов не теряются.

Миграция `api/prisma/migrations/20260918160000_ai_usage_raw_response/migration.sql`: `ALTER TABLE "ai_usage" ADD COLUMN "raw_response" TEXT` — простое nullable-поле, без дефолта.

Схема HTTP-контракта `api/src/routes/internal.routes.ts`, `aiUsageBodySchema`: `status` теперь принимает `'ok' | 'timeout' | 'error' | 'parse_error'`, `rawResponse: { type: ['string', 'null'] }` **без `maxLength`** — намеренно, комментарий рядом: «слишком длинное тело отбило бы всю строку учёта… режет его сервис, на записи», то есть длина не должна быть причиной отказа схемы, обрезка — забота сервиса.

### Sentry: сигнал есть, текста нет

`socket-gateway/src/helpers/sentry-scrub.ts`, `ALLOWED_EXTRA_KEYS` — добавлен `'responseId'` с комментарием: «Указатель на строку ai_usage: сам сорванный ответ модели остаётся в базе, в Sentry едет только сигнал, по которому её находят. Это идентификатор провайдера, не текст ученика.» Само событие (`captureError` выше) намеренно не кладёт `rawText`/`contentLength`-текст в `extra` — только длину (`contentLength`) и `responseId`; allow-list в scrub'е и так резал бы неразрешённые поля, но здесь текст изначально не передаётся в событие, а не полагается только на фильтр.

### Учёт в `/admin/ai-cost`

`api/src/admin/ai-cost.service.ts` — SQL-запросы уже считали `errors` как `COUNT(*) FILTER (WHERE status IN ('error', 'parse_error'))` (и в `breakdownForParent`, и в `dashboard`) — то есть парс-фейл автоматически попадает в тот же счётчик ошибок, что и прежние виды отказов, без отдельной колонки в UI. На фронте `frontend/pages/admin/ai-cost/index.vue:392-393` показывает всплывающую подсказку с числом ошибок/таймаутов по `surface/kind` — отдельного визуального различия «parse_error vs error» в UI нет, только общий счётчик и `title`-тултип.

- `socket-gateway/src/sockets/streams/__tests__/stream-abort-usage.test.ts` — переживание `unbind()`, восстановление после позднего валидного чанка, сравнение с `chat`-каналом (тот же таймаут-путь).

## Как перепроверить

**После выката на стенде: главный P0-сценарий — воспроизвести реальный парс-фейл живым прогоном, а не только через внутреннюю ручку.** Ручка `/internal/ai-usage` напрямую (то, что сделал разработчик 23.09) проверяет только последний отрезок цепочки — запись и агрегацию, не сам путь «модель ответила мусором → `recognitionResponseHelper` не распарсил → `parseFailure` пережил `unbind()` → строка и Sentry-сигнал». Раз детерминированного переключателя нет, единственный практический способ — гонять реальное распознавание (доска/фото) и стараться спровоцировать неразбираемый ответ (например, через нестандартный ввод/зашумлённое фото), либо ждать естественного случая на большом объёме трафика.

Если реальный парс-фейл всё же пойман (свой или замеченный в проде):
1. Проверить строку в `ai_usage`: `status='parse_error'`, `raw_response` непустой (и совпадает с текстом до 8000 символов), `cost_usd_micros` посчитан (не `null`/`0`, если провайдер вернул usage).
2. Проверить `/admin/ai-cost` — вызов должен попасть в счётчик `errors` соответствующего `surface/kind` (тултип над таймингом).
3. Проверить событие в GlitchTip (см. MIA-192 — трекер ошибок это self-hosted GlitchTip, не Sentry SaaS) с тем же `responseId`, что и в строке `ai_usage`, и убедиться, что сам текст ответа модели туда **не** попал (ни в `message`, ни в `extra`).
4. Проверить, что ученик по-прежнему видит штатную реплику «Возникла проблема с разбором ответа» (UX не должен был измениться — фикс полностью про диагностику, не про сам UX ошибки).

**Регрессия (быстрый прогон без похода за живым парс-фейлом):**
5. Обычное успешное распознавание — `status='ok'`, `raw_response IS NULL`, счётчик ошибок не растёт.
6. Таймаут/обрыв стрима (без парс-фейла) — `status='timeout'`, `raw_response IS NULL` (не путать с parse_error).
7. Ответ модели приходит несколькими чанками: первый неразбираемый, второй — валидный JSON → итоговый статус `ok`, `raw_response IS NULL` — поздний валидный чанк должен «снимать подозрение» с раннего сбоя (см. «Реализация», намеренная логика перезаписи `parseFailure`).
8. Ручной прогон описанного разработчиком метода (POST в `/internal/ai-usage` с `status: parse_error` и длинным текстом) как быстрая sanity-проверка контракта — не заменяет пункт 1, но быстро ловит регресс в схеме/усечении.

## Что посмотреть рядом

- **Два независимых места усечения до 8000** (`socket-gateway/src/helpers/ai-usage.helper.ts` и `api/src/services/ai-usage/ai-usage.service.ts`) — при будущих правках лимита легко поправить только одно место и разойтись; сейчас оба на 8000, но это не связано общей константой между сервисами.
- **`chunkFilter`/повторная логика replace `\n`** в `recognitionResponseHelper` — `chunk.text` мутируется (`chunk.text = chunk.text.replace(/\n/g, '')`) до попытки `JSON.parse`, а `rawText` сохраняет именно **исходный, домутационный** текст (`originalText`) — стоит перепроверить, что в БД действительно попадает то, что реально прислала модель, а не результат замены переносов строк, если возникнут сомнения при разборе конкретного случая.
- **`whiteboard-blob` recognition** (`PATCH /internal/whiteboard-blobs/:id/recognition`, схема принимает `rawResponse: object|null`) — отдельный, не тронутый этим MR путь распознавания с собственным хранением сырого ответа; не смешивать с `ai_usage.raw_response` при разборе логов.
- **`ai-proxy/src/helpers/sentry-scrub.ts` и `frontend/utils/sentry-scrub.ts`** — по `CLAUDE.md` это зеркальные копии одного и того же scrub-файла в 4 местах, CI-джоб `sentry_scrub_mirror_check` проверяет их идентичность; в дифф MR !455 попали и они — стоит убедиться, что `responseId` добавлен во все четыре копии одинаково, а не только в socket-gateway (в рамках этого чтения проверен только socket-gateway/api).

## Открытые вопросы

1. **Детерминированного способа спровоцировать парс-фейл модели по-прежнему нет.** Это прямо ограничивало QA 21.09 и не изменилось к 23.09 — единственное новое подтверждение (POST во `/internal/ai-usage`) проверяет запись, а не срабатывание самого условия `parseFailure`. Стоит явно решить с разработчиком: тестовый флаг/эндпоинт, дающий гарантированно неразбираемый ответ на тестовом стенде, снял бы этот риск для будущих регрессий.
2. **Sentry-сигнал (GlitchTip-событие) с `responseId` не подтверждён живым прогоном ни разу** — ни 21.09, ни 23.09. Автор прямо признаёт: «искусственно его не вызвать без настоящего сбоя модели». До первого реального инцидента это остаётся неподтверждённой частью acceptance («в Sentry - событие с тем же responseId»).
3. Доступ к панели GlitchTip для QA — тот же организационный вопрос, что и в MIA-17/MIA-192: без него пункты 3 и 2 (открытые вопросы) непроверяемы вовсе, только со слов разработчика.
