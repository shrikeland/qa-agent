## Как перепроверить

### 1. Спровоцировать `parse_error` на стенде

Естественным путём (через обычный UI тренажёра) заставить конкретную модель детерминированно вернуть неразбираемый JSON - нельзя: код не содержит ни тестового флага, ни фикстуры, ни спец-режима для принудительного вызова этой ветки (грепы по `TEST_MODE`, `forceParseError`, `mockRecognition` и подобным в `socket-gateway/src` и `ai-proxy/src` ничего не находят). Ветка реагирует на реальное поведение модели: судя по юнит-тесту, один из известных триггеров - ответ, обёрнутый в markdown-ограждение (`` ```json ... ``` ``) вместо чистого JSON, что у LLM-провайдеров иногда случается под нагрузкой или на редких промптах, но заставить это произойти по requestу нельзя.

Варианты для этого прогона:
- **Основной вариант - поднять исторические записи.** Если на тестовом стенде уже случались parse_error (в проде или на тесте до этого фикса они просто не писались никуда, но после выката фикса любые новые случаи начнут появляться сами по себе при обычном фоновом использовании тренажёра/диагностики) - искать через SQL-запрос из `docs/educational-process/recognition-flow.md` (см. выше) или через `/admin/ai-cost` (там `parse_error` учитывается в категории «ошибки», см. «Что изменено»).
- **Понаблюдать пассивно** какое-то время после выката: submit решений в тренажёре в достаточном объёме, потом свериться запросом на `status = 'parse_error'` - без гарантии, что за время QA-сессии случай воспроизведётся (вероятность зависит от поведения модели-провайдера, не от кода продукта).
- Если у QA есть доступ к метрике `sgw_recognition_parse_error_total` (Prometheus-счётчик, уже существовал в коде до этой задачи, не добавлялся этим MR) - можно свериться, был ли на стенде хоть один инцидент за нужный период, не поднимая БД напрямую.
- Специально ломать сеть/провайдера (обрывать соединение к AI на середине ответа в devtools) даст скорее `status='error'`/`'timeout'`, а не `'parse_error'` - это разные ветки в `recordCall`, не подходит как замена.

### 2. Строка в `ai_usage`

После срабатывания (см. п.1): SQL напрямую (если есть доступ к БД теста) или через `/admin/ai-cost`, где эти вызовы агрегируются в категорию «ошибки» вместе с обычным `error`.
- `status = 'parse_error'`.
- `raw_response` непустой - сырой текст ответа модели (до 8000 символов, дважды усечён - на socket-gateway перед отправкой и второй раз на api при записи).
- Цена (`cost_usd_micros`) - смотреть внимательно: по коду (`api/src/services/ai-usage/ai-usage.service.ts`, `costUsdMicros = input.usage ? computeCostUsdMicros(...) : null`) цена ненулевая ровно тогда, когда в записи есть `usage` (провайдер успел прислать токены до того, как разбор сорвался) - у типичного parse_error (модель ответила полностью, просто в неожиданном формате) `usage` из `STREAM_END` будет присутствовать, и цена должна быть ненулевой. Но если разбор сорвался на потоке, который оборвался раньше `STREAM_END` (не типичный случай для чистого parse_error, скорее пересечение с `timeout`/`error`), `usage` может быть `null`, а с ним и цена - тогда статус, вероятнее всего, будет `'timeout'`/`'error'`, а не `'parse_error'` (см. приоритет статусов в `recordCall`: `failure ?? (parseFailure ? 'parse_error' : 'ok')`). Если встретится `status='parse_error'` с нулевой ценой - стоит отдельно разобраться, это не то поведение, которое описано в тикете и подтверждено юнит-тестом.
- `response_id` заполнен (не `null`) - именно по нему ищется соответствующее событие в Sentry.

### 3. Событие в Sentry с тем же `responseId`, без сырого текста

**Ограничение проверки: живой доступ к панели `errors.mia360.ru` (self-hosted GlitchTip) организационно ограничен** - см. `notes/MIA-17.md` в этом же репозитории: «нет подтверждённого безопасного доступа к панели, отдельного от админки Mia». В этом прогоне живая проверка события в Sentry физически не выполнялась по той же причине, не из-за бага в текущей задаче.

Что проверено по коду вместо живого похода в панель (см. «Что изменено» выше):
- `captureError` вызывается с `extra: { kind: 'recognition_parse_error', streamId, model, responseId, contentLength }` - сырой текст (`rawText`/`originJson`) в этот объект не передаётся вообще, поэтому вопрос «улетит ли текст в Sentry» закрыт на уровне вызова, ещё до скраб-фильтра.
- Скраб-фильтр (`ALLOWED_EXTRA_KEYS`) отдельно подтверждён как allow-list, а не deny-list - даже гипотетическое случайное добавление поля с текстом в будущем было бы отфильтровано, если не попадёт в список разрешённых ключей явно.
- Если доступ к GlitchTip будет получен в отдельном прогоне: искать событие с `extra.kind = 'recognition_parse_error'` и сверить `extra.responseId` с `response_id` найденной строки `ai_usage` из п.2; глазами убедиться, что нигде в теле события (exception value, breadcrumbs, extra) нет фрагментов текста ответа модели длиннее пары слов - это ручная, а не автоматическая проверка, скраб-фильтр не гарантирует смысловую полноту, только структуру allow-list.

### 4. UI-поведение не изменилось

Это чисто серверная задача про логирование/диагностику - `recognitionResponseHelper` по-прежнему возвращает `error: 'Возникла проблема с разбором ответа'` в тех же условиях, что и раньше (само сообщение не менялось, только добавилось поле `rawText` в объект результата, которое до ученика не доходит). Проверить: ученик при сорванном разборе видит ту же реплику об ошибке, что и до фикса, решение по-прежнему уходит в `review-error` с пустым вердиктом - никакой новой UI-реакции (тоста, баннера, иного текста) не появилось и не должно было появиться.

### Открытые вопросы / рекомендация на следующий раунд

Ключевой acceptance-кейс (цепочка `parse_error` → `ai_usage.raw_response` → Sentry `responseId`) на этом стенде и в это окно живьём не подтверждён не из-за дефекта кода, а потому что реальный parse-fail модели на тесте не произошёл, а детерминированного способа его вызвать в коде нет (проверено дважды: см. выше). Для следующего раунда:

1. **Если случай появится сам по себе** (после выката фикса такие вызовы начнут писаться в `ai_usage`, а не теряться) - искать по SQL из `docs/educational-process/recognition-flow.md` (`status = 'parse_error'`) или по `/api/admin/ai-cost` (категория «ошибки»), и тогда закрыть эту цепочку полностью одним прогоном: строка в БД → `raw_response`/усечение/цена → событие в Sentry с тем же `responseId`.
2. **Рекомендация разработчику, если случай не появится в разумный срок** - добавить безопасный тестовый переключатель для принудительного `parse_error`, ограниченный `requireSystemToken` (как остальные `/system/test/*` роуты в `api/src/controllers/test.controller.ts`), например `POST /system/test/force-recognition-parse-error`, который на socket-gateway отдаёт заведомо неразбираемый ответ (по образцу markdown-обёрнутого JSON из `stream-abort-usage.test.ts`) для конкретного `streamId`/пользователя, не трогая реальный AI-провайдер. Без этого acceptance-кейс MIA-194 в принципе не может быть подтверждён вживую детерминированно ни в одном QA-раунде - только пассивным ожиданием или подъёмом исторических данных.
3. Доступ к панели `errors.mia360.ru` (GlitchTip) остаётся отдельным блокером (см. `notes/MIA-17.md`) - без него даже при наличии живого случая шаг с проверкой Sentry-события придётся снова закрывать «по коду», а не глазами.
