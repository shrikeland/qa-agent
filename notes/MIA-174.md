## Контекст

Продакт просил две вещи: (1) диагностику по всему курсу заменить на диагностику по темам
только первого блока (до первой контрольной), (2) внести правки в ЛК по комментариям на
доске Miro (https://miro.com/app/board/uXjVHmnVQSQ=/). MR !430 закрывает **только первый
пункт** - это явно и неоднократно подтверждено самим разработчиком в комментариях по ходу
задачи ("Правки ЛК с доски Miro в этот MR не входят - доска недоступна, скоуп по ним не
снят" / "Осталось в задаче: правки ЛК по доске Miro"). Доска Miro недоступна и агенту -
её содержимое нигде не задокументировано текстом, поэтому что именно требовалось поправить
в ЛК, из репозитория выяснить нельзя. Это открытый вопрос к постановщику, а не пропущенный
скоуп разработки - **не пиши, что "ЛК не доработан" как баг**, это заведомый remaining scope.

**Последний по времени комментарий в тикете (16.09, 19:43) - это QA FAIL**, код после него
не менялся. Это главный приоритет заметки: перепроверка находки QA и её уточнение по коду.

### Как отфильтрован первый блок

- `Diagnostic.sectionId` (поле уже существовало, было пустым у входной диагностики) теперь
  указывает на раздел первой контрольной работы - это и есть граница блока. Задаёт его
  `contentLoaderService.resolveDiagnostic()` по полю `section` из JSON файла диагностики.
- Файлы контента переключены на новую версию `v2026-09` для всех классов 5-9
  (`api/scripts/load-content.ts`, `DIAGNOSTIC_FILES`) - старые файлы (`v1`/`v2`) остаются в
  репозитории как история, не удалены.
- Заливка получила режим `--replace`: `contentLoaderService.loadDiagnosticTasks(diagnosticId, tasks, {replace: true})`
  гасит (`deletedAt = now()`) те `DiagnosticAssignment`, чьих `sourceKey` в новом файле нет,
  сам `Assignment` не трогает (на него ссылаются старые сабмишены). Без `--replace` (по
  умолчанию) поведение как раньше - только добавление, старые задачи никуда не деваются.
  Есть защита от случайного полного гашения: `loadDiagnosticTasks` бросает исключение, если
  `--replace` резолвит 0 задач ("Replace mode resolved zero tasks - refusing to retire the
  whole diagnostic").

### Скоринг - что реально поменялось (и это сделано правильно)

Раньше `scoreSession()` и `setLongProcessingScore()` в `diagnostic-session.service.ts`
буквально делали то, что описано как баг в задаче: тянули `topicRepository.getBySubjectId(...)`
- **все** темы предмета - и для каждой темы без сабмишена подставляли `aiScore = 0`
(`git diff` на этот файл в MR это подтверждает построчно - блок `const allSubjectTopics =
await topicRepository.getBySubjectId(...)` целиком удалён).

Сейчас обе функции сведены к общему приватному методу `_applyTopicProgress()`
(строки 410-425), который берёт **только** темы из `getTopicScoresBySession()` - то есть
темы, по которым реально был сабмишен в этой диагностической/контрольной сессии - и для
каждой вызывает `topicUserProgressService.initAfterDiagnostic()` (диагностика) или
`.openNextCycle()` (контрольная). Тем вне этого набора функция вообще не касается - строка
`TopicUserProgress` для них не создаётся и не обновляется. Юнит-тесты это явно проверяют
(`diagnostic-session.service.test.ts`, describe `«прогресс только по спрошенным темам»`):
`initAfterDiagnostic` вызван 1 раз, `expect(...).not.toHaveBeenCalledWith('user-1',
'topic-other-block', 0)`.

`topicUserProgressService.initAfterDiagnostic/openNextCycle` (в `topic-user-progress.service.ts`)
сами по себе тоже пишут ровно одну строку на переданный `topicId` - никакого скрытого цикла
по всем темам внутри них нет (грепом по репозиторию: единственные места, где `topicUserProgressRepository.create()`
вызывается в цикле по множеству тем - это была старая логика в `diagnostic-session.service.ts`,
которую и убрали).

**Вывод: на уровне БД (таблица `topic_user_progress`) код в этом MR читается как корректно
исправленный** - именно то, что просил acceptance ("После диагностики строки
`topic_user_progress` есть только по темам, которые спросили").

### Найденная вероятная причина FAIL у QA: не в скоринге, а в сборке `GET /api/me`

QA проверял через `GET /api/me` → поле `topicProgresses` и увидел там строки на ВСЕ темы
курса (46/52/46/44/43) с `masteryScore: 0, confirmedStatus: UNDEFINED, cycleNumber: 0` для
тем вне первого блока. Это выглядит как разметка нулём всего курса - но код показывает, что
это, скорее всего, **не строки из БД**, а искусственная подстановка на уровне ответа
`/api/me`, которая не входит в диф этого MR и существовала до него.

В `api/src/controllers/auth.controller.ts`, `meHandler` (строки ~415-429):

```ts
// v2: fill UNDEFINED progress for topics without a record (trainers always available)
const v2Progresses = getActiveVersion() !== 'v1'
  ? (entities.topics ?? []).map((t) => {
    const existing = topicProgresses.find((p) => p.topicId === t.id);
    if (existing) return existing;
    return {
      topicId: t.id,
      masteryScore: 0,
      confirmedStatus: 'UNDEFINED' as const,
      solvedAssignments: 0,
      totalAssignments: 0,
      cycleNumber: 0,
    };
  })
  : topicProgresses;
...
topicProgresses: v2Progresses,
```

Для `scoringVersion` v2/v3 (не v1) этот код мапит **все** темы предмета (`entities.topics`)
и для каждой темы без реальной строки в БД (`dashboardService.getTopicProgresses(id)` →
`topicUserProgressRepository.findAllCurrentForUser`, чистый SELECT без побочных эффектов)
подставляет виртуальный объект с `masteryScore: 0, confirmedStatus: 'UNDEFINED', cycleNumber: 0`
- **ничего не пишет в БД**, это чистое построение ответа API. Именно эта форма один в один
совпадает с тем, что описал QA. `git show eb191505 --stat` подтверждает: `auth.controller.ts`
**не входит** в список изменённых файлов этого MR - код там старый, найден единственный раз
в файле (не тронут задачей).

Комментарий в коде явно объясняет намерение: "trainers always available" - в v2/v3 тренажёр
не гейтится по наличию строки прогресса вообще (в отличие от v1, см. ниже), поэтому фронту
для любой темы курса нужен хоть какой-то объект статуса, чтобы отрисовать карточку темы в
тренажёре. По духу дизайн-спеки это даже соответствует пункту "дашборд показывает их
неначатыми" - `confirmedStatus: 'UNDEFINED'` смысловым образом и есть "не начато".

**Проблема на стыке:** для фронтенда/API-потребителя запись `{masteryScore: 0,
confirmedStatus: 'UNDEFINED'}` **синтетическая для темы, которую диагностика не касалась**
и запись `{masteryScore: 0, confirmedStatus: ...}`, которая была бы **реальной нулевой
оценкой темы** (старый баг) - неотличимы по форме объекта в `topicProgresses`, если не
знать, что это разные источники. QA прочитал их как "прогресс создан для всех тем" -
формально с точки зрения API-ответа это так и выглядит, даже если в БД строки нет. Является
ли это нарушением acceptance - зависит от того, к чему привязан acceptance: к таблице `topic_user_progress`
(тогда, похоже, PASS) или к тому, что видит фронт/ученик в ЛК (тогда нужно смотреть, как
именно фронт рисует `confirmedStatus: 'UNDEFINED'` - как "тема не начата" или как "тема
оценена в 0" - это уже вне API, не проверялось в этом раунде чтения кода).

### Как разделить два источника на перепроверке (конкретный инструмент)

Есть независимый способ увидеть **только настоящие строки БД** в обход синтетической
подстройки `/me`: `GET /api/admin/users/:id/progress` (`api/src/admin/topic-progress.controller.ts`
→ `topicProgressService.getForStudent()`, `api/src/admin/topic-progress.service.ts`) читает
`topicUserProgressRepository.findAllCurrentForUser()` напрямую и **не** дополняет список
темами без строки - если баг действительно пофиксен, тут должно быть ровно столько тем,
сколько было в диагностике (5-6), а не 43-52.

Также в ответе `GET /api/me` есть поле `scoringVersion: getActiveVersion()` - в том же
запросе, где смотрели `topicProgresses`, стоит проверить это поле. Синтетическая подстройка
работает только при `scoringVersion !== 'v1'`. Активная версия задаётся переменной
`SCORING_VERSION`, которая на test-1/проде приходит из CI-переменных `TEST_SCORING_VERSION`/
`PROD_SCORING_VERSION` (`gitlab/pipeline-prepare-test.yml`, `-prod.yml`) - какая версия там
реально стоит, из репозитория не видно, но `.env.example` по умолчанию содержит `v2`, и весь
код фичи (`v2-strategy`, `v3-strategy`, ML1-кредит по `v3`) указывает, что стенды, скорее
всего, не на `v1`.

### Гейт тренажёра для тем вне первого блока - зависит от той же переменной, и это важно

`api/src/controllers/trainer.controller.ts`, `joinTrainerSession()`: гейт "нет строки
прогресса → 403 «Сначала пройдите диагностику»" применяется **только при
`getActiveVersion() === 'v1'`** (новый тест `trainer.controller.gate.test.ts` это явно
фиксирует: `'не пускает в тему без строки прогресса: v1 не умеет её создавать сам'`).

Это значит:
- **На v2/v3** (похоже, боевая конфигурация) тренажёр открыт для любой темы независимо от
  наличия строки прогресса - фикс скоринга тут ничего не ломает, acceptance "тренажёр
  открыт для тем других блоков" выполняется тривиально, по этой ветке гейта regression
  маловероятен.
- **На v1** гейт, наоборот, **требует** существующую строку прогресса, чтобы пустить в тему.
  До этого MR такая строка создавалась для абсолютно всех тем (пусть и с нулевой/`RED`
  оценкой) - тренажёр был открыт везде. После фикса строка создаётся только для тем первого
  блока - **на v1 это означает, что тренажёр по темам вне первого блока станет для
  свежепродиагностированного ученика недоступен (403)**, пока не пройдена контрольная по
  этому разделу (только тогда `openNextCycle` создаст строку). Это прямое противоречие
  acceptance "тренажёр открыт для тем других блоков" - но **только в конфигурации v1**.
  Дизайн-спека в разделе "Скоринг" явно перечисляет места, которые проверялись на
  переживание отсутствия строки (`dashboard.service.isControlTestAvailable`, отчёты,
  бэкфилл рейтинга) - **гейт тренажёра в этом списке не упомянут**, что похоже на
  недосмотр именно для v1.

QA сам отметил гейт тренажёра как "Не покрыто" ("результат исказился бы уже созданной
нулевой строкой") - логично, пока прогресс размечался на все темы, гейт всё равно был бы
открыт и проверка ничего бы не показала. Теперь, когда скоринг сужен, это первое, что стоит
закрыть - см. тест-кейс ниже.

### Остальные сценарии (happy path и регресс из "как проверять" разработчика)

1. **Happy path по каждому классу 5-9.** Пройти диагностику классом X, сверить количество
   и состав задач с таблицей в дизайн-спеке: 5 класс - 5 задач ("Натуральные числа и
   шкалы"), 6 - 6 ("Делимость чисел"), 7 - 6 ("Выражения, тождества, уравнения"), 8 - 6
   ("Рациональные дроби"), 9 - 6 (повторение 8 класса + квадратичная функция, по комментарию
   разработчика на проде - 2 + 4 соответственно). Прогресс размечен только по темам блока
   (см. приоритетный кейс выше для точной проверки).
2. **Изоляция сессий.** Второй ученик пытается достучаться до чужой `diagnosticSessionId`
   (resume/`GET`-эквивалент) → 403. Это уже PASS у QA прошлого раунда, но при перепрогоне
   стоит зацепить заодно - логика в `joinOrCreateSession()` (`existing.userId !== userId →
   throw ERRORS.forbidden`) в этом MR не менялась, регресс маловероятен.
3. **Публичные поля заданий.** `GET /api/assignments?diagnosticId=…` не должен содержать
   непустые `answer/steps/hints/rules/examples` - тоже не менялось этим MR (см.
   `getDiagnosticPublicData`/маппинг в контроллере ассайнментов), но стоит перепроверить на
   новом контенте `v2026-09`, так как это новые данные, а не новый код.
4. **Контрольная тоже сужена.** Пройти контрольную работу (после диагностики и набора
   тренажёра, штатным флоу) - `setLongProcessingScore`/`scoreSession` при `type ===
   CONTROL_TEST` должны через `_applyTopicProgress` открыть новый цикл (`openNextCycle`)
   только по темам, которые контрольная спрашивала (обычно темы одного раздела) - не по
   всему предмету. Плюс отдельно проверить пограничный случай из комментария в коде:
   ученик, для темы которого ещё нет строки прогресса (`findMaxCycleNumber` вернёт `-1`),
   при создании контрольной должен получить `cycleNumber = 0` (`Math.max(0, -1) + 1 = 0`), а
   не отрицательный/некорректный номер цикла - это защита, добавленная именно в этом MR
   (unit-тест `'не открывает нулевой цикл темы, которой диагностика не касалась'` в
   `diagnostic-session.service.test.ts`), стоит убедиться на живом стенде, что контрольная
   по "новой" для ученика теме вообще открывается, а не падает с ошибкой цикла.
5. **Режим заливки `--replace`.** Прогнать `load-content.ts --grade=<N> --kind=diagnostic
   --replace` на тесте (если есть доступ к запуску скриптов на стенде, иначе - попросить
   разработчика прогнать и снять отчёт). Ожидаемо: в отчёте `retired` > 0 для классов, где
   менялся состав файла, `created`/`skipped` соответствуют факту; в БД у погашенных
   `DiagnosticAssignment` `deleted_at` непустой, у `Assignment` - пустой (не удалён);
   прошлые сессии учеников, которые сидели на погашенной задаче, по-прежнему открываются и
   читаются (не 404/500). Без флага `--replace` - старое поведение (только добавление,
   ничего не гасится), это тоже стоит быстро тронуть регрессом.
6. **Пустой файл в `--replace` не сносит диагностику целиком.** Не обязательно гонять на
   стенде намеренно (опасно для прод-данных), но если есть тестовое окружение - убедиться,
   что при 0 резолвнутых задач `loadDiagnosticTasks` бросает исключение ("Replace mode
   resolved zero tasks...") и не гасит диагностику - это защитный код именно из этого MR.

## Что посмотреть рядом (регресс)

- **Гейт тренажёра на v1** - см. "Реализация" выше, это не просто "посмотреть рядом", а
  вероятный прямой конфликт с acceptance, если стенд/прод реально работают на
  `SCORING_VERSION=v1`. Выяснить актуальную версию - первый шаг.
- **Открытие контрольной и floor для `cycleNumber`** - явно помечено QA как "не покрыто",
  разработчик добавил защитный `Math.max(0, ...)` именно в этом MR (иначе минус-цикл при
  `findMaxCycleNumber === -1`) - стоит закрыть отдельным прогоном контрольной для ученика
  без предшествующей строки прогресса по теме контрольной.
- **Live-replace контента** (`--replace` на реально работающем стенде, поверх активных
  сессий учеников) - не запускался в предыдущих раундах, см. тест-кейс 5 выше.
- **`dashboard.service.isControlTestAvailable`** - в v1-ветке итерирует `progresses` и для
  `RED`/`YELLOW`-тем считает решённые задачи тренажёра; с более коротким набором строк
  прогресса (только первый блок) это в теории должно вести себя мягче (меньше тем в
  проверке), но стоит свериться, что функция не спотыкается о полностью пустой список
  `progresses` (случай "проходит первую диагностику прямо сейчас, ни одной темы ещё не
  оценено") - выглядит покрытым (`if (targets.length === 0) return true`), но не мешает
  тронуть один раз вживую.
- **Бэкфилл рейтинга** (`api/scripts/backfill-rating.ts`) упомянут в дизайн-спеке как место,
  которое проверялось на переживание отсутствия строки прогресса - не читался в этом раунде,
  стоит отдельно прогнать на стенде с недавно продиагностированными учениками, если скрипт
  вообще предназначен для регулярного запуска на test-1/проде.

## Аналитика/API

В `api/src/constants/analytics-events.ts` для диагностики есть только уже существовавшие
события: `DIAGNOSTIC_START`, `DIAGNOSTIC_QUESTION_VIEW`, `DIAGNOSTIC_QUESTION_ANSWER`,
`DIAGNOSTIC_COMPLETE`, `DIAGNOSTIC_RESULTS_VIEW`, `DIAGNOSTIC_ABANDON`,
`PARENT_REPORT_DIAGNOSTIC_EMAIL_SENT`. Новых событий специально под "диагностику по первому
блоку" в этом MR не заведено - если продакт ожидал отдельную аналитику именно по факту
сужения диагностики (например, чтобы отличить старые полные прохождения от новых в
воронке), её в коде нет, стоит уточнить, нужна ли она вообще для оценки конверсии.

## Открытые вопросы

- **Правки ЛК по доске Miro** - вне скоупа текущего MR, доска недоступна агенту, нужно
  уточнить у постановщика, какие именно правки требовались и заведена ли под них отдельная
  задача.
- **Активный незакрытый FAIL по разметке прогресса** (комментарий QA от 16.09 19:43) - по
  итогам чтения кода наиболее вероятная причина - не в скоринге (тот, похоже, исправлен
  корректно и покрыт unit-тестами), а в том, что `GET /api/me` подмешивает синтетические
  `UNDEFINED`-записи на все темы курса для `scoringVersion !== 'v1'` (код в
  `auth.controller.ts`, вне диффа MR, существовал до задачи). Нужно подтвердить/опровергнуть
  это разделение через `GET /api/admin/users/:id/progress` или прямой SELECT по
  `topic_user_progress`, как описано в приоритетном тест-кейсе - это должно однозначно
  закрыть вопрос, PASS перед нами или нет.
- **Если разделение подтвердится (БД чистая, `/me` только "украшает" ответ)** - тогда это,
  вероятно, не блокер acceptance по духу задачи, но стоит спросить продакта/дизайнера: не
  вводит ли в заблуждение ученика то, что в ответе API (и, возможно, в UI, если фронт не
  различает "реальная оценка 0" и "тема не начата" по одному и тому же
  `confirmedStatus: 'UNDEFINED'`) тема вне первого блока выглядит как уже "потрогали
  диагностикой". UI-часть (собственно ЛК) в этом раунде не проверялась.
- **Гейт тренажёра на v1** - если стенд/прод реально работают на `SCORING_VERSION=v1`, это
  похоже на настоящую регрессию (тренажёр для тем вне блока станет закрыт после диагностики
  до первой контрольной), не упомянутую явно в дизайн-спеке среди мест, которые
  проверялись на "отсутствие строки прогресса ≠ ошибка". Нужно узнать активную версию
  скоринга на стендах и, если v1, поднять это отдельно.
