### Что такое «первый блок» и как он попадает в диагностику

Согласно спеке (`docs/superpowers/specs/2026-09-16-diagnostic-first-block-design.md`): блок - это разделы курса с `orderIndex` не больше, чем у раздела первой контрольной. `Diagnostic.sectionId` (поле уже существовало в схеме, было пустым у входной диагностики) теперь указывает на этот раздел. **Важная деталь для теста**: сама граница блока - это соглашение контента, а не рантайм-проверка. Диагностика физически спрашивает ровно те задачи, что перечислены в JSON-файле (`api/scripts/data/diagnostics-<N>grade-v2026-09.json`), подключённом через `DIAGNOSTIC_FILES` в `api/scripts/load-content.ts:10-15`. Никакой код не отфильтровывает «случайно вышедшую за блок» задачу - если файл наполнят задачей из другого раздела, диагностика её спросит без предупреждений. Прочитаны сами файлы - подтверждено количество задач и раздел (`section` в файле → `Diagnostic.sectionId`):

| Класс | Задач | `section` в файле |
|---|---|---|
| 5 | 5 | Натуральные числа и шкалы |
| 6 | 6 | Делимость чисел |
| 7 | 6 | Выражения, тождества, уравнения |
| 8 | 6 | Рациональные дроби |
| 9 | 6 | Квадратичная функция (КР №1 9 класса привязана ко второму разделу - первый является трёхчасовым повторением 8 класса, тоже входит в блок по `orderIndex`) |

Точно совпадает с цифрами из комментариев разработчика (16.09, 04:02 и 05:02).

### Заливка контента: режим замены (`--replace`)

`api/src/services/content/content-loader.service.ts`. Раньше `loadDiagnosticTasks()` умел только добавлять - старый набор из 11 задач остался бы рядом с новыми 6. Теперь при `opts.replace`:
- задачи, отсутствующие в файле, гасятся (`DiagnosticAssignment.deletedAt = now()`), а не удаляются - `Assignment` не трогается, т.к. на него ссылаются прошлые сабмишены (комментарий в коде и `docs/…-design.md` строка 84-86 подтверждают это намеренное решение);
- `_reviveDiagnosticMembership()` (`content-loader.service.ts:137-157`) возвращает в диагностику задачу, погашенную прошлым прогоном, если файл снова её перечисляет - без этого повторный `--replace` тем же набором тихо оставлял бы задачу мёртвой;
- пустой результат резолва (`keptAssignmentIds.length === 0`) выбрасывает ошибку и НЕ гасит диагностику целиком (`content-loader.service.ts` рядом с `_reviveDiagnosticMembership`, добавлено в `da8b4d53`) - защита от случайного полного погашения при кривом файле.

### Найденный QA дефект и его текущее состояние в коде - ПОФИКШЕНО

Смотри приоритетный тест-кейс ниже за развёрнутым выводом. Коротко: до правки `scoreSession()`/`setLongProcessingScore()` в `api/src/services/diagnostic-session.service.ts` брали **все темы предмета** через `topicRepository.getBySubjectId()` и инициализировали прогресс по каждой (`aiScore = scoreMap.get(topic.id) ?? 0` - именно отсюда нулевая разметка нетронутых тем). Коммит `078c60f3` (`feat(diagnostic): прогресс после работы создаётся только по спрошенным темам`) убрал этот цикл и заменил его на приватный метод:

```ts
// api/src/services/diagnostic-session.service.ts:408-425
private async _applyTopicProgress(
  lastDiagnostic: DiagnosticSession,
  diagnosticSessionId: string,
): Promise<IDiagnosticTopicScores[]> {
  const scoredTopics = await this.getTopicScoresBySession(diagnosticSessionId);
  for (const { topicId, score } of scoredTopics) {
    if (lastDiagnostic.type === DiagnosticType.DIAGNOSTIC) {
      await topicUserProgressService.initAfterDiagnostic(lastDiagnostic.userId, topicId, score);
    } else {
      await topicUserProgressService.openNextCycle(lastDiagnostic.userId, topicId, score, lastDiagnostic.cycleNumber);
    }
  }
  return scoredTopics;
}
```

`getTopicScoresBySession()` (`diagnostic-session.service.ts:395-406`) строит список тем строго из фактических сабмишенов сессии (`submission.assignment.topicId`) - тема, по которой задачи не было, в этот список не попадёт. Метод вызывается из обоих мест, где раньше был цикл по всем темам предмета: `scoreSession()` (строка 443) и `setLongProcessingScore()` (строка 618, ветка форс-скоринга по таймауту). `topicRepository` в файле больше не импортируется вообще (импорт убран тем же коммитом) - синтаксически невозможно случайно вернуть цикл по всем темам, не добавив импорт заново.

Ниже по цепочке `topicUserProgressService.initAfterDiagnostic()` и `.openNextCycle()` (`api/src/services/topic-user-progress.service.ts:64-135` и `:233-277`, не менялись этим MR) и раньше всегда принимали **один конкретный `topicId`** - они не создавали строк для чужих тем сами по себе, брешь была именно в цикле-вызывающем коде. Возврат данных пользователю тоже не подмешивает недостающие темы: `dashboardService.getTopicProgresses()` (`api/src/services/dashboard.service.ts:29-45`) и репозиторий `topicUserProgressRepository.findAllCurrentForUser()` (`api/src/repositories/topic-user-progress.repository.ts:18-29`) отдают ровно те строки, что реально есть в БД, без сведения к полному списку тем курса. `GET /api/me` использует именно этот метод напрямую (`api/src/controllers/auth.controller.ts:401`), без промежуточного кеша.

**Регрессионный юнит-тест на именно этот баг уже есть в диффе**, `api/src/services/__tests__/diagnostic-session.service.test.ts:573-611` (`describe('DiagnosticSessionService.scoreSession - прогресс только по спрошенным темам')`): мокает `topicRepository.getBySubjectId` возвращающим `['topic-asked', 'topic-other-block']`, сабмишен только по `topic-asked`, и явно проверяет `expect(topicUserProgressService.initAfterDiagnostic).not.toHaveBeenCalledWith('user-1', 'topic-other-block', 0)`. Тест такого же вида есть и для контрольной (`:613-622`, через `openNextCycle`).

### Побочный эффект фикса: гейт тренажёра v1 и тема вне блока

Отдельная находка код-ревью (второй коммит, `da8b4d53`): пока действовал баг, гейт тренажёра (`api/src/controllers/trainer.controller.ts:181-189`, только для `SCORING_VERSION=v1`) проверял «хоть одна строка прогресса есть у ученика» (`findAllCurrentForUser(...).length === 0`) - с багом это условие срабатывало правильно случайно, потому что диагностика создавала строки по ВСЕМ темам. После фикса такая проверка стала бы дырявой в другую сторону (тема вне блока никогда не получит строку - гейт пропустил бы туда без реальной диагностики). Разработчик откатил её к прежнему виду - строгой проверке **по конкретной теме**:

```ts
// api/src/controllers/trainer.controller.ts:181-189
if (getActiveVersion() === 'v1') {
  const progress = await topicUserProgressRepository.findCurrentByUserAndTopic(userId, topicId);
  if (!progress) {
    return reply.status(403).send({ message: 'Сначала пройдите диагностику' });
  }
}
```

Это осознанно создаёт **новое** отклонение от acceptance спеки (`docs/superpowers/specs/2026-09-16-diagnostic-first-block-design.md:122-123`: «Ученик, прошедший диагностику, открывает тренажёр по любой теме курса, включая темы других блоков») - но **только при `SCORING_VERSION=v1`**. Тест `api/src/controllers/__tests__/trainer.controller.gate.test.ts:71-80` прямо называется «не пускает в тему без строки прогресса: v1 не умеет её создавать сам» и подтверждает 403 для `topicId: 'topic-other-block'`. На `v2`/`v3` этой ветки гейта нет вовсе (`dashboard.service.ts:97-100`, `isControlTestAvailable` возвращает `true` сразу для не-v1; сам вход в тренажёр v2/v3 не проверяет факт диагностики по коду). По документации (`docs/superpowers/plans/2026-09-16-diagnostic-first-block.md:663`, `.env.example:257`) тестовый/локальный стенд рассчитан на `SCORING_VERSION=v2` - то есть при обычной конфигурации теста эта ветка не исполняется и не блокирует acceptance. Это дремлющий риск, актуальный только если версию скоринга когда-нибудь вернут на v1 (см. «Открытые вопросы»).

При этом по чтению текущего кода на `master` баг отсутствует, а разработчик после 19:43 не оставил ни одного комментария о повторном фиксе. Возможные объяснения: (а) QA тестировал не тот образ/стенд, который был реально задеплоен на момент теста (кэш контейнера, откат, другой стенд); (б) в момент теста на стенде стояла более старая версия, которую позже тихо переразвернули тем же тегом без нового комментария; (в) в тексте FAIL-комментария перепутаны цифры или окружение. Само по себе чтение кода не может подтвердить, что именно видел QA на экране 16.09 в 19:43 - это стоит явно закрыть живым прогоном приоритетного тест-кейса выше, а не полагаться только на этот вывод по коду.
- **Дремлющее расхождение с acceptance при `SCORING_VERSION=v1`.** После фикса гейт тренажёра для v1 (`trainer.controller.ts:181-189`) блокирует вход в любую тему без собственной строки прогресса - то есть постоянно блокирует темы вне первого блока диагностики, даже прошедшему её ученику, что напрямую противоречит acceptance-пункту спеки «открывает тренажёр по любой теме курса». Разработчик пошёл на это осознанно (v1 не умеет создавать строку прогресса от тренажёрного сабмишена и потерял бы ответы студента). По документации боевой конфигурации тестового стенда - `SCORING_VERSION=v2` (`docs/superpowers/plans/2026-09-16-diagnostic-first-block.md:663`, `.env.example:257`), где этой ветки гейта нет вовсе - но разные документы в репозитории расходятся в том, какая версия скоринга сейчас на проде (`v2` по одним, `v3` по релизному докладу `docs/educational-process/import-data/release-course-content.md`) - стоит явно снять `SCORING_VERSION` со стенда перед тестом п.7-8, а не полагаться на документацию.
