## Контекст

Задача заведена как краткая правка от постановщика: «диагностику сделать не по всем темам класса, а по всем темам первого блока (до первой контрольной) + комментарии по ЛК на доске Miro». Доска Miro недоступна агенту (не читаем внешние доски) - в скоуп этой заметки попадает **только часть про диагностику**, она сделана и выкачена. Правки личного кабинета по комментариям с доски Miro **не сделаны** - разработчик прямо пишет в последнем комментарии: «Осталось в задаче: правки ЛК по доске Miro», доска недоступна, скоуп по ним не снят. MR !430 (`feat/MIA-174-diagnostic-first-block`, коммиты `22f9e7d1` + фикс по ревью `da8b4d53`) смержен в master, контент диагностики уже залит и на test-1, и на проде (тег `2026.09.16.2`).

Живое прохождение на проде разработчиком не делалось (пришлось бы заводить диагностику на счёте реального ученика) - механика проверена только на тесте. Тексты задач писал не методолог - если по формулировкам будут правки, это отдельный заход через `api/scripts/data/diagnostics-*grade-v2026-09.json` + `load-content.ts --replace`, не код.

**Фронтенд диагностики не менялся вовсе** - весь диф MR (15 файлов) это backend/scripts/docs, компоненты прохождения диагностики (`screen-diagnostic.vue`, `stores/diagnostic-session.ts` и т.п.) не тронуты. Визуальный флоу прохождения идентичен прежнему - отличается только состав и число вопросов и то, что происходит с прогрессом после сдачи.

## Реализация

### Ограничение "первый блок" - это состав контента, не рантайм-фильтр

Ограничение задаётся файлами `api/scripts/data/diagnostics-{5..9}grade-v2026-09.json` - они содержат только задачи по темам первого блока (до раздела первой контрольной включительно). Загрузчик (`api/scripts/load-content.ts:126-138`, `api/src/services/content/content-loader.service.ts:159-230`) создаёт `Assignment`+`DiagnosticAssignment` из того, что есть в файле - никакой фильтрации «какой блок» в рантайме нет. Единственный источник истины про границу блока - поле `Diagnostic.sectionId` (`schema.prisma:502-506`, миграции не было, поле уже существовало) теперь означает раздел первой контрольной; понятие «текущий блок ученика» в системе в принципе не введено - это прямо названо границей скоупа в дизайн-доке задачи.

Число вопросов по классам (проверено по самим JSON, не по описанию коммита): **5 класс - 5 задач** («Натуральные числа и шкалы»), **6 класс - 6** («Делимость чисел»), **7 класс - 6** («Выражения, тождества, уравнения»), **8 класс - 6** («Рациональные дроби»), **9 класс - 6** (2 темы повторения 8 класса + 4 темы квадратичной функции). У 5 класса именно 5, не 6 - несовпадение с остальными не опечатка, так и задумано.

### Прогресс после диагностики - тема вне блока не получает НИКАКОЙ записи, не "статус unknown"

Ключевая правка - `api/src/services/diagnostic-session.service.ts:408-425` (`_applyTopicProgress`), вызывается из `scoreSession()` (443) и `setLongProcessingScore()` (618). Комментарий разработчика в коде: «тема, которую диагностика не спрашивала, остаётся без строки прогресса». Раньше цикл проходил по всем темам предмета и ставил `aiScore=0` темам без задач - это и был баг, из-за которого весь курс размечался нулём. Теперь строка `topic_user_progress` создаётся **только** по темам, реально встретившимся в сабмишенах диагностики; для остальных тем строки нет вообще, и это трактуется дашбордом/тренажёром как «тема не начата, открыта» - то есть открытая, а не заблокированная нулём.

То же исправлено для контрольной (`openNextCycle`) - для темы без прогресса добавлен `Math.max(0, ...)`-флоор на `cycleNumber` (строки 285-294, добавлено фикс-коммитом `da8b4d53`): без этого `findMaxCycleNumber` вернул бы `-1`, и работа переоткрыла бы нулевой цикл поверх уже засчитанного прогресса диагностики.

### Гейт тренажёра ("гейт v1") - фикс-коммит вернул точечную проверку по теме

`api/src/controllers/trainer.controller.ts:184-189` (`joinTrainerSession`) - гейт применяется **только для `SCORING_VERSION === 'v1'`** (дефолт в коде, `scoring.strategy.ts:5`, если переменная окружения не задана - **но реальное значение на test-1/проде выставляется через CI-переменные `TEST_SCORING_VERSION`/`PROD_SCORING_VERSION`, в самом репозитории не видно - см. открытый вопрос**). Первая версия правки (`22f9e7d1`) заменила точечную проверку на глобальную «делал ли ученик диагностику вообще» - это ломало инвариант v1 (по темам без строки прогресса v1 не создаёт её сам из сабмишена тренажёра, и ответы ученика было бы некуда писать). Фикс `da8b4d53` вернул проверку по конкретной теме (`findCurrentByUserAndTopic`) - `403 «Сначала пройдите диагностику»`, если по теме нет строки прогресса. Тест `trainer.controller.gate.test.ts` покрывает ровно этот случай на `topicId: 'topic-other-block'`.

**Практический вывод для тестировщика: на `SCORING_VERSION=v1` тренажёр по темам вне первого блока останется заперт после диагностики**, несмотря на то что дизайн-документ задачи говорит «тренажёр по любой теме курса открыт» - это верно только для v2/v3, где прогресс по теме автосоздаётся при первом же ответе в тренажёре. **Перед прогоном тест-кейсов уточнить, какая версия скоринга реально стоит на test-1** (в `.env.example` в репозитории для примера указано `v2`, но это не гарантирует реальное значение окружения).

### "Гашение" контента при `--replace` - soft-delete по timestamp, не флаг

`content-loader.service.ts:213-227`: при `--replace` все `DiagnosticAssignment` этой диагностики, чей `sourceKey` не найден в новом файле, получают `deletedAt = now()` (не удаляются физически - на них могут ссылаться прошлые сабмишены). Если после фильтрации не осталось ни одного assignment - выброс ошибки, замена не применяется (защита от случайно пустого файла). Есть и «оживление» (`_reviveDiagnosticMembership`, строки 137-157, добавлено фикс-коммитом): если ранее погашенная задача снова появляется в файле - `deletedAt` сбрасывается в `null`.

Для ученика **посреди диагностики** во время `--replace`: чтение сессии не фильтрует `deletedAt` в критичных местах - `diagnostic-assignment.repository.ts:30-36` (`isAssignmentInDiagnostic`) намеренно не фильтрует его (комментарий в коде: «ученик, сидящий на задаче, которую методолог только что снял, - это ровно тот, кто пожалуется в поддержку»), то есть доработать уже открытую снятую задачу можно без ошибки. Но `countByDiagnosticId` (используется в `tryScoreSession` для расчёта завершённости) фильтрует `deletedAt: null` - если запустить `--replace` во время активной сессии с уменьшением числа задач, `totalAssignments` изменится «на лету». MR-доки прямо рекомендуют гонять `--replace` только при отсутствии активных сессий диагностики - не тест-кейс для обычного QA-раунда, но стоит держать в уме.

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Happy path - объём диагностики и разметка прогресса

1. Пройти диагностику новым учеником в 7 классе - должно быть ровно 6 задач по разделу «Выражения, тождества, уравнения», а не по всем темам курса.
2. После завершения - в дашборде/карте пробелов оценены ровно темы первого блока (6 из ~46 в курсе), остальные темы **не должны быть отмечены как "0%"/провалены** - они должны выглядеть неначатыми/открытыми, как темы, до которых ученик просто не дошёл.
3. Открыть тренажёр по теме **из первого блока** (уже оценённой диагностикой) - должен открываться свободно.
4. Открыть тренажёр по теме **вне первого блока** - см. кейс 4 ниже (зависит от `SCORING_VERSION`).
5. Повторить пункты 1-2 для каждого класса 5-9, свериться с числом задач по классам из раздела «Реализация» (5/6/6/6/6).

### 2. [ПРИОРИТЕТ] Гейт тренажёра по теме вне первого блока - поведение зависит от SCORING_VERSION

**Сначала узнать у разработчика/по конфигу стенда фактическое значение `SCORING_VERSION` на test-1** - это определяет ожидаемый результат следующего шага.

1. Пройти диагностику (первый блок оценён).
2. Попытаться открыть тренажёр по теме, заведомо НЕ входящей в первый блок (например, из раздела следующей темы курса).
3. **Если `SCORING_VERSION=v1`:** ожидается `403 «Сначала пройдите диагностику»` - тема остаётся запертой, пока прогресс по ней не появится иным путём (это расходится с формулировкой acceptance «тренажёр по темам других блоков открыт» из комментария разработчика - стоит явно зафиксировать результат и передать разработчику, если на v1 это выглядит как незакрытый acceptance).
4. **Если `SCORING_VERSION=v2`/`v3`:** тема должна открываться свободно, прогресс по ней создастся автоматически при первом ответе.

### 3. Активная контрольная - floor на cycleNumber

1. Довести тему первого блока до открытия контрольной (`openNextCycle`).
2. Убедиться, что контрольная открывается на **первом** цикле, а не пытается "продолжить" несуществующий отрицательный цикл (регресс, который чинил фикс-коммит).

### 4. Замена контента живым способом (осторожно, координировать с разработчиком)

1. Не гонять `--replace` во время активного прохождения диагностики другим тестировщиком - явно спросить перед запуском, нет ли открытых сессий.
2. Если есть тестовая возможность: снять задачу из файла, перезалить, и убедиться, что ученик, уже видевший эту задачу в открытой сессии, может её доработать до конца без ошибки (снятая задача не блокирует прохождение).
3. Вернуть задачу в файл, перезалить, убедиться, что она снова доступна для новых сессий («оживление»).

### 5. Ученик со старой (широкой) диагностикой до деплоя

1. Найти/завести ученика, у которого диагностика была пройдена ДО выката этого MR (уже есть строки `topic_user_progress`, в т.ч. нулевые, по всем темам курса, включая темы вне первого блока).
2. Убедиться, что его старые нулевые оценки остаются как есть - миграции данных нет, новая логика скоринга применяется только к новым/повторным диагностическим сессиям.
3. Такой ученик диагностику повторно не увидит (сессия уже `SCORED`) - это ожидаемо, не баг.

### 6. Не в скоупе этого MR (проверять отдельно, когда будет сделано)

Правки личного кабинета по комментариям с доски Miro - код для них ещё не написан, ничего проверять не нужно до следующего MR/комментария разработчика.

## Открытые вопросы

- **Фактическое значение `SCORING_VERSION` на test-1 не видно из репозитория** (задаётся CI-переменной `TEST_SCORING_VERSION`, подставляется в `.env` пайплайном `gitlab/pipeline-prepare-test.yml`) - без него нельзя однозначно предсказать поведение теста №2 (гейт тренажёра по темам вне первого блока). Уточнить у разработчика перед прогоном.
- **Расхождение acceptance vs код на v1**: комментарий разработчика говорит «тренажёр по темам других блоков открыт», но по коду это верно только для v2/v3 - на v1 тема без прогресса всё ещё гейтится 403. Если стенд крутится на v1, это стоит явно обсудить с разработчиком - не факт, что баг, но точно расхождение с описанием.
- **Правки ЛК по доске Miro** - не сделаны, доска недоступна для чтения агентом; скоуп по ним не снят самим разработчиком тоже (ждут ревью доски).
- Живое прохождение на проде не проверялось разработчиком (только на тесте) - при первом реальном прохождении на проде стоит проверить хотя бы happy path (кейс 1) от начала до конца.
