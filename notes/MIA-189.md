## Контекст

Новый ученик сразу после регистрации видит вопрос «Как тебя зовут?» раньше, чем что-либо про учёбу - задача переставляет реплику про карту знаний (с карточкой-превью) перед этим вопросом, чтобы ученик сначала увидел, зачем он вообще пришёл. MR !441 (`feat(cabinet): карта знаний в приветствии Мии до вопроса об имени`, ветка `feat/MIA-189-intro-map-card`) смержен в master 2026-09-17T10:33:18Z, слитый коммит `603ad078`, сейчас на HEAD `master` (`0164cd7a`, чуть более поздний мердж другого MR !450, не связанного с этой задачей). Код прочитан целиком на этом HEAD.

Комментарий разработчика (Kirill Verzhitskii) уточняет число тем в карточке как «три», расходясь с формулировкой acceptance в описании тикета («темы курса вокруг текущего места ученика»). По коду - **три** темы, см. ниже.

## Реализация

### Где сеется приветствие и почему порядок такой

`api/src/services/home-intro.service.ts` - `HomeIntroService.seedFirstVisit()` (строки 28-62):
- Работает только для `Role.STUDENT` (строка 29).
- Дешёвая защита от повторного сева (строка 31): `if ((await prisma.homeInteraction.count({ where: { userId } })) > 0) return;` - до первого визита в `home_interaction` нет ни одной строки, после первого - есть, и весь метод больше не выполняется вообще (даже не считает `personal`/`scoredDiagnostics`/`submissions`).
- `kind` вычисляется из накопленной активности (строки 33-43): `known` - есть личные факты в памяти, `reintroduce` - уже были диагностики/сдачи, но фактов нет, `new` - вообще ничего.
- `askName` (строка 48): `!user.name && kind !== 'known' && !user.onboarding?.nameAskedAt` - карту не путает с вопросом об имени: у `known`-ученика имя не спрашивается никогда (комментарий строки 46-47: «reads as amnesia»), у остальных - один раз, отслеживается через `onboarding.nameAskedAt`.
- Сами строки реплик собираются `introSeed(kind, firstName, points, askName, user.grade)` и передаются в `homeInteractionRepository.seedIfEmpty(...)` (строка 50-61).

Порядок реплик задаёт `introSeed()` в `api/src/data/home-intro-texts.ts`, ветка `kind === 'new'` (строки 75-88):
```ts
return [
  { text: `${hello(firstName)} Я Мия — буду заниматься с тобой математикой. ...`, ...(points ? { meta: { points } } : {}) },
  ...mapLine(grade),
  askName
    ? { text: 'А как тебя зовут?', meta: { asksAbout: 'name' } }
    : { text: 'Чем занимаешься, когда не уроки? ...', meta: { suggests: INTRO_SUGGESTS, asksAbout: 'student' } },
];
```
`mapLine(grade)` (строки 53-63) - функция, которая либо возвращает массив из одной реплики с `meta: { card: { type: 'map_preview' } }`, либо пустой массив, если `grade` не задан (тогда карты в переписке вообще нет - ни реплики, ни карточки). Комментарий на строках 49-51 объясняет почему: `/me` для ученика без класса отвечает базовым набором без тем, карте нечего рисовать, а реплика-обещание над пустотой осталась бы в переписке навсегда.

Итого порядок для нового ученика с классом и без имени: **приветствие+баллы → карта знаний → вопрос об имени** (3 реплики) - именно то, что требует acceptance. Для нового ученика с классом, но уже названным именем: **приветствие → карта → «чем занимаешься»** (тоже 3 реплики, просто вместо вопроса об имени - вопрос про увлечения). Это подтверждено юнит-тестом `api/src/services/__tests__/home-intro.service.test.ts:48-54` (`rowsOf()` длиной 3, `rowsOf()[1].meta.card` равен `{ type: 'map_preview' }`).

### «Разовость» реплики - защита на два уровня

1. Дешёвая проверка в сервисе (`home-intro.service.ts:31`) - не под транзакцией, чисто оптимизация.
2. Настоящая гарантия - `api/src/repositories/home-interaction.repository.ts`, метод `seedIfEmpty()` (строки 187-214): под advisory-локом на `hashtext(userId)` повторно считает `homeInteraction.count({ where: { userId } })`, и только если 0 - пишет все строки и одним запросом помечает `onboarding.miaIntroDoneAt` (+`nameAskedAt`, если был задан вопрос про имя). Комментарий на строках 184-185 явно объясняет, зачем это нужно: кабинет запрашивает историю из нескольких мест, и две открытые вкладки не должны каждая посеять свой комплект реплик.
3. Точка вызова - `api/src/controllers/home-chat.controller.ts`, `getHomeMessagesHandler` (строки 32-55): `seedFirstVisit()` вызывается **до** чтения истории, ошибка сева гасится и логируется (`.catch(...)`, строка 46) - т.е. один неудачный сев не ломает загрузку чата, а просто повторится на следующей.

### Карточка карты - три темы, живые данные, а не снимок

`frontend/cabinet/chat/map-preview.ts` - ключевой файл, полностью новый.
- `PREVIEW_ROWS = 3` (строка 16) - явная константа с комментарием «дальше это уже экран карты, а не предпросмотр». **Это и есть подтверждение по коду: карточка показывает ровно 3 темы**, а не «темы курса» в целом (расхождение с description тикета, но совпадает с комментарием разработчика).
- Заголовочный комментарий файла (строки 7-13) прямо формулирует контракт «живых данных»: «Рисуется по тем же данным, что и сам экран карты, а не по снимку, сохранённому вместе с сообщением: карточка остаётся в переписке навсегда, и месяц спустя она обязана показывать сегодняшнее положение ученика».
- `mapPreview()` (строки 77-113) вызывает `toCabinetMap({ topics, mlProgress })` - тот же конвейер, что рисует полноценный экран карты (`frontend/cabinet/screen/map.ts`), затем фильтрует только `kind === 'topic'` (без строк контрольных работ).
- `currentIndex()` (строка 51) - первая тема, у которой `state !== 'done'` (`-1`, если все закрыты - тогда никто не выделен).
- Окно из трёх тем строится вокруг текущей позиции, но у конца курса сдвигается назад, чтобы не показать одну строку вместо трёх (строки 89-92, `start = current < 0 ? 0 : Math.min(current, Math.max(all.length - 3, 0))`).
- Подпись под темой (`rowSub()`, строки 58-62): `тема закрыта` (done) / `первая тема маршрута` (текущая = индекс 0) / `здесь ты сейчас` (текущая, но не первая) / `откроется следом` (следующая после текущей) / `дальше по программе` (остальные).
- У каждой темы 5 «пипсов»-блоков (`row.pips`, строка 100-104) - по одному на элемент `LEVELS` из `frontend/cabinet/shared/tokens.ts:5-11` (Повтор по образцу / Применение / Осмысление / Перенос / Защита знания), цвет каждого - из `ML_STATE[block].bg` (`tokens.ts:13-26`: `passed` зелёный, `credited-early`/`credited-capped` - штриховка, `top-up` жёлтый «добираем точность», `active` светло-жёлтый, `locked` серый).
- Счётчик закрытых тем и заголовок: `closed: '${done} из ${all.length} закрыто'`, `sub: '${course} · N тем'` (`plural()`), `width` - процент для полоски прогресса (строки 106-112) - все три считаются **по всем темам курса**, а не только по трём показанным.
- Легенда (`legendOf()`, строки 64-71) показывает подписи только тех состояний, которые реально встретились среди трёх показанных тем блоков - не выдумывает лишние.

Подтверждено юнит-тестами `frontend/tests/cabinet-map-preview.test.ts` (все 9 кейсов), в частности:
- «показывает первые три темы курса в порядке программы» (строки 16-21);
- «едет за учеником: закрытая тема не остаётся первой темой маршрута» (23-27) - при прохождении первой темы окно сдвигается на следующие три;
- «у конца курса окно сдвигается назад» (29-35);
- «считает закрытые темы по живому прогрессу, а не по снимку в сообщении» (55-59, дословно к acceptance);
- «у каждой темы пять блоков» (61-64);
- «без курса карточки нет» (70-72, `topics: []` → `null`).

### Что делает данные «живыми», а не снимком - механизм пересчёта

Это ключевой техдолг проверки. Карточка **не хранит своих данных** в базе:
- `api/src/data/home-intro-texts.ts:36`: `card?: { type: 'map_preview' }` - у типа карточки нет поля `payload`, комментарий: «A card rendered inside the reply - the cabinet reads its own data for it, so there is no payload».
- На фронте `cardOf()` (`frontend/cabinet/chat/home-chat.ts:73-115`), ветка для `map_preview` (строки 82-84): `if (raw.type === 'map_preview') return { type: 'map_preview' };` - комментарий: «No payload: the map preview draws the student's own course from /me, so a card stored months ago still shows where they are now rather than where they were».
- Реальные данные подставляются на каждый рендер в `frontend/cabinet/shell/use-cabinet.ts`, `computed` `homeMapPreview` (строки 705-711):
```ts
const homeMapPreview = computed(() =>
  mapPreview({
    topics: userStore.getUser?.topics,
    mlProgress: userStore.getUser?.mlProgress,
    grade: userStore.getUser?.grade,
  }),
);
```
Источник - `userStore.getUser` (текущее состояние `/me` в сторе), не что-либо, привязанное к конкретному сообщению. Дальше в `homeFeed` (строки 713-737) `cards.mapPreview = homeMapPreview.value` подставляется в `CardRowDeps` **на каждый пересчёт `homeFeed`**, а `card-row.ts` (`cardRow()`, строки 65-76) при рендере любой реплики с картой берёт именно это текущее значение. То есть при каждом открытии/перерисовке чата (заход в кабинет, обновление страницы, возврат из тренажёра) `/me` перечитывается стором и карточка в **старой** реплике показывает **текущее** положение ученика - ровно то, что требует acceptance «месяц спустя видно сегодняшнее положение». Комментарий на строках 699-700 повторяет это прямым текстом: «Своих данных карточка карты не носит: она рисуется по тому же /me, что и её экран, и поэтому реплика годовой давности показывает сегодняшнее положение ученика».

### Ученик без класса

`mapLine(grade)` в `home-intro-texts.ts:53-63` при `grade == null` возвращает `[]` - ни реплики, ни карточки не сеется вовсе (не «пустая карточка», а полное отсутствие строки). Подтверждено тестом `home-intro.service.test.ts:61-68` («без класса карту не обещает»): при `grade: null` `rowsOf()` содержит 2 строки вместо 3, и ни у одной из них нет `meta.card`.

### Верстка карточки

`frontend/components/cabinet/chat/chat-feed.vue`, блок `v-if="msg.hasMapPreview && msg.mapPreview"` (строки 239-293): шапка «Карта знаний» + `mapPreview.sub` (строки 246-250), справа - счётчик `mapPreview.closed` и полоска `--fill-width: mapPreview.width` (251-256), три строки тем с иконкой лампочки, названием, подписью-статусом и пятью пипсами с `title`-подсказкой (259-281, `class="is-active"` на текущей теме), легенда (283-288) и ссылка `NuxtLink :to="msg.mapPreviewTo"` («Открыть карту», строки 289-291) со стрелкой. SCSS-блок `.cabinet-mapcard` начинается на строке 707 того же файла (стили пипсов, активной строки - см. `.cabinet-mapcard__row.is-active` на строках 806 и 829), отдельного файла токенов под карточку не заведено - использует общие `ML_STATE`/`LEVELS` из `frontend/cabinet/shared/tokens.ts`.

Клик по карточке (и по кнопке «Открыть карту», и по самой карточке через `onRoute`) отмечен через `data-card-key`/`data-card-type` (строки 241-244) и наблюдается `IntersectionObserver`-ом в `chat-feed.vue` (строки 36-60) для события показа - см. раздел «Аналитика» ниже.

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Happy path: новый ученик с классом, без имени

Нужен свежий аккаунт ученика с известным классом, который ни разу не открывал кабинет/чат (реплики сеются один раз при первом `GET` истории).

1. Зарегистрироваться/зайти таким учеником, открыть домашний чат Мии впервые.
2. Проверить порядок реплик сверху вниз: (1) приветствие «Привет! Я Мия…» (+баллы за первый вход, если они реально начислены в журнале - см. `arrivalPoints()`, `home-intro.service.ts:71-75`, чип не показывается, если начисления нет); (2) реплика про карту знаний «Смотри, вот твоя карта знаний — все темы N класса. У каждой пять блоков…» с карточкой карты сразу под ней; (3) «А как тебя зовут?».
3. В карточке карты проверить: заголовок «Карта знаний», подзаголовок вида «Программа N класса · M тем» (или «Твоя программа · M тем», если класс всё же не резолвится на фронте - см. п. 6 ниже), справа - счётчик «X из M закрыто» и полоска прогресса.
4. Убедиться, что показаны **ровно три темы** (не больше и не меньше) - подряд по программе вокруг текущего положения ученика; первая из показанных тем у ученика без прогресса подписана «первая тема маршрута» и выделена как активная.
5. У каждой темы - ровно пять индикаторов-блоков (пипсов) в ряд; навести на любой - всплывающая подсказка вида «N. Название уровня — статус» (например, «1. Повтор по образцу — ещё не открыт»).
6. В подвале карточки - легенда с подписями встретившихся состояний (для нового курса, где всё ещё заперто, должна остаться только «не открыт») и кнопка/ссылка «Открыть карту».
7. Кликнуть «Открыть карту» → переход на экран карты знаний (`/app/map`), маршрут ведёт именно туда, а не в тренажёр/на дашборд.
8. После карточки - реплика «А как тебя зовут?» без карточки и без чипов-подсказок.

### 2. Разовость реплики - повторный заход не показывает карту снова

9. После сценария №1 обновить страницу / выйти и снова зайти в чат тем же учеником → комплект реплик (приветствие/карта/вопрос об имени) не дублируется, история осталась той же длины, что и после первого визита.
10. Ответить на вопрос об имени → следующая реплика Мии не должна снова показать карту (карта сеется один раз при первом посещении, а не при каждом «новом» повороте разговора).
11. Если технически возможно открыть кабинет тем же новым учеником в двух вкладках одновременно (или сымитировать гонку двумя параллельными запросами истории) - должен появиться только один комплект реплик, не два. Это защищено advisory-локом в `seedIfEmpty()` (`api/src/repositories/home-interaction.repository.ts:187-214`) - специальный тест-кейс на регрессию, если стенд позволяет так проверить, иначе - зафиксировать как проверено по коду, не по факту наблюдения.

### 3. [ПРИОРИТЕТ] Ученик без класса

12. Завести/использовать нового ученика, у которого класс не указан (`grade = null`, ещё не выбран онбордингом).
13. Открыть домашний чат впервые. Ожидание: приветствие есть, а реплики про карту знаний **нет вовсе** (не пустая карточка, не заглушка) - сразу за приветствием идёт вопрос («А как тебя зовут?» или «Чем занимаешься, когда не уроки?» в зависимости от того, известно ли имя).
14. Если у этого ученика позже появится класс (сценарий выбора класса в анкете/настройках) - карта в старых репликах ретроактивно не появится (реплика про карту не сеется задним числом), это ожидаемое поведение, а не баг - стоит явно свериться с продактом/разработчиком, если появится сомнение при тестировании.

### 4. [ПРИОРИТЕТ] «Живые» данные: карточка в старом сообщении показывает текущее положение

15. У ученика из сценария №1 (карта уже посеяна) пройти любую тему в тренажёре так, чтобы её статус в прогрессе изменился (например, закрыть первую тему из показанных трёх, или хотя бы продвинуть её на один блок).
16. Вернуться в домашний чат (не создавая нового сообщения) - к той самой, старой реплике с картой. Проверить, что карточка **в этом же сообщении** обновила данные: если тема закрыта - её подпись сменилась на «тема закрыта», следующая незакрытая тема выделена как активная («здесь ты сейчас»), счётчик «X из M закрыто» и ширина полоски увеличились, а окно из трёх тем могло сдвинуться на следующую тройку, если пройденная тема выпала за пределы окна.
17. Обновить страницу целиком (`F5`) - убедиться, что после перезагрузки в этой же старой реплике карточка также показывает актуальное состояние (не кэш прошлого запроса) - соответствует acceptance «месяц спустя видно сегодняшнее положение», проверяемому здесь через «сразу после действия», а не буквально через месяц.
18. (Регрессионная проверка по коду, не требует отдельного шага в UI) Убедиться, что дело именно в отсутствии payload у карточки: карточка не должна «застрять» на состоянии момента отправки реплики ни при каких действиях с прогрессом - если увидите обратное, это прямое расхождение с `frontend/cabinet/chat/map-preview.ts:7-13` и `frontend/cabinet/chat/home-chat.ts:82-84`.

### 5. Дополнительные / граничные сценарии

19. Ученик, у которого закрыты все темы курса (конец программы): карточка не должна пытаться показать несуществующую следующую тему - последние три темы курса показываются без выделения активной строки (см. `mapPreview.test.ts:37-42`, «на закрытом курсе никого не выделяет»); стоит поискать на стенде ученика в конце короткого курса (например, класс с малым числом тем) или временно продвинуть тестового ученика до конца.
20. Курс короче трёх тем (если такой существует на стенде): карточка должна показать все имеющиеся темы (меньше трёх), не падать и не дублировать строки - тест `mapPreview.test.ts:44-53` покрывает курс из трёх тем, но стоит явно проверить курс из одной-двух тем на реальных данных, если такой конфиг существует в проде.
21. Возвращающийся ученик (`kind === 'reintroduce'`/`known`, уже занимался или есть личные факты) не должен видеть карту при повторном визите вообще - карта сеется только в ветке `kind === 'new'` (`introSeed()`, `home-intro-texts.ts:75`). Если под рукой есть такой аккаунт (без истории home-чата, но уже занимавшийся по трекеру занятий/диагностик) - убедиться, что вместо карты идёт сразу «Мы уже сколько занимаемся…».
22. Ученик, у которого уже стоит `onboarding.miaIntroDoneAt` от старой (домодальной) реализации приветствия, но нет ни одной строки в `home_interaction` - должен всё равно получить полный новый комплект реплик, включая карту (см. тест `home-intro.service.test.ts:180-186`, «сеет и тому, у кого уже стоит miaIntroDoneAt от старой модалки») - граничный случай миграции со старого приветствия на чатовое, стоит поискать такого ученика на стенде (зарегистрированного до перехода на чатовые приветствия) отдельно.

## Открытые вопросы

- **Расхождение «три темы» vs формулировка acceptance в описании тикета.** Description говорит «темы курса вокруг текущего места ученика» (можно прочитать как «все темы», без числа), комментарий разработчика и код (`PREVIEW_ROWS = 3`, `frontend/cabinet/chat/map-preview.ts:16`) однозначно фиксируют **три**. Подтверждено юнит-тестами. Тестирую и приёмаю по факту реализации (три темы) - если продукт ожидал другое число, это предмет отдельного уточнения с автором задачи, а не баг найденной реализации.
- **Нет юнит-теста на аналитику клика по `map_preview`** (см. раздел «Аналитика/API») - не блокирует приёмку, но стоит перепроверить руками при ручном прогоне и, возможно, завести техдолг на дополнение параметризованного теста.
- **Реплика про карту не появляется ретроактивно**, если класс выставлен уже после первого визита без класса (см. тест-кейс №14) - выглядит как осознанное поведение («сеется один раз»), но не описано явно в acceptance; стоит свериться с продактом, ожидаемо ли это для сценария «ученик указал класс сильно позже регистрации».

**Баг 1 - ученик без имени был без связи с Мией (мёртвый сокет).**
- Было: `use-auth.ts` - `const isAuthorized = () => !!(userStore.user?.name ?? null);` - «авторизован» определялось по наличию заполненного имени. Имя же теперь ученик называет Мие в чате (см. флоу MIA-189 выше - вопрос «А как тебя зовут?» идёт в самом чате). Пока имени нет, `isAuthorized()` возвращал `false`, и `plugins/socket.ts` вообще не набирал сокет (`if (!loading && isAuthorized()) { ... socket.connect() ... }`) - то есть сам чат, где имя и предполагалось спросить, был мёртв: сообщения не летели, сокет не открывался ни разу.

**Баг 2 - карточка карты уезжала за край экрана на телефоне.**

Его гипотеза, почему расхождение было воспроизводимо только один раз: карточка и состояние после F5 читаются из одного источника (`/me`, `loadMe()`), снимка в сообщении нет (`meta.card` без `payload`), и разойтись они могли только если в момент проверки `/me` ответил без `mlProgress` - а с 18.09 в частности влит и сегодняшний фикс сокета у ученика без имени, из-за чего «у свежего ученика без имени теперь живой сокет, раньше его не было вовсе, это меняет поведение ровно того сценария, на котором шла проверка».

**Проверка этой гипотезы по коду - она слабая, и это стоит явно держать открытым вопросом, а не принимать на веру:**
- И `/api/me` (`userStore.loadMe()`, `frontend/stores/user.ts:48-66`, HTTP `api<...>('/me')`), и история домашнего чата (`frontend/cabinet/chat/use-home.ts:92-109`, `load()`, HTTP `api<...>('/me/home/messages')`, вызывающая `api/src/controllers/home-chat.controller.ts:getHomeMessagesHandler`) идут **чистым HTTP**-путём, аутентифицированным HttpOnly-cookie через `auth.global.ts` middleware - никакого обращения к WebSocket-гейтвею в этой цепочке нет вообще. Карточка карты (`mapPreview()`) в `use-cabinet.ts:705-711` берёт данные из `userStore.getUser` - результата именно этого HTTP `/me`, а не чего-либо, что приходит по сокету.
- `isSessionJoined` (флаг, который выставляет именно сокет-подключение) в кодовой базе гейтит только `topicId`-join в `cabinet/chat/use-session.ts:179-222` (диагностика/тренажёр/домашка - `use-diagnostic.ts`, `use-homework-solve.ts`), но **не** используется ни в `stores/user.ts`, ни в `cabinet/chat/use-home.ts`, ни где-либо в пути загрузки `/me` или истории домашнего чата.
- Иными словами: баг «мёртвый сокет у ученика без имени», который чинит MR !461, механически не мог влиять на то, что показывает `/api/me` или карточку после F5 - это два архитектурно независимых пути (WebSocket для тренажёра/диагностики/лайв-стрима ответов Мии vs. HTTP для `/me` и истории чата, включая карточку карты). Само наблюдение «сегодня не воспроизводится» может быть верным, но объяснение «раньше не воспроизводилось из-за мёртвого сокета» по коду не подтверждается - более вероятны альтернативы: race condition, зависящая от тайминга (карточка успевает отрисоваться до того, как `/me` дозагрузит `mlProgress`), особенность конкретного стенда/релиза на 18.09, устаревший фронтенд-бандл в кэше браузера на момент проверки, или разовая деградация, которая не оставила следа в логах.
- Раз причинно-следственная связь не подтверждена, статус «сегодня не воспроизводится» нельзя считать закрытием FAIL - нужна отдельная, более настойчивая перепроверка на актуальном стенде, а не однократное наблюдение (см. инструкцию ниже).
