## Контекст

Родительские репорты должны стать понятнее и мотивирующее: родитель видит прогресс ребёнка и причину продолжать занятия.

**Репорт «Итоги недели» — доработки:**
- Заблокированные темы у фримиум-родителя помечаются замочком; открытая тема (на фримиуме доступна одна) — без замка.
- Добавлен персональный AI-комментарий по итогам недели.
- CTA сделан тёплым и адресным: с именем ребёнка и темой в фокусе.

**Новый репорт «Итоги месяца»:**
- Раз в месяц, в первое воскресенье месяца — вместо недельного на этой неделе.
- Показывает результат вводной диагностики как точку отсчёта + динамику «было → стало» по темам и общему баллу.

**Acceptance (из задачи):** замочки у фримиум-родителя в недельном; AI-комментарий + адресный CTA в недельном; новый репорт «Итоги месяца» с диагностикой, статусом, динамикой.

## Реализация

Код прочитан на ветке `kirillverzhitskii/mia-25-reporti-roditelyam-dorabotki-itohi-nedeli-novii-report-itohi` (реальный source_branch MR !225 — отличается от `gitBranchName` в Linear, найден через GitLab API по MR). Дифф — 12 файлов: `parent-report.schemas.ts`, `parent-report.service.ts`, `parent-report-ai.service.ts`, `report-scheduler.service.ts`, `render.ts`, новый шаблон `parentMonthlyReport.mjml`, `analytics-events.ts` (api + frontend), `frontend/pages/report/[token].vue`, тесты.

Ключевые находки по коду (важно для тест-кейсов, некоторые расходятся с текстом задачи/комментариев):

1. **Лок тем** (`isLocked`) считается одинаково и для недельного, и для месячного отчёта: `isFreemium && freeTopicId !== null && topicId !== freeTopicId` (`parent-report.service.ts`). Т.е. **и в месячном отчёте лок работает**.
   - Краевой случай: если у ученика `student_free_topic_id === null` (нет назначенной бесплатной темы), `isLocked` будет `false` у ВСЕХ тем даже для фримиума — ни одного замка не будет.
2. **AI-комментарий недели** генерируется только если `daysActive > 0` за неделю (`createWeeklyReport`).
3. **AI-комментарий месяца** генерируется **всегда**, если есть скоренная диагностика — не зависит от активности за месяц.
4. **Месячный отчёт не отправляется вовсе**, если у ученика нет ни одной диагностической сессии со статусом `SCORED` (`if (!session) return;` в начале `createMonthlyReport`) — ни email, ни строка в `parent_report` не создаются. Без диагностики — отчёт молча пропускается каждый месяц (в БД нет записи → в следующем месяце попытка отправить повторится, тоже молча пропустится).
5. **Важный нюанс, которого нет в тексте задачи**: сам email (`parentWeeklyReport.mjml` — не менялся, и новый `parentMonthlyReport.mjml`) содержит только заголовок, generic `summaryLine`/строку с диагностическим баллом, кнопку «Смотреть полный отчёт» и отписку. **AI-комментарий, замочки и тёплый CTA видны только на веб-странице отчёта** (`/report/[token]`), куда ведёт кнопка — в самом письме их нет. Стоит уточнить у автора/продакта, осознанное ли это решение (короткое письмо + богатая страница) или недосмотр относительно acceptance-критериев.
6. **CTA-копирайт** (`buildWeeklyCtaCopy`) переиспользуется для месячного отчёта, но `focusTopicName` туда всегда передаётся `null` (`ctaCopy = buildWeeklyCtaCopy(ctaResult.cta, studentName, null)`) — то есть в месячном CTA никогда не будет фразы «Сейчас в фокусе тема «X»», только в недельном.
7. **Цвет темы в месячном** = статус по **диагностике** (`statusFromAiScore(diagnosticScore)`), не по текущему прогрессу — дот всегда про «было». Числовая дельта (+N/=) считается на единой шкале mastery: baseline пересчитан через `strategy.computeMasteryScore` из диагностического балла — та же шкала, что и текущий `masteryScore`, реального риска «ложного регресса» из-за разных шкал в коде не видно.
8. **Планировщик**: `isMonthlySendWindow` = первое воскресенье месяца (`getUTCDate() <= 7`) И час ≥ `SEND_HOUR_MSK` (тот же час, что для недельного). `runReportTick`: если попали в месячное окно — шлёт **только** месячный и выходит (`return`), недельный в этот тик не проверяется вовсе. Остальные недели — обычная недельная логика без изменений.
9. **Найден undefined SCSS-токен**: стиль замка `.topic__lock` (`frontend/pages/report/[token].vue:928`) использует `color: $color-trainer-muted;` — такой переменной нет нигде в `frontend/assets/scss/_variables.scss` (там определён `$color-text-muted: #6b7280`, `$color-trainer-*` токенов вообще не существует в проекте). Похоже на опечатку. Стоит проверить, не ломает ли это сборку (Sass обычно падает на undefined variable) и как в итоге выглядит замок — задача для TC1/TC5 ниже.
10. Выборка кандидатов для месячного использует тот же SQL-запрос по подпискам, что и для недельного (`dispatchReports`), с проверкой `NOT EXISTS ... type = 'monthly' ... period_start = ...`. Общий фильтр запроса (не менялся в этом MR) уже требует наличия скоренной диагностики и для недельных кандидатов тоже — если у ученика нет диагностики, он не попадёт и в недельную рассылку; это не связано с MIA-25, но стоит иметь в виду при подборе тестовых пользователей.

## Тест-кейсы

### Итоги недели — доработки

**TC1 (happy path). Фримиум-родитель, активность за неделю есть.**
1. Открыть `/report/[token]` для недельного отчёта фримиум-родителя с активностью за неделю.
   Ожидается: одна (бесплатная, `freeTopicId`) тема — без замка; остальные — с иконкой замка (Lucide Lock, 13px) рядом с названием темы. **Отдельно проверить цвет иконки замка** — по коду используется несуществующий SCSS-токен `$color-trainer-muted` (см. «Реализация», п.9), убедиться, что сборка не падает и замок не рендерится «сломанным» цветом (чёрным/дефолтным).
2. Проверить блок AI-комментария (карточка «Mia»).
   Ожидается: комментарий на месте, релевантен реальным данным ребёнка (2 абзаца, без markdown/списков, без "-" вместо тире).
3. Проверить CTA-блок.
   Ожидается: заголовок «Не останавливайте прогресс», текст содержит имя ребёнка; если есть фокус-тема (RED/YELLOW статус) — упоминание темы в фокусе; кнопка «Привязать карту» (триал) или «Оплатить полный доступ» (фримиум) в зависимости от `cta`.
4. **Открыть само письмо (email), не переходя по ссылке.**
   Ожидается: в письме — только заголовок, обычная строка сводки (дни/задачи/минуты), кнопка «Смотреть полный отчёт», отписка. Замочков, AI-комментария и тёплого CTA-текста в письме НЕТ — это по коду ожидаемо, но стоит явно сверить с продактом/автором (см. «Реализация», п.5).

**TC2. Платный (не фримиум) родитель.**
Ожидается: `isLocked` всегда `false` (условие `isFreemium && ...`) → замков нет ни на одной теме; AI-комментарий и CTA на месте при наличии активности; при `cta: 'none'` — нейтральный блок «Следующий отчёт о занятиях придёт через неделю».

**TC3. Фримиум-родитель, за неделю 0 активности (`daysActive = 0`).**
Ожидается: AI-комментарий отсутствует (`aiSummary: null` жёстко по условию `daysActive > 0`), UI не показывает пустой/битый блок вместо комментария (проверить `v-if` вокруг блока Mia); замочки по-прежнему считаются от `isFreemium`/`freeTopicId`, не от активности — должны отображаться независимо.

**TC4. У ученика `student_free_topic_id = null` (фримиум без назначенной бесплатной темы).**
Ожидается (по коду): `isLocked` = `false` у всех тем → замков нет вообще, хотя родитель фримиум. Проверить, баг это или ожидаемое поведение (в задаче не оговорено) — если у продакшна не бывает фримиум-ученика без назначенной темы, кейс маловероятен, но стоит спросить у разработчика.

**TC5. Много тем, почти все заблокированы.**
Ожидается: список с замками не переполняет вёрстку (адаптив, мобильная/десктопная ширина страницы); иконки замков читаемы и одного цвета (см. п.9 про `$color-trainer-muted`).

**TC6. Несколько детей у одного родителя.**
Ожидается: у каждого ребёнка свой токен/страница — свой набор замков, свой AI-комментарий, свой CTA с именем именно этого ребёнка; данные не путаются (общая архитектура отчётов, отдельного кода под MIA-25 нет, но стоит перепроверить).

**TC7. Регресс общей структуры недельного репорта.**
Ожидается: `weeklySummaryLine`, легенда, футер, ссылка отписки — без изменений и без визуальных сдвигов от нового блока `topic__lock`.

**TC8. Адаптив/почтовые клиенты.**
Ожидается: страница отчёта и письмо корректно рендерятся на мобильном/десктопе; иконка замка не съезжает и не обрезает название темы на длинных названиях.

### Итоги месяца — новый репорт

**TC9 (happy path). Первое воскресенье месяца, у ребёнка есть скоренная диагностика.**
Ожидается: письмо `parentMonthlyReport` (тема «Итоги месяца: {имя}»), в письме — кнопка на `/report/[token]` с `type: 'monthly'`; на странице — эйброу «Итоги месяца», период (`periodStart`–`periodEnd` — календарный месяц, а НЕ «с даты диагностики»), блок `monthly-anchor` с датой диагностики, баллом `X/10` и распределением зелёный/жёлтый/красный по диагностике.

**TC10. Подавление недельного письма в неделю первого воскресенья.**
Ожидается (по коду `runReportTick`): в эту неделю уходит только месячное письмо — весь тик обрабатывает `dispatchReports('monthly', ...)` и завершается через `return`, к недельной логике код в этот тик не обращается вовсе. Продублированного недельного письма быть не должно.

**TC11. У ребёнка НЕТ ни одной диагностики со статусом SCORED.**
Ожидается (по коду, `if (!session) return;`): месячный отчёт **не отправляется вообще** — ни письма, ни записи в `parent_report`. Отчёт либо полный, либо не приходит совсем, промежуточного варианта нет. Стоит зафиксировать как факт для приёмки — уточнить у продакта, ожидаемо ли молчаливое отсутствие письма (нет ни лога, ни фолбэка).

**TC12. Проверка цвета/статуса темы.**
Ожидается: цвет (`topic__dot`) каждой темы = статус по диагностическому баллу (`statusFromAiScore(diagnosticScore)`), НЕ по текущему mastery. Сверить конкретную тему: если на диагностике был RED, а сейчас mastery высокий — дот всё равно должен быть красным, а числовая дельта — показывать большой плюс.

**TC13. Шкала динамики «было → стало».**
Ожидается: `prevMasteryScore` (baseline) вычислен через ту же `computeMasteryScore`, что и текущий `masteryScore` — визуально это один и тот же 0-100 диапазон. Проверить на теме с реальным ростом — дельта должна быть положительной.

**TC14. Легенда и статус-лейблы в месячном отчёте.**
Ожидается: легенда (зелёный/жёлтый/красный, подписи «Освоено/Уверенно/Нужно подтянуть») отображается и для месячного отчёта (тот же `v-if="diagnosticData || monthlyData"`) — регресс не ожидается, но стоит пройтись глазами.

**TC15. Фримиум + месячный отчёт (лок).**
Ожидается: лок применяется идентично недельному — `isLocked` по тому же условию `isFreemium && freeTopicId !== null`. Открытая тема — без замка, остальные — с замком.

**TC16. CTA в месячном отчёте.**
Ожидается: заголовок и текст CTA — из той же функции `buildWeeklyCtaCopy`, но **без** упоминания темы в фокусе (`focusTopicName` жёстко `null` для месячного) — сверить, что фраза «Сейчас в фокусе тема...» не появляется в месячном CTA даже если явный фокус есть по данным.

**TC17. Несколько детей — месячный отчёт.**
Ожидается: у каждого ребёнка свой блок с собственной диагностикой/динамикой, без смешения (общий регресс токен-страницы).

**TC18. Адаптив месячного отчёта.**
Ожидается: блок `monthly-anchor` (дата диагностики, балл, распределение) и список тем с динамикой корректно адаптируются на мобильном/десктопе, не обрезаются при длинных названиях тем и при 3-значных числах.

**TC19. Регресс расписания в обычные недели месяца.**
Ожидается: во все недели месяца, кроме недели с первым воскресеньем, `isMonthlySendWindow` = `false`, код идёт по старой ветке `isWeeklySendWindow` — недельные письма приходят как раньше, без пропусков и дублей.

**TC20. Письмо месячного отчёта само по себе.**
Ожидается (см. «Реализация» п.5): в письме `parentMonthlyReport.mjml` — заголовок, строка с диагностическим баллом (если есть) + имя ребёнка, кнопка, отписка. Диагностика/темы/лок в письме НЕ показываются — только на веб-странице по клику.

## Аналитика/API

Сверено с `frontend/constants/analytics-events.ts` и `api/src/constants/analytics-events.ts` (совпадают построчно):

- `PARENT_REPORT_MONTHLY_EMAIL_SENT` (`parent_report_monthly_email_sent`) — новое серверное событие, шлётся через `trackServerEvent` в конце `createMonthlyReport`, с параметром `{ report_id }` и `parentId` как ID пользователя для Метрики. Проверить: событие уходит ровно один раз на отправленное письмо, не дублируется при ретраях тика.
- `PARENT_REPORT_CTA_CLICK` (`parent_report_cta_click`) — существующее клиентское событие (`frontend/pages/report/[token].vue:321`), уже поддерживает `report_type: 'monthly'` без доработок (`{ report_type: p.type, cta: p.cta }`) — отдельного события под месячный клик заводить не пришлось, только проверить, что `report_type` действительно приходит как `'monthly'`, а не `'weekly'`/`undefined` по ошибке маппинга типа.
- `PARENT_REPORT_PAGE_OPEN` в диффе не используется (не менялся в MR) — если продакт ожидает трекинг открытия месячного отчёта отдельно от клика по CTA, такого события в этом MR не появилось, стоит уточнить, нужно ли.
- Точечная проверка "для удобства тестирования": прямого способа форсировать отправку письма/тик через API нет в диффе — тестировать через ожидание тика или ручной вызов `runReportTick`/`createMonthlyReport` в тестовом окружении (спросить у разработчика, если нужен шорткат).

## Открытые вопросы

1. **Undefined SCSS-переменная `$color-trainer-muted`** в стиле иконки замка (`[token].vue:928`) — такого токена нет в `_variables.scss`, похоже на опечатку (возможно, имелся в виду `$color-text-muted`). Нужно проверить на живом стенде — компилируется ли стиль и как выглядит иконка замка.
2. **AI-комментарий и тёплый CTA не отражены в самом письме**, только на веб-странице отчёта — уточнить у автора/продакта, осознанное ли это решение (короткое письмо + богатая страница) или недоработка относительно acceptance-критериев задачи.
3. **Молчаливый пропуск месячного отчёта** при отсутствии скоренной диагностики — нет уведомления/лога уровня warning, событие тика просто не создаёт отчёт для этого ученика. Уточнить, устраивает ли такое поведение (без экрана/письма-заглушки «пройдите диагностику для итогов месяца»).
4. **Краевой случай `student_free_topic_id = null`** у фримиум-ученика — замки не показываются вообще ни для недельного, ни для месячного отчёта. Проверить, бывает ли такое состояние в реальных данных.
