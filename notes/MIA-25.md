## Контекст

Родительские репорты должны стать понятнее и мотивирующее: родитель видит прогресс ребёнка и причину продолжать занятия.

**Репорт «Итоги недели» — доработки:**
- Заблокированные темы у фримиум-родителя помечаются замочком; открытая тема (на фримиуме доступна одна) — без замка.
- Добавлен персональный AI-комментарий по итогам недели.
- CTA сделан тёплым и адресным: с именем ребёнка и темой в фокусе.

**Новый репорт «Итоги месяца»:**
- Раз в месяц, в первое воскресенье месяца — вместо недельного на этой неделе.
- Показывает результат вводной диагностики как точку отсчёта + динамику «было → стало» по темам и общему баллу.

**Acceptance (из задачи):** замочки у фримиум-родителя в недельном; AI-комментарий + адресный CTA в недельном; новый репорт «Итоги месяца» с диагностикой, статусом, динамикой.

Ключевые находки по коду (важно для тест-кейсов, некоторые расходятся с текстом задачи/комментариев):

1. **Лок тем** (`isLocked`) считается одинаково и для недельного, и для месячного отчёта: `isFreemium && freeTopicId !== null && topicId !== freeTopicId`. Т.е. **и в месячном отчёте лок работает** (открытый вопрос из задачи закрыт по коду).
   - Краевой случай: если у ученика `student_free_topic_id === null` (нет назначенной бесплатной темы), `isLocked` будет `false` у ВСЕХ тем даже для фримиума — ни одного замка не будет.
2. **AI-комментарий недели** генерируется, только если `daysActive > 0` за неделю (`createWeeklyReport`) — подтверждает комментарий автора.
3. **AI-комментарий месяца** генерируется **всегда**, если есть скоренная диагностика — не зависит от активности за месяц.
4. **Месячный отчёт не отправляется вовсе**, если у ученика нет ни одной диагностической сессии со статусом `SCORED` (`if (!session) return;` в начале `createMonthlyReport`) — ни email, ни строка в `parent_report` не создаются. Без диагностики — отчёт молча пропускается каждый месяц (закрывает открытый вопрос TC15 из предыдущей версии заметки).
5. **Важный нюанс, которого нет в тексте задачи**: сам email (`parentWeeklyReport.mjml` / новый `parentMonthlyReport.mjml`) **не менялся** и содержит только заголовок, generic `summaryLine`/`monthlyEmailLine`, кнопку «Смотреть полный отчёт» и отписку. **AI-комментарий, замочки и тёплый CTA видны только на веб-странице отчёта** (`/report/[token]`), куда ведёт кнопка — в самом письме их нет. Формально acceptance «в недельном репорте есть AI-комментарий и адресный CTA» выполняется только если считать репортом связку письмо+страница. Стоит уточнить у автора/продакта, это осознанное решение или недосмотр.
6. **CTA-копирайт** (`buildWeeklyCtaCopy`) переиспользуется для месячного отчёта, но `focusTopicName` туда всегда передаётся `null` — то есть в месячном CTA никогда не будет фразы «Сейчас в фокусе тема «X»», только в недельном.
7. **Цвет темы в месячном** = статус по **диагностике** (`statusFromAiScore(diagnosticScore)`), не по текущему прогрессу — светофор всегда про «было». Прогресс/дельта (числовая, +N/=) считается отдельно на единой шкале mastery (baseline пересчитан через `strategy.computeMasteryScore` из диагностического балла — та же шкала, что и текущий `masteryScore`, поэтому реального риска «ложного регресса» из-за разных шкал в коде не видно).
8. **Планировщик**: `isMonthlySendWindow` = первое воскресенье месяца (`getUTCDate() <= 7`) И час ≥ `SEND_HOUR_MSK` (тот же час, что для недельного). `runReportTick`: если попали в месячное окно — шлёт **только** месячный и выходит (`return`), недельный в этот тик не проверяется вовсе. Остальные недели — обычная недельная логика без изменений.
9. Выборка кандидатов для месячного использует тот же SQL-запрос по подпискам, что и для недельного (тот же `dispatchReports`), с проверкой `NOT EXISTS ... type = 'monthly' ... period_start = ...` — но если `createMonthlyReport` рано вышел (нет диагностики), строка в `parent_report` не создаётся, значит в следующем месяце для этого же ученика попытка повторится.

Макет: в `mockups/index.md` нет строки под экран отчёта родителям — сверка с макетом не проводилась, тест-кейсы ниже — по коду `[token].vue` и диффу.

### Итоги недели — доработки

**TC1 (happy path). Фримиум-родитель, активность за неделю есть.**
1. Открыть `/report/[token]` для недельного отчёта фримиум-родителя с активностью за неделю.
   Ожидается: одна (бесплатная, `freeTopicId`) тема — без замка; остальные — с иконкой замка (Lucide Lock, 13px) рядом с названием темы.
2. Проверить блок AI-комментария (карточка «Mia»).
   Ожидается: комментарий на месте, релевантен реальным данным ребёнка (2 абзаца, без markdown/списков, без "-" вместо тире).
3. Проверить CTA-блок.
   Ожидается: заголовок «Не останавливайте прогресс», текст содержит имя ребёнка; если есть фокус-тема (RED/YELLOW статус) — упоминание темы в фокусе; кнопка «Привязать карту» (триал) или «Оплатить полный доступ» (фримиум) в зависимости от `cta`.
4. **Открыть само письмо (email), не переходя по ссылке.**
   Ожидается: в письме — только заголовок, обычная строка сводки (дни/задачи/минуты), кнопка «Смотреть полный отчёт», отписка. Замочков, AI-комментария и тёплого CTA-текста в письме НЕТ — это по коду ожидаемо, но стоит явно сверить с продактом/автором (см. «Реализация», п.5), не баг ли это по восприятию accept-критериев.

**TC2. Платный (не фримиум) родитель.**
Ожидается: `isLocked` всегда `false` (условие `isFreemium && ...`) → замков нет ни на одной теме; AI-комментарий и CTA на месте при наличии активности; при `cta: 'none'` — нейтральный блок «Следующий отчёт о занятиях придёт через неделю».

**TC3. Фримиум-родитель, за неделю 0 активности (`daysActive = 0`).**
Ожидается: AI-комментарий отсутствует (`aiSummary: null` жёстко по условию `daysActive > 0`), UI не показывает пустой/битый блок вместо комментария (проверить `v-if` вокруг блока Mia); замочки по-прежнему считаются от `isFreemium`/`freeTopicId`, не от активности — должны отображаться независимо.

**TC4. У ученика `student_free_topic_id = null` (фримиум без назначенной бесплатной темы).**
Ожидается (по коду): `isLocked` = `false` у всех тем → замков нет вообще, хотя родитель фримиум. Проверить, баг это или ожидаемое поведение (в задаче не оговорено) — если у продакшна не бывает фримиум-ученика без назначенной темы, кейс маловероятен, но стоит спросить у разработчика.

**TC5. Много тем, почти все заблокированы.**
Ожидается: список с замками не переполняет вёрстку (адаптив, мобильная/десктопная ширина письма-страницы).

**TC6. Несколько детей у одного родителя.**
Ожидается: у каждого ребёнка свой токен/страница — свой набор замков, свой AI-комментарий, свой CTA с именем именно этого ребёнка; данные не путаются (это регресс общей архитектуры отчётов, отдельного кода под MIA-25 нет, но стоит перепроверить).

**TC7. Регресс общей структуры недельного репорта.**
Ожидается: `weeklySummaryLine`, легенда, футер, ссылка отписки — без изменений и без визуальных сдвигов от нового блока `topic__lock`.

**TC8. Адаптив/почтовые клиенты.**
Ожидается: страница отчёта и письмо корректно рендерятся на мобильном/десктопе; иконка замка не съезжает и не обрезает название темы на длинных названиях.

### Итоги месяца — новый репорт

**TC9 (happy path). Первое воскресенье месяца, у ребёнка есть скоренная диагностика.**
Ожидается: письмо `parentMonthlyReport` (тема «Итоги месяца: {имя}»), в письме — кнопка на `/report/[token]` с `type: 'monthly'`; на странице — эйброу «Итоги месяца», период (`periodStart`–`periodEnd` — календарный месяц, а НЕ «с даты диагностики»), блок `monthly-anchor` с датой диагностики, баллом `X/10` и распределением зелёный/жёлтый/красный по диагностике.

**TC10. Подавление недельного письма в неделю первого воскресенья.**
Ожидается (по коду `runReportTick`): в эту неделю уходит только месячное письмо — весь тик обрабатывает `dispatchReports('monthly', ...)` и завершается через `return`, к недельной логике код в этот тик не обращается вовсе. Продублированного недельного письма быть не должно.

**TC11. У ребёнка НЕТ ни одной диагностики со статусом SCORED.**
Ожидается (по коду, `if (!session) return;`): месячный отчёт **не отправляется вообще** — ни письма, ни записи в `parent_report`. Это отличается от прежнего предположения «отчёт всегда полный»: отчёт либо полный, либо не приходит совсем, промежуточного варианта нет. Стоит зафиксировать как факт для приёмки — уточнить у продакта, ожидаемо ли молчаливое отсутствие письма (нет ни лога, ни фолбэка).

**TC12. Проверка цвета/статуса темы.**
Ожидается: цвет (`topic__dot`) каждой темы = статус по диагностическому баллу (`statusFromAiScore(diagnosticScore)`), НЕ по текущему mastery. Сверить конкретную тему: если на диагностике был RED, а сейчас mastery высокий — дот всё равно должен быть красным, а числовая дельта — показывать большой плюс.

**TC13. Шкала динамики «было → стало».**
Ожидается: `prevMasteryScore` (baseline) вычислен через ту же `computeMasteryScore`, что и текущий `masteryScore` — то есть визуально это один и тот же 0-100 диапазон. Проверить на теме с реальным ростом — дельта должна быть положительной (не должно казаться "регрессом" из-за разных шкал).

**TC14. Легенда и статус-лейблы в месячном отчёте.**
Ожидается: легенда (зелёный/жёлтый/красный, подписи «Освоено/Уверенно/Нужно подтянуть») отображается и для месячного отчёта (тот же `v-if="diagnosticData || monthlyData"`), т.е. UI переиспользует существующий компонент — регресс не ожидается, но стоит пройтись глазами.

**TC15. Фримиум + месячный отчёт (лок).**
Ожидается (закрыт открытый вопрос из прошлой версии): лок применяется идентично недельному — `isLocked` по тому же условию `isFreemium && freeTopicId !== null`. Открытая тема — без замка, остальные — с замком.

**TC16. CTA в месячном отчёте.**
Ожидается: заголовок и текст CTA — из той же функции `buildWeeklyCtaCopy`, но **без** упоминания темы в фокусе (`focusTopicName` жёстко `null` для месячного) — сверить, что фраза «Сейчас в фокусе тема...» не появляется в месячном CTA даже если явный фокус есть по данным.

**TC17. Несколько детей — месячный отчёт.**
Ожидается: у каждого ребёнка свой блок с собственной диагностикой/динамикой, без смешения (общий регресс токен-страницы).

**TC18. Адаптив месячного отчёта.**
Ожидается: блок `monthly-anchor` (дата диагностики, балл, распределение) и список тем с динамикой корректно адаптируются на мобильном/десктопе, не обрезаются при длинных названиях тем и при 3-значных числах.

**TC19. Регресс расписания в обычные недели месяца.**
Ожидается: во все недели месяца, кроме недели с первым воскресеньем, `isMonthlySendWindow` = `false`, код идёт по старой ветке `isWeeklySendWindow` — недельные письма приходят как раньше, без пропусков и дублей.

**TC20. Письмо месячного отчёта само по себе.**
Ожидается (см. «Реализация» п.5): в письме `parentMonthlyReport.mjml` — заголовок, `monthlyEmailLine` (одна строка с диагностическим баллом, если есть, + имя ребёнка), кнопка, отписка. Диагностика/темы/лок в письме НЕ показываются — только на веб-странице по клику.
