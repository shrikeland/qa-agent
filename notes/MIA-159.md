К родительскому отчёту MIA-154 задача отношения не имеет. Данных по п.1/п.2 требовалось только собрать в отчёт — инструментирование уже было; опрос по п.3 сделан в MIA-158.

## Реализация

### `api/src/admin/feedback-report.admin.controller.ts` (весь файл, 28 строк)

- `type ListQuery` (строка 4): `{ from?: string; to?: string; page?: string; pageSize?: string }` — **никакого `studentId` в типе нет**.
- `filtersOf` (12-17): собирает объект фильтров только из `from`, `to`, `page` (через `parseCount`), `pageSize` (через `parseCount`) — любой другой query-параметр, включая `studentId`, никогда не читается из `request.query` и никуда не попадает.
- `listEngagementReportHandler` (19-22) → `feedbackReportAdminService.engagement(filtersOf(request.query))`.
- `listTopicCompletionsHandler` (24-27) → `feedbackReportAdminService.topicCompletions(filtersOf(request.query))`.

### `api/src/admin/admin.routes.ts`

- Маршруты зарегистрированы строками 133-134: `fastify.get('/reports/engagement', listEngagementReportHandler)`, `fastify.get('/reports/topic-completions', listTopicCompletionsHandler)` — полные пути `GET /api/admin/reports/engagement`, `GET /api/admin/reports/topic-completions`.

### `api/src/admin/feedback-report.admin.service.ts` (весь файл, 398 строк)

- `interface ReportFilters` (19-24): `{ from?: string; to?: string; page?: number; pageSize?: number }` — тоже без `studentId`. Значит фильтра по ученику нет ни в контроллере, ни в сервисном слое — весь бэкенд-стек не знает о таком параметре, это не «баг парсинга», а нереализованный функционал.
- `resolvePeriod` (30-44): период — календарные дни по МСК (`mskDay`). Без валидных `from`/`to` (regex `^\d{4}-\d{2}-\d{2}$`) — дефолт: `to` = вчера по МСК, `from` = `to - 6 дней` (последняя полная неделя, 7 дней включительно). Если `from > to` — откат на тот же дефолт. `MAX_PERIOD_DAYS = 92` (комментарий: «Квартал — потолок и на длину периода, и на объём строк в памяти») — диапазон длиннее квартала обрезается до `[to - 92 дня, to]`, `to` сохраняется.
- `paging` (51-54): `PAGE_SIZE_DEFAULT = 50`, `PAGE_SIZE_MAX = 200`; `page = max(1, ...)`, `pageSize = min(200, max(1, ...))` — `pageSize=999` вернёт 200.
- `engagement()` (225-298, источник 1):
  - Строится от **всех** студентов (`role: 'STUDENT', deletedAt: null`) без фильтра по активности — комментарий в коде: «Ученик, переставший заниматься, — главный адресат этого отчёта... отбор по активности прятал бы ровно тех, ради кого отчёт и заведён». Это осознанно даёт нулевые строки для неактивных учеников.
  - Метрики за период: `trainerDays`/`trainerMinutes` (из `engagementTime` stage='trainer' + дни решений из `trainerSubmission`), `avgDayMinutes` (минут в день занятий, не в календарный день), `controlTests` (`diagnosticSession` CONTROL_TEST/SCORED), `homeworks` (`homework.finishedAt` в периоде), `ratingGained` (`ratingAward` сумма за период). Отдельно `ratingTotal` — сумма **за всё время**, без ограничения периодом (строка 272, `groupBy` без `where` по датам).
  - `strength` считается только для строк текущей страницы (`strengthOf`, 301-312) — сырой SQL по `rating_event`, последние `RATING_WINDOW` оценок на ученика.
  - Пагинация — **в памяти**, после сортировки всех строк (`rows.slice((page-1)*pageSize, page*pageSize)`, строка 288); сортировка: `trainerDays desc, trainerMinutes desc, имя по алфавиту`.
  - **Полей динамики к прошлой неделе (дельта дней/минут/контрольных/домашек/силы к предыдущему периоду) в объекте строки нет вообще** — только `ratingGained` (прирост рейтинга в границах выбранного периода) и `ratingTotal` (всё время). Других сравнительных полей ни в `EngagementReportRow`, ни в `buildEngagementRows` не возвращается.
- `topicCompletions()` (319-393, источники 2+3):
  - Источник строк — `ratingAward` с `reason: 'topic_closed'` за период, пагинация — **на уровне БД** (`skip`/`take`), в отличие от `engagement()`.
  - Для каждого закрытия пары «ученик-тема» точность считается **по попыткам до момента закрытия включительно** (`createdAt: { lte: c.awardedAt }`, комментарий: «Строка описывает тему на момент закрытия. Без этой границы возврат в уже закрытую тему задним числом переписывал бы точность»).
  - `feedback` — `Map` из `topicFeedback` по паре `(userId, topicId)`, `null` если ответа нет; строка всё равно попадает в отчёт (комментарий: «A student who skipped the survey stays in the report with empty scores» — прямое соответствие acceptance-пункту задачи).
  - `ml` — всегда 5 объектов (`ML_LEVELS = [1..5]`), у непройденных блоков `attempts=0`, `accuracy=null`.

### Frontend — `frontend/pages/admin/feedback/engagement.vue` и `frontend/pages/admin/feedback/topics.vue`

Оба файла структурно идентичны (общий паттерн, отличаются заголовком/колонками/иконкой пустого состояния):

- `useAdminListQuery({ perPageOptions: [50, 100, 200], defaultPerPage: 50, filters: ['from', 'to'] as const })` — **список `filters` содержит только `'from'` и `'to'`, `studentId` там нет**; строка 21 в обоих файлах. Это фронтовая часть того же дефекта: даже если бы бэкенд поддерживал `studentId`, UI не хранил бы его в URL/состоянии и не отправлял бы в запрос.
- Инпуты дат (`type="date"`, оба файла ~84-97): `@change` сразу вызывает `patch({ from/to: value || undefined, page: undefined })` — фильтр применяется без отдельной кнопки «Применить», сбрасывая страницу на 1.
- Кнопка «Сбросить» (`v-if="hasFilters"`, `hasFilters = !!from || !!to`) — `resetFilters()` = `patch({ from: undefined, to: undefined, page: undefined })`.
- `loadItems()` (37-56 в обоих) вызывается в `onMounted` и на `watch(stateKey, ...)` (перерисовка при любом изменении query-состояния этого списка). При ошибке: `console.error` + `pushToast({ tone: 'error', icon: 'cancel', title: 'Не удалось загрузить' })` — `items`/`total` при ошибке остаются в прежнем значении (на первой загрузке — пустыми), отдельного визуального «состояния ошибки» в разметке нет, только toast.
- Пустое состояние: `v-if="!items.length && !loading"` → `<AdminEmpty>` (`icon="activity" text="За период никто не занимался"` в engagement.vue:127; `icon="check" text="За период тем не закрывали"` в topics.vue:126). **Важно**: при `loading=true` это условие ложно, поэтому во время самой первой загрузки (когда `items` ещё `[]`) рендерится `v-else`-ветка с таблицей (только заголовки, без строк) — индикатор загрузки виден лишь как спиннер на кнопке «Обновить» (`icon="refresh" :class="{'is-spinning': loading}"`), отдельного skeleton/оверлея нет.
- Таблица `engagement.vue` (130-162): колонки Ученик (ссылка `NuxtLink` на `/admin/users/${student.id}`) / Класс / Дней / Всего мин / Мин в день / Контрольных / Домашек / Рейтинг (`ratingTotal` + зелёный `+ratingGained` если `>0`) / Сила (`-` при `null`, иначе `${strength} %`).
- Таблица `topics.vue` (130-166): Закрыта (`fmtDateTime(closedAt)`) / Ученик (ссылка) / Тема / Точность (`{pct}% \n correct/attempts`) / ML1-ML5 (`pct`, класс `tc-empty` при `null`) / Мин / Дней / Занятия, Сложность, Уверенность (три оценки опроса; класс `tc-empty`, текст `-`, если `!row.feedback`).
- `AdminPagination`: `page`/`totalPages` (`Math.ceil(total/pageSize)`)/`pageRowsCount`/`total`/`perPage`/`perPageOptions`; смена страницы — `patch({page})`, смена размера страницы — `patch({perPage, page: undefined})`.
- `periodLabel` = `${period.from} - ${period.to}` из ответа API (эффективный период после клэмпа), показан в `AdminCardHead meta`.
- `frontend/components/admin/admin-feedback-nav.vue`: три вкладки `AdminTabs` — Опросы (`/admin/feedback`, icon `target`), Активность (`/admin/feedback/engagement`, icon `activity`), Закрытые темы (`/admin/feedback/topics`, icon `check`); активная вкладка определяется по точному совпадению `route.path`, переключение — `router.push`.

### `frontend/composables/use-admin-list-query.ts`

`patch()` (67-95) мёржит новые query-параметры в текущий `route.query` и вызывает `router.push` (не `replace`) по умолчанию — каждое изменение даты/страницы/размера страницы создаёт отдельную запись в истории браузера, поэтому кнопка «назад» шаг за шагом возвращает предыдущие значения фильтров; пустые/`undefined` значения не попадают в URL. `state` на чтение (53-65) парсит `route.query` при каждом рендере — этим объясняется переживание перезагрузки страницы (URL — источник истины).

### `frontend/composables/use-admin-api.ts`

- Типы `AdminEngagementReportRow` (683-693), `AdminTopicCompletionRow` (695-707), `AdminReportPeriod` (672-675), `AdminReportStudent` (677-681), `AdminReportListResponse<T>` (709-715) — один в один повторяют серверные интерфейсы, `studentId`/полей динамики нигде нет.
- `listEngagementReport`/`listTopicCompletions` (1402-1426): принимают `{ from?, to?, page?, pageSize? }`, дефолт `page: 1, pageSize: 50` на фронте (дублирует дефолт бэкенда), в `params` запроса передаются буквально те же 4 поля — подтверждает, что и композабл не пропустит `studentId`, даже если бы вызывающий код его передал.

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Happy path — три вкладки, доступ, переключение

1. Открыть `/admin/feedback` под basic-auth админки.
2. Убедиться, что сверху три вкладки: «Опросы», «Активность», «Закрытые темы» (`admin-feedback-nav.vue`), активная подсвечена по текущему пути.
3. Переключиться на «Активность» (`/admin/feedback/engagement`) и «Закрытые темы» (`/admin/feedback/topics`) — обе открываются под тем же basic-auth (200, не 404/401), заголовок страницы и подзаголовок меняются, навигация остаётся видна на обеих.
4. Без basic-auth — оба API (`GET /api/admin/reports/engagement`, `GET /api/admin/reports/topic-completions`) и обе страницы должны возвращать 401/редирект на логин, а не отдавать данные.

### 2. Активность — дефолтный период и наполнение реальными данными

1. Открыть `/admin/feedback/engagement` без параметров дат.
2. Проверить период в шапке карточки (`periodLabel`) — должен быть равен последней полной неделе по МСК: `to` = вчера, `from` = `to - 6 дней` (`resolvePeriod`, `feedback-report.admin.service.ts:30-44`).
3. В таблице должны быть строки с ненулевыми «Дней»/«Всего мин»/«Мин в день» для учеников, занимавшихся в периоде, и строки с нулями для неактивных — это ожидаемое поведение отчёта про отток (сортировка: сначала активные по убыванию дней/минут, дальше по алфавиту), не дефект.
4. Клик по имени ученика открывает карточку `/admin/users/:id`.
5. Столбец «Рейтинг» показывает `ratingTotal` (всё время) и, если за период было начисление, зелёный `+ratingGained` рядом.
6. Столбец «Сила» — прочерк, если у ученика ещё нет оценок, иначе `N %`.

### 3. Активность — пагинация и размер страницы

1. Задать период с достаточным числом учеников (например, весь период истории/квартал).
2. Постранично (при `pageSize=50` по умолчанию) пройти страницу 1 и 2 — убедиться, что строки не повторяются между страницами (сортировка стабильна: `trainerDays desc, trainerMinutes desc, имя`) и что `total`/подпись счётчика («N учеников») соответствуют общему числу студентов, а не размеру страницы.
3. Переключить размер страницы на 100 и 200 через контрол пагинации — страница должна сброситься на 1 (`patch({ perPage, page: undefined })`), список — перезагрузиться.
4. Через API проверить клэмп: `GET /api/admin/reports/engagement?pageSize=999` — в ответе `pageSize=200` (потолок `PAGE_SIZE_MAX`), а не 999.

### 4. Закрытые темы — happy path, связка прогресс + опрос в одной строке

1. Открыть `/admin/feedback/topics`, задать период, покрывающий известные закрытия тем на стенде.
2. В каждой строке должны одновременно присутствовать: дата закрытия, ученик (кликабелен → карточка), тема, общая точность (`correct/attempts` + `%`), 5 колонок ML1-ML5, минуты и дни, потраченные на тему, и три оценки опроса (Занятия/Сложность/Уверенность) — всё в одной строке, без перехода на другую страницу.
3. Для ML-блока, за который ученик не брался, — прочерк (`accuracy=null`, класс `tc-empty`), не «0 %» (важно отличать «не пробовал» от «не решил ни одного верно»).
4. Найти (или создать на тесте) закрытие темы, где ответа на опрос не было: строка **не пропадает** из отчёта, три колонки оценок — прочерк (`tc-empty`), остальные данные (точность/минуты/дни) заполнены как обычно — это прямая проверка acceptance-критерия задачи.
5. Для строки, где опрос пройден, — все три оценки видны рядом с объективными метриками той же темы того же ученика.

### 5. Закрытые темы — пагинация и ограничение периода кварталом

1. Запросить `GET /api/admin/reports/topic-completions` с периодом длиннее 92 дней (например 6 месяцев) — в ответе `period.from` должен быть ровно `period.to - 92 дня`, а не запрошенная дальняя дата (клэмп `MAX_PERIOD_DAYS`, `resolvePeriod`).
2. Пагинация здесь — на уровне БД (`skip`/`take` по `ratingAward`), в отличие от «Активности» (в памяти) — по факту для UI разницы быть не должно, но полезно знать при расхождениях в поведении/производительности между вкладками.
3. Задать `pageSize=999` — как и для активности, ответ должен клэмпнуться к 200.

### 6. Пустая выдача

1. «Активность»: задать диапазон дат в будущем (после сегодняшней даты стенда) или до появления первых данных — ожидается `total=0`, пустая таблица заменяется на `AdminEmpty` с иконкой `activity` и текстом «За период никто не занимался».
2. «Закрытые темы»: задать диапазон без закрытий тем (например один день без активности) — `AdminEmpty` с иконкой `check` и текстом «За период тем не закрывали»; `GET /api/admin/reports/topic-completions?from=...&to=...` за такой день должен вернуть `items: []`, `total: 0`.
3. Убедиться, что пустое состояние не путается с состоянием ошибки — при реальной пустой выдаче toast с ошибкой не появляется.

### 7. UI-состояния: загрузка и ошибка сети/сервера

1. На вкладке «Активность» или «Закрытые темы» нажать «Обновить» и понаблюдать за кнопкой — должна получить класс `is-spinning`/задизейблиться на время запроса; отдельного скелетона таблицы нет, это ожидаемо по коду — не заводить как баг, если так и выглядит.
2. Спровоцировать сетевую ошибку (например через дев-тулзы — offline на время запроса) и нажать «Обновить»: ожидается toast `Не удалось загрузить` (иконка cancel), таблица не должна молча показать «За период никто не занимался»/«тем не закрывали» без объяснения — если при ошибке данные пустые и никакого toast не появилось, это баг несоответствия между `AdminEmpty` (легитимная пустая выдача) и ошибкой загрузки.
3. Проверить, что после восстановления сети повторное «Обновить» подтягивает данные без перезагрузки страницы.

### 8. Даты в URL: сохранение при перезагрузке, обе границы, сброс

1. На любой из двух вкладок задать «с» и «по» — URL должен обновиться `?from=YYYY-MM-DD&to=YYYY-MM-DD` (плюс `page`/`perPage`, если заданы).
2. Перезагрузить страницу (F5) — фильтры и данные должны восстановиться из URL, а не сброситься на дефолтный период.
3. Изменить только «с» (оставив «по» прежним) и отдельно только «по» (оставив «с» прежним) — оба поля должны работать независимо друг от друга, каждое изменение перечитывает список (`watch(stateKey)`).
4. Кнопка «Сбросить» (видна только когда задан хотя бы один из `from`/`to`) должна снимать оба параметра и `page` разом, возвращая к дефолтному периоду.
5. Кнопкой «назад» браузера после нескольких последовательных смен дат — вернуться к предыдущему значению фильтра (каждое изменение — `router.push`, отдельная запись истории).

### 10. [ИЗВЕСТНЫЙ ДЕФЕКТ, НЕ ПОФИКШЕН на момент заметки] Фильтр по ученику не реализован — ни в UI, ни в API

Подтверждено чтением кода на текущем HEAD: `filtersOf` в `api/src/admin/feedback-report.admin.controller.ts:12-17` и тип `ListQuery` (строка 4) читают только `from`, `to`, `page`, `pageSize` — `studentId` (или любое другое имя) не объявлен в типе и не читается из `request.query`, поэтому передан он или нет, значения не имеет. То же на уровне сервиса: `ReportFilters` (`feedback-report.admin.service.ts:19-24`) не содержит такого поля. На фронте `filters: ['from', 'to'] as const` в `useAdminListQuery` (`engagement.vue:21`, `topics.vue:21`) — контрола выбора ученика в разметке нет вовсе (не задизейблен, а отсутствует).

Шаги воспроизведения:
1. Открыть `/admin/feedback/engagement` или `/admin/feedback/topics` — убедиться, что в тулбаре есть только поля «с»/«по», контрола фильтра по ученику нет.
2. Прямым вызовом API (basic-auth): `GET /api/admin/reports/engagement?from=<дата>&to=<дата>&page=1&pageSize=50&studentId=<любой существующий id>`.
3. Сравнить с тем же запросом без `studentId`.

Ожидалось (по скоупу задачи — «Фильтр по датам и по ученику»): либо ошибка на неизвестный параметр, либо фильтрация результата до одного ученика. Фактически: ответы идентичны (`total`, состав и порядок строк на странице не меняются) — параметр молча отбрасывается уже на входе в `filtersOf`, до сервисного слоя.

Тот же дефект — тот же паттерн отсутствия `studentId` в `ListQuery`/`filtersOf`/`ReportFilters` — верен и для `GET /api/admin/reports/topic-completions`, стоит перепроверить аналогично при регрессионном прогоне.

### 11. [ИЗВЕСТНЫЙ ДЕФЕКТ, НЕ ПОФИКШЕН на момент заметки] Динамика к прошлой неделе не реализована

Подтверждено чтением кода: `EngagementReportRow` (`feedback-report.admin.service.ts:62-74`) и функция `buildEngagementRows` (89-127) не содержат ни одного поля сравнения с предыдущим периодом — есть только `ratingGained` (сумма начислений рейтинга **внутри выбранного периода**, не дельта к предыдущей неделе) и `ratingTotal` (сумма за всё время). Для `trainerDays`, `trainerMinutes`, `avgDayMinutes`, `controlTests`, `homeworks`, `strength` сравнительных значений или процента изменения нет вообще — ни в сервисе, ни в типах фронта (`AdminEngagementReportRow`, `use-admin-api.ts:683-693`), ни в разметке таблицы `engagement.vue:130-162` (только абсолютные текущие значения).

Шаги проверки:
1. Открыть `/admin/feedback/engagement` за произвольную неделю.
2. Убедиться, что ни в одной колонке таблицы нет значений вида «дней: 5 (+2 к прошлой неделе)» — единственное сравнительное значение во всей строке — зелёный `+N` рядом с рейтингом, и это прирост рейтинга **в границах текущего периода** (сумма начислений `ratingAward` с `awardedAt` внутри `from..to`), а не сравнение с предыдущей неделей.
3. Смена периода на соседнюю неделю (вручную датами) не показывает никакого индикатора «было/стало» — просто новый набор абсолютных чисел.

Если имелось в виду только это (прирост рейтинга внутри произвольно выбранного периода) — формулировку в скоуп задачи стоит уточнить у автора/постановщика; при буквальном прочтении Scope («строка на ученика... с динамикой к прошлой неделе», подразумевающей сравнение week-over-week по всем метрикам сводки) пункт не выполнен.

API-поверхность:

## Открытые вопросы

- **Экспорт в CSV.** Прямо назван «Требует решения» в описании задачи и повторно — открытым вопросом в обоих комментариях автора реализации; в MR !392 не сделан ни на одной из двух вкладок (в разметке `engagement.vue`/`topics.vue` нет кнопки экспорта). Решение нужно от постановщика задачи, тест-кейс на это заводить не за что — фичи просто нет.
- **Объём тестовых данных ограничивает глубину проверки связки «прогресс + опрос».** Автор реализации (комментарий 2) указывал на тесте 3 закрытия тем за 60 дней и 0 ответов опроса на момент деплоя; в QA-отчёте Andrei зафиксировано уже 4 закрытия за 2026-06-10—2026-09-10 и 1 строка с заполненными тремя оценками — то есть данные на стенде с тех пор пополнились (видимо, руками, как и предлагал автор: «чтобы проверить связку, тему надо закрыть руками и ответить на опрос»). При повторном QA стоит держать в уме, что колонки ML и опроса всё ещё будут почти пустыми на бо́льшей части выборки — это ограничение трафика, не баг реализации, но затрудняет визуальную проверку «нормально выглядящей» заполненной таблицы без искусственно созданных данных.
- **Расхождение способа пагинации между вкладками.** «Активность» пагинирует в памяти после полной выборки всех студентов и сортировки (`rows.slice`, `feedback-report.admin.service.ts:288`), «Закрытые темы» — на уровне БД (`skip`/`take`). Для текущего объёма данных это не создаёт видимой разницы в поведении, но стоит иметь в виду как потенциальный риск производительности «Активности» при росте базы студентов — не тест-кейс для этого раунда, скорее заметка на будущее.
- **Что считать «динамикой к прошлой неделе»** (см. известный дефект №11) — нужно уточнение у постановщика: сравнение каких именно метрик (дни/минуты/контрольные/домашки/сила/рейтинг), за какой ровно предыдущий период (календарная предыдущая неделя vs период той же длины непосредственно перед выбранным), и в каком виде показывать (дельта/стрелка/проценты) — прежде чем заводить это как баг-фикс в реализацию.
- **Формат/имя параметра для фильтра по ученику** (известный дефект №10) — в задаче не уточнено, каким контролом выбирать ученика (поиск по имени, выпадающий список, вставка id) и должен ли фильтр быть один на обе вкладки или независимый; нужно решить перед реализацией фикса, а не только добавить `studentId` в `ListQuery`.
