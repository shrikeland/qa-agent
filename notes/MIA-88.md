## Контекст

Фундамент новой модели обучения (Edu v3): тема тренажёра больше не «мешок задач», а последовательность из пяти mastery-блоков (ML1-ML5), поверх которых считается процентный рейтинг ученика 0-100%. Сильный ученик может закрыть ML1 досрочно через короткую «проверку», а не молчаливым авансом. Механика включается флагом `SCORING_VERSION=v3` (дефолт `v1`, см. `api/src/services/scoring/scoring.strategy.ts:5`) — на проде не активна, весь функционал ниже виден только там, где флаг выставлен в `v3` (тестовый стенд).

Два MR одной фичи: !280 (основной, фундамент ML1-ML5 + рейтинг) и !288 (доп. этап — «проверочный вход» для ML1, автозачёт по диагностике и честные счётчики прогресса вместо старого молчаливого аванса). Ревью веду по факту в коде — c учётом того, что !288 сознательно отменяет часть механик из !280 (аванс 50% ML2, зачёт ML1 «из ниоткуда» на входе в тему).

Спека: `docs/educational-process/mastery-levels/v3-overview.md` (исходное ТЗ методолога и модель данных), `docs/educational-process/mastery-levels/v3-config.md` (актуальные параметры после сверки с ТЗ — пороги в overview.md устарели, статус «до сверки»), `docs/educational-process/mastery-levels/v3-auto-ml1-ux.md` (UX проверочного входа, добавлен в !288, там же зафиксированы расхождения с ТЗ).

## Реализация

**Пять ML-блоков темы.** Порядок строгий, следующий блок (`ML_STATUS.LOCKED` → `ACTIVE`) открывается только после закрытия предыдущего (`api/src/services/topic-ml-progress.service.ts:170` `registerResolution`, `226-230`). Актуальные (уже сверенные с ТЗ и реализованные в коде) параметры блоков — константа `ML_BLOCKS` в `api/src/services/scoring/v3-strategy.ts:18-24`, а не таблица из `v3-overview.md` (там устаревшие 80/80/60/80/60% и +2 у ML1 — по `v3-config.md` это признанное расхождение, уже исправленное):

| ML | Название | Основных задач | Доп. за промах | Порог точности |
|----|----------|----------------|-----------------|----------------|
| 1 | Повтор по образцу | 5 | +1 | 72.5% |
| 2 | Применение | 10 | +1 | 75% |
| 3 | Осмысление (найди ошибку) | 3 | +1 | 60% |
| 4 | Перенос | 5 | +1 | 65% |
| 5 | Защита знания (найди ошибку + `why_not_questions`) | 2 | +1 | 60% |

- **Точность** засчитывается, если задача решена верно с первой отправки И `helpScore <= 2` (`isAccurateSolve`, `v3-strategy.ts:30-36`; наводящий вопрос 0-2 не штрафуется, подсказка хода решения 3+ — штрафуется).
- **Завершённость** = все выданные задачи блока доведены до верного ответа (дорешивание сохраняется, как и раньше).
- **Закрытие блока** (`isBlockClosable`, `v3-strategy.ts:38-68`): сначала должна быть 100% завершённость, затем точность >= порога. Если всё решено, а точность ниже порога — добирается ещё одна доп. задача из резерва (топ-ап, `_deriveBlockState`, `topic-ml-progress.service.ts:472-486`, целочисленный расчёт нехватки, есть комментарий про особенность округления `0.8 * 9 = 7.2000...1`). Если резерв кончился, а порог математически недостижим — блок закрывается авансом (`credited_exhausted`), в лог пишется `logger.warn` (`topic-ml-progress.service.ts:217-222`) — **отдельного вида алерта в админке или аналитике для этого случая в коде нет**, только серверный лог; в спеке («если кончились вопросы — обязательно алертить») подразумевается что-то более заметное — уточнить у автора, устраивает ли только `logger.warn` на этом этапе.
- **Основная задача (`mlRole: 'core'`) vs доп. (`'reserve'`)** — поле `Assignment.mlRole` (`api/prisma/schema.prisma:279`). Доп. задачи не идут ни в точность блока, ни в рейтинг темы (`topicRatingValue`, `topic-ml-progress.service.ts:383-391` — учитывает только `min(accuracySolved, coreCount)` по каждому блоку, доп. задачи считаются отдельно от core и не увеличивают вклад).
- **Прогресс не едет назад.** Полоса темы (`mlProgressPct`, `frontend/utils/ml-progress.ts:60-66`) считается по формуле `(закрытые блоки + coreSolved/coreCount активного) / 5` — знаменатель активного блока это `coreCount` (только основные задачи), доборы в знаменатель не идут, поэтому монотонна по построению. Отдельная колонка `topic_ml_progress.core_solved` для этого специально добавлена в !288 (раньше знаменателем был подвижный `issuedTotal`, и полоса могла откатываться назад на доборе — это фикс из `v3-auto-ml1-ux.md`).
- Когда основные задачи блока решены, а точность ещё не набрана — блок в состоянии `top-up` («на доборе»), не «закрыт»: `mlBlockState`, `ml-progress.ts:26-32`.

**Рейтинг ученика.** `RatingEvent` (`api/prisma/schema.prisma:343-355`, уникальность `(userId, sourceType, sourceId)` — повторная контрольная/диагностика **обновляет** значение события, а не плодит новое). Источники: `topic` (закрытие ML5, значение = `topicRatingValue`), `control_test` и `diagnostic` (% верно решённых задач сессии, `diagnostic-session.service.ts:418-443`), `error_correction` (фаза 3, вне скоупа этой задачи). Домашняя работа рейтинг не трогает — соответствующего вызова `recordEvent` для homework в коде просто нет.
Текущий рейтинг = среднее последних 5 событий по `createdAt` (`currentRating`, `v3-strategy.ts:104-109`, `RATING_WINDOW = 5`), округление `Math.round`. Значение события клампится в 0-100 и округляется при записи (`rating.service.ts:15`).

**Проверочный вход (ML1, из !288).** `isProbeOffered` (`v3-strategy.ts:76-83`): предлагается только на ML1, при рейтинге **строго > 80** (не `>=`) и если основных задач в блоке доступно больше 2 (`coreAvailable > PROBE_CORE_TASKS`) — т.е. если в теме 3 и меньше core-задач ML1, проверка не предлагается вообще (грань чуть жёстче, чем «меньше двух» из `v3-auto-ml1-ux.md`: при ровно 3 доступных core-задачах проверка всё ещё предлагается, у ТЗ формулировка «меньше двух» неоднозначна — стоит перепроверить, при 3-х доступных core проверка есть). Проверка проходит (`isProbePassed`, `v3-strategy.ts:85-97`), если решено ровно 2 core-задачи и обе точны (`helpScore <= 2`, с первой попытки). Тогда ML1 → `credited` с **честными счётчиками** (`coreSolved` = 2 из 5, не 5 из 5 — специально исправлено в !288), пропущенные 3 задачи доступны через практику. Если хотя бы одна из двух не точна — обычный ML1 целиком (5 core + доборы, порог 72.5%), без потерь.
Отдельно: если тема **полностью** решена верно в диагностике — ML1 засчитывается сразу без проверки (`creditMl1AfterDiagnostic`, `topic-ml-progress.service.ts:352-364`), и это тоже «зачтено досрочно» с честными нулевыми счётчиками (не выдаётся авансом 5 из 5).
⚠️ Замечено при чтении `diagnostic-session.service.ts:428-431`: «полностью решена тема» вычисляется как «в теме есть хотя бы одна верно решённая диагностическая задача» (`fullySolvedTopics` строится фильтром `isCorrect === true` по `assignmentId → topicId`, без проверки, что ВСЕ диагностические задачи темы в сессии решены верно). Если в одной диагностической сессии на тему приходится больше одной задачи и хотя бы одна из них ошибочна — по этому коду тема всё равно может попасть в `fullySolvedTopics`. Возможно, это не баг, если на диагностику всегда приходится ровно 1 задание на тему (нужно уточнить у автора/по банку — раздел 5 `v3-overview.md` про 20 диагностических заданий на ~10 тем на это похоже, но не гарантирует явно). **Стоит отдельно проверить этот кейс на стенде**, если удастся собрать диагностику с 2+ заданиями на одну тему.

**Практика по пропущенным задачам.** `POST /trainer/practice` (`setBlockPractice`, `trainer.controller.ts:217-234` → `topicMlProgressService.setPractice`) открывает/закрывает `practiceOpen` на уже закрытом блоке с недорешёнными core. Практика выдаёт только нерешённые core (резерв не трогается), не меняет статус/точность/рейтинг (`_registerPractice`, `topic-ml-progress.service.ts:249-263`), закрывается сама, когда пропущенных не остаётся.

**Find_error (ML3/ML5).** `Assignment.presentedSolution` (шаги с заложенной ошибкой) уходит студенту, а `errorStep`/`whyNotQuestions` — нет: белый список в `api/src/utils/assignment-privacy.ts:6-16` явно исключает эти поля с комментарием «they reveal the answer». `chat-assignment-card.vue` рендерит шаги пронумерованным списком (`Шаг N:`) с плейсхолдером-подсказкой «Найди шаг с ошибкой и объясни в чате, что в нём не так» — сам номер ошибочного шага нигде на фронте не подсвечен.

**Миграция существующих учеников** — по `v3-overview.md` §8 (скрипт разового пересчёта блоков по прошлым submissions) и уточнению в `v3-auto-ml1-ux.md`: у части старых учеников в `topic_ml_progress` уже мог быть легаси-аванс (`pre_credited_core` на ML2 от старого молчаливого зачёта). Точечный фикс — `api/scripts/normalize-legacy-ml-credit.ts` (трогает только ML2). Есть также `api/scripts/backfill-ml-core-solved.ts`, но по комментарию в самом `v3-auto-ml1-ux.md` (строка про «название обманывает») этот скрипт при прогоне пересчитывает **все** блоки через `recomputeCounters`, включая уже показанный ученику зачтённый легаси-ML1, и обнуляет его счётчики — что прямо противоречит принципу «не отбирать уже показанный прогресс». **Это не влияет на ручное тестирование на новом стенде** (там учеников со старым прогрессом нет), но стоит явно уточнить у автора, что в проде/на будущих миграциях будет запущен `normalize-legacy-ml-credit.ts`, а не `backfill-ml-core-solved.ts` — иначе есть риск случайно обнулить прогресс реальных учеников при внедрении на проде.

**Админка.** `GET /admin/students/:studentId/rating` (`rating.admin.controller.ts`) отдаёт `currentRating` + до 20 последних событий. Вкладка ученика «Обучение» → саб-таб «Рейтинг» (`admin-user-learning.vue:60`, компонент `admin-user-rating.vue`). Саб-таб «Темы» (`admin-user-progress.vue`) — это старый v1/v2 прогресс по теме, ML-блоки там **не отображаются**; отдельного вида в админке с разбивкой по ML-блокам/статусам (`credited_exhausted` и т.п.) нет — единственный источник данных о конкретных блоках это `/me` (для самого ученика) и логи сервера.

## Тест-кейсы

### Предусловие

Тестовый стенд работает на новой механике «с нуля» (`SCORING_VERSION=v3`). На момент передачи в тест ни у одного ученика на стенде нет ни ML-прогресса, ни рейтинговых событий — **тестировать только со свежими (новыми) учениками**. У существующих на стенде учеников `topic_ml_progress`/`rating_event` могут отсутствовать или быть в непредсказуемом состоянии — не показательно для проверки фичи. Банк задач на стенде уже засеян (в т.ч. 100 find_error задач для ML3/ML5).

### Happy path

1. **Блоки идут по порядку.** Новый ученик заходит в новую тему тренажёра → открыт только ML1 (`active`), ML2-ML5 — `locked`, недоступны. Решить все 5 core-задач ML1 верно с первой попытки без существенных подсказок → блок закрывается (оверлей `block-complete-overlay.vue`, заголовок «Уровень 1 пройден!», точность 100%, показывается полоса из 5 сегментов, только что закрытый — тёмно-зелёный с анимацией пульса) → открывается ML2.
2. **Рейтинг появляется по диагностике.** Новый ученик проходит диагностику полностью → в админке (ученик → «Обучение» → «Rейтинг») появляется строка события с источником «Диагностика» и текущий рейтинг = проценту верно решённых заданий диагностики, округлённый (`Math.round`). До первого события в этой вкладке — состояние «Событий рейтинга ещё нет» (`AdminEmpty`).
3. **Тема целиком закрыта (все 5 ML).** После закрытия ML5 — модалка `topic-complete-modal.vue` («Тема закрыта!», чипы «5/5 уровней» и «Рейтинг обновлён», кнопки «Выбрать следующую тему» / «Остаться здесь»). В этот момент создаётся `rating_event` с источником «Тема», значение = `topicRatingValue` (доля основных задач всех 5 блоков, решённых верно с первой попытки, округлённая по 4% за задачу, 25 задач в базе).
4. **Доп. задачи за промах, полоса не откатывается.** В любом блоке (например ML2) намеренно ошибиться в задаче или запросить содержательную подсказку → в блок добавляется +1 доп. задача, полоса прогресса темы **не уменьшается** (знаменатель — только core, доборы в него не входят).
5. **Проверочный вход для сильного ученика.** У ученика с текущим рейтингом > 80% зайти в новую тему → приветствие Мии должно анонсировать сделку до первой задачи (промпт с фразой в духе «база у тебя крепкая... проверим на двух задачах», конкретный текст генерит AI по `buildGreetingPrompt`/`buildTopicEntryBlock`, не фиксирован дословно) → решить точно (верно с первой попытки, без содержательных подсказок) ровно 2 первые core-задачи ML1 → сразу на экране: ML1 закрывается статусом «зачтён по проверке» (оверлей: заголовок «Проверка пройдена - уровень 1 зачтён», ссылка «Прорешать пропущенные для практики»), пропущенные 3 задачи не выданы, открывается ML2. Прогресс темы не должен быть виден заранее (0% на входе, скачок только в момент зачёта).
6. **Проверка не пройдена.** Тот же сценарий, но одна из двух первых задач решена неточно (с ошибкой или существенной подсказкой) → обычный ML1 целиком: 5 core + доборы по общим правилам, порог 72.5%, тост «Пройдём базовый уровень целиком» / «Так надёжнее - зато дальше пойдёт легче».
7. **Тема полностью верно решена в диагностике → автозачёт ML1.** Пройти диагностику, решив верно **все** диагностические задания по конкретной теме → зайти в тренажёр этой темы → ML1 сразу в статусе «зачтён по проверке»/«credited» (честные нулевые счётчики, карточка темы показывает «пропущено 5»), без проверочного диалога (сообщение про диагностику отдельное: «в диагностике ты решил эту тему полностью верно»).
8. **Досрочно зачтённый блок можно прорешать и бросить.** На теме с зачтённым (по проверке или диагностике) ML1 нажать «Прорешать пропущенные для практики» → выдаются оставшиеся core-задачи как необязательные → решить одну и выйти на середине → статус блока, точность и рейтинг темы не меняются (только счётчик «пропущено N» уменьшается по факту решённых).
9. **Задания «найди ошибку» (ML3/ML5).** Дойти до ML3 → задача показывает готовое (но с ошибкой) решение по шагам, без подсветки, какой шаг неверный → ученик сам указывает и объясняет ошибку в чате → Мия не подсказывает номер ошибочного шага. Для ML5 — дополнительно 2 вопроса «почему не так» (`why_not_questions`), участвующих в итоговой оценке задачи.

### Альтернативы, состояния, edge cases

10. Блок с недостижимым порогом точности после исчерпания резерва (специально накопить промахи в ML3/ML5, где резерв всего +1 за промах) → блок закрывается авансом (`credited_exhausted`); оверлей должен показать заголовок «Уровень N зачтён» (без «пройден!») и эмодзи 👍 вместо 🎉, подзаголовок «... засчитан - к этим задачам ещё вернёмся». Явного алерта в админке для этого состояния нет (только серверный лог) — стоит уточнить у автора, ожидается ли видимость в этом релизе.
11. В теме с 3 и менее core-задачами в ML1 (если такое возможно на тестовых данных) — проверочный вход не должен предлагаться даже при рейтинге > 80%, обычный поток ML1.
12. Повторный заход в уже зачтённую по проверке тему — сообщение о зачёте не должно повторяться (объясняется один раз).
13. Рейтинг из одного события (только диагностика, без завершённых тем) — правило про полностью решённую тему всё ещё работает; кросс-тематический ярлык (рейтинг > 80% по одному событию) не должен запускать проверку на несвязанных темах раньше, чем накопится достаточно данных — по спеке это ожидаемо, но стоит явно проверить, что при единственном diagnostic-событии рейтинг всё равно доступен и проверочный вход по нему уже может сработать (в коде `AUTO_ML1_RATING`/`isProbeOffered` не требует минимального числа событий в окне, кроме `rating !== null`).
14. Контрольная работа, пройденная повторно по той же теме → значение существующего `rating_event` **обновляется** (не создаётся новая запись) — в списке событий в админке не должно плодиться дублей по одному и тому же источнику.
15. Домашняя работа (если доступна на стенде) не должна создавать событий рейтинга и не должна влиять на ML-прогресс темы.
16. Прогресс «не врёт» при добора на точность: специально решить блок так, чтобы завершённость дошла до 100%, но точность оказалась ниже порога (например в ML1 — решить 5/5, но с 1-2 подсказками/ошибками) → полоса должна показать блок пройденным **по объёму** (не «закрыт»), карточка блока — состояние «на доборе», Мия говорит что-то в духе «все задачи решены, осталась одна — закрепить точность», выдаётся доп. задача.

### Админка

17. ## Аналитика/API

- `TRAINER_BLOCK_PROBE_CREDITED` (`trainer_block_probe_credited`, «[Тренажёр] Уровень зачтён по проверке») — фронт шлёт при первом наблюдении зачёта блока с пропущенными core-задачами (`frontend/pages/trainer/[topicId].vue:282`, параметры `topic_id`, `ml_level`, `skipped_core`).
- `TRAINER_PRACTICE_START` (`trainer_practice_start`, «[Тренажёр] Запуск практики по пропущенным задачам»).
- `GET /admin/students/:studentId/rating` → `{ currentRating, events }` (до 20 событий).
- `/me` (авторизованный ученик, только при `getActiveVersion() === 'v3'`) отдаёт `mlProgress[]` (по каждому topic+ML: `status`, `completionSolved`, `accuracySolved`, `coreSolved`, `issuedTotal`, `practiceOpen`, добавленные на лету `coreCount` и `probe`) и `currentRating` — рейтинг показывается ученику на дашборде («Твой текущий рейтинг: N%», `frontend/pages/dashboard.vue:274-275`).
- `POST /trainer/practice` — `{ topicId, mlLevel, open }`, 409 если блок недоступен для практики.

## Открытые вопросы

1. **Включение механики на проде** — отдельный шаг отдельным решением, в этот тест-раунд не входит; здесь проверяется только тестовый стенд с флагом `v3`.
2. **Алерт на `credited_exhausted`** — в коде это только `logger.warn` на сервере, нет ни отдельного отображения в админке, ни аналитического события. Уточнить у автора, ожидается ли что-то более заметное в этом релизе, или лог достаточен на фазе 1.
3. **`fullySolvedTopics` в `diagnostic-session.service.ts:428-431`** считает тему «полностью решённой», если есть хотя бы одна верно решённая диагностическая задача по теме, без явной проверки, что решены абсолютно все диагностические задания этой темы в сессии. Возможно безобидно, если на тему всегда ровно одно диагностическое задание — нужно подтвердить у автора/по данным банка, и по возможности проверить руками с темой, у которой в диагностике 2+ задания.
4. **Порог `coreAvailable > 2` для предложения проверки** (`isProbeOffered`) чуть отличается по формулировке от «меньше двух core-задач — проверку не предлагаем» из `v3-auto-ml1-ux.md`: при ровно 3 доступных core проверка по коду предлагается. Не баг с высокой вероятностью (совпадает с духом правила), но стоит явно свериться с автором на пограничном значении.
5. **`api/scripts/backfill-ml-core-solved.ts`** — по собственному комментарию в `v3-auto-ml1-ux.md` этот скрипт при прогоне пересчитывает все блоки и обнуляет счётчики уже показанного легаси-ML1-зачёта, что противоречит задекларированному принципу «не отбирать уже показанный прогресс». Не блокирует тестирование текущего стенда (там легаси-учеников нет), но важно перед прод-миграцией: подтвердить, что реально будет использован `normalize-legacy-ml-credit.ts`, а не этот скрипт.
6. Пороги точности/пороги ТЗ (72.5% / 75% / 60% / 65% / 60%) и `helpScore <= 2` помечены в `v3-config.md` статусом «предложено»/«из ТЗ», требуют финальной валидации методологом — сама валидация вне скоупа ручного QA, но полезно знать, что цифры ещё не «утверждено».
7. Бонусный ML (своя задача) официально вне скоупа — в коде подтверждений/следов реализации не найдено, тестировать не нужно.
