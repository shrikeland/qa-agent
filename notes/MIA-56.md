## Контекст

Фича (label `Bug` в Linear не стоит, но по сути закрывала продуктовый разрыв, воспринимавшийся учеником как баг): раньше ответ в тренажёре засчитывался только с рабочей области (доски) + кнопка «Проверить». Если ученик писал ответ в чат Мии, она могла на словах согласиться, что ответ верный, но задание не засчитывалось и прогресс не двигался — тот же «7» на доске + «Проверить» засчитывался, а «7» в чат — нет. Пример из задачи: «найди коэффициент одночлена 7x²y», ответ «7» в чат.

До реализации команда сама называла нерешёнными несколько edge-кейсов (см. описание тикета): как отличить финальный ответ от рассуждения / числа внутри рассуждения; ответ на промежуточный вопрос Мии, а не на задание; источник истины, если доска непустая; тратит ли попытку неверный ответ из чата; как триггерится приём ответа. По коду (см. ниже) все они решены; ответы на них — ключевая часть этой заметки.

Out of scope (не тестировать сейчас): математическая клавиатура в чате — отдельный тикет MIA-57.

## Реализация

Живёт в том же MR !271, что и MIA-75 (фикс «тупика» в тренажёре/диагностике) — здесь описана только часть, отвечающая за приём ответа из чата; общий фон фикса «эталон с сервера» и «Мия не выносит вердиктов» затрагивает оба тикета.

**Как размечается финальный ответ (нет парсинга чисел на фронте — решает LLM):**
- `socket-gateway/src/services/trainer.prompt.ts`, `createConversationPrompt` — Мие явно запрещено подтверждать/опровергать ответ ученика («Не подтверждай и не опровергай... Никогда не пиши «верно», «правильно», «ответ верный»»), и добавлена инструкция: если сообщение ученика — **финальный ответ на задание** (а не ответ на промежуточный вопрос Мии и не число внутри рассуждения), завершить реплику меткой `[[answer:X]]` (X — plain math, парсибельный mathjs). Явно оговорено: «Если сомневаешься — не ставь». То есть разграничение «финальный ответ / ответ на промежуточный вопрос / число в рассуждении» отдано на суждение модели, детерминированного парсинга на фронте нет — при плохом суждении модели маркер может не появиться (или появиться не там), это открытый риск, не баг конкретной реализации.
- `frontend/utils/answer-marker.ts` — `hasAnswerMarker`/`stripAnswerMarker`/`stripPendingMarker`: чисто механическая работа с уже проставленным маркером (детект, вырезание из текста, скрытие незакрытого хвоста во время стрима, чтобы `[[ans` не мелькал на экране). Значение ответа никогда не переизвлекается и не переписывается моделью — используется то же сообщение ученика, что предшествовало ответу Мии с маркером.

**UI — чип «Отправить как ответ»:**
- `frontend/components/trainer/chat-message.vue` — под репликой Мии с маркером показывается чип `Отправить как ответ: {answerText}`, где `answerText` — это дословно предыдущее сообщение ученика (не то, что «понял» ИИ). Условие показа: `showAnswerChip = hasAnswerMarker(text) && !!answerText`, дополнительно гейтится `canSubmitAnswer` и `isCurrentAssignment`.
- `frontend/components/trainer/chat-messages.vue` — `answerText` вычисляется как текст предыдущего пользовательского сообщения, только если оно не было служебным токеном (подсказка/пример/шаги).
- **Гейт по текущему заданию** (коммит `dd128ca` в истории): чат тренажёра — одна непрерывная история на всю сессию и не перерисовывается при смене задания. Чип рендерится только у сообщений `message.assignment.id === currentAssignmentId`; чипы у старых реплик Мии из прошлых заданий не активны — раньше клик по такому чипу отправлял старый ответ на проверку против уже другого текущего задания.
- Клик по чипу → `frontend/pages/trainer/[topicId].vue: onSubmitAnswerFromChat` → `trainer-session.ts: sendTextSubmission` → сокет `TRAINER_INTERACTION_SEND` с `text: ':submission.text:'`, `meta.gradeMode: 'text'`, `meta.answer: <X>`.

**Роутинг грейдинга (источник истины при непустой доске):**
- `socket-gateway/src/handlers/trainer.handler.ts` — `useTextGrading = gradeMode === 'mathpix' || gradeMode === 'text'`: и распознанное с доски решение (mathpix), и ответ из чата идут через один и тот же `createTextGradingPrompt` + CAS-сверку (`checkEquivalence`) с эталоном. Пустой ответ из чата (`answer: ''`) не уходит в модель вообще — сразу `review-error`.
- **Про «непустую доску»:** доска и чат — независимые, несвязанные каналы отправки. Отправка из чата не читает и не учитывает содержимое доски вообще (`sendTextSubmission` не трогает whiteboard); если ученик что-то нарисовал на доске, но не нажал «Проверить», это никак не участвует в грейдинге ответа из чата. Если отправить и с доски, и из чата (два отдельных submission), победит последний принятый сервером результат (`lastSubmission`/`assignmentResolving` перезаписываются по факту прихода ответа) — специального слияния/приоритета «доска важнее чата» в коде нет.
- **Эталон только с сервера:** `trainer.handler.ts` (`trainerSubmissionPosted`) больше не доверяет `assignment.answer` из клиентского payload — рефетчит задание через `aiMathApi.getAssignment`. При сбое рефетча (сеть/404) — деградация: `answer: null`, грейдинг идёт по «голому» суждению LLM без CAS-сверки и без утечки ответа в промпт (условная строка с эталоном пропадает из инструкций вместо `"null"` в тексте).
- CAS-сверка не просто добавочная: если LLM ошибочно посчитала ответ верным, а `checkEquivalence(finalAnswer, серверный_answer)` говорит «different» — вердикт принудительно переопределяется на `isCorrect: false` (и наоборот при «equivalent»). Работает одинаково что для доски (mathpix), что для чата (text).

**Тратит ли попытку неверный ответ из чата:** да, наравне с доской. `frontend/pages/trainer/[topicId].vue: onSubmitAnswerFromChat` инкрементирует `attemptCount.value++` безусловно (до отправки, до получения результата) и шлёт `TRAINER_SOLUTION_SUBMITTED` с `input_type: 'chat'` — точно так же, как `confirmSubmission()` для доски.

## Тест-кейсы

1. **Happy path из задачи.** Тренажёр, задание «найди коэффициент одночлена 7x²y». Написать в чат Мии «7». Ожидаемо: Мия не хвалит явно «верно» словами, реплика заканчивается предложением отправить на проверку и под ней появляется чип «Отправить как ответ: 7». Клик по чипу → в чате появляется служебная плашка «Отправка ответа на проверку» → приходит ответ грейдинга (не Мии-собеседницы) → задание засчитывается, прогресс (шкала) растёт, doступна кнопка «Следующее» — как при отправке с доски.
2. **Неверный ответ в чат.** Написать заведомо неверный ответ. Ожидаемо: Мия не подтверждает его как правильный (не пишет «верно»/«правильно»); после отправки через чип — задание НЕ засчитывается, попытка (attempt_count) при этом учтена (см. аналитику ниже — трекинг `attempt_count` растёт).
3. **Число внутри рассуждения, не финальный ответ.** Написать в чат промежуточное вычисление с числом, которое не является ответом на задание (например, в процессе решения упомянуть промежуточный коэффициент/шаг). Ожидаемо: маркер `[[answer:X]]` не проставляется, чип не появляется — Мия просто продолжает диалог. (Это решение модели по инструкции «если сомневаешься — не ставь»; при регрессии на конкретных формулировках стоит завести отдельный баг, а не считать проверку MIA-56 проваленной в целом.)
4. **Ответ на промежуточный вопрос Мии.** Если Мия сама задаёт уточняющий вопрос («а что дальше?», «сколько будет x?») до того, как ответ на исходное задание назван, и ученик отвечает на этот промежуточный вопрос — маркер и чип не должны появляться, пока не назван именно финальный ответ задания.
5. **Гейт по текущему заданию.** Ответить в чат так, чтобы появился чип с маркером у сообщения Мии, затем перейти к следующему заданию (доска, «Следующее»). Проскроллить чат назад к старой реплике с чипом. Ожидаемо: старый чип не активен / не отправляет ответ на текущее задание (проверить, что клик по старому чипу — если визуально ещё виден — не приводит к ложной попытке на новом задании; по коду видимость чипа завязана на `currentAssignmentId`, так что чип у старой реплики должен вовсе не отображаться на новом задании).
6. **Непустая доска + ответ в чат.** Начать решать на доске (что-то нарисовать/написать), не нажимая «Проверить», затем ответить на то же задание в чат и отправить через чип. Ожидаемо: грейдинг идёт по ответу из чата, содержимое доски не мешает и не учитывается; после — можно всё ещё отправить решение с доски отдельно (второй submission), затем поведение управляется тем, какой ответ пришёл/подтверждён последним.
7. **Пустой ответ через чип.** Убедиться, что чип не может отправить пустую строку (по коду пустой `meta.answer` не должен уходить в модель — сразу `review-error`); практически проверить это трудно через UI напрямую (чип всегда несёт непустой `answerText`), но стоит проверить, что нет способа спровоцировать это через быстрый повторный клик/гонку.
8. **Мия не выносит вердиктов до грейдинга.** На любом этапе диалога (до отправки через чип) убедиться, что Мия никогда не пишет «верно»/«правильно»/«ответ верный» про названный учеником ответ — только предлагает отправить на проверку.
9. **Стриминг маркера.** Понаблюдать за репликой Мии, которая заканчивается маркером, во время самого стриминга текста — маркер `[[answer` не должен мелькать как видимый текст, чип должен появиться только после того, как реплика полностью пришла и маркер закрылся.
10. **Регрессия — отправка с доски по-прежнему работает** как раньше (кнопка «Проверить»/«Подтвердить»), включая mathpix-путь (фото/распознавание почерка) — эта фича не должна была сломать существующий флоу.
11. **Регрессия — CAS-сверка и на доске.** Известный сценарий: LLM ошибочно посчитала ответ с доски верным, но CAS-сверка с серверным эталоном должна принудительно исправить вердикт (сложно спровоцировать вручную, но если попадётся кейс с явно неверным вердиктом от Мии — заслуживает отдельного репорта, не обязательно баг этой фичи).

## Аналитика/API

- `TRAINER_SOLUTION_SUBMITTED` (`frontend/constants/analytics-events.ts`, `trainer_solution_submitted`) — теперь шлётся и из чат-флоу (`onSubmitAnswerFromChat`) с полем `input_type: 'chat'` (было только `'board'`/`'photo'`/`'mixed'` с доски). Параметры те же: `topic_id`, `task_id`, `attempt_count`. Отдельного нового события специально под «ответ из чата» не заводилось — расширили существующее полем `input_type`.
- `attempt_count` в аналитике инкрементируется на каждую отправку из чата так же, как на доске (см. коммит «Count chat submissions as attempts in analytics» в истории).
- API/сокет: интеракция ответа из чата уходит как `text: ':submission.text:'` (новое зарезервированное слово `PromptReservedWords.SUBMISSION_TEXT`, зеркалировано между фронтом и `socket-gateway`), `meta.gradeMode: 'text'`, `meta.answer: <строка>`. В чате такая интеракция отображается служебной плашкой «Отправка ответа на проверку» (`frontend/utils/message-segments.ts`), а не зелёным пузырём — сам текст ответа виден только в чипе над ней.
- Специального ручного API-эндпоинта для QA не требуется — весь путь идёт через существующий сокет-флоу тренажёра.

## Открытые вопросы

- Триггер простановки маркера — это суждение LLM по промпт-инструкции («Если сомневаешься — не ставь»), не детерминированный парсер. Возможны false negative (ответ явно финальный, но маркер не проставлен — чип не появится) и, реже, false positive на нетипичных формулировках задания. Стоит намеренно погонять несколько разных формулировок заданий (не только «найди коэффициент») на стенде, чтобы оценить, насколько стабильно ставится маркер.
- Нет явного продуктового решения/индикации для случая «ответил и на доске, и в чате на одно и то же задание» — оба пути независимы, побеждает последний пришедший с сервера результат. Если это неожиданное поведение для продукта — стоит уточнить у автора/продукта, не баг ли это по духу тикета (там источником истины предполагалась либо доска, либо явный приоритет).
- Фича покрыта тестами на бэкенде (`trainer.handler.test.ts` — роутинг в текстовый грейдинг, пустой ответ, CAS-override) и на фронте (`answer-marker.test.ts`, `trainer-session-store.test.ts` — нормализация assignment у прогруженных интеракций), по словам автора: gateway 131 pass / 0 fail, frontend 409 / 409 — регрессий тестами не поймано, ручная проверка выше нужна на реальном LLM-суждении, которое юнит-тестами не покрывается.
- Follow-up вне скоупа сейчас (не в отслеживаемых статусах): MIA-80 (nuxi typecheck), MIA-81 (findSolvedSubmissions + v2-штраф), MIA-57 (математическая клавиатура в чате).
