## Контекст

До этой задачи провал привязки карты был статистически невидим: `binding_attempt.status` навсегда оставался `PENDING`, `payment_attempt_resolved` не уходило, писем и алертов не было. Причина — дыра между двумя тиками шедулера: `runStaleBindingRevertTick` обнуляет `subscription.pending_payment_method_id` на 30-й минуте (после чего `runBindingCheck` физически не может найти подписку по этому полю), а YooKassa переводит `payment_method` в `inactive` только когда истекает срок подтверждения 3DS — то есть примерно через час, когда искать уже некому. За сентябрь так зависли 10 из 12 попыток, в июле 23 из 29, в июне 12 из 27.

Задача чисто бэкендовая (фоновый шедулер + письмо + метрики + алерт в Grafana), UI не имеет — проверка идёт по данным (`binding_attempt` в БД), письму и метрикам/алерту, а не по кликам.

Это **четвёртый** круг `Ready for Test → Testing`. Ниже — фактическое состояние кода на коммите `1790a226` (финальный смердженный MR !513), включающее все три предыдущих MR (!460, !462, !485). QA финальный MR !513 ещё **не ретестировал** — эта заметка готовится именно под этот ретест.

## Реализация

### Тик `runStaleBindingAttemptTick` — `api/src/services/binding-attempt-sweeper.service.ts`

Регистрируется в `api/src/services/trial-scheduler.service.ts` через `STALE_BINDING_ATTEMPT_INTERVAL_MS` (сейчас **5 минут**, до MR !513 было 15 — см. историю итераций ниже).

- **Выборка**: `bindingAttempt.findMany({ where: { status: 'PENDING', createdAt: { lt: now - 35 минут } }, orderBy: { createdAt: 'desc' }, take: 50 })`. 35 минут — запас в 5 минут после того, как `runStaleBindingRevertTick` на 30-й минуте обнуляет `pending_payment_method_id` (комментарий в коде объясняет именно этим). Сортировка **`desc` (свежие сначала)** — это тоже правка MR !513 (было `asc`); мотивация в коммите: строка, которую родитель вообще не открыл, годами висит в PENDING и при `asc`+`take 50` вытесняла из пачки как раз ту попытку, у которой сейчас истекает дедлайн подтверждения.
- **Верхней границы возраста в самом SQL-запросе нет** — 7-дневный дедлайн (`GIVE_UP_AFTER_MS`) проверяется уже в цикле, после ответа провайдера: `expired = row.createdAt < now - 7 дней`. Если провайдер всё ещё отвечает `pending` и попытка не просрочена — `continue`, строка остаётся `PENDING` до следующего прохода.
- **Закрытие через провайдера** (`paymentsProvider.getPaymentMethod(row.pmId)`):
  - `pending`, не старше 7 дней → пропуск (ждёт дальше);
  - `pending`, старше 7 дней → `FAILED`, `failureReason: 'pm_never_confirmed'`;
  - `active && saved` → `SUCCEEDED` (случай «родитель всё же подтвердил карту, но уже после отката подписки»);
  - всё остальное (`inactive`, `canceled`, `active && !saved` и т.п.) → `FAILED`, `failureReason` из `classifyFailure(pm)` (`pm_inactive` / `pm_canceled` / `pm_not_saved` / `pm_<status>`);
  - провайдер отвечает 404 (`isGone`) → `FAILED`, `failureReason: 'pm_not_found'` (пояснение в коде: карты, созданные ещё в мае, у YooKassa физически не существуют — без этой ветки такие строки перечитывались бы каждые 15/5 минут вечно и заваливали логи);
  - любая другая ошибка провайдера (500, обрыв) → строка не трогается, ждёт следующего прохода.
- **CAS-барьер закрытия** — в `bindingAttemptService.resolve()` (`api/src/services/binding-attempt.service.ts`), файл не менялся в MR !513, но именно он был предметом бага в циклах 4–5:
  ```ts
  const result = await prisma.bindingAttempt.updateMany({
    where: { pmId: input.pmId, status: 'PENDING' },
    data: { status: input.status, ... },
  });
  if (result.count === 0) return false; // строку уже закрыл кто-то другой
  casWon = true;
  bindingAttemptsTotal.inc({ status: input.status }); // только после барьера
  ... // трек payment_attempt_resolved
  return true;
  ```
  `resolve()` — общая точка входа: её же вызывают вебхук `/webhooks/yookassa` и поллинг `runBindingCheck` (оба через `confirmBindingForSub` в `binding.service.ts`), так что гонка возможна между сохранением сети (сначала успешный вебхук/поллинг), пока свипер уже прочитал `PENDING` и получил от YooKassa `active && saved`.

### Письмо «оплата не прошла»

- Отправляется только из ветки `FAILED` (включая `pm_not_found`), никогда из `SUCCEEDED` — функция `notifyParent()` в свипере.
- Условия отправки: у попытки есть `parent.email` и `parentId`; строка не старше `NOTICE_MAX_AGE_MS = 48 часов` (иначе тик закрывает статус молча — расчёт на первый деплой/большой бэклог, «оплата не прошла» про попытку из июня читалась бы как ошибка, а не как помощь); в рамках одного прохода тика — не более одного письма на `parentId` (дедуп через `Set`, на случай если один родитель сделал несколько попыток подряд внутри одного тика); между проходами — `NOTICE_COOLDOWN_MS = 24 часа`: перед отправкой ищется другая строка этого же `parentId` с `notifiedAt` за последние 24 часа, если найдена — письмо не шлётся.
  - **Важный нюанс для теста**: acceptance в тикете говорит «письмо уходит ровно один раз» — по коду это не «один раз навсегда», а «не чаще раза в 24 часа на родителя». Если у одного и того же родителя случится вторая, независимая брошенная попытка спустя более 24 часов — придёт второе письмо. Идемпотентность в рамках одной попытки обеспечивает колонка `notified_at` (миграция `20260918180000_binding_attempt_notified_at`), которая проставляется **до** отправки письма (на случай падения процесса между записью и отправкой — дубль хуже пропуска).
- Шаблон — `api/src/services/email/templates/bindingFailed.mjml`: тема `«Оплата не прошла — Мия360»`, текст подтверждает «деньги списаны не были», кнопка **«Выбрать тариф»** ведёт на `parentLink`. `parentLink` — не голая ссылка на страницу тарифов, а подписанный токен входа родителя (`signParentLoginToken`) на `/parent/enter?token=...&child=<studentId>` — по коду это осознанно, потому что кабинет родителя не имеет пароля и не пускает неавторизованного посетителя. После входа по ссылке родитель должен оказаться в биллинге (доступ к этому моменту уже закрыт). Ребёнок в ссылке — тот, чья подписка стояла за попыткой (`subscription.studentId`); если попытка не привязана к подписке — параметр `child` просто отсутствует, кабинет откроется на первом ребёнке.

### Метрики и алерт

- `binding_attempts_total{status}` (`Counter`, labels `status`) — инкрементится в `resolve()` сразу после выигранного CAS, **из обоих мест**: и из свипера, и из вебхука/`runBindingCheck` (общий код). `binding_attempts_recovered_total` (без лейблов) — только из свипера, только на `SUCCEEDED` и только при выигранном CAS.
- Alerting-конфиг — `monitoring/grafana/provisioning/alerting/binding.yml`, два правила в группе `binding-alerts` (интервал оценки 5m):
  - **`binding-failure-ratio`** — `sum(increase(binding_attempts_total{status="FAILED"}[1h])) / sum(increase(binding_attempts_total[1h])) > 0.5`, при этом `sum(increase(binding_attempts_total[1h])) >= 5` (иначе одна неудача при малом трафике даёт долю 1.0 каждую ночь); `for: 10m`, `severity: critical`, `noDataState: NoData` (пустой ряд — это «привязок не было», а не «всё плохо»).
  - **`binding-recovered-cards`** — `sum(increase(binding_attempts_recovered_total[1h])) > 0`, `for: 0s` (срабатывает почти мгновенно, это не поломка, а «спрятанные деньги», severity `warning`); в описании явно сказано, что доступ руками не выдаётся автоматически — нужно искать родителя в `binding_attempt` со `status=SUCCEEDED`.

### 6. Возраст попытки — границы 35 минут / 7 дней / 48 часов

14. Попытка младше 35 минут не должна попадать в выборку тика вообще (проверить, что она не трогается до истечения этого порога).
15. Попытка, которую YooKassa держит в `pending` дольше 7 дней (`GIVE_UP_AFTER_MS`) — закрывается как `FAILED` с `failure_reason = 'pm_never_confirmed'`, даже если провайдер продолжает отвечать `pending`.

### 7. Провайдер отвечает 404 / ошибкой

17. Попытка с `pmId`, которого YooKassa больше не знает (404) — закрывается `FAILED`, `failure_reason = 'pm_not_found'`, письмо отправляется по тем же правилам, что и обычный `FAILED` (через тот же CAS-флаг).
18. Попытка, на которой провайдер вернул 500/обрыв связи — строка не трогается, статус остаётся `PENDING`, ошибка в логах, попытка возьмётся на следующем проходе.

19. Свериться, что `binding_attempts_total{status}` и `binding_attempts_recovered_total` реально видны в `/metrics` (prom-client `registry`) и растут по кейсам выше.

- `PAYMENT_ATTEMPT_STARTED` (`stage: 'binding'`) — трекается в `bindingAttemptService.start()`, не менялся в этой задаче, но полезен для сверки знаменателя воронки.

## Открытые вопросы

- **Acceptance «письмо уходит ровно один раз» технически означает «не чаще раза в 24 часа на родителя»** (`NOTICE_COOLDOWN_MS`), а не «один раз навсегда за попытку». Для одиночной попытки это одно и то же (`notified_at` не даёт продублировать конкретную строку), но для родителя с двумя независимыми брошенными привязками с разницей больше суток второе письмо уйдёт — стоит уточнить у автора/в тикете, это ожидаемое поведение или acceptance стоит переформулировать точнее (аналогично тому, как уже переформулировали пункт про «час»).
- **Гонку CAS невозможно детерминированно воспроизвести на стенде** — это подтвердил ещё QA в цикле 6 («логика подтверждена тестами, хотя саму гонку на стенде не смоделировать»). Решение о PASS/FAIL для этого пункта acceptance фактически опирается на код-ревью CAS-барьера и на зелёные юнит-тесты, а не на живой воспроизведённый инцидент — стоит явно об этом написать в результатах ретеста, чтобы не создавать ложного впечатления, что гонка была прогнана вживую.
- **Сортировка `desc` (свежие сначала) + `take: 50` за проход** — при большом бэклоге давно зависших (`>7 дней`) попыток они, наоборот, могут постоянно вытесняться новыми и закрываться позже, чем закрылись бы при `asc`. При текущих объёмах (единицы-десятки попыток в месяц, тик каждые 5 минут) это не должно быть проблемой, но acceptance «`PENDING` старше недели не осталось» стоит перепроверить именно в момент первого включения на проде/после большого простоя тика, а не только в стабильном режиме с небольшим потоком.
- `classifyFailure(pm)` умеет возвращать `'pm_still_pending'` для `pm.status === 'pending'`, но в обоих местах, где эта функция вызывается из этой задачи (свипер и `binding.service.ts`), ветка `pending` уже отфильтрована раньше (`continue`/`return 'pending'`) — по коду эта строка `failure_reason` в текущих условиях недостижима. Не блокер, но если в базе когда-нибудь встретится `failure_reason = 'pm_still_pending'` — это сигнал, что что-то в условиях изменилось непреднамеренно.
