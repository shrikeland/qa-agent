## Контекст

Провал оплаты при привязке карты был статистически невидим: попытка навсегда оставалась
`binding_attempt.status = PENDING`, `payment_attempt_resolved` не уходил в аналитику, письмо
и алерт не срабатывали никогда. За сентябрь зависли 10 попыток из 12, в июле - 23 из 29, в
июне - 12 из 27.

Причина - дыра между двумя существующими тиками шедулера (`api/src/services/trial-scheduler.service.ts`):
- `runStaleBindingRevertTick` (интервал 15 мин) на 30-й минуте обнуляет
  `subscription.pending_payment_method_id` и откатывает подписку в `freemium`/предыдущий статус;
- `runBindingCheck` (интервал 5 мин) ищет подписки строго по `pendingPaymentMethodId: { not: null }` -
  после отката ему физически нечего искать.

YooKassa же переводит `payment_method` в `inactive` позже, когда истекает срок подтверждения
(обычно уже после 30-минутного отката) - терминальный статус приходить уже некуда, ни один
существующий тик его не видит. Новый код читает не подписку, а саму таблицу `binding_attempt` -
у неё этой дыры нет.

Работа закрыта двумя MR:
- **!460** (`feat/MIA-191-binding-attempt-sweeper`, смержен 2026-09-18) - сам тик, `resolve`,
  письмо, миграция `notified_at`.
- **!462** (`feat/MIA-191-binding-alert`, смержен 2026-09-20) - алерт-правила в Grafana; бэкфилл
  49 исторических записей снят со скоупа (см. «Реализация» ниже) и закрыт отдельно, деплоем на
  прод 20.09.

## Реализация

Код прочитан на `origin/master` (оба MR в нём слиты, ветки-источники после мержа удалены из
remote).

### Новый тик - `runStaleBindingAttemptTick`

`api/src/services/binding-attempt-sweeper.service.ts`, зарегистрирован в
`trial-scheduler.service.ts` (`STALE_BINDING_ATTEMPT_INTERVAL_MS = 15 * 60_000`, рядом с уже
существующими `staleBindingHandle`/`staleChargingHandle`).

Окна:
- `MIN_AGE_MS = 35 минут` - берёт `binding_attempt` в `PENDING` **старше** этого возраста
  (с запасом после 30-минутного отката), `orderBy: createdAt asc`, `take: 50` за проход;
- `GIVE_UP_AFTER_MS = 7 дней` - если провайдер всё ещё отвечает `pending` по истечении недели,
  попытка закрывается как `FAILED` с `failureReason: 'pm_never_confirmed'` (карту так и не
  открыли) - без этого дедлайна строки перепрашивались бы бесконечно и держали открытым
  знаменатель воронки;
- `pm.status === 'pending' && !expired` → пропуск, ждём следующий проход;
- `pm.status === 'active' && pm.saved` → `SUCCEEDED` (см. отдельно про recovered ниже);
- иначе → `FAILED` с `failureReason` через `classifyFailure(pm)`
  (`pm_inactive` / `pm_still_pending` / `pm_canceled` / `pm_not_saved` / `pm_<status>`);
- отдельная ветка на 404 от провайдера (`isGone`) - метод точно не существует (майские id давно
  вычищены у YooKassa) → `FAILED` с `failureReason: 'pm_not_found'`, не дожидаясь недельного
  дедлайна.

Закрытие идёт через **уже существующий** `bindingAttemptService.resolve()` - тик его не
дублирует и не обходит.

### `resolve` - CAS-барьер и метрика (`api/src/services/binding-attempt.service.ts`)

```ts
const result = await prisma.bindingAttempt.updateMany({
  where: { pmId: input.pmId, status: 'PENDING' },
  data: { status: input.status, ... },
});
// updateMany is the CAS barrier: count===0 means another webhook already
// resolved this attempt, so the event must not fire twice.
if (result.count === 0) { ...; return; }

// After the CAS barrier, never before it: counting a race twice would inflate
// the numerator the alert divides by.
bindingAttemptsTotal.inc({ status: input.status });
```
`updateMany` со связкой `pmId + status: 'PENDING'` в `WHERE` - это и есть барьер: если строку
уже закрыл другой путь (webhook / `runBindingCheck`) между чтением и записью, `count === 0` и
ни метрика, ни `payment_attempt_resolved` повторно не пишутся. Инкремент `binding_attempts_total`
стоит строго **после** барьера - это явное условие для корректности алерта (доля делится на
эту же метрику).

После успешного `updateMany` дальше как раньше - шлётся `ANALYTICS_EVENTS.PAYMENT_ATTEMPT_RESOLVED`
(`stage: 'binding'`, `result: 'success'|'failed'`, `reason: failureReason`) - это и есть событие,
которое раньше не уходило вовсе для зависших попыток.

### Письмо «оплата не прошла» - три условия

`notifyParent()` в том же файле, вызывается только для веток `FAILED` (не для `SUCCEEDED`):

1. **Один раз на родителя, не на попытку.** `notified` (Set в рамках одного прохода тика) +
   запрос по БД `bindingAttempt.findFirst({ parentId, notifiedAt: { gt: now - NOTICE_COOLDOWN_MS } })`,
   `NOTICE_COOLDOWN_MS = 24 часа`. Комментарий в коде прямо объясняет мотивацию: «один родитель
   сделал три попытки за час - три одинаковых письма выглядят как поломка». Строка помечается
   `notifiedAt` **до** отправки письма (`updateMany` → потом `sendBindingFailed`), чтобы гонка
   между двумя проходами тика или падение процесса между записью и отправкой не привели к
   дублю - риск «письмо не ушло» здесь сознательно предпочтён риску «ушло дважды».
2. **Только по свежим записям.** `NOTICE_MAX_AGE_MS = 48 часов` - записи старше суток-двух не
   вызывают письмо вообще (первый деплой встречает месяцы истории, писать «оплата не прошла»
   про июньскую брошенную попытку бессмысленно и выглядит как ошибка).
3. **Только `FAILED`.** `SUCCEEDED` (карта recovered) в `notifyParent` не попадает - см. ветку
   `if (succeeded) bindingAttemptsRecoveredTotal.inc(); else await notifyParent(...)` в самом
   тике.

Письмо: `api/src/services/email/templates/bindingFailed.mjml` - заголовок «Оплата не прошла»,
текст «платёж не завершился - деньги списаны не были», кнопка **«Выбрать тариф»** ведёт на
`parentLink`. Ссылка собирается в `subscription-email.service.ts::sendBindingFailed`:

```ts
const child = studentId ? `&child=${encodeURIComponent(studentId)}` : '';
const parentLink = `${publicBaseUrlFor(market)}/parent/enter?token=${signParentLoginToken(parentId)}${child}`;
```

Два важных момента про ссылку:
- у кабинета родителя нет пароля, голый заход на `/parent` без токена отдаёт «нужно войти
  заново» - поэтому письмо всегда несёт подписанный `token` на `/parent/enter`
  (`frontend/pages/parent/enter.vue` разбирает `route.query.token`, дальше `api.parentLogin`);
- `child` в ссылке - **только селектор**, не авторизация. `frontend/parent/child-param.ts`
  (`readChildParam`) и `frontend/parent/use-parent.ts` (`pickChild`) явно прокомментированы:
  `pickChild` ищет `id` среди детей **этого** родителя (`children.find(c => c.id === selected) ?? children[0]`)
  - если `id` чужой или устаревший (ребёнок удалён), тихо откатывается на первого ребёнка
  семьи, не на ошибку и не на чужие данные. Реальный доступ по-прежнему целиком определяется
  сессией родителя, полученной через `token`.

### Recovered - карта, подтверждённая после отката

Если YooKassa к моменту опроса тика говорит `active && saved` (родитель всё-таки прошёл 3DS уже
после того, как `runStaleBindingRevertTick` откатил подписку) - попытка закрывается как
`SUCCEEDED`, инкрементится отдельный счётчик `binding_attempts_recovered_total`
(`api/src/metrics.ts`), письмо не шлётся. **Доступ не выдаётся автоматически** - это explicit
out-of-scope из тикета: тик только фиксирует факт и поднимает счётчик, дальше это работа
человека (см. алерт `binding-recovered-cards` ниже - текст аннотации в нём прямо описывает, что
делать: искать в `binding_attempt` строки `status=SUCCEEDED` с `resolved_at` за последний час).

### Миграция `notified_at`

`api/prisma/migrations/20260918180000_binding_attempt_notified_at/migration.sql`:
```sql
ALTER TABLE "binding_attempt" ADD COLUMN "notified_at" TIMESTAMP(3);
CREATE INDEX "binding_attempt_parent_id_notified_at_idx" ON "binding_attempt"("parent_id", "notified_at");
```
Nullable, без дефолта - старые записи остаются `NULL` (не тронуты), новый индекс закрывает
именно тот запрос, который `notifyParent` гоняет на каждый проход тика (по `parentId +
notifiedAt`).

### Алерт (MR !462) - `monitoring/grafana/provisioning/alerting/binding.yml`

Два независимых правила, оба на 1-часовом окне (`relativeTimeRange: 3600s`, `interval: 5m`):

1. **`binding-failure-ratio`** - «Доля неудачных привязок карты выше половины». PromQL:
   `sum(increase(binding_attempts_total{status="FAILED"}[1h])) / sum(increase(binding_attempts_total[1h]))`,
   отфильтровано через `and (sum(increase(binding_attempts_total[1h])) >= 5)` - **порог объёма**,
   без него один ночной отказ при нулевом трафике даёт долю `1.0` и будит дежурного зря. Порог
   срабатывания - `gt 0.5`, `for: 10m`, `noDataState: NoData` (пустой ряд - «привязок не было»,
   не «всё плохо»), `severity: critical`.
2. **`binding-recovered-cards`** - «Найдена привязка, подтверждённая после отката подписки».
   `sum(increase(binding_attempts_recovered_total[1h])) > 0`, `for: 0s` (срабатывает сразу, без
   задержки - это не техническая поломка, а деньги, которые лежат и ждут человека),
   `severity: warning`. Аннотация прямо инструктирует, где искать: `binding_attempt` со
   `status=SUCCEEDED` и `resolved_at` за последний час.

Обе метрики инкрементятся строго в `resolve()` после CAS-барьера - см. «Реализация» выше,
двойной счёт гонки исключён на уровне кода, не только по комментарию в MR.

**Рядом, не в этом MR:** правило `high-cpu-usage` в `monitoring/grafana/provisioning/alerting/default.yml`
имеет `condition: ""` (пустая строка) и не содержит стадий `reduce`/`threshold` в `data` - только
голый `expr` без `refId: A → B → C`. Прочитано в коде, подтверждает комментарий разработчика: в
Grafana такое правило не сработает никогда. Не трогалось в рамках MIA-191, фиксирую как факт для
отдельного тикета.

### Бэкфилл - снят со скоупа, не баг

Из описания !462 и комментария разработчика: ручной прогон бэкфилла 49 исторических записей
оказался не нужен - новый тик сам вычерпывает историю без верхней границы возраста (только
нижняя, `MIN_AGE_MS`). Проверено на тесте (28 записей закрыто: 22 `pm_inactive`, 6 `SUCCEEDED`,
писем 0 - все старше 48ч) и подтверждено на проде 20.09 (закрыто 49 накопленных с мая: 49 FAILED
(`pm_inactive`), 1 SUCCEEDED, писем отправлено 2 - двум родителям с попытками моложе 48ч).
`PENDING` после выката - 0 на обоих окружениях. Разумное решение: отдельный скрипт бэкфилла
дублировал бы ровно ту же логику, которую и так гоняет тик каждые 15 минут.

## Тест-кейсы / Как перепроверить

Основной эффект уже проверен и выкачен на прод самим разработчиком на реальных исторических
данных (комментарий от 20.09: `PENDING=0`, 49 закрыто как `FAILED`/`pm_inactive`, 1 - `SUCCEEDED`
(живая подписка с `insufficient_funds`, не потерянная оплата), 2 письма отправлены адресатам
моложе 48ч, `payment_method_shop_id` сверен, рассинхрона магазинов нет). Поэтому для QA-раунда
это не «поиск бага с нуля», а точечная памятка: что было сломано → что изменилось → что живьём
перепроверить.

### 1. [ПРИОРИТЕТ] Новая зависшая попытка проходит тик и получает терминальный статус

1. На тестовом стенде создать `binding_attempt` в `PENDING` (обычный флоу привязки карты,
   которую банк отклонит/не подтвердит - например тестовая карта с 3DS, который специально не
   проходить, см. `e2e/specs/bind/failed-3ds.spec.ts`) и **не давать** ей завершиться штатно.
2. Дождаться отката `runStaleBindingRevertTick` (~30 минут) - `pending_payment_method_id` у
   подписки должен обнулиться, `binding_attempt.status` при этом остаться `PENDING` (это и есть
   старое поведение, воспроизводящее баг из описания задачи).
3. Дождаться прохода `runStaleBindingAttemptTick` (интервал 15 минут, возраст записи должен
   перевалить за 35 минут от создания) либо прогнать функцию руками
   (`runStaleBindingAttemptTick` экспортируется из `api/src/services/binding-attempt-sweeper.service.ts`)
   на стенде, где это возможно техническим способом. Ожидание: `binding_attempt.status` стал
   `FAILED`, `failure_reason` заполнен (`pm_inactive` для типичного случая истёкшего срока
   подтверждения), `resolved_at` проставлен.
4. Проверить, что в Метрику (аналитику) ушло `payment_attempt_resolved` с `stage: 'binding'`,
   `result: 'failed'`, `reason` = тот же `failure_reason` - именно это событие раньше не
   отправлялось никогда для зависших попыток.
5. Проверить Prometheus/Grafana: `binding_attempts_total{status="FAILED"}` вырос на 1 после
   шага 3 (не раньше - счётчик инкрементится строго после CAS-барьера в `resolve`).

### 2. Письмо - один раз, только FAILED, только свежее

6. После шага 3-4 предыдущего кейса проверить, что письмо «Оплата не прошла» пришло на email
   родителя ровно один раз, кнопка «Выбрать тариф» ведёт на `/parent/enter?token=...` (магический
   вход, у кабинета родителя нет пароля) и, если попытка была привязана к конкретному ребёнку -
   с `&child=<studentId>` в ссылке.
7. Прогнать тик ещё раз (следующий цикл `runStaleBindingAttemptTick` или ручной повторный вызов)
   по уже закрытой (`FAILED`, `notified_at` не пуст) записи - письмо **не должно** уйти повторно
   (это и есть смысл `notified_at` + `NOTICE_COOLDOWN_MS = 24ч`).
8. Смоделировать несколько попыток одного родителя подряд (в духе описанного разработчиком
   случая «один человек 17.09 пытался трижды подряд») - убедиться, что письмо ушло один раз на
   родителя, а не на каждую попытку.
9. Смоделировать запись старше 48 часов (искусственно состарить `createdAt` в БД перед прогоном
   тика, если стенд это позволяет) - попытка должна закрыться (`FAILED`/`SUCCEEDED`), но письмо
   уходить не должно (`NOTICE_MAX_AGE_MS`).
10. Перейти по ссылке из письма под сессией **другого** ребёнка того же родителя (если у семьи
    несколько детей) - убедиться, что `child` в ссылке только предвыбирает вкладку/раздел, а не
    даёт доступ к данным другого ребёнка помимо тех, что и так доступны родителю через его
    сессию; ссылка с несуществующим/чужим `child` должна тихо откатываться на первого ребёнка
    семьи, не на ошибку.

### 3. SUCCEEDED задним числом (recovered) - доступ НЕ выдаётся

11. Смоделировать случай, когда провайдер к моменту опроса тика отвечает `active && saved`
    (карта подтверждена родителем уже после отката подписки). Ожидание: `binding_attempt.status`
    → `SUCCEEDED`, письмо **не** отправляется, счётчик `binding_attempts_recovered_total`
    вырос на 1, а `subscription.status`/`access.allowed` у родителя **не** меняются
    автоматически - доступ по этой карте не выдаётся (это explicit out-of-scope тикета, не
    баг). Отдельно свериться, что `payment_attempt_resolved` для этого случая ушёл с
    `result: 'success'`.

### 4. Регресс bind/*-сценариев

В репозитории `e2e/specs/bind/` сейчас 8 спеков: `after-expired-trial`, `cancelled` (постоянно
`test.skip` - у YooKassa нет настоящей кнопки отмены, из UI-теста этот сценарий не воспроизвести,
не относится к MIA-191), `during-trial`, `expired-trial-db-race`, `failed-3ds`, `from-registration`,
`rebind-during-dunning`, `rebind-modal-after-link-burned`. Разработчик уже прогнал полный набор

все зелёные (`from-registration` 31с, остальные по ~1.9 мин) - регрессии от MIA-191 не найдено,
первый результат был артефактом среды. Для QA-раунда: если есть техническая возможность прогнать
этот набор ещё раз на незагруженном стенде - имеет смысл разово сверить, что зелень
воспроизводится; переизобретать сценарии заново не нужно, они уже покрывают bind-флоу с разных
сторон (первичная регистрация, во время триала, после истечения триала, гонка с БД, неподтверждённый
3DS, ребайнд во время дуннинга, ребайнд после протухшей ссылки).

### 5. Открытый вопрос - алерт до Telegram НЕ подтверждён вживую

Единственный пункт acceptance, который по словам разработчика (оба комментария, 20.09) остаётся
непроверенным сквозняком - реальное срабатывание правил `binding-failure-ratio`/
`binding-recovered-cards` до сообщения в Telegram. `promtool check rules` пройден, структура
правил валидна (`condition` указывает на существующую стадию `threshold`), но живого прогона
`monitoring-setup` с реальной серией отказов и проверкой, что уведомление дошло до Telegram, не
было. **Это стоит перепроверить явно**, если на тестовом окружении есть техническая возможность
сымитировать серию `FAILED`-попыток (например, руками довести ≥5 попыток за час до `FAILED`
через тик) и посмотреть на доставку алерта end-to-end, а не только на корректность PromQL/YAML.

## Аналитика/API

- `ANALYTICS_EVENTS.PAYMENT_ATTEMPT_RESOLVED` (`stage: 'binding'`, `result: 'success'|'failed'`,
  `reason`, `plan_type`, `amount`, `subscription_id`) - шлётся из `bindingAttemptService.resolve()`
  и для нового тика, и для всех прежних путей (webhook, `runBindingCheck`) - без дублей, CAS
  гарантирует ровно один вызов на попытку.
- `binding_attempts_total{status}` (Counter, `status = SUCCEEDED|FAILED`) и
  `binding_attempts_recovered_total` (Counter, без лейблов) - `api/src/metrics.ts`.
- Для точечной проверки без ожидания реального тика: `bindingAttemptService.resolve()` и
  `runStaleBindingAttemptTick()` - обычные экспортируемые функции/методы, юнит-тесты
  (`api/src/services/__tests__/binding-attempt-sweeper.service.spec.ts`,
