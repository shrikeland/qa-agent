## Контекст

Провал оплаты был статистически невидим: попытка привязки карты навсегда оставалась в `binding_attempt.status = PENDING`, событие `payment_attempt_resolved` не уходило, писем и алертов не было. Причина — дыра между двумя тиками шедулера: `runStaleBindingRevertTick` обнуляет `pending_payment_method_id` подписки на 30-й минуте, после чего `runBindingCheck` физически не может найти подписку по этому pmId; YooKassa переводит саму `payment_method` в `inactive` позже, когда истекает срок подтверждения — и терминальный статус приходить уже некуда. За сентябрь так зависли 10 попыток из 12, в июле — 23 из 29, в июне — 12 из 27.

Скоуп реализован четырьмя последовательными MR одного автора (Kirill Verzhitskii), с двумя проходами через QA:

- **!460** (18.09) `feat/MIA-191-binding-attempt-sweeper` — основной тик, письмо, миграция `notified_at`. Бэкфилл и алерт explicitly не входили.
- **!462** (20.09) `feat/MIA-191-binding-alert` — метрики и два Grafana-правила. Бэкфилл снят со скоупа: «свипер вычерпывает историю сам» (подтверждено на тесте — PENDING ушёл в ноль).
- **!463** (20.09) `fix/MIA-191-sweeper-404` — найден выкаткой на прод: свипер стабильно получал `404` от YooKassa на 39 из 50 записей и уходил в вечный опрос. Причина глубже свипера — старые карты живут в другом («прежнем») магазине YooKassa, и `getPaymentMethod` (в отличие от `getPayment`) не имел отката на него.
- **!485** (23.09) `fix/payments: свипер привязок уважает результат CAS` — **найдено QA 21.09, FAIL**: `resolve()` не сообщал о результате CAS-гонки (вебхук против свипера), из-за чего проигравший гонку проход свипера всё равно инкрементил `binding_attempts_recovered_total` **и слал родителю письмо «карта не привязалась» даже когда вебхук уже закрыл ту же попытку успехом**. Пофикшено 23.09, статус вернулся в Ready for Test.

**Раунд Testing 21.09 — FAIL по существу.** QA поймал реальную гонку: свипер прочитал PENDING-строку и получил от YooKassa `active && saved`, но до `bindingAttemptService.resolve()` вебхук успел закрыть ту же строку первым; `updateMany({status: 'PENDING'})` вернул `count=0`, но `resolve()` возвращал `void`, и `runStaleBindingAttemptTick` безусловно делал `bindingAttemptsRecoveredTotal.inc()` — то есть ложно считал гонку выигранной. Это была не косметика: ложный рост `binding_attempts_recovered_total` мог поднять alert `binding-recovered-cards` и отправить письмо о неудаче человеку, которому она уже не грозила.

**Прод-инциденты по дороге (вне тест-раунда, из комментариев разработчика).** Выкатка `!460`+`!463` на прод 20.09 разобрала все 50 накопленных с мая попыток: 49 закрыто `FAILED` (`pm_inactive`), 1 — `SUCCEEDED` (карта жива и используется, просто временная нехватка средств при продлении — не связана с багом), писем ушло 2 (только тем, кто моложе 48 часов). Отдельно, вне скоупа задачи, но упомянуто автором как причина самих провалов: пейволл по умолчанию выделяет годовой тариф (179 ₽/мес в карточке, реально списывает 7908 ₽) — 8 из 10 провальных попыток сентября были именно годом; `featured`-тариф переключён на месяц отдельным изменением тарифов (не в этом MR).

## Реализация

Код прочитан целиком на HEAD master (коммит `45e14901`, накопительно включает все 4 MR — линейная цепочка предков, `485` — потомок `463`, который потомок `462`, который потомок `460`).

### Тик `runStaleBindingAttemptTick`

`api/src/services/binding-attempt-sweeper.service.ts`:
```ts
const MIN_AGE_MS = 35 * MINUTE;                 // младше не трогать - ещё может закрыться штатно
const GIVE_UP_AFTER_MS = 7 * 24 * 60 * MINUTE;  // старше - закрыть как pm_never_confirmed
const NOTICE_COOLDOWN_MS = 24 * 60 * MINUTE;    // не более 1 письма в сутки на родителя
const NOTICE_MAX_AGE_MS = 48 * 60 * MINUTE;     // не писать про давно брошенные попытки
```
Планировщик (`api/src/services/trial-scheduler.service.ts`) гоняет тик каждые `STALE_BINDING_ATTEMPT_INTERVAL_MS = 15 * 60_000` (15 минут) — это и покрывает acceptance «терминальный статус в течение часа» (35 минут возраста + до 15 минут ожидания следующего тика = максимум ~50 минут).

Забирает до 50 PENDING-записей возрастом 35 мин - 7 дней (`orderBy: createdAt asc`, старые в приоритете), спрашивает статус у `paymentsProvider.getPaymentMethod(pmId)`. Если `pending && !expired` — пропускает (ещё может закрыться штатно). Иначе закрывает через `bindingAttemptService.resolve()`:
- `active && saved` → `SUCCEEDED` (потерянная, но подтверждённая карта);
- иначе → `FAILED` с причиной: `pm_never_confirmed` (если 7+ дней и всё ещё `pending`) или `classifyFailure(pm)` (`pm_inactive` / `pm_still_pending` / `pm_canceled` / `pm_not_saved`).
`404` от обоих магазинов (см. ниже) — терминальный `pm_not_found`, единственный случай, когда `pm: null` передаётся в `resolve()` (выдумывать статус записи, о которой провайдер ничего не сказал, было бы ложью — прямая цитата из кода).

**CAS-барьер (после фикса !485).** `resolve()` возвращает `boolean` (было `void`):
```ts
async resolve(input: ResolveInput): Promise<boolean> {
  let casWon = false;
  try {
    const result = await prisma.bindingAttempt.updateMany({ where: { pmId: input.pmId, status: 'PENDING' }, data: {...} });
    if (result.count === 0) {
      logger.warn(...); return false;   // CAS проигран - строку закрыл кто-то другой первым
    }
    casWon = true;
    bindingAttemptsTotal.inc({ status: input.status });  // строго после барьера
    ...
    return true;
  } catch (err) {
    return casWon;  // сбой аналитики ПОСЛЕ барьера - не проигрыш CAS, письмо/метрика уже состоялись
  }
}
```
В свипере: `if (!resolved) continue;` — теперь и метрика `binding_attempts_recovered_total`, и письмо родителю условны на `resolved === true`. Ключевой нюанс, который объясняет, почему `catch`-ветка возвращает `casWon`, а не всегда `false`: если аналитика (`trackServerEvent`) упадёт уже после успешного `updateMany`, откат `resolve()` в `false` заставил бы вызывающего думать, что гонка проиграна — а строка уже не PENDING, следующий проход свипера её не подхватит, и письмо потерялось бы навсегда.

### Карта из прежнего магазина YooKassa (`!463`)

`api/src/services/payments-provider/yookassa.provider.ts`, `getPaymentMethod()`:
```ts
// Same reason as getPayment: a card bound before the shop migration is unknown to the current
// shop's key and answers 404, though it exists and may well be active.
let shop = currentShop();
const raw = await getWith<RawPm>(path, shop).catch((err) => {
  if (!legacy || !(err instanceof YookassaHttpError) || err.status !== 404) throw err;
  shop = legacy;
  return getWith<RawPm>(path, legacy);
});
return { ..., shopId: shop.id ?? null };
```
До этого фикса откат на прежний магазин (`1347793`, текущий — `1451807`) существовал только у `getPayment`, но не у `getPaymentMethod` — то есть **привязка, сделанная в прежнем магазине, вообще не могла подтвердиться**: `confirmBindingForSub` падал на 404, подписка вечно висела в `pending_binding`, а `stale-binding-revert` откатывал родителя на бесплатный тариф. Свипер эту давнюю дыру не создал, а обнажил (стал первым, кто систематически дёргает `getPaymentMethod` по старым записям). `PaymentMethodResult.shopId` теперь несёт магазин, который реально ответил — это специально прокинуто до `binding.service`, чтобы штампануть в подписку верный `shopId`, иначе рекуррентное списание упало бы, пытаясь списать картой текущего магазина ключом текущего магазина.

### Метрики и алерты (`!462`)

`api/src/metrics.ts`:
```ts
export const bindingAttemptsRecoveredTotal = new Counter({ name: 'binding_attempts_recovered_total', ... });
export const bindingAttemptsTotal = new Counter({ name: 'binding_attempts_total', labelNames: ['status'], ... });
```
Оба инкрементируются строго внутри `resolve()`, после CAS-барьера.

`monitoring/grafana/provisioning/alerting/binding.yml` — два правила, live-провижининг из гита (в отличие от правил GlitchTip из MIA-192, которые живут только в БД GlitchTip):
- `binding-failure-ratio` (severity `critical`): доля `FAILED` от всех терминальных за час > 0.5, **и** порог объёма `>= 5` попыток за час (иначе один ночной отказ при нулевом трафике даёт 100% и будит дежурного зря) — `for: 10m`.
- `binding-recovered-cards` (severity `warning`): любой прирост `binding_attempts_recovered_total` за час > 0 — `for: 0s`, реагирует немедленно, т.к. каждый такой случай это конкретный человек, которому нужно вручную выдать доступ.

### Письмо «оплата не прошла»

`api/src/services/email/subscription-email.service.ts`, `sendBindingFailed()` — рендерит шаблон `bindingFailed` (`api/src/services/email/templates/bindingFailed.mjml`, заголовок «Оплата не прошла», кнопка «Выбрать тариф») со ссылкой вида `${publicBaseUrlFor(market)}/parent/enter?token=${signParentLoginToken(parentId)}&child=${studentId}` — вход по одноразовому подписанному токену (у кабинета родителя нет пароля), ребёнок в ссылке — не авторизация, а только селектор (чужой/битый id откатывается на первого ребёнка родителя).

Условия отправки в `binding-attempt-sweeper.service.ts`, `notifyParent()`: только если есть email и `parentId`; не более одного раза за проход на родителя (`Set<string>` в рамках одного вызова тика — защита от нескольких попыток одного родителя в одной пачке); не для попыток старше `NOTICE_MAX_AGE_MS = 48ч` (чтобы не писать про давно брошенные майские попытки при первом деплое); кулдаун `NOTICE_COOLDOWN_MS = 24ч` на родителя по `notifiedAt` в БД (переживает рестарт процесса, в отличие от `Set` выше). Строка помечается `notifiedAt` **до** отправки письма — осознанный компромисс «дубликат хуже пропуска».

## Тест-кейсы

Оплату руками намеренно не сорвать «по заказу» (комментарий автора в Linear) — большинство сценариев проверяются либо на подготовленных зависших записях, либо по факту (не осталось накопленных PENDING).

1. **[P0] Брошенная привязка получает терминальный статус в течение часа.** Создать тестовую привязку карты, довести до 3DS-гейта и не подтверждать (как делал QA 21.09: тестовая карта с 3DS доходит до `3ds-gate`, дальше не подтверждается). Дождаться `stale-binding-revert` (30 мин) + один-два прохода свипера (по 15 минут) → `binding_attempt.status` должен стать `FAILED` (или `SUCCEEDED`, если карта неожиданно подтвердится) в пределах часа от создания, у закрытой записи должен появиться `failure_reason`.
2. **[P0] Событие `payment_attempt_resolved` уходит по новым попыткам.** После пункта 1 — в аналитике должно появиться `payment_attempt_resolved` с `result=failed` (или `success`), `stage=binding`, привязанное к правильному `subscription_id`/`parent_id`.
3. **[P0, регрессия по FAIL 21.09] CAS-барьер не даёт свипёру перебить вебхук.** Искусственно создать гонку: запустить оплату до успешного подтверждения карты (`active && saved` на стороне YooKassa), но так, чтобы **вебхук закрыл попытку первым**, пока свипер уже читает ту же строку (проще всего — модульный тест `binding-attempt.service.spec.ts` / `binding-attempt-sweeper.service.spec.ts`, они уже покрывают этот кейс; на живом стенде воспроизвести гонку по таймингу почти невозможно). Ожидание: `binding_attempts_recovered_total` не растёт и письмо не уходит, если строку закрыл не этот проход. Если стенд позволяет — хотя бы убедиться, что обычный (без гонки) `SUCCEEDED`-кейс по-прежнему инкрементит метрику и не шлёт письмо (письмо — только для `FAILED`).
4. **Письмо уходит ровно один раз.** У одного родителя несколько попыток подряд (как было 17.09 в проде — три подряд) → письмо приходит один раз в сутки на родителя, не на попытку; повторный проход свипера в течение 24ч не дублирует письмо (`notifiedAt`-кулдаун).
5. **Письмо ведёт на страницу тарифов и содержит верный вход.** Открыть ссылку из письма → должен произойти вход в кабинет родителя (по одноразовому токену) с корректно выбранным ребёнком (селектор), а не ошибка/чужой ребёнок.
6. **Не писать про старые попытки.** Попытка старше 48 часов (смоделировать данными или дождаться) закрывается свипером (терминальный статус выставляется), но письмо не отправляется — защита по возрасту.
7. **Карта, подтверждённая после отката (`active && saved`).** Смоделировать случай, когда родитель подтвердил карту уже после того, как `stale-binding-revert` откатил подписку на бесплатный тариф → запись помечается `SUCCEEDED`, растёт `binding_attempts_recovered_total`, но **доступ не выдаётся автоматически** (out of scope задачи, явно).
8. **Карта из прежнего магазина YooKassa (регрессия по `!463`).** Если на стенде остались тестовые привязки, сделанные до миграции магазинов (`shopId=1347793`) — свипер должен успешно получить статус (через откат на legacy-магазин), а не зависнуть в вечном 404-опросе. При успехе — `PaymentMethodResult.shopId` в записи должен соответствовать магазину, который реально ответил, а не текущему по умолчанию.
9. **Алерт `binding-failure-ratio` срабатывает на всплеск FAILED.** Проверить через PromQL/Grafana UI (не обязательно провоцировать реальную серию из 5+ отказов на проде): запрос `sum(increase(binding_attempts_total{status="FAILED"}[1h])) / sum(increase(binding_attempts_total[1h])) and (sum(increase(binding_attempts_total[1h])) >= 5)` возвращает данные и правило заведено в Grafana (`binding-alerts` group). Сквозная доставка до Telegram — отдельно проверяется через MIA-192 (relay/чат уже есть после той задачи).
10. **Алерт `binding-recovered-cards` срабатывает немедленно.** Любой прирост `binding_attempts_recovered_total` за час → алерт `for: 0s`, должен сработать без задержки на следующем evaluation-цикле (`interval: 5m` группы).
11. **Бэкфилл — снят со скоупа, не тестировать отдельно.** Оба QA-раунда и разработчик сходятся: свипер сам вычерпывает исторические PENDING-записи при первом же проходе после деплоя. По факту на проде это уже случилось 20.09 (49 `FAILED` + 1 `SUCCEEDED` из 50 накопленных с мая) — искать отдельный скрипт бэкфилла не нужно, его нет.
12. **`PENDING` старше недели не остаётся.** Проверить на актуальном стенде: `SELECT COUNT(*) FROM binding_attempt WHERE status='PENDING' AND created_at < now() - interval '7 days'` должно быть 0 (закрывается как `pm_never_confirmed` при истечении `GIVE_UP_AFTER_MS`).

## Аналитика/API

- `payment_attempt_resolved` (в `binding-attempt.service.ts`, `resolve()`) — `stage: 'binding'`, `entry_point`, `result: 'success'|'failed'`, `reason` (= `failure_reason` при неудаче), `plan_type`, `amount`, `subscription_id`. Уходит **после** CAS-барьера, независимо от исхода аналитики (см. «Реализация», `catch` возвращает `casWon`).
- `payment_attempt_started` (в `start()`, не менялось этой задачей) — для контекста полноты воронки.
- Prometheus: `binding_attempts_total{status}`, `binding_attempts_recovered_total` — оба только через `resolve()`, инкремент строго после CAS.
- `binding_attempt.rawResponse` (JSON) — теперь пишется сырой ответ `getPaymentMethod` целиком при каждом `resolve()`, независимо от исхода — полезно при разборе конкретной записи руками.
- `binding_attempt.notified_at` — новая колонка, единственный источник правды о том, отправлялось ли уже письмо по этой попытке/этому родителю.

## Открытые вопросы

- **Сквозная доставка обоих Grafana-алертов до Telegram ни разу не подтверждена живьём** — ни в раунде 21.09, ни в комментариях разработчика («что осталось непроверенным» повторяется в трёх из четырёх MR). Нужен `monitoring-setup` и реальная (или искусственно устроенная) серия из 5+ отказов за час на стенде с доступным каналом доставки. После MIA-192 relay/чат для Grafana-алертов уже есть («Mia 360 Tech») — стоит закрыть эту проверку в этом же QA-заходе, раз инфраструктура готова.
- **CAS-гонку (тест-кейс 3) практически невозможно воспроизвести вживую по таймингу** — она покрыта модульными тестами (`binding-attempt.service.spec.ts`: «reports a won CAS to the caller», «still reports the won CAS when the analytics read after it fails»; `binding-attempt-sweeper.service.spec.ts`: «does not count a recovered card the webhook closed first», «sends nothing when the webhook resolved the attempt first»), но живой E2E-регрессии на эту конкретную гонку у QA не будет — стоит явно принять юнит-тесты как единственное доказательство для этого пункта.
- **Причина самих провалов оплаты (годовой тариф по умолчанию, 179 ₽/мес в карточке vs 7908 ₽ факт списания) прямо названа в Out of scope задачи и починена отдельно, в админке**, не релизом — переключение `featured` с года на месяц уже сделано на тесте и проде (по словам автора от 20.09), но это не часть кода MIA-191 и не тестируется в рамках этого тикета.
- Автор отдельно, вне скоупа, отметил существующий баг: правило `high-cpu-usage` в `monitoring/grafana/provisioning/alerting/default.yml` имеет пустой `condition` и не содержит стадий reduce/threshold — подтверждено чтением файла (строка `condition: ""`), правило в Grafana не сработает никогда. Не в скоупе MIA-191, но стоит завести отдельным тикетом, если ещё не заведён.
