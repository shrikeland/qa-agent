# MIA-128: Тренажер: Мия остановилась

## Контекст

Ветка `fix/MIA-128-stuck-on-solved-task` уже смёржена в master и снесена; код разбирался по коммиту `44b3a001` (состояние ветки перед мержем) в подготовленном git worktree — сам MR !351 на GitLab доступен.

Баг новый, ранее на тестировании не был; единственный источник по нему — комментарий разработчика (Kirill Verzhitskii, 2026-08-25) с разбором из данных прода, это не полноценный отчёт QA с логами прогона, так и стоит считать при верификации.

Автор нашёл на проде живой блок в состоянии тупика: ML5, обе core-задачи решены, точность 0 (обе верные отправки find_error помечены «с подсказкой» из-за отдельного дефекта грейдинга — MIA-127), в теме лежат невыданные резервные задания. Ученик 22.08 ответил верно и застрял — новых сообщений с тех пор нет.

Сложились два дефекта:
1. **Грейдинг find_error штрафовал точность за подсказку, которую сам же и предписывал** — из-за этого блок не мог формально закрыться, несмотря на верные ответы. Это MIA-127, чинится отдельно.
2. **Клиентская проверка `isLastTaskOfTopic`** считала тему оконченной, раз core-задачи открытого блока решены и выше нет открытых блоков — и глушила автопереход к следующему заданию, хотя на самом деле оставались невыданные резерв/ретейк-задания.

Почему это тупик, а не неудобство: в чате тренажёра нет кнопки «следующая задача» — весь переход вперёд делает автопереход на `solved`. Комментарий у убранной проверки обещал, что ошибка безопасна («задачу, принятую за последнюю, ученик добьёт кнопкой») — но кнопки нет, поэтому цена ошибки — не лишний клик, а полная остановка занятия.

## Реализация

Guard `isLastTaskOfTopic` убран целиком (не сужен — сузить некуда: `practiceOpen` ставится только на закрытом блоке и только пока задания ещё есть, так что единственный оставшийся случай «да» приходился бы ровно на состояние, где работа не кончена).

- `frontend/utils/ml-progress.ts` — функция `isLastTaskOfTopic` удалена полностью (считала по счётчикам блока: core решены и нет открытых блоков выше).
- `frontend/cabinet/chat/use-session.ts`, вотчер `solved` (~строка 367) — условие автоперехода
  ```
  if (solved.value && !store.isLocked && !store.isFinished && !isLastTaskOfTopic(blocks.value)) {
  ```
  стало
  ```
  if (solved.value && !store.isLocked && !store.isFinished) {
  ```
  Клиент теперь после любого верного ответа всегда запрашивает следующее задание (`store.nextAssignment`) через socket; решает, что выдать (резерв, нетронутое ретейк-задание или закончить занятие), только сервер.
- `socket-gateway/src/handlers/trainer.handler.ts`, `trainerNextAssignmentHandler` — раньше молчал на любую ошибку кроме 409 «Trainer Session Ended» (не эмитил вообще ничего, чат оставался заблокирован без объяснения). Теперь: 409+«Trainer Session Ended» по-прежнему эмитит `TRAINER_SESSION_ENDED` и завершает обработку (`return`), а на любую другую ошибку (сеть, 500 и т.п.) отправляется `sendTrainerCriticalErrorResponse(..., ErrorResponsesRu.ERROR_RESPONSE)` — это `TRAINER_INTERACTION_RECEIVE` с текстом «Извини, возникла непредвиденная ошибка в процедуре анализа работы. Попробуй отправить ещё раз.» и `meta.isError: true`, которое на клиенте снимает блокировку ввода.
- Серверный контракт «сервер сам заканчивает занятие, когда выдавать больше нечего» закреплён тестом на стороне api (`trainer-session-next-assignment.test.ts`, v3): при `nextBlockAssignment → null` сервис бросает `ERRORS.trainerSessionEnded` (409) — раньше это поведение было покрыто только гейтвеем.
- `socket-gateway/src/handlers/__tests__/trainer.handler.test.ts` — новый тест «answers a failed next-assignment instead of leaving the student locked»: на ошибку 500 от `nextAssignmentTrainerSession` ожидается ровно одно событие `TRAINER_INTERACTION_RECEIVE` с `meta.isError: true`.

## Как перепроверить

1. **Основной сценарий бага (ИСПРАВЛЕНО).** Довести блок до состояния «все core-задачи решены, но точность не набрана» — проще всего решать задания с подсказками (запросить hint/example/steps перед ответом, это опускает `helpScore`/`trainerPoints`), чтобы блок не закрылся начисто, но core оказались исчерпаны. Ответить верно на последнее core-задание блока → ожидается, что придёт **резервное задание** (или сообщение о завершении темы, если резерва действительно нет), а не тишина/зависший чат без новых сообщений.
2. **Ретейк (ИСПРАВЛЕНО).** Открыть ретейк на уже закрытом («credited») блоке через практику (`openPractice`, кнопка «пересдать»/«практика» в модалке закрытия блока) так, чтобы в нём остались нетронутые задания → ответить верно на текущее задание ретейка → должно прийти следующее нетронутое задание ретейка, а не стоп.
3. **Обрыв запроса следующего задания (ИСПРАВЛЕНО).** Спровоцировать ошибку `nextAssignment` на верном ответе — проще всего через дев-тулзы (заблокировать/уронить сетевой запрос к сокет-гейтвею на событии next-assignment, или временно уронить бэкенд/эндпоинт `nextAssignmentTrainerSession` на стенде) → ожидается сообщение в чате «Извини, возникла непредвиденная ошибка в процедуре анализа работы. Попробуй отправить ещё раз.» и снятие блокировки ввода (не вечная заблокированная плашка/спиннер). Проверить также, что до фикса на 500 гейтвей не отвечал ничем — то есть регресс именно на «тишину», а не на текст ошибки.

## Что посмотреть рядом (регресс)

- **Внутри блока ещё есть core-задачи** — верный ответ на не последнюю core-задачу блока по-прежнему сразу даёт следующую задачу (это поведение не менялось, но по логике теперь всё идёт через тот же единый путь «сервер решает» — стоит один раз пройти глазами).
- **Последняя core закрывает блок, выше есть другие блоки** — переход на первую задачу следующего блока должен работать как раньше.
- **Полное прохождение темы до конца** — когда закрывшийся блок — последний (ML5) и активных блоков не остаётся, должен появиться штатный экран завершения темы (топик-модалка/финал), автор отдельно подтверждает, что тут поведение не изменилось: закрывшийся блок в ту же отправку получает статус `passed`, `topicClosed`/`sessionOver` срабатывает так же, как раньше — стоит пройти тему целиком «в один присест» и убедиться, что экран завершения не пропал и не задваивается.
- **Занятие, действительно закончившееся** (без невыданных резервов/ретейков) — `TRAINER_SESSION_ENDED` по-прежнему должен приходить и переводить фазу в `empty`, а не в текст ошибки — это разные ветки в `trainerNextAssignmentHandler` (409+`Trainer Session Ended` против любой другой ошибки), стоит явно различить их на проверке.

## Открытые вопросы

- Фикс завязан на **MIA-127** (калибровка `helpScore`/грейдинга find_error): если MIA-127 ещё не выкачена на стенд, где идёт проверка, воспроизвести исходный прод-сценарий «core решены, точность 0 из-за штрафа за подсказку» будет сложнее (грейдинг может уже не занижать точность так же) — но сам фикс MIA-128 (автопереход всегда спрашивает сервер) от статуса MIA-127 не зависит и проверяется прямым доведением блока до «core решены, точность не набрана» любым способом.
- Единственный источник контекста по багу — комментарий разработчика с разбором прода; отдельного QA-отчёта/логов с прода не было, воспроизвести придётся с нуля на стенде.
- Аналитика: отдельных новых аналитических событий фикс не вводит (это правка guard-логики автоперехода и обработки ошибок гейтвея, не новая функциональность) — раздел аналитики не применим.
