### Гейт доступа — `api/src/middleware/require-topic-access.ts` (весь файл прочитан, `requireTopicAccess`, строки 44-58)

```ts
export const requireTopicAccess =
  (resolveTopicId: TopicIdResolver) =>
  async (request, reply) => {
    if (!request.currentUser) { reply.status(401)...; return; }
    const access = await accessService.canAccessTrainer(request.currentUser);
    if (access.level === 'full') return;                       // ← пропускает ЛЮБОГО full-доступ ученика на ЛЮБУЮ тему
    const topicId = await resolveTopicId(request);
    if (topicId !== null && (access.freeTopicId === null || access.freeTopicId === topicId)) return;
    reply.status(403).send(PAYWALL_RESPONSE);
  };
```

Это универсальный пейволл-гейт (используется во всех trainer-роутах), он проверяет только **оплаченный/фремиум доступ к теме вообще**, а не факт закрытия темы (все 5 ML-блоков). Ни `TopicRatingBreakdown`, ни `closedPoints`, ни статус блоков здесь не читаются.

### Контроллер — `api/src/controllers/topic-feedback.controller.ts` (весь файл, 31 строка)

`createTopicFeedbackHandler` сразу вызывает `topicFeedbackService.submit({ userId, topicId, satisfaction, difficulty, confidence })` — никакой проверки между гейтом и сервисом нет.

### Сервис — `api/src/services/topic-feedback.service.ts` — `TopicFeedbackService.submit()` (строки 31-47, весь файл прочитан)

```ts
async submit(input): Promise<{ points: number }> {
  const stored = await topicFeedbackRepository.createIfAbsent({ ...input, reason: TOPIC_FEEDBACK_REASON_TOPIC_CLOSED });
  if (!stored) {
    const paid = await ratingAwardRepository.findAward(input.userId, TOPIC_FEEDBACK_AWARD_REASON, input.topicId);
    if (paid) return { points: paid.points };
  }
  await ratingAwardService.awardTopicFeedback(input.userId, input.topicId);
  return { points: EFFORT_POINTS.topicFeedback };               // 20, из api/src/services/rating-rules.ts:25
}
```

`TOPIC_FEEDBACK_REASON_TOPIC_CLOSED = 'topic_closed'` (строка 6) — это **константная строка-лейбл**, которая пишется в колонку `reason` таблицы `topic_feedback` для любого запроса, а не результат проверки. Нигде в `submit()` не читаются ни breakdown темы (`ratingAwardService.topicBreakdown`), ни `ratingAwardRepository.hasAward(userId, 'topic_closed', topicId)`, ни какой-либо иной признак «все 5 блоков закрыты». `ratingAwardService.awardTopicFeedback()` (`api/src/services/rating-award.service.ts:144-152`) тоже ничего не проверяет — просто платит `upsert` по уникальному ключу `(userId, reason='topic_feedback', sourceId=topicId)`.

Миграция `api/prisma/migrations/20260910120000_topic_feedback/migration.sql` подтверждает модель данных: таблица `topic_feedback` хранит только `user_id, topic_id, satisfaction, difficulty, confidence, reason (default 'topic_closed'), created_at` + уникальный индекс `(user_id, topic_id)` (обеспечивает идемпотентность — не связь с закрытием) — никакого поля/ограничения, привязанного к факту закрытия темы, в схеме нет.

Единственное место, где `topicFeedbackService` вообще соприкасается с закрытием темы — `api/src/controllers/trainer.controller.ts:278-282`, и там `topicFeedbackService.exists(userId, topicId)` используется только чтобы отдать флаг `feedbackDone` в ответе `GET /trainer/topics/:id/rating` (для фронта — прятать кнопку повторно), это read-only и не гейт для POST.

**Вывод: находка Andrei подтверждена чтением кода полностью.** Сервер действительно не проверяет закрытие темы ни перед записью фидбека, ни перед начислением баллов — используется общий пейволл-гейт (`requireTopicAccess`), который отвечает только на вопрос «оплачена ли тема», а не «пройдена ли она». У ученика с полным (`full`) доступом это работает для любой темы курса, у фремиум-ученика — для его единственной бесплатной темы, в обоих случаях независимо от прогресса по ML-блокам. Клиентская модалка (`frontend/cabinet/shell/use-cabinet.ts:901-907`, `startSurvey()`) открывает опрос только при `session.topicJustClosed`, но это чисто клиентское условие — прямой вызов API его не видит.

## Тест-кейсы

### 1. [ИЗВЕСТНЫЙ ДЕФЕКТ, НЕ ПОФИКШЕН] Опрос и +20 баллов доступны без закрытия темы

Подтверждено и кодом (см. раздел выше), и ручным QA-тестом на test-1 (комментарий 5). При новом ручном прогоне заводить баг-репорт на этот кейс не нужно — он уже заведён и описан; кейс здесь для регрессионного контроля, что дефект не пофикшен на момент раунда.

Шаги воспроизведения (по факту прочитанного кода `requireTopicAccess` — работает для ученика с ЛЮБЫМ уровнем доступа, не только «свежего без прогресса», как в отчёте Andrei; вариант ниже проще воспроизвести вручную):

1. Взять ученика с активной (full) подпиской, открыть любую тему, по которой не пройден ни один из пяти ML-блоков (`GET /trainer/topics/:topicId/rating` → `blocks: []`, `closedPoints: 0`).
2. Не открывая модалку «Тема закрыта» (её не должно быть на экране — тема не закрыта), напрямую отправить `POST /api/trainer/topics/:topicId/feedback` с валидным телом (`satisfaction`, `difficulty`, `confidence` — каждое `1..10`) и валидной сессионной cookie этого ученика.
3. **Фактически (баг):** `200 {"points":20}`; строка появляется в `/admin/topic-feedback`; в `GET /api/rating/dashboard` — новая milestone `reason: "topic_feedback"` с `+20` и названием темы.
4. **Ожидается:** до закрытия всех пяти ML-блоков запрос должен быть отклонён (4xx) и не должен ни создавать запись, ни начислять баллы.
5. Проверить также вариант с фремиум-учеником на его единственной бесплатной теме, не закрытой — `requireTopicAccess` пропустит запрос по ветке `access.freeTopicId === topicId`, тот же результат.
6. Не путать с легитимным сценарием: тема, реально закрытая (все 5 блоков), но фидбек по которой ещё не отправлен — там `200` ожидаем (см. кейс 2).

Куда смотреть в коде при фиксе (из отчёта Andrei, подтверждено): `api/src/routes/topic-feedback.routes.ts:39` — у POST только `requireTopicAccess`, нет проверки закрытия; `api/src/services/topic-feedback.service.ts:31-47` — `submit()` не читает breakdown/статус блоков перед `createIfAbsent`/`awardTopicFeedback`. Тип 4xx для отказа контрактно не определён — стоит уточнить у разработчика.

### 2. [ПРИОРИТЕТ] Happy path — опрос после закрытия темы, награда +20 баллов

1. Пройти тему до закрытия всех пяти ML-блоков.
2. В модалке «Тема закрыта» убедиться, что кнопка называется «Ответить на три вопроса» (не «Ответить Мие»).
3. Нажать её, выставить три оценки (по одной на каждый вопрос — «Отправить» задизейблена, пока не выставлены все три, `surveyCanSubmit = surveyComplete(scores) && !sending`), отправить.
4. Экран благодарности должен показать «Спасибо — я это учту. За ответ начислено +20 баллов рейтинга.»
5. `GET /api/admin/topic-feedback` (или UI `/admin/feedback`) — новая строка сверху: ученик, тема, три оценки, дата.
6. Дашборд рейтинга (`/api/rating/dashboard` или UI): в журнале начислений строка «Ответ на опрос» с названием темы и `+20`; общая сумма рейтинга выросла на 20.

### 3. Кнопка «Пропустить» — без начисления

1. Дойти до шага опроса (тема закрыта), нажать «Пропустить», не выставляя оценок.
2. Модалка должна закрыться своим состоянием — «Хорошо, пропустим — вопросы вернутся после следующей темы.» — без слова «спасибо» и без упоминания баллов.
3. В `/admin/topic-feedback` строка по этой теме не появляется; в журнале рейтинга начисления `topic_feedback` нет; сумма рейтинга не меняется.

### 4. Повторно ранее закрытая тема опрос не предлагает

1. Ответить на опрос по теме (кейс 2) либо пропустить его.
2. Вернуться на страницу/пере-открыть модалку по этой же теме (если тема уже была закрыта раньше — например, повторный визит).
3. Кнопка должна вести сразу к «Выбрать следующую тему», шаг с тремя вопросами не показывается (`feedbackDone=true` из `GET /trainer/topics/:id/rating` переключает `primaryLabel`/`primaryAction`, см. `topic-done-vals.ts:79-82`).
4. Примечание: если тема пропущена (не отвечена), а не отвечена — `feedbackDone` всё равно `true`, т.к. флаг завязан на `topicFeedbackService.exists()` (есть строка в БД), а «пропустить» строку не создаёт — то есть после «Пропустить» повторный заход в ЛК по той же теме опрос предложит снова только если это НОВОЕ закрытие темы (см. кейс 6 «опрос не догоняется» в открытых вопросах — по факту при простом возврате на страницу без нового закрытия модалка вообще не откроется).

### 5. Идемпотентность повторного POST

1. Отправить валидный `POST /trainer/topics/:topicId/feedback` дважды подряд с одинаковыми или разными оценками для одной и той же пары ученик+тема.
2. Первый ответ — `200 {"points":20}`, вторая запись в `/admin/topic-feedback` не создаётся (уникальный индекс `user_id+topic_id` в БД, `createIfAbsent` ловит `P2002`).
3. Второй ответ — тоже `200`, `points` равен уже начисленному значению (сервис читает `ratingAwardRepository.findAward` и возвращает его `points`), повторного начисления в журнале рейтинга нет (одна milestone `topic_feedback`).

### 6. Валидация значений — 400

Для авторизованного ученика с доступом к теме отправить:
- `satisfaction=0` (или `11`) — вне диапазона `1..10` → `400`.
- `difficulty=7.5` (дробное) — схема требует `integer` → `400`.
- Тело без одного из трёх обязательных полей → `400`.
- Лишнее поле в теле — `additionalProperties: false` → тоже `400` (стоит явно проверить, т.к. это доп. строгость схемы).

### 7. Rate limit — 429 после 30 в час

1. Для одного ученика (один `userId`, ключ лимита — `req.currentUser.id`, не IP) отправить 30 валидных POST на feedback-эндпоинт (по разным `topicId`, т.к. на один `topicId` сработает идемпотентность, а не лимит) в течение часового окна.
2. Первые 30 — `200`/`429` не ожидается.
3. 31-й запрос в этом же окне — `429`.
4. Отдельно проверить, что лимит именно per-user: два ученика за одним NAT/IP не делят один бакет (комментарий в коде `topic-feedback.routes.ts:18`: «per user, not per IP»).

### 8. Аутентификация/доступность — 401

1. `POST /trainer/topics/:topicId/feedback` без сессионной cookie → `401` (`requireAuth`, глобальный `preHandler` роутера).
2. `GET /admin/topic-feedback` без basic-auth → `401` (`requireAdmin` на весь admin-роутер).
3. Оба маршрута должны существовать на стенде (не `404`) — если стенд не обновился, будет 404 вместо 401, это тоже стоит зафиксировать как «маршрут не задеплоен», а не как проходящий тест.

### 9. Текст благодарности без начисления (упавший запрос)

1. Спровоцировать сетевую ошибку/недоступность API в момент `submitSurvey()` (например, через DevTools throttling/offline) при отправке валидного опроса.
2. По коду (`use-cabinet.ts:922-928`) шаг всё равно переходит в `'thanks'` (опрос не блокируется ошибкой), но `surveyAwardedPoints` остаётся `null`.
3. Текст благодарности — «Спасибо — я это учту.» БЕЗ фразы про баллы (сервер не обещает то, чего не начислил).
4. Проверить, что реальное начисление при этом на бэке не произошло (в `/admin/topic-feedback` и в журнале рейтинга — пусто по этой теме), и что повторная попытка (если ученик перезайдёт в тему и она снова будет «только что закрыта») способна дозаписать фидбек и начислить баллы (штатный ретрай через новое открытие модалки — опрос не «дожимается» автоматически, см. открытые вопросы).

### 10. Сумма благодарности соответствует именно тому, что вернул сервер

1. Отправить валидный опрос, дождаться ответа `200 {"points": N}`.
2. Число N в благодарности на экране должно буквально совпадать с `points` из ответа API (не константа `20`, зашитая на фронте — фронт явно берёт число из ответа, см. `topic-done-vals.ts:29-33`, `use-cabinet.ts:917`).
3. Специально проверить сценарий «повторный ответ после ранее упавшего начисления» (комментарий 4, MR !393): если у ученика уже есть строка `topic_feedback` в БД без записи в `ratingAwardRepository` (гипотетически — при рассинхроне после сбоя), повторный POST должен доначислить и вернуть реальные `points`, а не молчаливый `0`.

## Аналитика/API

Задача добавляет три новых события в `api/src/constants/analytics-events.ts` и зеркально в `frontend/constants/analytics-events.ts` (оба файла — часть диффа MR !391, строки 130-134 в обоих):

- `TRAINER_TOPIC_FEEDBACK_SUBMITTED` → `'trainer_topic_feedback_submitted'` — шлётся из `use-cabinet.ts:918-921` (`submitSurvey()`, только при успешном ответе API), параметры `{ topic_id, points }` — `points` берётся из фактического ответа сервера, а не константы.
- `TRAINER_TOPIC_FEEDBACK_SKIPPED` → `'trainer_topic_feedback_skipped'` — шлётся из `use-cabinet.ts:932-934` (`skipSurvey()`), параметр `{ topic_id }`.

Все три события — фронтовые (`analytics.track(...)` в `use-cabinet.ts`), серверных `trackServerEvent`-вызовов из `topic-feedback.service.ts`/`trainer.controller.ts` для этих трёх событий не найдено — фиксация только клиентская. Это и есть три из «15 событий без цели», о которых разработчик пишет в комментарии 1 (см. открытые вопросы) — на тесте и проде под них не удалось завести цели в Яндекс.Метрике (лимит целей исчерпан), фактическая отправка `analytics.track` в Метрику этим раундом QA не проверяется (см. «Не покрыто» у Andrei).

API-контракт `POST /trainer/topics/:topicId/feedback` после MR !393: `200 {"points": number}` (было `204` без тела на MR !391 — follow-up сменил формат ответа, это подтверждено ручным тестом на стенде: «API на стенде отвечает обновлённым контрактом»). `GET /admin/topic-feedback`: `{ items, total, page, pageSize }`, `items[].user`/`items[].topic` — только `{id, name}` (не полный объект).

## Открытые вопросы

- **Опрос без закрытия темы начисляет баллы — см. тест-кейс 1.** Это единственный явный незакрытый дефект в задаче на момент заметки, подтверждён чтением `topic-feedback.routes.ts`/`.controller.ts`/`.service.ts` — сервер проверяет только оплаченный/фремиум доступ к теме (`requireTopicAccess`), но не факт прохождения всех пяти ML-блоков.
- **Цели в Яндекс.Метрике под новые события не заведены** (комментарий 1): оба счётчика (тест — 207/213, прод — 208/213 целей) упёрлись в `limit_exceeded`. Без целей остаются 15 событий, три из них — из этой задачи (`TRAINER_TOPIC_FEEDBACK_SHOWN/SUBMITTED/SKIPPED`). Ответы при этом не теряются — источник правды БД/админка, а не Метрика. Решение, какие старые цели высвобождать (удаление необратимо стирает историю, а часть целей может быть занята в кампаниях Директа — со стороны разработки не проверялось), требуется отдельно, вне скоупа ручного QA этой задачи.
- **Опрос сознательно «не догоняется».** Если ученик закрыл модалку, ушёл со страницы или перезагрузил до ответа — второго шанса ответить по этой закрытой теме не будет (нет серверного состояния «опрос ждёт ответа»). Это прямое архитектурное решение автора (комментарий 1: «ТЗ догона не требует, а серверное состояние вышло бы дороже самого опроса»), не баг — не заводить дефект на этот сценарий.
- **Доплата баллов вручную для тестовых ответов до деплоя MR !393.** Автор (комментарий 4) отдельно доплатит баллы за ответы, оставленные на тестовом стенде до раскатки follow-up — это разовая ручная операция на конкретном стенде, не тест-кейс и не паттерн для проверки.
- **Низкий объём данных по триггеру «закрытие темы».** На проде 10 закрытий тем в августе и 5 в сентябре, всего 4 ученика за 90 дней (комментарий 1) — механика рабочая, но выборка ответов будет в единицах в месяц; это ограничение реального трафика, не дефект реализации, стоит держать в уме при оценке «мало ответов в админке после деплоя».
