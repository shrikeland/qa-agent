## Реализация

### Как теперь исправлено (MR !446)

Цепочка запроса не изменилась: `api/src/routes/topic-feedback.routes.ts` (44 строки, весь файл перечитан на новом HEAD) всё так же вешает на POST только `requireTopicAccess(topicIdFromParams)` (строка 39) — это по-прежнему общий пейволл-гейт (`api/src/middleware/require-topic-access.ts`), который проверяет оплаченный/фремиум доступ к теме, а не факт её закрытия. Разработчик сознательно не стал развешивать вторую проверку на уровне гейта/контроллера — проверка закрытия темы добавлена **на уровне сервиса**, перед любой записью:

`api/src/services/topic-feedback.service.ts`, `TopicFeedbackService.submit()` (строки 37-57, весь файл прочитан):

```ts
async submit(input: TopicFeedbackSubmitInput): Promise<{ points: number }> {
  if (!(await topicMlProgressService.isTopicClosedFor(input.userId, input.topicId))) {
    throw ERRORS.topicNotClosed;                                   // строки 38-40
  }

  const stored = await topicFeedbackRepository.createIfAbsent({
    ...input,
    reason: TOPIC_FEEDBACK_REASON_TOPIC_CLOSED,
  });
  if (!stored) {
    const paid = await ratingAwardRepository.findAward(
      input.userId, TOPIC_FEEDBACK_AWARD_REASON, input.topicId,
    );
    if (paid) return { points: paid.points };
  }

  await ratingAwardService.awardTopicFeedback(input.userId, input.topicId);
  return { points: EFFORT_POINTS.topicFeedback };
}
```

Проверка выполняется **до** `createIfAbsent` и **до** `awardTopicFeedback` — при незакрытой теме не пишется ни строка в `topic_feedback`, ни начисление в рейтинге, что и требовалось по итогам находки QA.

Источник истины о закрытии — `api/src/services/topic-ml-progress.service.ts`, новый метод `isTopicClosedFor()` (строки 175-181):

```ts
/**
 * Reads the blocks instead of seeding them: an answer to a question about a topic the
 * student never opened must not create progress rows as a side effect.
 */
async isTopicClosedFor(userId: string, topicId: string): Promise<boolean> {
  return this.isTopicClosed(await topicMlProgressRepository.findByUserAndTopic(userId, topicId));
}
```

`isTopicClosed()` (строки 171-172, существовал и раньше, использовался в других местах, но не был подключён к `topicFeedbackService`) — `blocks.length > 0 && blocks.every(b => CLOSED_ML_STATUSES.includes(b.status))`, где `CLOSED_ML_STATUSES = [PASSED, CREDITED, CREDITED_EXHAUSTED]` (строки 49-52). Важная деталь комментария в коде: метод читает существующие блоки через `findByUserAndTopic`, а не через `getOrInitBlocks` — специально, чтобы сам факт запроса опроса по теме, которую ученик вообще не открывал, не создавал ему нулевые ML-блоки как побочный эффект. Для ученика без единой строки прогресса по теме `blocks.length === 0` → `isTopicClosed` вернёт `false` → `409`.

Ошибка — новая запись в `api/src/helpers/errors.helper.ts:32`:

```ts
topicNotClosed: new AppError('Topic is not closed', 409, 'topic_not_closed'),
```

**Нюанс по фактическому телу ответа**, важный для приёмки тест-кейса: общий обработчик `handleServerError` (`errors.helper.ts`, строки 51-54) для `AppError` отдаёт `reply.status(error.statusCode).send({ message: error.message })` — **только `message`**, поле `code` (`'topic_not_closed'`) в тело ответа не попадает (в отличие от, например, `auth.controller.ts`, где `code` добавляется вручную). Значит фактический ответ сервера — ровно `409 {"message":"Topic is not closed"}`, как и написал разработчик в комментарии от 02:59; строки `"topic_not_closed"` в самом JSON тела не будет, это внутренний код ошибки для логов/будущих потребителей, не контракт ответа. QA не должен считать тест проваленным, если в теле нет ключа `code`.

Тесты фикса прочитаны целиком: `api/src/services/__tests__/topic-feedback.service.test.ts` (кейс «refuses an answer for a topic that is not closed, storing and paying nothing», проверяет и `statusCode: 409`, и что ни `createIfAbsent`, ни `awardTopicFeedback` не вызываются) и `api/src/routes/__tests__/topic-feedback.routes.test.ts`.

Штатный путь не изменился: закрытая тема (`isTopicClosedFor === true`) проходит проверку и ведёт себя как раньше — `200 {"points":20}` на первый ответ, идемпотентность на повторный (см. кейс 5).

**Данные-шум на стенде:** на test-1 остались строки `topic_feedback` (и соответствующие начисления +20), полученные QA/разработчиком до фикса на незакрытых темах — по словам разработчика их специально не чистили («исторический шум», «последствие прежнего поведения, а не нового»). Не путать эти существующие строки с новым багом при просмотре админки — ориентироваться нужно на то, создаётся ли **новая** строка новым запросом, а не на общее наличие «плохих» строк в таблице.

### 2. [ПРИОРИТЕТ] Happy path — опрос после закрытия темы, награда +20 баллов

2. В модалке «Тема закрыта» убедиться, что кнопка называется «Ответить на три вопроса».
3. Нажать её, выставить три оценки, отправить (`surveyCanSubmit = surveyComplete(scores) && !sending`).
4. Экран благодарности — «Спасибо — я это учту. За ответ начислено +20 баллов рейтинга.»

6. Дашборд рейтинга: milestone «Ответ на опрос» с названием темы и `+20`; общая сумма рейтинга выросла на 20.

2. Модалка — «Хорошо, пропустим — вопросы вернутся после следующей темы.» — без «спасибо» и без баллов.

### 4. Повторно ранее закрытая тема опрос не предлагает

1. Ответить на опрос по теме (кейс 2) либо пропустить его.
2. Вернуться на страницу/пере-открыть модалку по этой же теме.
3. Кнопка должна вести сразу к «Выбрать следующую тему», шаг с тремя вопросами не показывается (`feedbackDone=true` переключает `primaryLabel`/`primaryAction`).
4. Примечание: `feedbackDone` завязан на наличие строки в БД (`topicFeedbackService.exists()`), а не на факт «был ли показан опрос» — после «Пропустить» повторный показ опроса по той же теме произойдёт только при новом закрытии темы, а не при простом возврате на страницу.

### 5. Идемпотентность повторного POST

1. Отправить валидный `POST /trainer/topics/:topicId/feedback` дважды подряд (после закрытия темы) для одной и той же пары ученик+тема.
2. Первый ответ — `200 {"points":20}`, вторая запись в `/admin/topic-feedback` не создаётся (уникальный индекс `user_id+topic_id`, `createIfAbsent` ловит `P2002`).
3. Второй ответ — тоже `200`, `points` равен уже начисленному значению (сервис читает `ratingAwardRepository.findAward`), повторного начисления в журнале рейтинга нет.
4. Это поведение фикс MR !446 не менял — проверка закрытия темы стоит раньше по коду, чем проверка идемпотентности, но обе ветки (закрыта и уже отвечена / закрыта и не отвечена) остаются рабочими как раньше.

### 6. Валидация значений — 400

Для авторизованного ученика с доступом к теме (тема может быть как закрыта, так и нет — валидация тела схемой Fastify отрабатывает раньше сервиса и раньше проверки закрытия):
- `satisfaction=0` (или `11`) — вне `1..10` → `400`.
- `difficulty=7.5` (дробное) — схема требует `integer` → `400`.
- Тело без одного из трёх полей → `400`.
- Лишнее поле — `additionalProperties: false` → `400`.

### 7. Rate limit — 429 после 30 в час

1. Для одного ученика (ключ лимита — `req.currentUser.id`, не IP) отправить 30 валидных POST на feedback-эндпоинт по разным `topicId` (закрытым, чтобы не путать с `409`/идемпотентностью) в течение часового окна.
2. 31-й запрос в этом же окне — `429`.
3. Отдельно проверить, что лимит per-user, а не per-IP.

### 8. Аутентификация/доступность — 401

1. `POST /trainer/topics/:topicId/feedback` без сессионной cookie → `401` (подтверждено комментарием разработчика от 02:59 — «без cookie — 401»).
2. `GET /admin/topic-feedback` без basic-auth → `401`.
3. Оба маршрута должны существовать на стенде — если 404 вместо 401/409, это «маршрут/фикс не задеплоен на этом стенде», а не проходящий тест.

### 9. Текст благодарности без начисления (упавший запрос)

1. Спровоцировать сетевую ошибку/недоступность API в момент `submitSurvey()` при отправке валидного опроса по закрытой теме.
2. Шаг всё равно переходит в `'thanks'`, `surveyAwardedPoints` остаётся `null`.
3. Текст — «Спасибо — я это учту.» без фразы про баллы.
4. Проверить, что реального начисления на бэке не произошло, и что повторная попытка (новое открытие модалки при новом закрытии темы) способна дозаписать фидбек и начислить баллы.

### 10. Сумма благодарности соответствует именно тому, что вернул сервер

1. Отправить валидный опрос по закрытой теме, дождаться `200 {"points": N}`.
2. Число N на экране должно совпадать с `points` из ответа API, а не быть зашитой на фронте константой.
3. Сценарий «повторный ответ после ранее упавшего начисления»: если у ученика есть строка `topic_feedback` без записи в `ratingAwardRepository` (рассинхрон после сбоя), повторный POST по закрытой теме должен доначислить и вернуть реальные `points`.

## Аналитика/API

Три события — `trainer_topic_feedback_shown/_submitted/_skipped` (`api/src/constants/analytics-events.ts:118-122`, зеркально во фронтовом файле) — без изменений в логике отправки (`use-cabinet.ts`, клиентские `analytics.track`, серверных `trackServerEvent` для них нет). Новое по сравнению с прошлым раундом: под все три события заведены цели в Яндекс.Метрике на тесте и на проде (комментарий от 03:23) — открытый ранее вопрос про `limit_exceeded` закрыт. Общий механизм группировки целей (MR !447, карта `ANALYTICS_GOAL_GROUPS` пока пустая) — инфраструктурная новость на будущее, на эти три цели сейчас не влияет.

API-контракт `POST /trainer/topics/:topicId/feedback`: `200 {"points": number}` при закрытой теме (не изменилось), **новое** — `409 {"message":"Topic is not closed"}` при незакрытой (только на тесте, см. тест-кейс 1), `401` без сессии, `400` при невалидном теле, `429` при превышении лимита. `GET /admin/topic-feedback`: `{ items, total, page, pageSize }`, без изменений.

## Открытые вопросы

- **Фикс `409 topic_not_closed` не выкачен на прод.** Комментарий от 2026-09-18T03:23:01 подтверждает, что это осознанное решение, но причина/условие выката на прод в доступных комментариях не названы — стоит уточнить у разработчика или PM перед закрытием задачи, иначе прод продолжит начислять +20 баллов и создавать записи опроса без закрытия темы бессрочно.
- **На test-1 остались тестовые данные-шум** от старого поведения: отзыв(ы) и начисление(я) +20 баллов, полученные на незакрытых темах до фикса (по словам разработчика — минимум одна пара из отчёта QA плюс «две строки topic_feedback по темам, где закрытых блоков нет» из проверки 02:59). Это исторические записи, не новый баг — при ручной проверке ориентироваться на то, создаёт ли **новый** запрос новую строку/начисление, а не на факт присутствия старых записей в админке.
- **Механизм группировки целей Метрики (MR !447)** введён как общая инфраструктура на будущее (карта групп пока пустая, поведение существующих целей, включая три цели этой задачи, не меняется) — для этой задачи не создаёт новых проверяемых сценариев, но стоит иметь в виду при последующих задачах с событиями аналитики (правила выбора «своя цель / группа» — в `CLAUDE.md`).
- **Опрос сознательно «не догоняется».** Если ученик закрыл модалку/ушёл со страницы/перезагрузил до ответа — второго шанса ответить по этой закрытой теме не будет (нет серверного состояния «опрос ждёт ответа»). Архитектурное решение автора, не баг.
- **Низкий объём данных по триггеру «закрытие темы».** На проде было 10 закрытий тем в августе и 5 в сентябре, всего 4 ученика за 90 дней (из предыдущего раунда) — механика рабочая, но выборка ответов в админке будет в единицах в месяц; ограничение реального трафика, не дефект реализации.
