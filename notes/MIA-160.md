## Контекст

Инвайт на оффер с `card_upfront=false` и `trial_days=0` (например `month_promo_discount50`) до этой правки создавал подписку `status=trial` с `trial_ends_at=NULL`. `isAllowed()` (`api/src/services/access.service.ts:49-64`) для `TRIAL` требует `trialEndsAt` в будущем — при `NULL` условие `!!sub.trialEndsAt && ...` ложно, доступа нет с первой секунды. Оплату при этом никто не просит (подписка не в `awaiting_payment`/`pending_binding`), а в кабинете рисовалась плашка «Пробный период закончился», причём дата бралась из `expires_at`, вычисленного в будущее — отсюда «мёртвый триал» с датой окончания триала из будущего у ученика без доступа вовсе.

Фикс (MR !387, смержен `2ac2c673`, входит в историю текущего HEAD `dca4fda5`): для комбинации `cardUpfront=false && trialDays===0` регистрация по инвайту теперь создаёт `status=freemium` с зафиксированным `planType`/снапшотом скидки оффера вместо мёртвого `trial`. Ученик получает обычный фремиум-доступ (одна бесплатная тема + пейволл), а тариф и скидка сохраняются до первой оплаты — оплата списывает цену оффера со скидкой, а не публичный прайс. Побочные правки того же MR (вошли по ревью, коммит `ae0ef633` включён в диф): тариф из инвайта больше не перебивается публичным слагом со страницы оплаты по ссылке, и плашка периодичности списания на фремиуме больше не врёт «спишем эту сумму каждый месяц», когда сумма содержит промо-скидку на первый платёж.

Комментарий автора отдельно фиксирует, что подписки, созданные ДО правки (пример: `test@test.ru` на тесте), остаются в мёртвом `trial` — лечение старых записей вне скоупа задачи.

## Реализация

### `api/src/services/auth.service.ts` — `registerParentWithChild` (строки 140-230)

Комментарий в коде прямо перечисляет 4 ветки создания подписки при регистрации:
1. Инвайт, `cardUpfront=false`, `trialDays>0` — `status=TRIAL`, `trialEndsAt = now + trialDays`, `expiresAt = trialEndsAt + durationDays` (не изменилось этим MR).
2. Инвайт, `cardUpfront=false`, `trialDays===0` — **новая ветка этой задачи**: `status=FREEMIUM`, `planType=offer.slug`, `...buildRenewalSnapshot(offer)` (офферId/сумма/скидка/`isRecurring` из оффера), `amount=offer.price`, `expiresAt=2099-01-01` (фремиум не истекает сам), `trialEndsAt=null`, `paymentMethodId=null`. Комментарий в коде: «TRIAL would lock them out on the spot — isAllowed only opens a trial while trialEndsAt is in the future».
3. Инвайт, `cardUpfront=true` — `status=PENDING_BINDING`, дальше создаётся `paymentMethod` у провайдера и возвращается `confirmationUrl` для редиректа на привязку карты сразу при регистрации (не изменилось).
4. Без инвайта — фремиум без тарифа (`planType=null`, `amount=null`), как и раньше.

`resolvedOffer` резолвится через `catalogService.resolveBySlug(input.selectedPlanType)` — не через `resolveInvitableBySlug`, то есть сам `auth.service.ts` не перепроверяет, что оффер ещё `public`/`invite_only` (эта проверка, судя по всему, происходит раньше, в `inviteService`/эндпоинте `/auth/invite/:token`).

Аналитика: `ANALYTICS_EVENTS.INVITE_ACTIVATED` шлётся `trackServerEvent` при `input.inviteToken && resolvedOffer` — событие существовало до этой задачи (общее для любой инвайт-регистрации), MIA-160 новых событий не добавляет (см. «Аналитика/API»).

### `api/src/services/catalog.service.ts`

- `ResolvedOffer`/`RenewalSnapshot`/`buildRenewalSnapshot` (строки 12-30, 66-79) — снапшот оффера (`offerId`, `renewalAmount`, `renewalDurationDays`, `renewalDescription`, `discountSnapshot`, `discountPeriodsRemaining`, `isRecurring`) сохраняется на подписку при создании и **никогда не перечитывается из каталога** — комментарий: «Billing reads these (never the live catalog) so a later price/offer edit never re-prices an existing subscriber». Именно этот снапшот и есть «зафиксированная скидка оффера» из Scope задачи.
- `toDiscountSnapshot` (84-88) проверяет `isDiscountLive` на момент резолва — скидка попадает в снапшот, только если офферная скидка ещё активна на момент регистрации.
- `isInviteOnlyTariff(planType)` (144-147) — **ключевая функция для «пейволл не даёт выбрать другой тариф»**: `true`, если `planType` не `null` и не выбираем публично (`!isPubliclySelectable`). Комментарий по-русски прямо описывает сценарий этой задачи: «инвайт выдал непубличный оффер со своей скидкой, а ссылка на оплату всегда рисует общий пикер — слаг из него затёр бы промо».
- `resolveInvitableBySlug` (151-154) — резолвит оффер по слагу, только если `status` `public` ИЛИ `invite_only` (не `draft`/`archived`) — так `invite_only` офферы (как `month_promo_discount50`, судя по всему) раздаются по инвайтам, но не попадают в `listPublicOffers()` (только `status='public'`, строка 158) — то есть не появляются в публичном каталоге, что и требует Out of scope.

### `api/src/controllers/subscriptions.controller.ts`

- `payLinkInfoHandler` (`GET /subscriptions/pay-link-info`, 80-133) отдаёт `tariffFinal: await catalogService.isInviteOnlyTariff(sub.planType)` — именно это поле фронт (`select-tariff.vue`) читает, чтобы решить, рисовать пикер или нет, в HMAC-режиме (переход по ссылке оплаты без сессии).
- `confirmBindingFromEmailHandler` (`POST /subscriptions/confirm-binding-from-email`, 284-451): `canCommitTariff = sub.paymentMethodId === null && !inviteOnlyTariff` — если тариф invite-only, смена тарифа полностью заблокирована на бэке (даже если фронт как-то всё же прислал `tariffId`, строка 394: `else if (!inviteOnlyTariff && requestedTariff && requestedTariff !== sub.planType) return 422 tariff_mismatch`) — то есть при invite-only тарифе присланный `tariffId` **тихо игнорируется**, а не валится 422 (проверено тестом «тариф из инвайта не переписывается публичным слагом из письма», `subscriptions.controller.test.ts:1099-1121`). Также здесь фремиум переводится в `AWAITING_PAYMENT` перед привязкой карты («Freemium pays now», строка 329), чтобы общий charge-путь именно списал деньги, а не просто прикрепил карту.

### `api/src/controllers/payments.controller.ts`

- `bindCardHandler`/`bindAndChargeHandler` содержат идентичную логику `isInviteOnlyTariff`/`canCommitTariff`/`wantsTariffSwitch`, что и `confirmBindingFromEmailHandler` — тариф из инвайта одинаково защищён что через кабинет (`bindCardHandler`), что через email-ссылку (`confirmBindingFromEmailHandler`).
- `bindCardHandler` (330-353): `freemiumUpgrade = sub.status === FREEMIUM` → флип `FREEMIUM → AWAITING_PAYMENT` и вызов `startAwaitingPaymentBinding`, которая создаёт `paymentMethod` у YooKassa и ждёт вебхук. Сумма списания при этом не пересчитывается в контроллере — она приходит из уже сохранённого на подписке `renewalAmount`/`discountSnapshot`/`discountPeriodsRemaining` (снапшот из `buildRenewalSnapshot`), которые читает `applyChargeOutcome`/`chargeAmount` (`api/src/data/discount.ts:76-80`) при обработке вебхука `yookassaWebhookHandler` — так фактическое списание = `chargeAmount(renewalAmount, discountSnapshot, discountPeriodsRemaining)`, то есть именно цена оффера со скидкой (899 в примере автора), а не `offer.price` из публичного каталога.

### `api/src/data/discount.ts`

- `applyDiscount`/`chargeAmount`: скидка `scope='forever'` действует на каждое списание, `first_charge` — только на первое (`chargeIndex===0`/`periodsRemaining` после `buildRenewalSnapshot` = 1), `n_periods` — на первые N. `remainingChargesForDiscount` (58-63) кладёт в `discountPeriodsRemaining` то самое число оставшихся списаний со скидкой — именно это поле фронт **не получает** для плашки периодичности (см. ниже про `price.ts`).

### `api/src/services/access.service.ts` — модель статусов подписки

- `SUBSCRIPTION_STATUS` (`api/src/data/subscription-status.ts`): `trial`, `active`, `charging`, `cancelled`, `expired`, `pending_binding`, `binding_failed`, `trial_charge_failed`, `awaiting_payment`, `freemium`.
- `isAllowed(sub)` (`access.service.ts:49-64`) — единственное место, решающее «есть полный доступ или нет»:
  - `ACTIVE` → `expiresAt` в будущем;
  - `TRIAL` → `trialEndsAt` в будущем (именно это условие делало мёртвый триал мёртвым при `trialEndsAt=null`);
  - `CHARGING` → всегда `true` (платёж уже в процессе — доступ не закрывают, пока провайдер не ответит);
  - `CANCELLED` → доступ остаётся, пока не истёк уже оплаченный/триальный период (`trialEndsAt`/`expiresAt` в будущем);
  - `FREEMIUM` → всегда `false` — то есть `isAllowed` для фремиума **всегда** возвращает `false`, полный доступ никогда не открывается автоматически, только через оплату/бинд карты.
  - Любой другой статус (`expired`, `pending_binding`, `binding_failed`, `trial_charge_failed`, `awaiting_payment`) → `false` (default).
- `canAccessTrainer()` (66-105) превращает `isAllowed` в `level: 'full' | 'freemium'`. `level='freemium'` — это и есть «одна бесплатная тема»: ограничение накладывается в `topicAllowed()` (39-40) — `access.level === 'full' || access.freeTopicId === null || access.freeTopicId === topicId`, то есть при фремиуме доступна только тема с `id === user.freeTopicId` (первая, за которую ученик взялся — фиксируется в `ensureFreemiumSubmissionAllowed`/`claimFreeTopic`, 126-145), остальные темы недоступны (пейволл). Это общий, не специфичный для MIA-160, механизм фремиума — задача лишь меняет то, какой статус подписки в него попадает (freemium вместо мёртвого trial).

### `frontend/cabinet/shared/price.ts` — плашка суммы/периодичности на фремиуме

`toCabinetPrice()` (30-90): при `tariffFinal && mode==='freemium'` (комментарий: «а фремиум по промо-инвайту наоборот приходит с готовым тарифом и своей скидкой») сумма = `subscription.nextChargeAmount ?? offer.price` (уже посчитанная бэком цена со скидкой, `access.service.ts:76-80`). Периодичность («списываем 899 ₽ каждый месяц») показывается **только если** `amount === offer.price` (`recurring = offer && amount === offer.price`, строка 60) — то есть только когда скидка НЕ действует на текущее списание. Комментарий в коде: «Периодичность обещаем только по неснижённой цене: сколько списаний покрывает скидка, фронту не видно». Пока скидка активна — `note` = просто `'отмена в один клик'`, без слова «каждый месяц» вообще (подтверждено тестом `фремиум с тарифом из инвайта показывает цену своего оффера`, `frontend/tests/cabinet-price.test.ts:115-131`, ожидающим ровно `note === 'отмена в один клик'`).

### `frontend/pages/select-tariff.vue` — пейволл

- `hasPlan` (67-75): в сессионном режиме — `isTariffFinal({planType, paymentMethodId, pickerSlugs})`; в HMAC-режиме (переход по ссылке) — `linkTariffFinal`, заполняемый из ответа `payLinkInfoHandler.tariffFinal` (то есть из `catalogService.isInviteOnlyTariff`).
- `tariffOptions` (78): `hasPlan.value ? [] : allTariffOptions.value` — при `hasPlan=true` пикер получает **пустой массив**, `SubscriptionTariffPicker` не рендерится (`v-if="!hasPlan && ..."`, строка 335) — так пейволл физически не даёт выбрать другой тариф для инвайт-only оффера. Вместо пикера рисуется блок `.select-tariff__committed` (341-344) с названием оффера и `committedTariffLabel` — `${formatRoubles(amount)} ${offer.periodLabel}`, где `amount = subscription?.nextChargeAmount ?? offer.price` (244) — сумма со скидкой.
- `promoFineprint`/`fineprintText` (280-315): при выбранном (несохранённом, для обычного пикера) оффере с промо — мелкий текст называет `first` (цену со скидкой на первый платёж) и отдельно «Далее — {regular}». Для committed-инвайт-оффера (`hasPlan=true`) в HMAC-режиме конкретную сумму первого списания называет `chargeInfo`/API, а не локальный `offerPrices` (т.к. `selectedOffer` не выставлен — пикер скрыт).
- Оплата (`onBind`, 180-237): в HMAC-режиме `hasPlan.value` не шлёт `tariffId` в теле запроса (`...(hasPlan.value ? {} : { tariffId: selected.value })`) — так подтверждается, что пейволл не пытается перебить закреплённый тариф даже случайно.

### `frontend/pages/register.vue` — регистрация по инвайту (для открытого вопроса копирайта)

`inviteOffer`/`inviteTrialLabel`/`inviteDiscountNote` (34-57) формируют заголовок страницы: название оффера, зачёркнутая полная цена + цена со скидкой, отдельно строка «Скидка N% {навсегда/на первый платёж/на первые K платежей}», и, только если `offer.trialDays > 0`, строку «N дней бесплатно, далее …» (строка 330, `v-if="inviteTrialLabel"`). Для `trialDays===0` (случай этой задачи) эта строка просто не рендерится — на странице остаются только название, цена и скидка, **без единого слова о том, что доступ будет фремиумным** (одна бесплатная тема + пейволл на остальное). Подтверждает то, что пишет автор во втором комментарии — это открытый вопрос копирайта, не баг кода.

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Happy path — регистрация по промо-инвайту без карты и без триала

Предусловие (по инструкции автора из комментария 1): у оффера `month_promo_discount50` выключить «Карта при старте» (`cardUpfront=false`), `trialDays=0` должен быть уже выставлен.

1. Открыть ссылку регистрации по инвайту на этот оффер (`/register?invite=<token>`).
2. Убедиться, что заголовок карточки показывает название оффера, цену со скидкой (899 ₽) и зачёркнутую полную цену (1799 ₽) — без строки «N дней бесплатно» (её быть не должно при `trialDays=0`).
3. Заполнить форму, отправить. Карту на этом шаге просить не должны, сразу должен открыться доступ в ЛК (без редиректа на YooKassa/бинд карты) — `POST /auth/register` не должен возвращать `confirmationUrl` (по коду: `confirmationUrl=null`, т.к. `subscriptionForBinding` не создаётся для этой ветки).
4. В ЛК ученика: доступна ровно одна тема (первая, за которую взялся), остальные — под пейволлом. Плашки «Пробный период закончился» быть не должно (это и есть главный acceptance-пункт: раньше висела дата из `expires_at` в будущем, сейчас `expiresAt=2099-01-01` и статус `freemium`, а не мёртвый `trial`).
5. По API (если доступно): у созданной подписки `status=freemium`, `planType='month_promo_discount50'`, `trialEndsAt=null`, `paymentMethodId=null`, `discountSnapshot` заполнен снапшотом скидки оффера на момент регистрации.

### 2. Пейволл называет цену со скидкой и не даёт выбрать другой тариф

1. Из состояния теста №1 (фремиум с закреплённым инвайт-оффером) открыть пейволл (клик на любую недоступную тему или прямой переход на `/select-tariff`).
2. Проверить: показана ровно одна сумма — 899 ₽ (не 1799 ₽ и не сумма другого публичного тарифа), название оффера/периодичность соответствуют инвайт-офферу.
3. Убедиться, что пикер тарифов (список карточек с другими планами) **отсутствует на странице** — по коду `tariffOptions=[]` при `hasPlan=true` для invite-only оффера, компонент `SubscriptionTariffPicker` не рендерится вовсе (не просто задизейблен).
4. Кнопка привязки карты — «Привязать карту и оплатить»/аналог с суммой 899 ₽, без возможности сменить тариф перед оплатой.

### 3. Привязка карты списывает цену со скидкой, а не публичный прайс

1. Из состояния теста №1/2 нажать привязку карты, пройти оплату на стороне YooKassa тестовой картой.
2. Проверить фактическую сумму списания в форме оплаты YooKassa/в ответе провайдера — должна быть 899 ₽.
3. После успешного вебхука: подписка переходит в `active`/`awaiting_payment→active` (в зависимости от таймингов), `paymentMethodId` заполнен, следующее списание (если `isRecurring`) при отсутствии активной `n_periods`/`first_charge` скидки — по полной цене (899 ₽ был скидкой на первый платёж/навсегда — сверить со `scope` реальной скидки оффера на стенде: `forever` спишет 899 и на продлении, `first_charge`/`n_periods` — только на первом(ых)).
4. Убедиться, что сумма в ЛК после оплаты (если показывается) соответствует фактически списанной, не пересчитывается на лету по текущему публичному прайсу оффера.

### 4. Регрессия — оффер с `trial_days > 0` без карты работает как раньше (обычный триал)

Явный acceptance-пункт, нужно перепроверить, что НЕ сломалось этой правкой.

1. Взять/создать инвайт-оффер с `cardUpfront=false`, `trialDays>0` (например 3 или 7 дней).
2. Зарегистрироваться по инвайту на этот оффер. Заголовок страницы регистрации ДОЛЖЕН показать «N дней бесплатно, далее {цена}» (в отличие от кейса без триала).
3. После регистрации: карту не просят, статус подписки `trial` (не `freemium`), `trialEndsAt = now + trialDays`, `expiresAt = trialEndsAt + durationDays` оффера.
4. В ЛК: доступ ПОЛНЫЙ (не фремиумный, не одна тема) всё время действия триала — `isAllowed` для `trial` при `trialEndsAt` в будущем возвращает `true`.
5. По истечении триала (или искусственно откатив `trialEndsAt` в прошлое на тесте) — доступ закрывается, появляется предложение привязать карту с оплатой по цене оффера (обычный пост-триальный флоу, `trialExpiredNoCard` в `bindCardHandler`).

### 5. Регрессия по ревью — тариф из инвайта не перебивается публичным слагом ссылки на оплату

1. Зарегистрироваться по промо-инвайту без карты и без триала (как в тесте №1) — получить фремиум с закреплённым `planType` и скидкой.
2. Получить/сформировать ссылку на оплату «для родителя» (`GET /subscriptions/parent-pay-link`, либо ссылка из письма/уведомления) — она **не** содержит `plan` в URL по дизайну.
3. Открыть эту ссылку на другом устройстве/без сессии (HMAC-режим `/select-tariff?sub=...&t=...`), при желании вручную дописать в URL `&plan=<другой публичный slug>`.
4. Убедиться, что даже с чужим `plan` в query выбранный/списываемый тариф остаётся инвайт-оффером со своей скидкой (899 ₽), а не переключается на публичный (1799 ₽ или любой другой тариф из пикера) — по коду `payLinkInfoHandler` игнорирует `plan` для расчёта `tariffFinal` (использует `sub.planType`, не query) и `confirmBindingFromEmailHandler`/`bindAndChargeHandler` отбрасывают `requestedTariff`, если `isInviteOnlyTariff(sub.planType)===true`.
5. Пройти привязку карты по этой ссылке — списание должно быть 899 ₽, не 1799 ₽.

### 6. Плашка периодичности списания на фремиуме (UX-гэп, не баг по коду)

1. Взять фремиум с активной первоплатной скидкой (899 ₽ на первый платёж, регулярная цена — 1799 ₽) — зайти в ЛК, посмотреть текст под суммой к оплате.
2. Ожидаемо по коду: текст = «отмена в один клик» БЕЗ фразы «списываем 899 ₽ каждый месяц» (специально скрыто, чтобы не соврать про повторные списания).
3. Для сравнения — фремиум БЕЗ активной скидки (следующее списание = полная цена оффера): текст = «списываем {цена} каждый месяц · отмена в один клик».
4. Это не баг (осознанное решение по коду и юнит-тесту `frontend/tests/cabinet-price.test.ts:133-143`), но стоит визуально оценить, не выглядит ли отсутствие фразы «каждый месяц» как недосказанность для родителя — см. «Открытые вопросы».

### 7. Оффер остаётся invite_only, не в публичном каталоге

1. Открыть публичный лендинг/пейволл БЕЗ перехода по инвайт-ссылке (обычный визит).
2. Убедиться, что промо-оффер (`month_promo_discount50` или другой `invite_only`) не отображается среди публично выбираемых тарифов — `listPublicOffers()` читает только `status='public'`.
3. Это уже покрыто Out of scope задачи («Показ invite_only офферов в публичном каталоге» не тестируем детально) — достаточно смоук-проверки, что оффер не «утёк» в общий список после этой правки.

### 8. Граничные/смежные кейсы из юнит-тестов (перенесены в ручные сценарии)

- **Инвайт с `cardUpfront=true`** (любой `trialDays`) — регистрация ДОЛЖНА по-прежнему сразу уводить на привязку карты (`status=pending_binding`, `confirmationUrl` заполнен) — эта ветка не менялась MIA-160, но стоит перепроверить смоуком, что её не задело.
- **Регистрация без инвайта вообще** — фремиум без тарифа (`planType=null`), обычная воронка «зарегистрировался → фремиум → сам выбрал тариф на пейволле» — не должна была измениться, но раз `auth.service.ts` переписан, стоит смоук-тестом подтвердить, что ветка "иначе" (без `resolvedOffer`) не затронута.
- **Гонка активации инвайта** (`invite_race`) — активация инвайта в `activateByToken` — общий для всех веток механизм, специфике MIA-160 не подвержен, но если есть время — стоит проверить, что повторная попытка активировать уже использованный/одноразовый инвайт с `card_upfront=false && trial_days=0` не создаёт вторую фремиум-подписку/не 500-ит.
- **Оффер с `discountSnapshot=null`** (без скидки вообще) по инвайту без карты и без триала — фремиум должен создаться так же, просто без скидочного блока в цене (`toCabinetPrice` покажет полную цену и «каждый месяц», см. тест-кейс №6, второй пункт).

## Аналитика/API

Фича не добавляет новых событий аналитики. `ANALYTICS_EVENTS.INVITE_ACTIVATED` (`api/src/constants/analytics-events.ts:254`) уже существовал до MIA-160 и продолжает шириться при любой успешной регистрации по инвайту (`auth.service.ts:234-240`, `{ invite_token_prefix, plan_type }`) — не специфично для фремиум-ветки, тестировать отдельно от общей инвайт-регистрации не нужно. Файл `analytics-events.ts` не входит в диф MR !387 (список из 10 изменённых файлов его не содержит) — подтверждает, что новых событий фича не заводит. Точечных API-проверок именно на аналитику для этой задачи не требуется; общие проверки сумм/статусов подписки покрыты тест-кейсами 1-5 выше через прямые API-ответы (`/auth/register`, `/subscriptions/pay-link-info`, вебхук YooKassa).

## Открытые вопросы

- **Копирайт страницы регистрации по инвайту не говорит про фремиум.** `frontend/pages/register.vue` (`inviteOffer`/`inviteTrialLabel`, строки 39-57, 326-334) показывает название оффера, цену со скидкой и (только при `trialDays>0`) срок триала — но при `trialDays===0` (ровно случай этой задачи) страница не сообщает, что доступ откроется фремиумным (одна бесплатная тема, остальное под пейволлом). Автор явно называет это вопросом копирайта для отдельного решения, не багом — фиксируется как открытый вопрос, не тест-кейс на FAIL.
- **Плашка периодичности списания на фремиуме не говорит, сколько списаний покрывает скидка.** `frontend/cabinet/shared/price.ts:57-69` — пока скидка активна, текст ограничивается «отмена в один клик» без суммы и периода следующих списаний вообще (ни «каждый месяц», ни «первые N платежей»). Осознанное решение (комментарий в коде + отдельный юнит-тест), но стоит держать в уме как потенциальный будущий запрос на уточнение копирайта — родитель не узнаёт из ЛК, когда скидка на первый платёж закончится и сколько будет стоить продление.
- **Старые подписки (например `test@test.ru` на тестовом стенде) намеренно НЕ лечатся этой правкой.** Они остаются в `status=trial` с `trialEndsAt=NULL` — это ожидаемое поведение по прямому указанию автора («лечить их эта правка не умеет»), НЕ регрессия и не баг для этого раунда QA. При тестировании не заводить дефект на такие аккаунты, только на новые регистрации после деплоя.
- **`resolveBySlug` в `auth.service.ts` не проверяет `status` оффера повторно.** Регистрация резолвит оффер по слагу через `catalogService.resolveBySlug` (без фильтра по `status`), полагаясь, что до вызова `registerParentWithChild` уже была проверка через `/auth/invite/:token` (`inviteService`). Не нашёл в рамках этого MR явного щита от повторной регистрации по уже `archived`/`revoked` инвайту напрямую через API в обход страницы — если у QA есть возможность звать `/auth/register` напрямую (не через форму), стоит попробовать протащить `selectedPlanType` архивного/черновикового оффера и убедиться, что бэкенд это где-то отклоняет (вне зафиксированного в этом MR кода, значит либо не в скоупе, либо покрыто раньше — стоит уточнить у автора, если найдётся дыра).
