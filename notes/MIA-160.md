## Контекст

Инвайт на оффер с `card_upfront=false` и `trial_days=0` (например `month_promo_discount50`) до этой правки создавал подписку `status=trial` с `trial_ends_at=NULL`. `isAllowed()` (`api/src/services/access.service.ts:49-64`) для `TRIAL` требует `trialEndsAt` в будущем — при `NULL` условие `!!sub.trialEndsAt && ...` ложно, доступа нет с первой секунды. Оплату при этом никто не просит (подписка не в `awaiting_payment`/`pending_binding`), а в кабинете рисовалась плашка «Пробный период закончился», причём дата бралась из `expires_at`, вычисленного в будущее — отсюда «мёртвый триал» с датой окончания триала из будущего у ученика без доступа вовсе.

Фикс (MR !387, `merge_commit 2ac2c673`, уже в `master` HEAD `/tmp/repo`): для комбинации `cardUpfront=false && trialDays===0` регистрация по инвайту теперь создаёт `status=freemium` с зафиксированным `planType`/снапшотом скидки оффера вместо мёртвого `trial`. Ученик получает обычный фремиум-доступ (одна бесплатная тема + пейволл), а тариф и скидка сохраняются до первой оплаты — оплата списывает цену оффера со скидкой, а не публичный прайс. Побочные правки того же MR: тариф из инвайта больше не перебивается публичным слагом со страницы оплаты по ссылке, и плашка периодичности списания на фремиуме больше не врёт «спишем эту сумму каждый месяц», когда сумма содержит промо-скидку на первый платёж.

Автор задачи отдельно фиксирует, что подписки, созданные ДО правки (пример: `test@test.ru` на тесте), остаются в мёртвом `trial` — лечение старых записей вне скоупа задачи.

**Новое с прошлого прогона (важно):** содержательно задача не менялась, но 2026-09-10 после деплоя на test-1 ручной QA (Andrei Chepurchenko) нашёл непочиненный дефект именно в HMAC-режиме пейволла (переход по ссылке из письма/без сессии): закреплённый invite-only тариф API определяет верно (`tariffFinal:true`), но UI не показывает родителю ни название оффера, ни сумму к списанию — см. тест-кейс **2b** и раздел кода `select-tariff.vue` ниже. Раньше (прошлая версия этой заметки) сессионный и HMAC-режим не различались отдельно и проверялись только теоретически.

## Реализация

### `api/src/services/auth.service.ts` — `registerParentWithChild` (строки 140-230)

Комментарий в коде прямо перечисляет 4 ветки создания подписки при регистрации:
1. Инвайт, `cardUpfront=false`, `trialDays>0` — `status=TRIAL`, `trialEndsAt = now + trialDays`, `expiresAt = trialEndsAt + durationDays` (не изменилось этим MR).
2. Инвайт, `cardUpfront=false`, `trialDays===0` — **новая ветка этой задачи**: `status=FREEMIUM`, `planType=offer.slug`, `...buildRenewalSnapshot(offer)` (офферId/сумма/скидка/`isRecurring` из оффера), `amount=offer.price`, `expiresAt=2099-01-01` (фремиум не истекает сам), `trialEndsAt=null`, `paymentMethodId=null`. Комментарий в коде: «TRIAL would lock them out on the spot — isAllowed only opens a trial while trialEndsAt is in the future».
3. Инвайт, `cardUpfront=true` — `status=PENDING_BINDING`, дальше создаётся `paymentMethod` у провайдера и возвращается `confirmationUrl` для редиректа на привязку карты сразу при регистрации (не изменилось).
4. Без инвайта — фремиум без тарифа (`planType=null`, `amount=null`), как и раньше.

`resolvedOffer` резолвится через `catalogService.resolveBySlug(input.selectedPlanType)` — не через `resolveInvitableBySlug`, то есть сам `auth.service.ts` не перепроверяет, что оффер ещё `public`/`invite_only` (эта проверка, судя по всему, происходит раньше, в `inviteService`/эндпоинте `/auth/invite/:token`).

Аналитика: `ANALYTICS_EVENTS.INVITE_ACTIVATED` шлётся `trackServerEvent` при `input.inviteToken && resolvedOffer` — событие существовало до этой задачи (общее для любой инвайт-регистрации), MIA-160 новых событий не добавляет (см. «Аналитика/API»).

### `api/src/services/catalog.service.ts`

- `ResolvedOffer`/`RenewalSnapshot`/`buildRenewalSnapshot` (строки 12-30, 66-79) — снапшот оффера (`offerId`, `renewalAmount`, `renewalDurationDays`, `renewalDescription`, `discountSnapshot`, `discountPeriodsRemaining`, `isRecurring`) сохраняется на подписку при создании и **никогда не перечитывается из каталога** — комментарий: «Billing reads these (never the live catalog) so a later price/offer edit never re-prices an existing subscriber». Именно этот снапшот и есть «зафиксированная скидка оффера» из Scope задачи.
- `toDiscountSnapshot` (84-88) проверяет `isDiscountLive` на момент резолва — скидка попадает в снапшот, только если офферная скидка ещё активна на момент регистрации.
- `isInviteOnlyTariff(planType)` (144-147) — **ключевая функция для «пейволл не даёт выбрать другой тариф»**: `true`, если `planType` не `null` и не выбираем публично (`!isPubliclySelectable`). Комментарий по-русски прямо описывает сценарий этой задачи: «инвайт выдал непубличный оффер со своей скидкой, а ссылка на оплату всегда рисует общий пикер — слаг из него затёр бы промо».
- `resolvePublicBySlug` (137-140) резолвит слаг, только если `offer.status === 'public'` — для invite_only оффера (`month_promo_discount50`) вернёт `null`. Это важно не только для регистрации/оплаты, но и для `payLinkInfoHandler` (см. ниже) — тот тоже использует именно этот резолвер.
- `resolveInvitableBySlug` (151-154) — резолвит оффер по слагу, только если `status` `public` ИЛИ `invite_only` (не `draft`/`archived`) — так `invite_only` офферы раздаются по инвайтам, но не попадают в `listPublicOffers()` (только `status='public'`, строка 158) — то есть не появляются в публичном каталоге.

### `api/src/controllers/subscriptions.controller.ts`

- `payLinkInfoHandler` (`GET /subscriptions/pay-link-info`, 80-133) — единственный источник данных для страницы `/select-tariff` в HMAC-режиме (переход по ссылке без сессии). Из БД он выбирает только `id, status, planType, trialEndsAt, expiresAt, paymentMethodId` (строки 92-96) и в ответе отдаёт **строго** `{ bound, chargeAt, reason, tariffFinal }` (строки 121-128) — `tariffFinal: await catalogService.isInviteOnlyTariff(sub.planType)`. Никакого названия оффера, суммы, `offerId` или `nextChargeAmount` в ответе нет и не может быть без правки самого хендлера.
  - Локальная переменная `offer` внутри хендлера (строка 108, `slug ? await catalogService.resolvePublicBySlug(slug) : null`) используется **только** для `trialDays` при расчёте `chargeAt`/`reason` (`resolveChargeMoment`) — и для invite-only оффера она тоже `null` (см. `resolvePublicBySlug` выше), то есть даже сам хендлер не держит в памяти данные промо-оффера, а не просто не отдаёт их наружу.
  - Именно поле `tariffFinal` фронт (`select-tariff.vue`) читает, чтобы решить, рисовать пикер или нет, в HMAC-режиме — и именно отсутствие в этом же ответе названия/суммы закреплённого тарифа — корневая причина дефекта из теста **2b**.
- `confirmBindingFromEmailHandler` (`POST /subscriptions/confirm-binding-from-email`, 284-451): `canCommitTariff = sub.paymentMethodId === null && !inviteOnlyTariff` — если тариф invite-only, смена тарифа полностью заблокирована на бэке (даже если фронт как-то всё же прислал `tariffId`, строка 394: `else if (!inviteOnlyTariff && requestedTariff && requestedTariff !== sub.planType) return 422 tariff_mismatch`) — то есть при invite-only тарифе присланный `tariffId` **тихо игнорируется**, а не валится 422 (проверено тестом «тариф из инвайта не переписывается публичным слагом из письма», `subscriptions.controller.test.ts:1099-1121`). Также здесь фремиум переводится в `AWAITING_PAYMENT` перед привязкой карты («Freemium pays now», строка 329), чтобы общий charge-путь именно списал деньги, а не просто прикрепил карту.

### `api/src/controllers/payments.controller.ts`

- `bindCardHandler`/`bindAndChargeHandler` содержат идентичную логику `isInviteOnlyTariff`/`canCommitTariff`/`wantsTariffSwitch`, что и `confirmBindingFromEmailHandler` — тариф из инвайта одинаково защищён что через кабинет (`bindCardHandler`), что через email-ссылку (`confirmBindingFromEmailHandler`).
- `bindCardHandler` (330-353): `freemiumUpgrade = sub.status === FREEMIUM` → флип `FREEMIUM → AWAITING_PAYMENT` и вызов `startAwaitingPaymentBinding`, которая создаёт `paymentMethod` у YooKassa и ждёт вебхук. Сумма списания при этом не пересчитывается в контроллере — она приходит из уже сохранённого на подписке `renewalAmount`/`discountSnapshot`/`discountPeriodsRemaining` (снапшот из `buildRenewalSnapshot`), которые читает `applyChargeOutcome`/`chargeAmount` (`api/src/data/discount.ts:76-80`) при обработке вебхука `yookassaWebhookHandler` — так фактическое списание = `chargeAmount(renewalAmount, discountSnapshot, discountPeriodsRemaining)`, то есть именно цена оффера со скидкой (899 в примере из QA-отчёта), а не `offer.price` из публичного каталога.

### `api/src/data/discount.ts`

- `applyDiscount`/`chargeAmount`: скидка `scope='forever'` действует на каждое списание, `first_charge` — только на первое (`chargeIndex===0`/`periodsRemaining` после `buildRenewalSnapshot` = 1), `n_periods` — на первые N. `remainingChargesForDiscount` (58-63) кладёт в `discountPeriodsRemaining` то самое число оставшихся списаний со скидкой — именно это поле фронт **не получает** для плашки периодичности (см. ниже про `price.ts`).

### `api/src/services/access.service.ts` — модель статусов подписки

- `SUBSCRIPTION_STATUS` (`api/src/data/subscription-status.ts`): `trial`, `active`, `charging`, `cancelled`, `expired`, `pending_binding`, `binding_failed`, `trial_charge_failed`, `awaiting_payment`, `freemium`.
- `isAllowed(sub)` (`access.service.ts:49-64`) — единственное место, решающее «есть полный доступ или нет»:
  - `ACTIVE` → `expiresAt` в будущем;
  - `TRIAL` → `trialEndsAt` в будущем (именно это условие делало мёртвый триал мёртвым при `trialEndsAt=null`);
  - `CHARGING` → всегда `true` (платёж уже в процессе — доступ не закрывают, пока провайдер не ответит);
  - `CANCELLED` → доступ остаётся, пока не истёк уже оплаченный/триальный период (`trialEndsAt`/`expiresAt` в будущем);
  - `FREEMIUM` → всегда `false` — то есть `isAllowed` для фремиума **всегда** возвращает `false`, полный доступ никогда не открывается автоматически, только через оплату/бинд карты.
  - Любой другой статус (`expired`, `pending_binding`, `binding_failed`, `trial_charge_failed`, `awaiting_payment`) → `false` (default).
- `canAccessTrainer()` (66-105) превращает `isAllowed` в `level: 'full' | 'freemium'`. `level='freemium'` — это и есть «одна бесплатная тема»: ограничение накладывается в `topicAllowed()` (39-40) — `access.level === 'full' || access.freeTopicId === null || access.freeTopicId === topicId`, то есть при фремиуме доступна только тема с `id === user.freeTopicId` (первая, за которую ученик взялся — фиксируется в `ensureFreemiumSubmissionAllowed`/`claimFreeTopic`, 126-145), остальные темы недоступны (пейволл). Это общий, не специфичный для MIA-160, механизм фремиума — задача лишь меняет то, какой статус подписки в него попадает (freemium вместо мёртвого trial).

### `frontend/cabinet/shared/price.ts` — плашка суммы/периодичности на фремиуме

`toCabinetPrice()` (30-90): при `tariffFinal && mode==='freemium'` (комментарий: «а фремиум по промо-инвайту наоборот приходит с готовым тарифом и своей скидкой») сумма = `subscription.nextChargeAmount ?? offer.price` (уже посчитанная бэком цена со скидкой, `access.service.ts:76-80`). Периодичность («списываем 899 ₽ каждый месяц») показывается **только если** `amount === offer.price` (`recurring = offer && amount === offer.price`, строка 60) — то есть только когда скидка НЕ действует на текущее списание. Комментарий в коде: «Периодичность обещаем только по неснижённой цене: сколько списаний покрывает скидка, фронту не видно». Пока скидка активна — `note` = просто `'отмена в один клик'`, без слова «каждый месяц» вообще (подтверждено тестом `фремиум с тарифом из инвайта показывает цену своего оффера`, `frontend/tests/cabinet-price.test.ts:115-131`, ожидающим ровно `note === 'отмена в один клик'`). Этот компонент работает только в кабинете с активной сессией — на HMAC-странице `/select-tariff` не используется, дефект теста 2b его не касается.

### `frontend/pages/select-tariff.vue` — пейволл (перечитан заново целиком для этого прогона)

- Два режима страницы разделены по наличию `sub`/`t` в query: `hasHmac` (28-30) — переход по подписанной ссылке без сессии; `sessionMode = !hasHmac && !!sessionSub` (32-33) — обычный визит из кабинета с активной сессией.
- `sessionSub` (32) = `userStore.user?.access?.subscription ?? null`. `userStore.user` заполняется вызовом `userStore.loadMe()` в `onMounted`, но этот вызов обёрнут в `if (sessionMode.value)` (строка 129) — **в HMAC-режиме `loadMe()` не вызывается вовсе**, значит `userStore.user` остаётся пустым и `sessionSub.value === null` всегда, для любой подписки.
- `hasPlan` (67-75): в сессионном режиме — `isTariffFinal({planType, paymentMethodId, pickerSlugs})` (данные берутся из `sessionSub`); в HMAC-режиме — `linkTariffFinal.value`, который заполняется в `loadChargeInfo()` (строка 110, `linkTariffFinal.value = !!res.tariffFinal`) из ответа `GET /subscriptions/pay-link-info`, то есть напрямую из `catalogService.isInviteOnlyTariff(sub.planType)`. Для закреплённого invite-only тарифа `hasPlan.value` в HMAC-режиме корректно становится `true`.
- `tariffOptions` (78): `hasPlan.value ? [] : allTariffOptions.value` — при `hasPlan=true` пикер получает пустой массив, а в шаблоне `SubscriptionTariffPicker` дополнительно закрыт условием `v-if="!hasPlan && !errorMsg && tariffOptions.length"` (строка 335) — то есть в HMAC-режиме для invite-only тарифа пикер не рендерится вообще, тариф физически сменить нельзя. Это часть работает верно и в HMAC-режиме тоже.
- **Дефект (подтверждён чтением кода, соответствует QA-отчёту от 2026-09-10):** `committedOffer` (строка 239) = `hasPlan.value ? (sessionSub.value?.offer ?? null) : null`. В HMAC-режиме `hasPlan.value === true` (из `linkTariffFinal`), но `sessionSub.value` **всегда `null`** (см. выше — сессия не грузится), поэтому `sessionSub.value?.offer` тоже `null`, а значит `committedOffer.value === null`, несмотря на `hasPlan=true`. В шаблоне блок рисуется условием `v-if="hasPlan && committedOffer"` (строка 341) — при `committedOffer=null` блок `.select-tariff__committed` (название оффера + `committedTariffLabel`, строки 342-343) **не рендерится совсем**. Одновременно с ним не рендерится и пикер (`hasPlan=true`), поэтому между `leadText` и кнопкой не остаётся ничего, что называло бы тариф или сумму.
  - `committedTariffLabel` (241-246) в принципе не достигается в HMAC-режиме — он вычисляется из `committedOffer`, который уже `null`.
  - Общий `fineprintText` в HMAC-режиме тоже не спасает: пока `chargeInfo.value` не пуст, он говорит `'Сумма выбранного тарифа спишется ...'` (строка 301, дефолтный `sum`, т.к. `promoFineprint` требует `selectedOffer`, а `selectedOffer` вычисляется из `selected`/`variantOffers` — публичного списка офферов, где invite-only оффера нет) — то есть даже мелкий текст не называет ни название, ни сумму, просто безликую фразу.
  - Это ровно диагноз автора QA-отчёта: «В HMAC-режиме фронт получает из pay-link-info только tariffFinal, chargeAt и reason. При tariffFinal=true committedOffer берётся из сессионного sessionSub, которого в HMAC-режиме нет» — подтверждено построчно.
  - Минимальный фикс потребует правки в двух местах: (1) `payLinkInfoHandler` должен резолвить и отдавать название/сумму закреплённого оффера (например через `resolveInvitableBySlug(sub.planType)` + `sub.renewalAmount`/`nextChargeAmount`, а не только `tariffFinal`), и (2) `select-tariff.vue` должен строить `committedOffer`/`committedTariffLabel` из этого нового поля ответа `pay-link-info` в HMAC-режиме, а не только из `sessionSub`.
- `promoFineprint`/`fineprintText` (280-315): при выбранном (несохранённом, для обычного пикера) оффере с промо — мелкий текст называет `first` (цену со скидкой на первый платёж) и отдельно «Далее — {regular}». Работает только когда есть `selectedOffer` (публичный пикер), то есть не в связке с закреплённым invite-only тарифом ни в сессионном, ни в HMAC-режиме — для committed-тарифа единственный явный источник суммы это `committedTariffLabel` (сессионный режим) либо ничего (HMAC-режим, дефект выше).
- Оплата (`onBind`, 180-237): в HMAC-режиме при `hasPlan.value` не шлёт `tariffId` в теле запроса (`...(hasPlan.value ? {} : { tariffId: selected.value })`) — так подтверждается, что пейволл не пытается перебить закреплённый тариф даже случайно. Эта часть не затронута дефектом — оплата технически безопасна, проблема чисто в отображении.

### `frontend/pages/register.vue` — регистрация по инвайту (для открытого вопроса копирайта)

`inviteOffer`/`inviteTrialLabel`/`inviteDiscountNote` (34-57) формируют заголовок страницы: название оффера, зачёркнутая полная цена + цена со скидкой, отдельно строка «Скидка N% {навсегда/на первый платёж/на первые K платежей}», и, только если `offer.trialDays > 0`, строку «N дней бесплатно, далее …» (строка 330, `v-if="inviteTrialLabel"`). Для `trialDays===0` (случай этой задачи) эта строка просто не рендерится — на странице остаются только название, цена и скидка, **без единого слова о том, что доступ будет фремиумным** (одна бесплатная тема + пейволл на остальное). Это открытый вопрос копирайта, не баг кода (см. «Открытые вопросы»).

## Тест-кейсы

### 1. [ПРИОРИТЕТ] Happy path — регистрация по промо-инвайту без карты и без триала

Предусловие: у оффера `month_promo_discount50` выключена «Карта при старте» (`cardUpfront=false`), `trialDays=0`, активная бессрочная скидка (пример из QA-отчёта: цена 1799 ₽, скидка 900 ₽, следующее списание 899 ₽).

1. Открыть ссылку регистрации по инвайту на этот оффер (`/register?invite=<token>`).
2. Убедиться, что заголовок карточки показывает название оффера, цену со скидкой (899 ₽) и зачёркнутую полную цену (1799 ₽) — без строки «N дней бесплатно» (её быть не должно при `trialDays=0`).
3. Заполнить форму, отправить. Карту на этом шаге просить не должны, сразу должен открыться доступ в ЛК (без редиректа на YooKassa/бинд карты) — `POST /auth/register` не должен возвращать `confirmationUrl`.
4. В ЛК ученика: доступна ровно одна тема (первая, за которую взялся), остальные — под пейволлом. Плашки «Пробный период закончился» быть не должно (главный acceptance-пункт: `expiresAt=2099-01-01` и статус `freemium`, а не мёртвый `trial`).
5. По API: `GET /api/me` для новой подписки — `status=freemium`, `planType='month_promo_discount50'`, `trialEndsAt=null`, `paymentMethodId=null`, `expiresAt=2099-01-01`, `nextChargeAmount=899`; доступ — `level=freemium`, не закрытый trial. (Подтверждено фактическим прогоном на test-1, раздел «Прошло» QA-отчёта.)

### 2. Пейволл закреплённого инвайт-тарифа: сессионный режим работает, HMAC-режим — известный дефект

**2a. Сессионный режим (в кабинете, с активной сессией) — работает**

1. Из состояния теста №1 (фремиум с закреплённым инвайт-оффером), будучи залогиненным, открыть пейволл (клик на недоступную тему или прямой переход на `/select-tariff` с сессией).
2. Проверить: показана ровно одна сумма — 899 ₽ (не 1799 ₽ и не сумма другого публичного тарифа), название оффера и периодичность соответствуют инвайт-офферу — блок `.select-tariff__committed` (`select-tariff.vue:341-344`) рендерится, т.к. в сессионном режиме `sessionSub`/`committedOffer` заполнены из `userStore`.
3. Убедиться, что пикер тарифов (список карточек с другими планами) отсутствует на странице — `tariffOptions=[]` при `hasPlan=true`, компонент `SubscriptionTariffPicker` не рендерится вовсе.
4. Кнопка привязки карты — «Привязать карту и оплатить»/аналог с суммой 899 ₽, без возможности сменить тариф перед оплатой.

**2b. HMAC-режим (переход по ссылке из письма, без сессии) — ИЗВЕСТНЫЙ ДЕФЕКТ, не пофикшен на момент заметки**

Найдено ручным QA на test-1 после деплоя (Andrei Chepurchenko, 2026-09-10). Подтверждено построчным чтением `frontend/pages/select-tariff.vue` и `api/src/controllers/subscriptions.controller.ts` — см. раздел «Реализация» выше.

Шаги воспроизведения:
1. Иметь новую подписку в фремиуме с закреплённым invite-only тарифом (как в тесте №1), карта не привязана.
2. Получить HMAC-ссылку на оплату (`GET /subscriptions/parent-pay-link`, без сессии; сам эндпоинт без авторизации отдаёт 401, ссылка формируется системой) — вида `/select-tariff?sub=<id>&t=<hmac>`; при желании дописать в query любой публичный слаг, например `&plan=quarter_std` (тариф всё равно не сменится, см. тест №5).
3. Открыть ссылку в приватном окне / без входа в аккаунт.
4. Проверить запрос `GET /api/subscriptions/pay-link-info?sub=...&t=...&plan=...` — он отрабатывает корректно: `bound:false`, `reason:"now"`, `tariffFinal:true` независимо от `plan`. Ошибок в консоли браузера нет.

Фактический результат (FAIL): на отрисованной странице — только заголовок «Выберите тариф», общий `leadText`, кнопка «Привязать карту и оплатить» и общий `fineprintText`. Ни названия оффера, ни суммы 899 ₽ (ни 1799 ₽) на странице нет. Пикер тарифов при этом тоже скрыт (тариф сменить действительно нельзя), то есть родитель готов оплатить, не видя, за что и сколько спишется.

Ожидаемый результат: закреплённый промо-оффер и сумма 899 ₽ должны быть явно показаны — так же, как в сессионном режиме (тест 2a).

Точная причина по коду:
- `committedOffer` (`select-tariff.vue:239`) = `hasPlan.value ? (sessionSub.value?.offer ?? null) : null`; `sessionSub` (`:32`) заполняется только `userStore.loadMe()`, которая в `onMounted` вызывается лишь `if (sessionMode.value)` (`:129`) — в HMAC-режиме сессия никогда не грузится, `sessionSub.value` всегда `null`.
- `hasPlan.value` в HMAC-режиме — это `linkTariffFinal` (`:64,110`), а не `sessionSub`, поэтому он корректно `true`; но `committedOffer` от него не зависит и остаётся `null`.
- В шаблоне блок `.select-tariff__committed` управляется условием `v-if="hasPlan && committedOffer"` (`:341`) — при `committedOffer=null` не рендерится, при этом пикер уже скрыт условием `v-if="!hasPlan && ..."` (`:335`) — получается пустое место.
- На бэкенде источника данных для этого блока просто не существует: `payLinkInfoHandler` (`api/src/controllers/subscriptions.controller.ts:80-133`) выбирает из БД только `id, status, planType, trialEndsAt, expiresAt, paymentMethodId` и возвращает клиенту только `{ bound, chargeAt, reason, tariffFinal }` — ни названия оффера, ни суммы там нет. Локальная переменная `offer` внутри хендлера (`:108`) резолвится через `catalogService.resolvePublicBySlug`, который матчит только `status==='public'` — для invite-only оффера (`month_promo_discount50`) она тоже `null`, то есть сам хендлер не держит данные промо-оффера в памяти, значит отдать их фронту без правки не может.
- Фикс требует правки в двух местах: `payLinkInfoHandler` должен резолвить закреплённый оффер (например через `resolveInvitableBySlug(sub.planType)`) и отдавать его название/сумму в ответе, а `select-tariff.vue` — строить `committedOffer` из этого поля в HMAC-режиме, а не только из `sessionSub`.

Что уже исключено как причина (см. QA-отчёт): API-фикс задеплоен и работает (`pay-link-info` отдаёт `tariffFinal:true`); подмена `plan` в query не переключает признак закреплённого тарифа; JS-ошибок в консоли нет — проблема именно в источнике данных для UI-блока, не в его условии рендера или в бэкендовой защите тарифа.

Не покрыто в рамках отчёта: фактическое списание через YooKassa тестовой картой в HMAC-режиме сознательно не выполнялось, чтобы не создавать платёжную операцию до исправления этого блокирующего UI-дефекта — стоит выполнить отдельно после фикса.

### 3. Привязка карты списывает цену со скидкой, а не публичный прайс

1. Из состояния теста №1/2 (сессионный режим) нажать привязку карты, пройти оплату на стороне YooKassa тестовой картой.
2. Проверить фактическую сумму списания в форме оплаты YooKassa/в ответе провайдера — должна быть 899 ₽.
3. После успешного вебхука: подписка переходит в `active`/`awaiting_payment→active` (в зависимости от таймингов), `paymentMethodId` заполнен, следующее списание (если `isRecurring`) при отсутствии активной `n_periods`/`first_charge` скидки — по полной цене (сверить со `scope` реальной скидки оффера на стенде: `forever` спишет 899 и на продлении, `first_charge`/`n_periods` — только на первом(ых)).
4. Убедиться, что сумма в ЛК после оплаты (если показывается) соответствует фактически списанной, не пересчитывается на лету по текущему публичному прайсу оффера.
5. Для HMAC-режима (оплата по ссылке) фактическое списание до фикса дефекта 2b тестировать нет смысла визуально — но можно подтвердить API-путём (`nextChargeAmount` в снапшоте подписки), как это сделал автор QA-отчёта, не доводя до реального платежа.

### 4. Регрессия — оффер с `trial_days > 0` без карты работает как раньше (обычный триал)

Явный acceptance-пункт, нужно перепроверить, что НЕ сломалось этой правкой. Подтверждено QA-отчётом от 2026-09-10 (раздел «Прошло»): инвайт с `trialDays=365`, `cardUpfront=false` создал `status=trial` с будущим `trialEndsAt` и полным доступом.

1. Взять/создать инвайт-оффер с `cardUpfront=false`, `trialDays>0` (например 3 или 7 дней).
2. Зарегистрироваться по инвайту на этот оффер. Заголовок страницы регистрации ДОЛЖЕН показать «N дней бесплатно, далее {цена}» (в отличие от кейса без триала).
3. После регистрации: карту не просят, статус подписки `trial` (не `freemium`), `trialEndsAt = now + trialDays`, `expiresAt = trialEndsAt + durationDays` оффера.
4. В ЛК: доступ ПОЛНЫЙ (не фремиумный, не одна тема) всё время действия триала — `isAllowed` для `trial` при `trialEndsAt` в будущем возвращает `true`.
5. По истечении триала (или искусственно откатив `trialEndsAt` в прошлое на тесте) — доступ закрывается, появляется предложение привязать карту с оплатой по цене оффера (обычный пост-триальный флоу, `trialExpiredNoCard` в `bindCardHandler`).

### 5. Регрессия по ревью — тариф из инвайта не перебивается публичным слагом ссылки на оплату

1. Зарегистрироваться по промо-инвайту без карты и без триала (как в тесте №1) — получить фремиум с закреплённым `planType` и скидкой.
2. Получить/сформировать ссылку на оплату «для родителя» (`GET /subscriptions/parent-pay-link`, либо ссылка из письма/уведомления) — она не содержит `plan` в URL по дизайну; без авторизации эндпоинт отдаёт 401 (подтверждено QA-отчётом).
3. Открыть эту ссылку на другом устройстве/без сессии (HMAC-режим `/select-tariff?sub=...&t=...`), при желании вручную дописать в URL `&plan=<другой публичный slug>` (например `quarter_std`).
4. Убедиться по сетевому запросу `GET /subscriptions/pay-link-info`, что даже с чужим `plan` в query ответ содержит `tariffFinal:true` (закреплённый тариф не переключается) — по коду `payLinkInfoHandler` использует для `tariffFinal` только `sub.planType`, `plan` из query влияет лишь на расчёт `trialDays` внутри `resolveChargeMoment`, не на сам признак закреплённости.
5. **Визуально** проверить название/сумму на этом шаге не получится — см. известный дефект теста 2b: страница не показывает ни закреплённый, ни (тем более) подставленный тариф. Достаточно подтвердить неизменность `tariffFinal`/суммы через API, как это сделал автор QA-отчёта, не доводя до реальной привязки карты.
6. (Опционально, после исправления дефекта 2b или на сессионном пути) пройти привязку карты по этой ссылке/из кабинета — списание должно быть 899 ₽, не 1799 ₽.

### 6. Плашка периодичности списания на фремиуме (UX-гэп, не баг по коду)

1. Взять фремиум с активной первоплатной скидкой (899 ₽ на первый платёж, регулярная цена — 1799 ₽) — зайти в ЛК, посмотреть текст под суммой к оплате.
2. Ожидаемо по коду: текст = «отмена в один клик» БЕЗ фразы «списываем 899 ₽ каждый месяц» (специально скрыто, чтобы не соврать про повторные списания).
3. Для сравнения — фремиум БЕЗ активной скидки (следующее списание = полная цена оффера): текст = «списываем {цена} каждый месяц · отмена в один клик».
4. Это не баг (осознанное решение по коду и юнит-тесту `frontend/tests/cabinet-price.test.ts:133-143`), но стоит визуально оценить, не выглядит ли отсутствие фразы «каждый месяц» как недосказанность для родителя — см. «Открытые вопросы».

### 7. Оффер остаётся invite_only, не в публичном каталоге

1. Открыть публичный лендинг/пейволл БЕЗ перехода по инвайт-ссылке (обычный визит) либо вызвать `GET /api/offers` напрямую.
2. Убедиться, что промо-оффер (`month_promo_discount50` или другой `invite_only`) не отображается среди публично выбираемых тарифов — `listPublicOffers()` читает только `status='public'`. Подтверждено QA-отчётом: в публичном `GET /api/offers` `month_promo_discount50` отсутствует.
3. Это уже покрыто Out of scope задачи («Показ invite_only офферов в публичном каталоге» не тестируем детально) — достаточно смоук-проверки, что оффер не «утёк» в общий список после этой правки.

### 8. Граничные/смежные кейсы

- **Инвайт с `cardUpfront=true`** (любой `trialDays`) — регистрация ДОЛЖНА по-прежнему сразу уводить на привязку карты (`status=pending_binding`, `confirmationUrl` заполнен). Подтверждено QA-отчётом на test-1: непустой `confirmationUrl` при регистрации.
- **Регистрация без инвайта вообще** — фремиум без тарифа (`planType=null`), обычная воронка «зарегистрировался → фремиум → сам выбрал тариф на пейволле». Подтверждено QA-отчётом: без инвайта создана фремиум-подписка с `planType=null`, `trialEndsAt=null`, `nextChargeAmount=null`.
- **Негатив: подмена тарифа на самой регистрации.** Передача `tariffId` публичного оффера вместе с промо-инвайтом. Подтверждено QA-отчётом: `tariffId=quarter_std` вместе с промо-инвайтом вернула `422 tariff_mismatch` (в отличие от привязки карты по инвайт-тарифу, где чужой `tariffId` тихо игнорируется, а не валится ошибкой, — разница веток стоит держать в уме при написании баг-репортов, чтобы не спутать поведения).
- **Гонка активации инвайта** (`invite_race`) — активация инвайта в `activateByToken` — общий для всех веток механизм, специфике MIA-160 не подвержен, но если есть время — стоит проверить, что повторная попытка активировать уже использованный/одноразовый инвайт с `card_upfront=false && trial_days=0` не создаёт вторую фремиум-подписку/не 500-ит.
- **Оффер с `discountSnapshot=null`** (без скидки вообще) по инвайту без карты и без триала — фремиум должен создаться так же, просто без скидочного блока в цене (`toCabinetPrice` покажет полную цену и «каждый месяц», см. тест-кейс №6, второй пункт).

## Аналитика/API

Фича не добавляет новых событий аналитики. `ANALYTICS_EVENTS.INVITE_ACTIVATED` (`api/src/constants/analytics-events.ts:254`) уже существовал до MIA-160 и продолжает шириться при любой успешной регистрации по инвайту (`auth.service.ts:234-240`, `{ invite_token_prefix, plan_type }`) — не специфично для фремиум-ветки, тестировать отдельно от общей инвайт-регистрации не нужно. Точечных API-проверок именно на аналитику для этой задачи не требуется; общие проверки сумм/статусов подписки покрыты тест-кейсами 1-5 выше через прямые API-ответы (`/auth/register`, `/subscriptions/pay-link-info`, `GET /api/me`, вебхук YooKassa) — все они фактически прогнаны в QA-отчёте от 2026-09-10, кроме визуального HMAC-пейволла (дефект 2b) и реального списания в YooKassa (сознательно отложено до фикса).

## Открытые вопросы

- **Копирайт страницы регистрации по инвайту не говорит про фремиум.** `frontend/pages/register.vue` (`inviteOffer`/`inviteTrialLabel`, строки 39-57, 326-334) показывает название оффера, цену со скидкой и (только при `trialDays>0`) срок триала — но при `trialDays===0` (ровно случай этой задачи) страница не сообщает, что доступ откроется фремиумным (одна бесплатная тема, остальное под пейволлом). Это вопрос копирайта для отдельного решения, не баг — фиксируется как открытый вопрос, не тест-кейс на FAIL.
- **Плашка периодичности списания на фремиуме не говорит, сколько списаний покрывает скидка.** `frontend/cabinet/shared/price.ts:57-69` — пока скидка активна, текст ограничивается «отмена в один клик» без суммы и периода следующих списаний вообще (ни «каждый месяц», ни «первые N платежей»). Осознанное решение (комментарий в коде + отдельный юнит-тест), но стоит держать в уме как потенциальный будущий запрос на уточнение копирайта.
- **Старые подписки (например `test@test.ru` на тестовом стенде) намеренно НЕ лечатся этой правкой.** Они остаются в `status=trial` с `trialEndsAt=NULL` — это ожидаемое поведение по прямому указанию автора, НЕ регрессия и не баг для этого раунда QA. При тестировании не заводить дефект на такие аккаунты, только на новые регистрации после деплоя.
- **`resolveBySlug` в `auth.service.ts` не проверяет `status` оффера повторно.** Регистрация резолвит оффер по слагу через `catalogService.resolveBySlug` (без фильтра по `status`), полагаясь, что до вызова `registerParentWithChild` уже была проверка через `/auth/invite/:token` (`inviteService`). Не нашёл в рамках этого MR явного щита от повторной регистрации по уже `archived`/`revoked` инвайту напрямую через API в обход страницы — если у QA есть возможность звать `/auth/register` напрямую (не через форму), стоит попробовать протащить `selectedPlanType` архивного/черновикового оффера и убедиться, что бэкенд это где-то отклоняет.
- **HMAC-пейволл закреплённого тарифа (тест 2b) блокирует полноценную проверку тестов 3 и 5 «до конца».** Пока дефект не пофикшен, реальное списание по HMAC-ссылке лучше не гонять вслепую (родитель на реальной странице не видит суммы) — после фикса стоит повторно пройти тесты 3 и 5 целиком, включая фактический платёж в YooKassa по HMAC-ссылке.
